# MaixCAM 开发助手 —— RAG 与 Agent 教学项目

> **当前状态：设计阶段（v0.1 设计稿），尚未编写代码。**
> 本目录是完整设计包，评审通过后进入实现。

---

## 这个项目是什么

一个以**「MaixCAM 开发助手」**为真实载体的 **RAG 与 Agent 教学项目**。

它同时是两样东西：

- **一个真实可用的工具**：问它 MaixPy 的用法，它从官方文档里找依据、给出能跑的代码，而不是编一个看起来很像的 API；
- **一份可跟做的教学材料**：读者做完，能建立起两个能力——**怎么设计可靠的 AI 应用**，以及**怎么根据场景把 RAG 的质量提上去**。

### 它解决的真实问题

MaixCAM 是比较新的硬件，大模型训练语料里几乎没有它。结果是：让模型写 MaixPy 代码，它会给出一堆**看起来对、粘进 IDE 就报错**的 API——参数名对一半、把 MaixPy 的接口和 OpenCV / 树莓派混在一起。

当时的应对方式是手工的：翻官方 wiki → 自己判断该看哪几页 → 把内容复制给 AI → AI 再回答。

**那套手工流程，就是一次人工执行的 RAG。** 这个项目把它自动化、工程化，并且——这是教学的关键——把每一步的质量都变成**可测量**的。

## 四条设计主线

### 1. 先问"要不要检索"，再问"怎么检索"

业界有一条被广泛引用但需要警惕的经验判断：**知识库小于约 20 万 token（大致 500 页）时，可以跳过检索，把全文放进 prompt 配合缓存**（来源为厂商工程博客，属 `[厂商自测]`，本项目把它当假设而非结论）。

MaixPy 语料正好在这个量级附近，所以本项目把**全文上下文**作为 `L-1` 级，并拆成三档：单模块全文（约 2 万 token）、全中文教程（**实测已越线，约 20 万+**）、加上 API 参考（约 30 万）。

| 对比 | 要回答的问题 |
| --- | --- |
| L-1a 单模块 vs L1 | 小范围全塞，是否**优于**检索？（预期：是） |
| L-1b/c 越线之后 | 质量与成本各付出什么 |

**结论不是"该不该"，而是一条曲线**：覆盖面多大时全文上下文开始不划算。绝大多数 RAG 教学项目开篇就假定必须做 RAG，从不质问这个前提——本项目把它变成第一课。

> **一次真实的估算纠错**：设计初稿凭直觉估中文语料约 12–13 万 token、判定"可行"；把算式摊开核算后发现真实量级在 20 万以上，结论**翻转为"越线"**。一个直觉偏差两倍——这就是本项目坚持"估算必须标注、实测不可替代"的原因。

### 2. 两条评测轴 —— 最重要的思维模型

RAG 答错了只有两种可能：**该召回的没召回**（检索失败），或**召回了但没用上**（生成失败）。这两者的修法几乎没有交集。

所以本项目要求：**所有评测报告必须并行展示两条轴**。没有这个纪律，调优就是碰运气。

### 3. 能力阶梯 —— 每项技术都给出增益、代价与失效场景

从 L-1 到 L9，**一次只加一个变量**，用同一套评测量化贡献：

```
L-1 全文上下文 → L0 无 RAG → L1 朴素 RAG → L2 结构化语料 → L3 混合检索
→ L4 结构感知检索 → L5 查询改写 → L6 重排序 → L7 上下文增强
→ L8 忠实生成 → L9 Agent 化
```

`configs/` 下这组配置文件**本身即是大纲**：读者跑一遍配置序列，就复现了整条能力阶梯。

教学立场是明确的：**不默认推荐任何技术。** 重排序和 Agent 默认都是关闭的。**被排除的技术（语义切分、GraphRAG、Self-RAG）也给出理由**，因为"为什么不用"同样需要判断力。

### 4. 语料是第一等公民

MaixPy 文档天然分两层，这个结构本身就是最值得教的材料：

| 语料层 | 内容 | 回答什么 |
| --- | --- | --- |
| 教程层 | 130 篇中文教程 | "怎么实现某个功能" |
| API 层 | 57 页 API 参考（由源码 docstring 生成） | "这个函数的签名是什么" |

**把它们混在一个索引里，会同时伤害两类问题。** 而 API 层恰恰是幻觉的重灾区，也是"符号白名单校验"这一防幻觉机制的物理基础——没有工程化好的 API 语料，"代码里不许出现不存在的符号"就只能靠模型自觉。

防代码幻觉采用**三级校验阶梯**：AST + 符号存在性（零成本、纯本地、抓主要幻觉）→ 签名/参数校验 → 真实执行（真机或 mock shim）。

## 三条分支：目标不同，工程选择就不同

**这不是同一个东西的三种写法，而是三个不同的目标**——工程选择由目标推导，不由口味决定。

| 分支 | 目标 | 工程上的必然选择 | 读者得到什么 |
| --- | --- | --- | --- |
| **A 主分支** | **教学** | **从零构建**——过程本身就是目的 | 理解 agent 是怎么被设计出来的 |
| **B Harness 分支** | **应用价值** | **用成熟基座（DeepSeek Harness）**——从零构建在这里是浪费 | 一个真能用的 MaixCAM 开发助手 |
| **C Skill 分支** | **普及** | **最轻形态**——不做 agent，装到任何桌面 Agent 即可 | 在任意 AI 上用上 MaixCAM 助手 |

三分法示范的判断力是：**同一个领域能力，交付形态可以有多种，选哪种取决于目标**。写错的方式恰恰是
用一种分支的标准去评判另一种——说主分支"工程不成熟"，或说 Skill 分支"功能太弱"，都是没看懂它们各自的目标。

三条分支共享同一个底座：**语料管线、评测集与评测器、API 符号白名单（1898 个符号）**。
其中评测器刻意保持**框架无关**——它如果被编排框架绑住，就不再是量尺。

详见 [06 项目结构与三条分支](./docs/design/06-项目结构与两条分支.md)。

### 第一个真实的消融结果

评测器第一次跑就抓到一个**设计缺陷**：`signature` 类问题召回率 **0.000**。根因是
API 参考页当时只用来生成白名单、**没有产出可检索的 chunk**，而教程层不会系统性地写出函数签名。

修复（让每个 API 符号渲染成一个 chunk）之后，**同一评测集、同一配置、只改语料这一项**：

| qtype | 修复前 | 修复后 | 变化 |
| --- | --- | --- | --- |
| **signature** | **0.000** | **0.500** | **+50 pt** |
| example | 0.250 | 0.750 | +50 pt |
| troubleshoot | 0.000 | 1.000 | +100 pt |
| **concept** | 0.625 | **0.500** | **−12.5 pt** |
| 总体 Recall@5 | 0.556 | 0.611 | +5.5 pt |

**这个结果同时说明了三件事**：

1. **只看总分会把结论看反**——总体 +5.5pt 不痛不痒，分组后才看到一类 +50pt、另一类 −12.5pt；
2. **语料工程是被低估的杠杆**——没改任何检索算法，只让语料里"有东西可召回"；
3. **加语料层不是免费的**——新增的 1898 个 API chunk 抢占了 Top-5 名额，把概念类需要的教程散文挤了出去。

第 3 点直接给出了 **L4 查询路由**的实验动机：既然两类问题需要不同的知识层，就该按问题类型把检索导向对应的层。

## 快速开始

```bash
# 1. 虚拟环境与依赖
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt        # Windows
# source .venv/bin/activate && pip install -r requirements.txt   # Linux/macOS

# 2. 密钥与端点（复制后填写；.env 已被 gitignore 保护）
copy .env.example .env

# 3. 嵌入模型（本地 Ollama，零成本可离线）
ollama pull bge-m3

# 4. 语料 → 索引 → 评测
python -m maixrag --config configs/l2_hybrid.yaml corpus adopt   # 或 corpus fetch（需网络）
python -m maixrag --config configs/l2_hybrid.yaml corpus build
python -m maixrag --config configs/l2_hybrid.yaml index build

# 5. 只测检索轴（不花钱、不联网、不需要模型 key）
python -m maixrag --config configs/l2_hybrid.yaml eval --level rag --fake-chat

# 6. 防幻觉校验器演示
python scripts/check_symbols_demo.py
```

**为什么嵌入用本地 Ollama 而不是 DeepSeek**：DeepSeek **不提供 embeddings 接口**（已实测 404）。
本地 `bge-m3` 多语言、中文强、零成本、可离线——对教学项目是最合适的选择。

三个 `--fake*` 开关的区别（这个划分本身是评测逼出来的）：

| 开关 | 作用 | 什么时候用 |
| --- | --- | --- |
| `--fake-chat` | 只换对话为空客户端 | **只想测检索轴**——检索轴本来就不需要模型 |
| `--fake-embed` | 只换嵌入为假客户端 | 验证管线、不下载模型 |
| `--fake` | 两者都换 | 完全离线冒烟测试 |

## 技术选型（已确认）

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | Python | RAG 教学生态最主流，新手最容易跑起来 |
| 模型接入 | **OpenAI 兼容接口** | 一套配置接任意提供方；换一行配置就能演示模型对质量的影响 |
| 编排 | **自写，不用 LangChain / LlamaIndex** | 要精确控制每一层才能做消融；透明的实现更有教学价值 |
| 检索 | NumPy 暴力检索 + BM25 | 语料小（约数千 chunk），暴力检索毫秒级，且完全可读 |
| 向量库 | 落盘矩阵，不引外部数据库 | 单机、零运维 |
| 分词 | jieba + 中文标识符保留 | 本场景查询必然混中英文 API 名 |

## 语料底数（已实测核实，2026-08）

| 分区 | 页数 | 字节数（实测） |
| --- | --- | --- |
| `/maixpy/doc/zh/` 中文教程 | 130 | 713,520 |
| `/maixpy/doc/en/` 英文教程 | 129 | 733,937 |
| `/maixpy/api/` API 参考 | 57 | 未测 |
| **合计** | **316** | — |

- 教程有 **Markdown 原文**可直接获取（仓库 `docs/doc/zh/`，**Apache 2.0 许可，已核实**），无需爬 HTML；
- API 参考由源码 docstring 生成，**不在仓库 Markdown 里**，需从文档站抓取或自行构建（已核实 release `v4.12.5` **没有**文档 zip）；
- 文档站提供 `sitemap.xml`，语料边界可程序精确枚举；
- 已发现站点与仓库存在**页面漂移**（站点有仓库无、页面名拼写不同），管线会显式产出差异报告而非静默丢弃。例如站点 sitemap 报英文 130 条、仓库实测 129 个 `.md`，差异来自站点上的非文档页面。

**这个体量决定了第一课。** 实测中文教程 713,520 字节，token 估算已到 **20 万以上**——**单独就超出了"全文塞进 prompt"的可行区间**（该经验阈值约 20 万 token）。但单个模块（如 `peripheral`，约 2 万 token）全塞绰绰有余。

**所以结论不是"该用 RAG"，而是一条边界曲线**：覆盖面多大时全文上下文开始不划算。这正是项目要教的判断力。
