## 1. 主线在教什么

一句话：**决策由谁做。**

一条链的决策是写死的——检索 → 拼提示词 → 生成，永远只走这一条路。
一个循环的决策是模型在运行时做的——它看到工具结果之后，自己决定"再查一次"还是"可以答了"。

这个区别带来全部后果。主线要教的不是"怎么把循环搭起来"（那很简单），
而是**这个区别带来的四类新问题**：

| 问题 | 机制 | 代码 |
| --- | --- | --- |
| 能力之间怎么解耦，怎么可插拔 | 服务注册表 + 插件生命周期 | `registry.py` |
| 模型怎么知道有哪些能力 | 工具注册与执行管线 | `tools.py` |
| 提示词怎么从多个来源拼出来 | 提示词装配 | `prompt.py` |
| 它怎么停下来、失败怎么办 | 循环 + 三条预算线 | `loop.py` |
| 它不能做什么 | 权限与沙盒 | `sandbox.py` |

## 2. 五块机制，每块一条核心判断

### 2.1 服务注册表：按名字解耦

**要解决的问题**：最直白的写法是让能力互相 `import`。那种写法会立刻带来两个后果——
换不掉（想换检索实现就要改所有 import 它的地方）、拆不开（想知道这个能力谁提供的、谁在用，只能翻代码）。

**做法**：能力按名字注册、按名字解析，提供方与消费方彼此不知道对方是谁。

**核心判断**（这一块唯一需要记的东西）：

> **这个服务会被作用域之外的消费者用到吗？**
> 会 → 全局平面，且**只创建一个提供方**
> 不会 → 隔离域

判断错会怎样，跑 `python scripts/demo_planes.py` 看现场。

**代码**：`maixrag/agent/registry.py`

---

### 2.2 工具：能力对模型的标准暴露面

**要解决的问题**：工具的设计质量直接决定 agent 的**实际**能力上限——不是模型能力的上限，是这个系统能做成什么的上限。

**三条纪律**：

1. **描述即提示词。** 模型选哪个工具完全靠读 `description`。所以空描述的工具被**当场拒绝注册**——没描述的工具体等于不存在。
2. **错误是结果，不是异常。** 工具失败必须作为可观察结果回到模型面前。循环崩了什么都做不了；模型看到"参数少了一个"会自己改。
3. **权限声明在工具上。** 每个工具声明 `requires`（`fs:write` / `exec` / `net`），权限系统因此有一个明确检查点。

**一个容易被忽略的顺序**：存在性 → 参数 → 权限 → 执行。
反了会有实际后果：先查权限再查参数，会让一次"参数写错的调用"也弹审批窗口，白白打扰人一次。

**代码**：`maixrag/agent/tools.py`

---

### 2.3 提示词装配：拼出来的，不是写死的

**要解决的问题**：几乎所有 agent 项目的第一版都是一个模块级的常量字符串，最后长成八百行、谁也不敢删的巨型常量。那种形态改不动、加不了、测不了。

**做法**：每个来源各贡献一段，装配器只负责排序和拼接。**装配器本身不知道任何具体内容。**

拆成两类的理由是可测的：

| | 静态段落 | 动态上下文 |
| --- | --- | --- |
| 内容 | 人设、纪律 | 工具说明书 |
| 变化 | 几乎不变 | 每轮都变 |
| 放哪 | 系统提示的稳定前缀 | 跟随用户消息 |

混在一起等于每轮都让提示词缓存失效。

**核心价值**：第三方插件想插一段进去，**不需要改装配器一行代码**，给个中间的 `order` 就行。

**代码**：`maixrag/agent/prompt.py`

---

### 2.4 循环与预算：它怎么停下来

**要解决的问题**：没有预算的循环不是"更灵活的链"，是一台会自己花钱的机器。

**三条预算线**，各防一种失效：

| 预算 | 防什么 |
| --- | --- |
| 轮次 | 模型反复横跳、想不清楚 |
| 工具调用次数 | 单轮内疯狂并发调工具 |
| token | 上下文无限膨胀 |

只设一条会漏：只有轮次上限时，一轮里可以调一百次工具。

**失败恢复三种，都是刻意的**：

| 情形 | 处理 | 为什么 |
| --- | --- | --- |
| 工具失败 | 作为观察结果回灌，**不终止** | 终止的话，一次参数写错就毁掉整个任务 |
| 连续同类失败 | 提前终止 | 防"在修不好的错上把预算烧光" |
| 预算耗尽 | **优雅降级** | 静默失败会伪装成成功 |

**跑一下 `python scripts/demo_budget.py`**，场景一里那种失败是**无声的**：
每次工具调用都"成功"，只是返回"找到 0 个片段"，没有报错，一轮一轮烧下去。

**代码**：`maixrag/agent/loop.py`

---

### 2.5 权限与沙盒：它不能做什么

**要解决的问题**：一个会执行命令、读写文件的 agent，如果没有能力边界，
它的错误就不再是"回答得不好"，而是"删了不该删的东西"。**这是性质上的差别。**

**三层，各回答不同的问题**：

| 层 | 问题 | 缺了它会怎样 |
| --- | --- | --- |
| 能力边界 | 能做哪类事 | 工具能直接调系统调用，绕开一切控制 |
| 范围边界 | 能做到多大 | 能"写文件"但不知道能写到哪，等于没有限制 |
| 审批边界 | 什么必须问人 | 危险操作被静默放行 |

**一条压倒性的原则：失败关闭。** 拿不准的时候一律拒绝，而不是放行。
没有审批人时拒绝、路径解析失败时拒绝、路径参数不是字符串时拒绝。

**最值得记的一节**：拦截越界**不能靠字符串前缀**。

```
workspace-evil/x.txt    ← 以 "/workspace" 开头，前缀判断认为它在范围内
workspace/../secret     ← 含 .. 会逃出
workspace/link -> /etc  ← 符号链接指向外部
```

正确做法：先 `resolve()` 规范化并解析符号链接，再用 `relative_to` 做包含判断。

**跑 `python scripts/demo_sandbox.py`** 看对比表。注意标题：
「拦住了」和「拦对了」是两回事。

**代码**：`maixrag/agent/sandbox.py`

## 3. 三个"故意写错"

教学项目最容易犯的错是只展示正确做法。主线刻意埋了三个错误，
它们对应**三类不同性质**的失败：

| 性质 | 错在哪 | 演示 |
| --- | --- | --- |
| **架构错** | 把该共享的服务放进隔离域；或该隔离的放进全局 | `demo_planes.py` |
| **工程错** | 不设预算，agent 跑飞（而且失败是**无声的**） | `demo_budget.py` |
| **安全错** | 权限越界；以及用字符串前缀判断路径，三种攻击全放行 | `demo_sandbox.py` |

每一条都是**可复现的现场**，不是文字描述。

## 4. 端到端：循环到底值不值

这是主线最终要回答的问题。

### 4.1 一个具体的对比

同一个问题：**"MaixPy 里怎么做 YOLO 物体检测？给出完整例程"**
同一份语料、同一套检索工具。

**链式（L1 基线）的回答**：

> 资料中没有给出 YOLO 物体检测的完整代码，因此无法提供可直接运行的完整示例。
> ……由于资料中未包含具体的 `maix.*` API 名称、参数和示例代码，按规则我不能凭其他框架
> （OpenCV、K210 时代 MaixPy v1 等）的习惯推测 API。

**agent（8 轮）的回答**：给出完整可运行代码，并**自己校验过两次**。

它的轨迹值得逐步看：

```
第1轮  search_docs("YOLO 物体检测 例程", k=8)
第2轮  search_docs("YOLOv5 YOLOv8 YOLO11 物体检测 代码 yolo = YOLOv5", k=10)   ← 自己改写查询
第3轮  lookup_api("maix.nn.YOLOv5")                                           ← 切到确定性工具
第4轮  search_docs("yolov5.py 例程代码 detector = nn.YOLOv5 完整代码")          ← 用学到的类名重检索
第5轮  check_api_usage(草稿代码…)                                             ← 写完自检
第6轮  lookup_api("maix.nn.YOLOv5.detect")                                    ← 补缺失的签名
第7轮  check_api_usage(修正后代码…)                                            ← 再校验一次
第8轮  final
```

**差别不在模型，也不在语料，只在有没有循环。**

### 4.2 但这个结论有前提

同一批测试里，**预算 4 轮的 agent 是失败的**——它做了四步完全合理的多跳，
第四步撞墙，然后优雅降级。

所以正确的结论不是"agent 更好"，而是：

> **agent 的能力上限更高，但它要求预算与任务深度匹配。**
> 预算给少了，它比链式还不如（链式至少给了一个答案）；
> 预算给够了，它能做到链式做不到的事。

而"给多少才够"**只能靠评测回答**，不能靠拍脑袋。这就是为什么评测器是第一批交付物。

### 4.3 一个必须说明的测量局限

上面那个对比是**定性的**。跑完整评测后，检索轴的数字是这样的：

| 指标 | 链式（L1） | agent 循环 |
| --- | --- | --- |
| Recall@K | 0.611 | 0.667 |
| MRR | 0.453 | 0.416 |
| 引用精确率 | 0.889 | **1.000** |
| 符号级幻觉率 | 0.000（**但覆盖面 0/18**） | **0.000**（覆盖面 16/18） |
| 触犯禁止项比例 | 0.000 | 0.056（已定位为**指标误报**，见下） |
| 拒答率 | 0.000 | 0.444 |

**注意 Recall@K 这一行：agent 现在是 0.667 > 0.611。**
而补 `read_doc` **之前**，同一把尺子给出的结论是反的（agent 0.556 < 0.611）。

**这不代表 agent 检索变好了。** 原因是这个指标的分子：

```
Recall@K 分子 = 召回片段里有几个落在 required_docs 上
read_doc 一次就把整篇文档的 5~20 个片段塞进 hits
→ 只要 agent 打开了对的那份文档，分子立刻被灌满
```

所以：

- **链式与 agent 不能用同一把检索尺子比。** 链式只有一次检索，那把尺子对它是完整的；agent 是累积的，而且会把"打开文档"也算成"检索命中"。
- agent 的收益体现在**答案层**（见 4.1 的 YOLO 对比），以及**可以自检**（`check_api_usage` 被调用 15 次）。
- 正确的做法是把**检索**（`search_docs` 带回了什么）与**取阅**（`read_doc` 打开了什么）拆成两个口径——这是一个**明确的待办**，不是已经解决的问题。

**这个局限本身就是教学点，而且是两条：**

> 1. 当一把尺子量不出差异时，**先怀疑尺子，再怀疑被测对象**。
> 2. **但"怀疑尺子"不能停在"所以这个数不用看"。**
>    尺子的偏差是有方向的，而且会随被测对象改变而**翻转**。
>    0.556 和 0.667 说的是同一件事：这个口径与 agent 的检索能力无关。

### 4.4 agent 的真实成本

同一批 18 题，agent 用了 **75 次工具调用**，分布是：

```
search_docs       23
read_doc          20
check_api_usage   15
lookup_api        13
list_api           4
```

平均每题 **4.2 次**。这就是 agent 的代价——而它必须由"答得更好"来偿还。

同时注意 `check_api_usage` 被调了 15 次：**agent 在主动自检**。
这是链式基线完全没有的行为，也是幻觉率能保持 0.000 的直接原因。

### 4.5 跑出你自己的数字

```bash
# 链式基线（单轮检索 + 生成）
python -m maixrag --config configs/l2_hybrid.yaml eval --level rag

# agent 循环
python -m maixrag --config configs/l2_hybrid.yaml agent-eval --max-turns 10

# 看诊断：每条指标实际覆盖了多少题
python scripts/inspect_eval.py
```

**注意 `inspect_eval.py`**。它存在的理由是一次真实的教训：
某份报告里"符号级幻觉率 = 0.000"看起来是好消息，
诊断脚本打出真相——`符号被检查到的题数 0/18`。

> **0.000 有两种含义**："真的很好"或"几乎没测到东西"。
> **指标必须能暴露自己的覆盖面，否则它会伪装成好消息。**

## 5. 动手练习

按难度排序，每个都有明确的验收标准。

| # | 练习 | 验收 |
| --- | --- | --- |
| 1 | 加一个新工具 `get_page(doc_id)`，按 doc_id 取整页 | 注册后 `agent --show-hits` 能看到它被调用 |
| 2 | 把 `search_docs` 的描述改差（删掉"什么时候不要用"） | 观察它被误用的次数变化 |
| 3 | 把预算改成 2 轮，跑 4.1 那个问题 | 复现"agent 比链式还差" |
| 4 | 给 `sandbox` 加一条"写操作需要审批"的策略 | 越界写入变成"等待审批"而不是直接拒绝 |
| 5 | 实现一个 `HypothesisModel`：先检索、再据结果生成子问题 | 看多跳能力是否提升，代价是多少轮 |

**练习 3 特别推荐**：它会让你亲身体会到"预算不是越大越好"这件事的另一面——
预算是**任务与成本之间的谈判**，不是安全阀。

## 6. 我们**没有**做的（以及为什么）

诚实列出边界，比假装完整更有用：

| 没做 | 真实系统为什么必须有 |
| --- | --- |
| 会话持久化与恢复 | 否则进程重启后上下文全丢；教学项目用内存够用 |
| 子 agent 委派 | 长任务需要并行与隔离，但显著推高理解成本 |
| 前端框架 | 属于应用形态而非 agent 原理；可以用插件形式加上 |
| 审计日志 | 出事后要能回答"谁在什么时候做了什么" |
| 提示词缓存 | 真金白银的差别，但属于工程优化，不影响机制理解 |

---

## 7. 一句话总结

> **循环与链的区别是"决策由谁做"，而这个区别带来的不是"更聪明"，
> 而是四类新问题：可插拔、可描述、可停止、可约束。**
>
> 主线就是把这四件事各讲一遍，并且每一件都留一个能跑出来的现场。
