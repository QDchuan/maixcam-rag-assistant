# 08 · 终端演示：把可插拔做成看得见的东西

> 这一章要你动手做的事：跑起一个终端程序，**看** agent 一轮一轮地做决策；
> 然后亲手把呈现层拔掉，确认 agent 一行代码都不用改、照常工作。
>
> 前置：[tutorial 06 Agent：五块机制](./06-Agent-五块机制.md)（注册表与插件）、
> [tutorial 07 端到端](./07-端到端.md)（装配与评测）。
> 这一章不重复它们，只让你**看见**它们。

---

## 1. 一句话结论

**"解耦"和"可插拔"如果只写在架构图里，就等于没说。
这一章的做法是：真的写一个插件插进去——插上就看得见过程，拔掉就安静如常，
而 agent 的代码一行没动。**

顺带它也是这套东西对外的样子：面试演示、给别人看的第一眼。

## 2. 为什么需要这一步

前面七章讲了很多机制，但它们有一个共同的弱点：**看不见。**

- 注册表说"按名字解耦"——可你读代码时看到的仍然是一堆方法调用；
- 循环说"每个副作用都登记了撤销函数"——可撤销与不撤销在正常运行时的表现**完全一样**；
- 沙盒说"权限是最后一道闸"——可默认策略放行，你永远不会看到它拦下什么。

**机制的价值只有在它被使用、并且使用代价可被观察时才是真的。**
一个"设计上可插拔"但从来没人插过第二个插件的系统，
它的可插拔性只是一个未被证伪的假设。

所以这一步做的事情是：**当一次真的用户**。

| 如果不做这一步 | 做了这一步 |
| --- | --- |
| "可插拔"是设计文档里的一句话 | 有一个真插件，插拔各验证过一次 |
| 轨迹只能靠事后翻 `result.events` | 过程在跑的时候就能看见 |
| 没人知道终端不支持颜色时会发生什么 | 发现订阅者异常必须被隔离（见 6） |
| 对外只有一个命令行 | 有一个能给人看的东西 |

### 3.2 核心：呈现层是一个插件

关键代码只有三行（[`maixrag/cli.py`](../../maixrag/cli.py) 的 `cmd_demo`）：

```python
presenter = TerminalPresenter(stream=not args.no_stream)
app.scope.mount(TuiPlugin(presenter), isolate=True)
```

`TuiPlugin` 的全部内容（[`maixrag/agent/tui.py`](../../maixrag/agent/tui.py)）：

```python
class TuiPlugin:
    name = "tui-presenter"

    def apply(self, ctx: Context) -> None:
        loop = ctx.require("agentLoop")
        # 订阅也是副作用：卸载时自动退订，否则会留下一个还在画的幽灵呈现器
        self._unsub = loop.subscribe(self.presenter.render)
        ctx.effect(lambda: self._unsub() if self._unsub else None)
        ctx.provide("presenter", self.presenter)
```

它做到的三件事，每一件都对应前面某一章的机制：

| 这里做的事 | 用的是哪条机制 | 在哪一章讲过 |
| --- | --- | --- |
| `ctx.require("agentLoop")` 按名字取服务 | 服务注册表 | [06 §3.1](./06-Agent-五块机制.md) |
| `loop.subscribe(...)` 订阅循环事件 | 事件解耦 | [06 §3.3](./06-Agent-五块机制.md) |
| `ctx.effect(...)` 登记退订 | 副作用可撤销 | [06 §3.2](./06-Agent-五块机制.md) |
| `mount(..., isolate=True)` 进隔离域 | 两个平面 | [concepts 08](../concepts/08-权限与沙盒.md) |

**为什么 `isolate=True`**：呈现器天然是"每个终端一份"的。
两个终端各挂一份，如果都往全局注册 `presenter`，第二个就会撞名。
这正是"发布服务的行不能裸放在会话级组合里"那条规则的由来——
判据不是"它重要不重要"，而是"**它是不是只属于这一次挂载**"。

### 3.3 亲手验证"插拔"

这是这一章最重要的动手部分。做两个实验。

**实验一：拔掉呈现层，agent 不受影响。**

```bash
python -m maixrag demo --fake-chat --show-architecture "MaixCAM 的 GPIO 怎么用？"
```

先把 `cmd_demo` 里那两行 `mount(...)` 注释掉，再跑一次。
你会看到：**agent 照常回答问题，只是安静地答。** 改动的代码量是零。

**实验二：让呈现层故意崩溃，agent 仍然跑完。**

在 `TerminalPresenter.render` 开头插一句 `raise RuntimeError("界面炸了")`，再跑。
会看到：没有轨迹输出，但**答案照常生成**。

这不是"防御性编程的洁癖"。原因是 [`loop.py`](../../maixrag/agent/loop.py) 的：

```python
def _notify(self, event: "Event") -> None:
    for fn in list(self._subscribers):
        try:
            fn(event)
        except Exception:  # 订阅者的问题不该传播给 agent
            pass
```

**演示程序最容易在"输出"上出问题**：终端不支持 ANSI、被重定向到文件、
编码不是 UTF-8、窗口太窄。如果这些能中断 agent，那这个架构就谈不上解耦。

## 4. 亲眼看一次

真实模型、真实检索，问一个需要多跳的问题：

```bash
python -m maixrag demo --max-turns 10 "MaixCAM 的 GPIO 怎么用？怎么点灯？"
```

**[本项目实测]** 5 轮、4 次工具调用，三种工具都用上了：

```
▶ MaixCAM 的 GPIO 怎么用？怎么点灯？

  ⏺ 第 1 轮 · 思考中…
    ✓ search_docs({'query': 'GPIO 控制 点灯 LED', 'k': 10})
  ⏺ 第 2 轮 · 思考中…
    ✓ lookup_api({'symbol': 'maix.peripheral.gpio.GPIO'})
  ⏺ 第 3 轮 · 思考中…
    ✓ lookup_api({'symbol': 'maix.peripheral.gpio.GPIO.__init__'})
  ⏺ 第 4 轮 · 思考中…
    ✓ check_api_usage({'code': 'from maix import gpio, pinmap, time, err\n\nerr.che…
  ⏺ 第 5 轮 · 思考中…
    ✓ 生成答案
```

**轨迹里最值得看的是第 1 → 2 → 3 步的换挡**：

1. 先用 `search_docs`（概率性）找"怎么点灯"；
2. 检索结果里出现类名之后，**换成 `lookup_api`**（确定性）去查准确签名；
3. 写完代码用 `check_api_usage` 自检。

这正是 [concepts 06](../concepts/06-Agent与链的区别.md) 说的"决策由模型做"：
链式永远只走检索 → 生成，而这里第二步是模型**看着第 1 步的结果自己决定**的。

结尾的运行指标：

```
╭─────────────────────────────────────────────────────────╮
│  工具调用 4   失败 0   被拒 0                           │
│  按工具 check_api_usage×1  lookup_api×2  search_docs×1  │
╰─────────────────────────────────────────────────────────╯
```

## 5. 证据

**呈现层确实是可插拔的**——两个实验的结论都有回归测试锁着
（`tests/test_agent_tui.py`，17 条）：

| 断言 | 测的是 |
| --- | --- |
| `test_unmounting_tui_plugin_removes_subscription` | 卸载后循环里**不留回调**（否则是看不见的泄漏） |
| `test_a_broken_subscriber_cannot_break_the_agent` | **订阅者抛异常，agent 仍跑完并给出答案** |
| `test_unsubscribe_stops_delivery` | 退订真的停止投递 |
| `test_banner_stats_come_from_the_real_assembly` | 启动画面的数字来自装配结果，不是常量 |
| `test_boxed_lines_are_all_equal_width` | 中英混排 + ANSI 的宽度计算（错了框会歪） |

其中第二条是整个文件里最重要的一条——**它守的是"解耦"这个说法本身**。
如果它红了，说明呈现层与逻辑层之间还有依赖没切断。

另有一条**不属于界面测试**的发现，见 [事故 07](../postmortem/07-校验静默放行.md)：

跑演示时读到 agent 自己写的最后一段——

> 我用 `check_api_usage` 校验了上面那段点灯代码，但工具返回「没有出现可校验的
> maix 符号」，也就是**这次自检实际没有起到校验作用**，请以文档依据为准。

顺这句话查下去，发现第一级防幻觉校验**在最需要它的那条路径上一次也没生效**，
却对模型返回了成功。这个 bug 靠读代码是找不到的，
只能靠**读 agent 自己的输出**——而终端演示恰好让那段输出变得显眼。

> **演示程序的一个额外价值**：它把原来埋在日志里的东西搬到了眼前。
> 有些 bug 不是难修，是**难被看见**。

## 6. 失败的样子

### 失败一：框歪了——中英混排的宽度陷阱

第一版框线在中文行错位。原因不是算错，是**算漏了一种东西**：

```python
# 第一版：把 ANSI 转义序列也当成可见字符数进去了
def _w(text):
    for ch in text:
        n += 2 if unicodedata.east_asian_width(ch) in ("W", "F") else 1
```

`\033[38;5;45m` 在屏幕上占 **0** 列，但有 10 个字符。
带颜色的内容装进框里，边框就会往外飘。

修法是量之前先剥掉转义序列（`_ANSI_RE`）。
**这个 bug 只在"内容带颜色"时出现**——所以关掉颜色调试时一切正常，
打开颜色才歪。见 `test_display_width_ignores_ansi_sequences`。

> 同类陷阱：`█` `╭` `·` 这些符号的 East Asian Width 是 **Ambiguous**。
> 本项目按"窄"处理（现代终端的默认行为）。如果你在
> 某些 CJK 传统终端上看到框歪，根因就在这里，而不是宽度算法写错了。

### 失败二：启动画面第一眼被日志糊住

```
Building prefix dict from the default dictionary ...
Loading model from cache C:\...\jieba.cache
Loading model cost 0.396 seconds.
Prefix dict has been built successfully.
```

jieba 首次初始化会往 stderr 打这四行。对人来说它是进度信息，
但对一个**演示程序**来说，启动画面被日志糊住就等于没有启动画面。

修法是在 `corpus/tokenize.py` 里 `jieba.setLogLevel(logging.ERROR)`——
压到 ERROR 而不是屏蔽整个 logger，真有异常时仍然看得见。

### 失败三：`--list` 要你先配好密钥

第一版 `--list` 放在装配之后，于是：

```
[错误] 未配置嵌入模型的 API Key。
```

而"我还没配密钥，想先看看能问什么"恰恰是最合理的第一个动作。
**列问题不该要求先能跑起来**——把 `--list` 移到装配之前就好了。

> 这是一类很常见的顺序问题：把一个纯展示动作放在了一个需要完整依赖的动作之后。
> 判据是问一句"**这个动作最少需要什么**"。

### 失败四：`Config.load(None)` 从不展开 `${VAR}`

跑演示时用默认配置（不传 `--config`），报"未配置嵌入模型的 API Key"，
而 `.env` 里明明配了。

根因在 [`maixrag/config.py`](../../maixrag/config.py)：

```python
if path is None:
    cfg = cls(project_root=root)   # ← 默认值里的 ${EMBED_API_KEY} 原样留下来了
    return cfg
# 走 YAML 的那条路才有 _expand_env(raw)
```

**两条代码路径，只有一条做了该做的处理。** 于是故障只在一半的用法里出现——
走 `--config` 正常，走默认值失败。这类 bug 的共同特征是：

> 校验没错、数据没错、报错信息也没错，错的是"两条路不一致"。

修法是让默认值也走一遍展开，并加了回归脚本
`scripts/check_default_config_expands.py`。

## 8. 课后习题

**A1（复现）** 做 3.3 的两个实验：注释掉 `mount` 那两行 / 让 `render` 抛异常。

- 验收：两次都能得到完整答案，并说出"改动了几行 agent 代码"（答案：0 行）
- 追问：第二个实验里，为什么"答案完整"反而是**正确**的行为？

**B1（诊断）** 你给一个 CLI 工具加了 `--progress` 选项来显示进度条。
加完之后发现：管道输出到文件时文件里全是 `\r` 和 ANSI 码，grep 完全没法用。

- 验收：指出该在哪一层判断"要不要显示动画"，并说明为什么不该在渲染函数里判断
- 参考：`TerminalPresenter.__post_init__` 与 `color_wanted()`

**C1（改造）** 再写一个呈现插件 `JsonPresenter`：订阅同样的事件，
但把每个事件输出成一行 JSON。

- 验收：不需要改 `loop.py` 和 `cli.py` 的任何一行（除了换一个 mount）
- 验收：它和 `TerminalPresenter` 能同时挂载，互不干扰
- 提示：这就是"换成 JSON 输出不用动 agent"那句话的实证

**D1（判断）** 有人说"演示程序不值得花时间，它不影响项目质量"。
用本章的一个具体发现回应他。

- 验收：必须指出演示**产生了什么在别处发现不了的东西**，而不是"它好看"
- 参考：事故 07 是靠读演示输出发现的，不是靠代码审查
