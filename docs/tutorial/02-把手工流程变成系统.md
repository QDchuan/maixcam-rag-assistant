# 02 · 把手工流程变成系统

> 本章要你动手做的：把「翻文档 → 自己判断看哪页 → 复制给 AI」逐条落成系统环节。
> 前置：[concepts 00](../concepts/00-为什么需要RAG.md) ·
> [concepts 01](../concepts/01-RAG的完整链路.md)。

---

## 1. 一句话结论

**手工流程方向是对的，缺的是"可测量"**——所以它整体保留，只是每段换成一个能报数字的模块。
它的第一课不是"怎么检索"，是**先问要不要检索**：20 万 token 阈值属厂商经验（[厂商自测]），
本项目实测落在阈值两侧，答案因此是一条**边界曲线**。

---

## 2. 为什么需要这一步

本项目的起点是**2025 年打电赛时的一次真实经历**——那时候 MaixCAM 还很新，
**模型完全没有它的知识**：

```
遇到报错 → 翻 wiki.sipeed.com → 自己判断该看哪几页
        → 把内容复制进对话框 → AI 给建议 / 写代码 → 不行再回去翻
```

**这套流程能跑通**，问题出在它坏掉的时候：AI 写的代码粘进 MaixVision 就报错、
它"记得"一个文档里没有的函数名、同一个问题昨天对今天错——**手工版本一个都说不清**。
因为两个环节都可能出错（**你翻的页**、**AI 有没有用好你复制的内容**），
而手工流程把它们揉成了一个动作，出了问题只能整条重来。

本项目的做法不是另起一套，而是**把动作拆开，让每一段各自报数字**。
拆开之后会发现：YOLO 那道题生成侧表现**优秀**（明确拒答、不编造 API），
根因 100% 在检索——真正含例程的 `zh/vision/yolov5` 根本没被召回；只看"答案里没有代码"
就去调提示词、换模型，全部调错方向。([concepts 01 · 4.1](../concepts/01-RAG的完整链路.md)) [本项目实测]

### 2.1 手工动作 → 系统环节 → 代码模块

| 手工动作 | 系统环节 | 对应代码模块 |
| --- | --- | --- |
| 翻 wiki、打开文档站 | 语料获取（快照 + 版本固定） | `maixrag/corpus/fetch.py`、`corpus/sources.py` |
| 「这几页讲得比较全」的取舍 | 解析与标题感知切分 | `maixrag/corpus/markdown.py`、`corpus/chunker.py` |
| 建立章节索引以便回头查 | 索引（BM25 + 向量） | `maixrag/indexing/bm25.py`、`indexing/vector.py` |
| **判断该看哪几页**（最易错） | 检索、融合 | `maixrag/retrieval.py` |
| 复制进对话框、贴成"依据以下资料" | 上下文组装与提示词 | `maixrag/builders.py` |
| AI 给建议、写代码 | 生成 | `maixrag/providers.py` |
| 「不行再回去翻」 | 校验与拒答；循环里变成工具调用 | `maixrag/agent/ragtools.py` |
| 「这次好像比上次准」 | 两轴评测（18 题 / 4 类 qtype） | `maixrag/evaluation/harness.py` |

**只有一行被整体改造**：手工的"判断该看哪几页"是**你自己拍脑袋**；系统里它换成
"用哪一类工具"，而且拆得更细——`lookup_api` 查签名是确定性查表，`search_docs`
才是概率性检索。**能用确定性工具解决的，不要交给概率性检索**
（完整对照在 `maixrag/agent/ragtools.py`）。

### 2.2 第一课为什么是"要不要检索"

业界有一条被广泛引用、但必须警惕的经验判断：**知识库小于约 20 万 token（大致 500 页）时，
可以把整个语料放进 prompt 并配合 prompt caching，跳过检索。**
它是**某厂商工程博客的观点**，属 `[厂商自测]` + 工程经验，不是独立研究
（出处与引用纪律见 [design 05](../design/05-调研与借鉴.md)）。
手工流程之所以值得保留，恰恰因为它**天然就是 L-1（全文上下文）**——你把文档整段复制进
对话框，做的就是这个。于是问题被换成**覆盖面**（[design 00 · 6.1](../design/00-项目定位与教学大纲.md)）：

| 覆盖面 | 实测 / 估算 | 与阈值的关系 |
| --- | --- | --- |
| 单模块（`peripheral` 相关页） | 约 **2 万** token [本项目实测（字节）+ 估算（token）] | 远在阈值内 → **该全塞，不该检索** |
| 全中文教程 | 713,520 字节 → 约 **20–22 万** token | 已越线 |
| 中文教程 + API 参考 | 约 **26–33 万** | 明显不可行 |

配置里用的是 `retrieval.mode: none` 这个**显式开关**，而不是"把 top_k 调大"——
前者说的是"我们决定不检索"，后者是"检索了但取回很多"，两者在报告里必须能区分开。

## 3. 怎么做

```bash
# ① 先量语料，才知道自己落在边界哪一侧（量上游仓库，需要网络）
python scripts/measure_corpus.py

# ② 认领磁盘上已有快照，重建清单（commit / 文件数 / 差异）
python -m maixrag --config configs/l2_hybrid.yaml corpus adopt

# ③ 解析 + 标题感知切分 + 抽 API 符号 → 统计报告与差异报告
python -m maixrag --config configs/l2_hybrid.yaml corpus build

# ④ 建索引：手写 BM25 + 向量（真实嵌入走本地 Ollama bge-m3）
python -m maixrag --config configs/l2_hybrid.yaml index build

# ⑤ 不带密钥先跑一遍全链路：假的决策模型，先检索一次再据结果作答
python -m maixrag --config configs/l2_hybrid.yaml agent "MaixPy 里怎么做 YOLO 物体检测？给出完整例程" --fake-chat
```

顺序不能反：**先量，再决定要不要检索**。第 ① 步顺带是
[事故 01](../postmortem/01-静默的空结果.md) 的修复现场——统计为 0 篇时它**显式失败
并返回退出码 2**。第 ⑤ 步是硬性要求：**读者不该卡在"配 API Key"上**；
`--fake-chat` 只换掉**决策模型**，嵌入仍走真实模型，而只想测检索轴时用 `eval --fake-chat`
——**检索轴本来就不需要对话模型**（`maixrag/builders.py` 的 `NoopChat`）。

> 下面是**伪代码**（示意映射，不能直接跑）：
>
> ```python
> hits = retriever.retrieve(question, k=5)      # 「该看哪几页」
> user = build_context_block(hits) + question   # 「复制进对话框」
> answer = chat.complete(SYSTEM_PROMPT, user)   # 「AI 给建议」
> ```
> 真实实现分散在 `maixrag/retrieval.py`、`builders.py`、`providers.py`；
> 完整参数表属 reference 层，本章不列。

## 4. 亲眼看一次

### 4.1 看真实字节数

```powershell
Get-ChildItem corpus/raw/repo -Recurse -Filter *.md |
  Get-Content -Raw -Encoding UTF8 |
  ForEach-Object { [System.Text.Encoding]::UTF8.GetByteCount($_) } |
  Measure-Object -Sum | Select-Object Count, Sum
```

我在本仓库跑出来 `119` 篇 / `688782` 字节。**要观察两件事**：这是**当前入库快照**，
与设计阶段量的上游 `docs/doc/zh` 全量（130 篇 / 713,520 字节）**不是同一个口径**；
**字节数是实测，token 只能估算**。

### 4.2 用 `--cjk-share` 看阈值判断有多敏感

`--cjk-share` 是 token 估算里**唯一的假设参数**（中文占字节的比例），
把它暴露成开关是脚本刻意的设计：

```powershell
python scripts/measure_corpus.py --cjk-share 0.4     # 需要网络
python scripts/measure_corpus.py --json
```

按脚本摊开的算式（`3 字节/字、约 1 token/字` + `英文与代码 1 字节 ≈ 0.25 token`），
对记录在案的 **713,520 字节**改算：

| cjk_share | 估算 token |
| --- | --- |
| 0.4 | 约 20.2 万 |
| 0.5 | 约 20.8 万 |
| 0.6 | 约 21.4 万 |
| 0.7 | 约 22.0 万 |

**要观察的就是这个跨度**：同一份字节数，四档假设相差约 1.8 万 token。这四档**都越线**
（20.2–22.0 万 > 20 万），所以这份语料的结论是稳的；`--cjk-share` 要暴露的是
**假设本身能有多大影响**——它既可能翻转结论，也可能（像这里一样）只移动结论的位置。
（上表是按脚本 `est_tokens` 对 713,520 字节实算的结果，
`python -c "import sys;sys.path.insert(0,'scripts');from measure_corpus import est_tokens;print([round(est_tokens(713520,s)/10000,1) for s in (0.4,0.5,0.6,0.7)])"` 可复现；
脚本自带注释给的是"约 20–22 万"，与之一致。）**精确 token 必须在构建索引时用真实分词器数出来**
（`maixrag/corpus/tokenize.py` 的 `count_tokens`），本脚本不能替代那一步。

### 4.3 跑一次离线评测：看到"哪一环在报什么数字"

**这一节在临时副本上做**，别在正式索引上重复（原因见第 6 节）。

```bash
# ① 建索引：--fake 用假嵌入，完全离线；--rebuild 强制重建
python -m maixrag --config configs/l2_hybrid.yaml index build --fake --rebuild

# ② 评测检索轴：--fake-chat 让生成侧不调用任何模型
python -m maixrag --config configs/l2_hybrid.yaml eval --level rag --fake-chat --top-k 5
```

报告落到 `eval/results/`，其中有**按 qtype 分组**的一段，形如
`| qtype | n | Recall@K | MRR | 幻觉率 | 拒答率 |`（四行：`concept` 8 / `example` 4 /
`signature` 4 / `troubleshoot` 2）。

**要观察三件事**：假嵌入下 **`concept` 那一行会明显偏低**——假嵌入是没有语义能力的哈希
词袋（`maixrag/providers.py` 的 `FakeEmbedder`），只证明**管线通了**；**分组表比总览表
有用**，同一改动可以做到一类 +50 pt、另一类 −12.5 pt，总分看不出来；**生成轴的指标
全部不可信**，报告会明确写"生成轴未被真实测量"。

## 5. 证据

| 项 | 值 | 性质 |
| --- | --- | --- |
| 中文教程字节数 | **713,520 字节（130 篇）**，两种独立方法交叉验证逐字节一致 | ✅ 实测 |
| 中文教程 token | 约 **20–22 万**；加 API 参考约 **26–33 万**；单模块 `peripheral` 约 **2 万** | 估算 |
| 20 万这个阈值本身 | —— | **`[厂商自测]`**，本项目当假设 |
| 文档 / chunk | 119 篇 / **3838 chunk**（605 代码 / 67 表格 / 1898 signature） | [本项目实测] |
| API 符号白名单 | **1898 个符号 / 4868 条** | [本项目实测] |
| 索引 | 手写 BM25（`ln((N+1)/df)` 保证 IDF 恒正）+ bge-m3（1024 维，本地 Ollama） | [本项目实测] |
| 评测 | 18 题 / 4 类 qtype | [本项目实测] |

**第一个消融结果**——同一评测集、同一配置，只改语料这一项（让 API 参考页产出可检索 chunk）：

| qtype | 修复前 | 修复后 | 变化 |
| --- | --- | --- | --- |
| **signature** | **0.000** | **0.500** | **+50 pt** |
| example | 0.250 | 0.750 | +50 pt |
| troubleshoot | 0.000 | 1.000 | +100 pt |
| **concept** | 0.625 | **0.500** | **−12.5 pt** |
| 总体 Recall@5 | 0.556 | 0.611 | +5.5 pt |

chunk 1940 → 3838。三件事同时成立：**语料工程是被低估的杠杆**、
**加语料层不是免费的**（Top-5 名额零和）、**总分对这两件事没有信息量**。[本项目实测]
（现场见 [事故 02](../postmortem/02-有文档却召不回.md)）

**agent 的真实成本**（手工"再回去翻"装进循环之后）：18 题共用 **75 次工具调用**
（平均 4.2 次/题；`search_docs` 23 / `read_doc` 20 / `check_api_usage` 15 / `lookup_api` 13 / `list_api` 4）。
预算 4 轮的 agent 在 YOLO 题上失败，10 轮成功并给出可运行代码。[本项目实测]

## 6. 失败的样子

### 6.1 一个直觉判断，偏差两倍

设计初稿里，我凭"中文技术文档多半是代码和英文"的直觉估出中文语料约 **12–13 万 token**，
据此判定"全文上下文可行"，打算跳过检索。把算式摊开后：

| | 直觉版 | 摊开算式后 |
| --- | --- | --- |
| 中文占字节比例 | 低估一半以上 | 中文 UTF-8 下 3 字节/字、约 1 token/字 |
| 估算 token | 12–13 万 | **20 万以上** |
| 结论 | 可行，跳过检索 | **越线，不能跳过** |

**一个直觉判断偏差两倍，而它本会导致整个项目的技术路线判断出错。**
（[design 00 · 6.1](../design/00-项目定位与教学大纲.md)）[本项目实测]
要学到的不是"要仔细"，而是：**估算必须标注、实测不可替代**，
而且**估算的敏感度要暴露出来**——这正是 `--cjk-share` 存在的理由。

### 6.2 这一招什么时候会误导你

| 情况 | 为什么会误导 |
| --- | --- |
| 把**本地裁剪过的快照**当成上游全量 | 快照 119 篇 / 688,782 字节，上游 `docs/doc/zh` 130 篇 / 713,520 字节；口径不同，越过/未越过的判断可能相反 |
| 拿 token 估算当精确值 | 不同模型分词器不同；这里的估算是**量级判断**，不是计费依据 |
| 把 `--fake` 的评测数字当检索质量 | 假嵌入无语义能力，只证明管线通了 |
| 看到语料统计是 0 就以为语料真的空 | 这**正是**事故 01：脚本曾安静地报告 0 篇、退出码 0。现在它会显式失败——别把修好的行为再当正常 |
| 在正式索引上随手 `index build --rebuild` | 我自己踩过：一次 `--fake --rebuild` 把 1024 维真实向量索引覆盖成 256 维假索引。**可重建的产物也值得先备份** |
| 把"手工流程"整体丢掉 | L-1（全塞）在小覆盖面下是**最优解**，不是待淘汰的旧做法 |

本章的映射表**不是"用系统取代手工"**，而是说手工动作里每一段都能在系统里找到一个
**可测量的对应物**，而最该保留的那一段，恰恰是"先问要不要检索"。

## 7. 自检

**任务**：给你手上的语料算出它的"该不该全塞"结论，并说明这个结论对假设有多敏感。

**验收标准**（三条全中才算过）：

1. 报出的是**字节实测值 + 口径**（哪一批文件、多少篇）；
2. token 给的是**区间**而不是一个数，并能说清区间被哪个假设撑开；
3. 能说出把 `cjk_share` 从 0.5 调到 0.6 时，结论会怎么变。

**做不出来的常见原因**：抄一个别人的 token 数，或把某一档估算当成实测。

## 8. 课后习题

**A1（复现）** 跑出本地语料的真实字节数，与本章 4.1 对照。

- 提示：`corpus/raw/repo` 是入库快照，`docs/doc/zh` 是上游全量，口径不同
- 验收：报出 `Count` 与 `Sum`；能解释为什么比设计阶段的 713,520 字节小
- 依据：[concepts 02 语料与切分](../concepts/02-语料与切分.md) ·
  [design 00 · 5.4](../design/00-项目定位与教学大纲.md)

**A2（复现）** 跑一次 `eval --level rag --fake-chat`，找到按 qtype 分组那一段。

- 提示：注意报告顶部的两条 `⚠️`，以及 `concept` 为什么明显偏低
- 验收：能指出哪些指标在这一跑里**不具参考意义**，并说出原因
- 依据：[concepts 03 检索：稀疏与稠密](../concepts/03-检索-稀疏与稠密.md) ·
  [事故 05](../postmortem/05-伪装成好消息的0.md)

**B1（改造）** 把 `scripts/measure_corpus.py` 已有的四档敏感度输出参数化成一个开关。

- 提示：改动集中在 `main()` 里那几行 `print`；**不要动 `est_tokens` 的算式**，
  它是被引用的一手实现
- 验收：能指定任意档位；先预测"极端档位下结论会不会翻转"，再与实测比对，
  不一致时能说出哪一步想错了
- 依据：[design 05 · 1.1](../design/05-调研与借鉴.md)（估算纠错的完整记录）

**B2（改造）** 用 `configs/l_minus1_full_context.yaml`（`retrieval.mode: none`）与
`configs/l2_hybrid.yaml` 跑同一套评测，比较两条路线。

- 提示：`--level full_context` 与 `--level rag`；先想清楚"全文注入"该在哪类问题上赢
- 验收：预测与实测方向一致；不一致时能解释是"检索没召回到"还是"上下文被截断"
  （`FullContextProfile` 有 `max_tokens` 截断，且**截断事实会出现在结果里**）
- 依据：[concepts 06 Agent 与链的区别](../concepts/06-Agent与链的区别.md) ·
  [事故 06 预算与任务不匹配](../postmortem/06-预算与任务不匹配.md)
