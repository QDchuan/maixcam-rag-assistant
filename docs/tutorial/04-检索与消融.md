# 04 · 检索与消融

> 这一章要你**亲手跑出本项目第一个真正的消融实验**：建索引 → 只跑 dense → 只跑 bm25 →
> 跑 RRF 融合 → 按 `qtype` 分组读那张表。消融不是"多跑几次评测"，而是
> **一次只改一个变量，并且预先写下预测**。
>
> 前置：读 [concepts/03 检索：稀疏与稠密](../concepts/03-检索-稀疏与稠密.md) 建立
> "词面 vs 语义"的概念，读 [concepts/04 融合与重排序](../concepts/04-融合与重排序.md) 建立
> "融合只在分名额"的概念。本节的数字全部来自 [concepts/07 两条轴](../concepts/07-评测-两条轴.md)
> 定义的检索轴指标。

---

## 1. 一句话结论

**三方对比（dense / bm25 / RRF）在本项目 18 题上的总体 Recall@5 是 0.611 / 0.444 / 0.611**——
融合与单路 dense **总分打平**；但逐题看，融合**救回一题、弄丢两题**（净得失为零）。
所以结论不在总分里，**只能按 `qtype` 分组读**。而这一切的前提是索引里那份语料，就是评测集标注的那份。

## 2. 为什么需要这一步

没有这一步，你会在两个方向上瞎调。

**方向一：以为"加一路检索总是更好"。** RRF 的机制是奖励"两路都说好"，但两路都不说好、
或只有一路说好时，它并不会救你——**它反过来可能把单路已经排进 Top-5 的片段挤出去**。
这件事只有跑三方对比才看得见，因为总分恰好打平。

**方向二：以为"分数变好就是变好"。** 本项目第一次语料层消融就是反例 [本项目实测]：
API 层产出 chunk 后 `signature` 召回 **0.000 → 0.500**（+50 pt），
而 `concept` **0.625 → 0.500**（−12.5 pt），总体的 **+5.5 pt** 把后者完全盖住
（[事故 02](../postmortem/02-有文档却召不回.md)）。

落在 MaixCAM 上还有第三件、也是本场景特有的事：**分词**。用户会问
`maix.camera.Camera 的构造函数有哪些参数`，也会问 `怎么找色块`。
通用中文分词器会把前者切碎成 `maix / camera / Camera`，而标识符正是本场景最重要的一类查询信号。
所以索引里必须有 [双重分词](../../maixrag/corpus/tokenize.py)：标识符整体保留 + 中文交给 jieba。
**不做这一步，消融测的是"被切碎的 BM25"，不是 BM25。**

## 3. 怎么做

### 3.1 先把语料与索引准备好

```bash
python -m maixrag --config configs/l2_hybrid.yaml corpus adopt
python -m maixrag --config configs/l2_hybrid.yaml corpus build
python -m maixrag --config configs/l2_hybrid.yaml index build
```

`index build` 打完会打印 BM25 篇数、向量条数与维度、符号白名单条数。
**建完立刻查一次自检**——`indexes/index_meta.json` 记的是语料指纹，不是语料内容：

```powershell
Get-Content indexes\index_meta.json
```

你要在这份 JSON 里核对三处（它们必须与 `corpus/reports/stats.md` 对得上）：

| 字段 | 本章实测值 |
| --- | --- |
| `corpus_fingerprint` | `9f1d0a2997ad7cea5afdf9bb8581087571a081abb9c8bd99f5341273141df52d` |
| `chunks` | 3838 |
| `embedding_model` / `retrievers` | `openai_compat:bge-m3` / `["dense","bm25"]` |

`chunks` 对不上就是**换了语料没重建索引**，此时 `build_indexes` 会硬失败并让你加 `--rebuild`
（`maixrag/builders.py`），而不是给你一份看起来正常的错位结果。这是刻意设计的：
**索引与语料不匹配时必须显式失败。**

⚠️ `corpus/` 与 `indexes/` 是**本地可重建状态**（已被 `.gitignore` 排除）。
如果你在同一台机器上换过切分策略（`heading` / `fixed` 会切出不同数量的 chunk），
先按上面三条命令重建一次，否则后面所有 `doc_id` 都可能对空——那是环境问题，不是检索问题。

### 3.2 三份配置，一次只改一个变量

三份配置都保持 `chunking.strategy: heading` 不变，**只改 `retrieval.retrievers`**：

| 配置 | `retrievers` | 代表 |
| --- | --- | --- |
| [configs/l3_dense_only.yaml](../../configs/l3_dense_only.yaml) | `[dense]` | 只用稠密 |
| [configs/l3_bm25_only.yaml](../../configs/l3_bm25_only.yaml) | `[bm25]` | 只用稀疏 |
| [configs/l2_hybrid.yaml](../../configs/l2_hybrid.yaml) | `[dense, bm25]` + `fusion: rrf` | 融合 |

配置字段的含义在 [`configs/`](../../configs) 的注释里，本节只用上面这三个键，不展开。

### 3.3 三条命令，同一把尺子

```bash
python -m maixrag --config configs/l3_dense_only.yaml eval --level rag --fake-chat --top-k 5
python -m maixrag --config configs/l3_bm25_only.yaml  eval --level rag --fake     --top-k 5
python -m maixrag --config configs/l2_hybrid.yaml     eval --level rag --fake-chat --top-k 5
```

两个开关的区别很重要，别用错：

- `--fake-chat`：只把**对话模型**换成空客户端。嵌入仍是真实的 bge-m3，
  所以**检索轴数字有效**，而且不联网、不花钱。测 dense 必须用它，不能加 `--fake`。
- `--fake`：嵌入也换掉。BM25 与嵌入无关，所以测 bm25 用它最省事；
  dense 加了它，检索轴数字就只证明"管线通了"。

每次跑完报告落在 `eval/results/`，文件名形如 `rag_L1_rag[rrf_dense].md`（含方括号，故文档里不给链接）。

## 4. 亲眼看一次

先跑三条命令（见 3.3）。然后看**报告里的那张分组表**——它在每份 Markdown 报告的
「按问题类型分组」一节，一共四行：`concept` / `example` / `signature` / `troubleshoot`。

**具体观察点：三份报告的 `signature` 那一行。**
它取 0.500 / 0.000 / 0.500：**只有 BM25 那份是 0.000**。
这不是"BM25 只会更差"——同一份报告里 `troubleshoot` 是 0.500，而 dense 那份也是 0.500，
**融合那份才是 1.000**。四行、三份报告横着读，你看到的是一张"各有胜负"的表，
而不是一条单调的优劣线。

再用一个脚本把"名次差"直接摆出来（它不重跑评测，秒级返回）：

```bash
python scripts/demo_retrieval.py
python scripts/demo_retrieval.py --query "MaixPy 里怎么做 YOLO 物体检测？给出一个完整例程。" -k 20
```

第二条命令会打出同一查询在三个检索器下的名次。**看 `zh/vision/yolov5` 这一个 doc_id**：
dense 排第 5、bm25 排第 6、**融合反而掉到第 12**。原因写在输出旁边：
融合先各取 20 个候选再重排，两路都把它放在 5–6 名，
而两路在它前面的那些片段被"一致认可"叠加了分数。
→ 这就是第 6 节失败案例①的现场：**单路进了 Top-5 的片段，融合可以把它挤出去。**

第三个现象是本节特有的：把 `demo_retrieval.py` 的内置查询换成 `YOLOv5 物体检测`，
看 BM25 那一列的前 5 个 `doc_id`——**里面没有 `zh/vision/yolov5`**（它排第 6）。
原因和验证手段都放在第 6 节③，这里只要求你**先把现象看到**。

## 5. 证据

同一评测集（18 题 / 4 类 qtype）、同一语料（3838 chunk）、同一 `top_k=5`，只改检索器。
下表全部为 **[本项目实测]**，复现命令即 3.3 的三条：

| 指标 | 只 dense | 只 bm25 | RRF（dense+bm25） |
| --- | --- | --- | --- |
| Recall@5（主指标） | **0.611** | 0.444 | **0.611** |
| Hit Rate@5 | 0.667 | 0.444 | 0.667 |
| MRR | **0.557** | 0.335 | 0.453 |
| Context Precision | 0.267 | 0.156 | 0.267 |

按 `qtype` 分组（这才是决策依据）：

| qtype | n | 只 dense | 只 bm25 | RRF |
| --- | --- | --- | --- | --- |
| concept | 8 | 0.500 | 0.500 | 0.500 |
| example | 4 | **1.000** | 0.750 | 0.750 |
| signature | 4 | 0.500 | **0.000** | 0.500 |
| troubleshoot | 2 | 0.500 | 0.500 | **1.000** |

**两处必须一起读的事实：**

1. **总分打平（0.611 = 0.611），内容不一样。** 逐题看：`q005`（YOLO 例程）
   在只 dense 时 `zh/vision/yolov5` 排第 5、命中；融合后排第 12、**丢了**。
   同一轮里 `q016`（内存不够）只 dense 排第 6、**没进 Top-5**；
   融合把它抬到第 2、**救回来了**。一题换一题。
2. **MRR 反而下降（0.557 → 0.453）。** 融合提升了"有没有"（troubleshoot），
   却恶化了"排得前不靠前"——`signature` 的 MRR 0.375 → 0.312。

语料层的那组数字（`signature` 0.000 → 0.500、`concept` 0.625 → 0.500、总体 +5.5 pt）
是 **[本项目实测]**，见 [事故 02](../postmortem/02-有文档却召不回.md)；
它是"必须按 qtype 分组"的第一份实证。

**一处诚实的边界**：18 题的样本量下，`signature` 只有 4 题，**一题之差就是 25 pt**。
所以分组数字**看方向，不看小数位**（[design/03 · 3.3](../design/03-评测与质量提升路线.md)）。
想要结论稳定，先把评测集扩到设计稿的 60 题。

## 6. 失败的样子

这一节是这一章最重要的部分。三招都是在真实数据上撞出来的。

### ① 秩融合不是万能：两路都错时，它不会救回来

RRF 的全部信息量就是"名次"。当两路都把正确片段放在很后面，融合只会把两份错误的
共识**加固**。上表里 `q003`（`Camera.read()` 要什么参数）与 `q004`（怎么列出摄像头设备）
在**三个配置里全部未命中**：

- `q003` 的 dense 其实把 `api/camera.Camera.read` 排到了第 3，但要求同时满足
  `required_spans=["def read","block_ms"]`——**靠前的那个 chunk 里没有参数信息**，
  而含参数的 chunk 没能进 Top-5。
- `q004` 的答案在 `api/maix.camera.list_devices`。dense 把它排到 **第 17**，
  bm25 的前 20 里没有它；融合也从两路名次里推不出它。

**判据**：融合只能在候选池里重排。**池子里没有的答案，任何融合方式都救不回来**；
这时该动的是语料（`list_devices` 这样的符号有没有渲染成可检索 chunk）或查询理解，不是融合。

### ② 只看总分会把结论看反

本项目已经有过一次：`signature` **+50 pt**、`concept` **−12.5 pt**、总体只有 **+5.5 pt**
[本项目实测]（[事故 02](../postmortem/02-有文档却召不回.md)）。
本章的融合是第二次：总体 0.611 = 0.611 **完全看不出**"丢了 YOLO 例程、救回内存问题"。

**判据**：任何一次检索改动，都至少给出 `by("qtype")` 那张分组表（`maixrag/evaluation/harness.py`
的 `Report.by` 就是为它写的）。**只报总分的变化，不足以支持任何结论**——包括"变好了"。

### ③ BM25 的高频词问题：IDF 修正只保证不为负，不会让高频词有区分力

先澄清一个容易混的点：本项目用的是 BM25+ 的 IDF 修正形式 `ln((N+1)/df)`，
所以 IDF **恒为正**，不会出现"文档里有这个词反而被扣分"（[`maixrag/indexing/bm25.py`](../../maixrag/indexing/bm25.py)）。

**但它解决不了另一件事**：在高频领域词上，"专讲这件事的那一篇"赢不过
"顺带提到这件事的一大堆"。查询 `YOLOv5 物体检测` 的 BM25 前 5 名实测 [本项目实测]：

```
1. zh/ai_model_converter/online_converter#h1   确认模型是否支持
2. zh/README_MaixCAM#h10.2                     运行例程
3. zh/README_MaixCAM2#h10.2                    运行例程
4. zh/README_no_screen#h10.2                   运行例程
5. api/maix.nn.YOLOv5                          nn / YOLOv5
```

真正系统讲这件事的 `zh/vision/yolov5` **排第 6，不在前 5 里**。
原因在 IDF 量级上：`yolo` 出现在 59 篇里（idf ≈ 4.18）、`检测` 144 篇（≈ 3.28），
而真正稀有的 `rtsp` 只有 21 篇（≈ 5.21）、`yolov5` 23 篇（≈ 5.12）——
**高频词的区分力天然就弱，这是 IDF 的定义，不是它的 bug。**

另外注意 `物体检测` 直接作为 token 的 df 是 **0**：分词器把它切成 `物体` + `检测`。
**验证 IDF 前先验证分词结果**——用 `maixrag.corpus.tokenize.tokenize_query` 打印一遍，
再用 `maixrag.indexing.bm25.debug_idf_table` 看 df 与 idf。
**"这个词没被检索到"和"这个词没被召回"必须分清楚**
（[事故 01](../postmortem/01-静默的空结果.md) 讲的就是把这两种情况混为一谈）。

**判据**：当"最该排第一的那篇"稳定地排在第 3–10 名、且查询词是该领域的通用词时，
先去看 IDF 表，再考虑字段化或加权——不要直接加大 `top_k`，
那只是把噪声一起放进上下文。

## 7. 自检

**做这件事**：把 `configs/l2_hybrid.yaml` 的 `fusion` 从 `rrf` 改成 `weighted`，
跑一次 `eval --level rag --fake-chat --top-k 5`，然后**对比两份报告的 MRR 与分组表**。

**验收标准**（三条都要能答）：

1. 你知道 `weighted` 与 `rrf` 在实现上的唯一区别（读 `maixrag/retrieval.py` 里的两个函数）；
2. 你能说出融合前每路各取了多少候选（`HybridRetriever.retrieve` 里的 `pool`），
   以及为什么池子太浅会让融合退化；
3. 你跑出的两份报告里，**至少有一个 `qtype` 行的差异方向是你事先预测对的**。

做不到第 3 条没关系——**预测错了才是这一章真正要你学会的东西**，
但你必须能说出是哪一步想错了。

## 8. 课后习题

**R1（复现）** 跑完 3.3 的三条命令，在 `eval/results/` 里找到三份报告，
把 `signature` 行的 Recall@5 抄出来。

- 提示：`--fake` 与 `--fake-chat` 用错会让 dense 那份的数字失去意义
- 验收：三份报告的 `signature` 行分别是 0.500 / 0.000 / 0.500
- 依据：[`concepts/03`](../concepts/03-检索-稀疏与稠密.md)、[`postmortem/02`](../postmortem/02-有文档却召不回.md)

**R2（复现）** 用 `python scripts/demo_retrieval.py --query "MaixPy 里怎么做 YOLO 物体检测？给出一个完整例程。" -k 20`，
记录 `zh/vision/yolov5` 在 dense / bm25 / fused 三列下的名次。

- 提示：融合那一列的名次**比两路都差**是正常现象，先别怀疑脚本
- 验收：能复现"dense 第 5 / bm25 第 6 / fused 第 12"，并说出多出来的那 6 名是从哪来的
- 依据：[`concepts/04`](../concepts/04-融合与重排序.md) 第 3.2 节

**C1（改造）** 给标题与 `heading_path` 加权（字段化 BM25：标题命中单独算一份分，
或把 `heading_path` 拼进 `Chunk.text` 前部）。

- 提示：先看 `chunk.heading_path` 里有什么——`api/maix.camera` 的 chunk
  标题就是 `["camera","Camera"]`，而 `zh/vision/yolov5#h0` 的标题是 `["目标检测概念"]`
- **先写下预测**：查询 `YOLOv5 物体检测` 的前 5 名会怎么变？`signature` 组的召回会升还是降？
- 验收：预测与实测方向一致；不一致时能指出是哪一步想错了
- 依据：[`concepts/04`](../concepts/04-融合与重排序.md)、[design/06 · 5.4](../design/06-项目结构与两条分支.md)（该实验的动机就写在这里）

**C2（改造）** 把 `configs/l2_hybrid.yaml` 的 `retrieval.top_k` 从 5 改到 20 再跑一次，
预测 `context_precision` 与 `recall` 各会怎么动。

- 提示：想清楚"多出来的名额"是给谁的——`Context Precision` 的分母会跟着变大
- 验收：预测两个方向都正确；并解释为什么本项目不靠"加大 top_k"解决 `q004`
- 依据：[`concepts/03`](../concepts/03-检索-稀疏与稠密.md) 误解三
