# 07 · 校验静默放行

> **类别**：校验与信任
> **教的是**：校验器说"没什么可查的"时，绝不能等同于"检查通过"
> **对应代码**：`maixrag/agent/ragtools.py` · `maixrag/evaluation/harness.py`

---

## 症状

终端演示里问"MaixCAM 的 GPIO 怎么用"，agent 检索、查签名、写出点灯代码，
然后在第 4 轮调用 `check_api_usage` 自检。

工具返回：

```
✓ check_api_usage({'code': 'from maix import gpio, pinmap, time, err...'})

检查了 0 个符号
```

**注意那个勾。它返回的是成功。**

代码里明明写着 `from maix import gpio` 和 `gpio.GPIO("GPIOA14", gpio.Mode.OUT)`。

更值得注意的是接下来发生的事——**agent 自己在答案里写道**：

> 我用 `check_api_usage` 校验了上面那段点灯代码，但工具返回「没有出现可校验的
> maix 符号」，也就是**这次自检实际没有起到校验作用**，请以文档依据为准。

它比工具本身更诚实。

## 它为什么危险

这是 [事故 01](./01-静默的空结果.md) 的**升级版**，而且更坏。

01 是一个数据管道安静地返回空，后果是下游拿到空数据。
这一次，安静地失效的是**防幻觉校验本身**——也就是这个项目最核心的那道闸门。

| | 数据管道静默失败 | 校验器静默放行 |
| --- | --- | --- |
| 谁被骗了 | 下游代码 | **模型和人** |
| 后果 | 结论建立在空数据上 | 模型以为代码已通过检查，**于是不再自查** |
| 发现难度 | 数字不合理时会去看 | 报告上都写着"✓"，没人会去看 |

第二种更坏的原因是一条**反馈回路**：

```
校验器失效 → 返回成功 → 模型认为"我检查过了" → 停止自查
           → 幻觉代码进入最终答案 → 没有任何一级拦住了它
```

**一个失效的校验器比没有校验器更危险**，因为它消耗掉了本该用于怀疑的注意力。

## 怎么发现的

不是靠代码审查，是靠**读 agent 自己的输出**。

演示跑完后逐字读答案，在最后一节看到那句"这次自检实际没有起到校验作用"。
如果没有读那一段，这个 bug 会一直躺在那里——因为它的所有表面信号都是正常的：

- 工具调用成功（✓）
- 没有异常
- 演示流程完整跑通
- 最终代码恰好是对的（官方例程）

> **教训**：跑通 ≠ 正确。**"每一步都成功了"本身不是证据**——
> 要问的是"每一步成功时，它到底做了什么"。
> 那个 `检查了 0 个符号` 就是唯一的线索，而它被一个 ✓ 盖住了。

## 根因

两个模块对同一段文本的理解不一致，而且**没有任何地方强制它们对齐**：

```python
# ragtools.py —— 调用方：传进去的是裸 Python 源码
unknown, checked = check_symbols(code, self.roster)

# harness.py —— 被调方：只找 markdown ``` 围栏
def extract_symbol_references(text: str) -> list[str]:
    for block in extract_code_blocks(text):   # ← 裸代码里一个围栏都没有
        ...
```

裸代码没有围栏 → 抽出 0 个符号 → `checked == 0` → 工具把 0 解释成
"没什么可查的" → **`ToolResult.success()`**。

链路里每一步单看都"说得通"：

| 步骤 | 它的想法 | 错在哪 |
| --- | --- | --- |
| `extract_symbol_references` | "我只查代码块，正文里的提及不算断言" | 这个约定**对评测是对的**（评测传的是自然语言答案） |
| `check_symbols` | "返回 (未知, 总数)" | 没说清"总数=0"代表什么 |
| `check_api_usage` | "0 个待查 = 没什么可查的 = 通过" | **把"没解析出来"和"确实没有"当成了一回事** |

**关键判断**：这三步里，只有第三步是真正的错误。
但**修第三步是不够的**——因为前两步的歧义还在，下一次换个调用场景就会再坏一遍。

`checked == 0` 这个值本身携带的信息不足以区分两种情况：

- 代码里确实没有 maix 符号（→ 通过是合理的）
- 代码里有 maix 符号，但校验器没解析出来（→ **必须失败**）

这是**接口设计缺陷**，不是实现 bug。

## 修复

两处，一层治标一层治本。

**第一层（治本）：让调用方显式声明意图，不靠猜。**

```python
def _code_regions(text: str, *, assume_code: bool = False) -> list[str]:
    if assume_code:
        return [text] if text.strip() else []      # 裸代码：整段都查
    return extract_code_blocks(text)               # 答案：只查围栏
```

`check_symbols(..., assume_code=True)` 由 `check_api_usage` 显式传入。

为什么不做成"没有围栏就当代码"的自动回退？因为那会把
**评测语义也一起改掉**：答案正文里提到一个不存在的符号就不再是"提及"，
而会被算成幻觉。事实上有现成的测试锁着这条（`test_prose_mentions_still_do_not_count`）。

> **能猜的就不要传参**是一种合理直觉，但这里的两种意图
> **无法从文本本身区分**——同一个字符串，两种调用方式都对。
> 这时参数不是啰嗦，是把隐含约定变成显式契约。

**第二层（治标，但必须有）：把"校验器失效"变成显式失败。**

```python
if checked == 0:
    if "maix" in code or "gpio" in code or "camera" in code:
        return ToolResult.failure(
            "第一级校验没能从这段代码里解析出任何 maix 符号……"
            "**这表示校验器失效了，不等于代码通过。**",
            kind="internal",
        )
    return ToolResult.success("代码里没有出现可校验的 maix 符号。")
```

原则与事故 01 完全一致，只是对象从"数据"换成了"校验结论"：

> **"我没检查出问题"和"我根本没能检查"必须是两个不同的结果。**

## 回归测试

**位置**：`tests/test_symbol_verification.py`（12 条）+ `scripts/regress_check_api_usage.py`

测试锁的不是"函数返回什么"，而是**四种情形必须被区分开**：

| 输入 | 期望 | 断言 |
| --- | --- | --- |
| 官方例程（裸代码） | 真的检查了 N 个符号，通过 | `test_bare_code_is_actually_parsed` |
| 官方例程 + 一个编造的方法 | 抓住那个编造的方法 | `test_hallucinated_method_is_caught` |
| 与 maix 无关的代码 | "没什么可查的"，通过 | `test_unrelated_code_is_not_a_failure` |
| 有 maix 痕迹却解析不出符号 | **失败** | `fail-closed` 分支 |

其中最重要的是这条——它直接对应本事故：

```python
def test_bare_code_is_actually_parsed():
    """**这是那次 bug 的正身。** 裸代码（无围栏）必须解析出符号。
    原来这条会得到 0 —— 于是后面所有"检查通过"都是假的。"""
    refs = extract_symbol_references(OFFICIAL_LED, assume_code=True)
    assert refs, "裸代码解析出 0 个符号：校验器对最常见的调用形态失明"
```

以及这条反向约束——**修 bug 时最容易顺手破坏的东西**：

```python
def test_prose_mentions_still_do_not_count():
    text = "文档提到 maix.camera.NonExistent 但那是描述。"
    assert extract_symbol_references(text) == []
```

**修复后实测**：

```
1) 官方点灯例程（裸代码）：解析出 7 个符号
2) 官方点灯例程：ok=True  检查了 7 个符号，全部存在。
3) 混入编造方法：ok=False  检查了 7 个符号，发现 1 个不存在：
4) 无关代码：ok=True  代码里没有出现可校验的 maix 符号
5) 有 maix 但解析不出符号：ok=False  kind=internal
```

## 同类问题清单

只要一个函数"可能合理地什么也没做"，这个坑就会出现：

| 变体 | 表现 | 正确做法 |
| --- | --- | --- |
| 测试跳过 | 依赖没装就 `pytest.skip`，CI 全绿 | 显式标注"未验证"，让覆盖面可见 |
| lint 配置错 | 规则文件没被读到 → 0 个问题 | 打一条"扫描了 N 个文件" |
| 权限检查 | 没找到策略 → 默认放行 | **fail-closed**：没策略就是拒绝 |
| 迁移脚本 | 匹配不到表 → 报告"迁移成功" | 报"匹配到 0 张表"并退出非零 |
| **本项目的 `--fake` 模式** | 假模型下指标好看，被当成真实表现 | 报告里写清"决策用的是假模型" |

**一条通用做法**：

> 让每个校验器都报告**它的覆盖面**（检查了多少项），
> 而不只是报告结论。
> 覆盖面的意思是"我到底看了多少东西"，
> 而这件事恰好是 [事故 05](./05-伪装成好消息的0.md) 里
> "指标必须暴露覆盖面"的同一条原则。

  而不改 `assume_code`，工具会对**所有**正常代码报什么？为什么这更糟？

- 提示：参考 [事故 01](./01-静默的空结果.md) 的"合理的输出长什么样"

让**模型**能自己判断"这次校验覆盖了多少"。

- 验收：模型读到返回值后，能区分"7 个符号全部存在"和"没找到符号可查"
- 相关：`maixrag/agent/ragtools.py` 的 `check_api_usage`
