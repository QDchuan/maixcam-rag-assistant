# 08 · 找到了文档，却读不到正文

> **类别**：工具接口
> **教的是**：检索对了不等于模型拿到了 —— 以及"成功但没有新信息"要怎么被看见
> **对应代码**：`maixrag/agent/ragtools.py` · `maixrag/agent/loop.py` · `maixrag/agent/tools.py`

---

## 症状

用终端演示问一个真实问题：

```
▶ 如何设计一个二维云台人脸跟踪系统

  ⏺ 第 1 轮 · 思考中…
    ✓ search_docs({'query': '人脸检测 云台 舵机 跟踪', 'k': 10})
  ⏺ 第 2 轮 · 思考中…
    ✓ search_docs({'query': '人脸追踪2轴云台 例程 代码 舵机 PWM PID 死区', 'k': 12})
  ⏺ 第 3 轮 · 思考中…
    ✓ search_docs({'query': '人脸追踪2轴云台 main.py 代码示例 Servos 舵机 人脸检测…'})
  ⏺ 第 4 轮 · 思考中…
    ✗ lookup_api({'symbol': 'Servos'})
  ⏺ 第 5 轮 · 思考中…
    ✓ search_docs({'query': 'face_tracking 云台 PID 死区 servos 舵机 引脚 活动范围…'})
  ⏺ 第 6 轮 · 思考中…
    ✓ search_docs({'query': '人脸追踪 云台 例程 源码 face_track gimbal 完整代码'})
  …
    ⚠ 轮次达到上限（10）

── 答案 ──
未能完成回答，原因是：轮次达到上限（10）
```

**六次搜索、六种措辞、零条新信息。**

而这份文档就在语料里：`corpus/raw/repo/projects/face_tracking.md`，
而且是全语料里**唯一**提到"云台"的文件。

## 它为什么危险

因为它看起来像"模型不行"。

用户的判断会很自然地落在"这个模型太笨了"或者"这题太难了"上，
然后去换模型、去调提示词、去加预算——**全都不会有用**，
因为真正缺的东西是一个工具。

这类故障的共同形态是：

> **每一层都汇报成功，而整件事失败了。**

| 层 | 它汇报的 | 真实情况 |
| --- | --- | --- |
| 语料 | 抓取、切分成功 | ✅ 真的成功了 |
| 检索 | 返回 5 个片段 | ✅ 真的返回了 |
| 工具 | `ok=True` | ✅ 真的没报错 |
| 循环 | 10 轮跑完 | ✅ 真的跑完了 |
| **整个系统** | **"未能完成回答"** | ❌ 文档一直躺在磁盘上 |

**没有任何一处是"错"的，所以没有任何一处会报警。**
这就是为什么它值得写进事故档案——它教的是"怎么想到去看工具接口"，
而不是"哪个函数写错了"。

## 怎么发现的

不是因为报错，是因为**读 agent 自己的轨迹时觉得那个轨迹不合理**。

第一轮 `search_docs('人脸检测 云台 舵机 跟踪')` 是**对**的查询。
如果它没找到东西，那还有得说；但它返回了 5 个片段、全是 `✓`。
那它为什么要换个说法再搜一遍？

顺着这个问题去查检索质量，结果出乎意料：

```
$ python scripts/diag_retrieval_miss.py
目标文档 zh/projects/face_tracking：17 个 chunk

'如何设计一个二维云台人脸跟踪系统'   命中第 1 位
'人脸检测 云台 舵机 跟踪'            命中第 1 位
'人脸追踪2轴云台 例程 代码 舵机 PWM'  命中第 1 位
'云台'                              命中第 1 位
'face_tracking'                     命中第 1 位
'人脸跟踪'                           命中第 1 位
```

**检索是完美的。** 每一个查询的第一名都是那份文档。

> **这一步是整篇事故里最值得记的**：如果不去查——如果只是看着轨迹觉得
> "检索好像不行"——那么接下来所有的工作都会花在调检索上，
> 而检索本来就是对的。
>
> **"先验证你打算优化的那个东西到底有没有坏"**，比优化本身更省时间。

## 根因

三个原因叠在一起。**每一个单独存在时都不致命，叠起来才致命。**

### 根因一：`search_docs` 返回的是片段，而片段不保证自洽

把检索器真正交给模型的那段文本打出来看：

```
[1] 人脸追踪2轴云台 — 简介
    类型：prose｜来源：zh/projects/face_tracking
基于 MaixCAM 和云台的人脸追踪程序。实际效果如下图所示：

[图片：图]

[2] 人脸追踪2轴云台 — 常见问题
人脸跟踪效果不理想。
不同的云台使用的 PID 参数不尽相同，您可以通过调节 PID 值来使得追踪效果更丝滑。

[3] 人脸追踪2轴云台 — 常见问题
在完成跟踪后，云台对着不动的人脸小幅度左右抖动一段时间。

[4] 人脸及关键点检测 — 简介
[5] 人脸表情情绪识别 — 简介
```

排名第一的是那份文档，**但返回的片段是"简介一句话"和两条 FAQ**。
真正的引脚与代码在文档中段，没进前 5。

为什么？因为同文档的 17 个片段共享同一段 `heading_path`（"人脸追踪2轴云台"），
它们在这一层的词法得分**几乎相同**，彼此的先后就由很弱的信号决定。
短的简介片段命中了"云台"和"人脸"，长代码片段在长度归一化下反而吃亏。

**模型看到 [1] 是一个只有一句话的"简介"，判断"这不是我要的"——这个判断是对的。**
它没错。错的是我们只给了它一个"模糊搜索"的旋钮，和一个"再搜一次"的动作。

### 根因二：循环看不见"成功但没有新信息"

循环里本来有一个防浪费的机制：

```python
if not ex.result.ok:
    sig = f"{call.name}:{ex.result.kind}"
    if sig == last_error:
        repeated += 1
    ...
    if repeated >= self.max_repeated_errors:
        ...  # 判断为卡住，提前终止
```

**它只数失败。** 而这里六次调用全是 `ok=True`，
所以这个计数器一次都没动过，预算被烧光了。

这是本项目的第三次同类问题——前两次是
[01 静默的空结果](./01-静默的空结果.md) 和
[07 校验静默放行](./07-校验静默放行.md)：

> **"成功"这个信号本身携带的信息太少了。**
> 一个只按 `ok` 分支的逻辑，看不见"成功了但什么也没得到"。

### 根因三：降级只打印状态报告，不给部分答案

预算耗尽时输出的是：

```
未能完成回答，原因是：轮次达到上限（10）
已完成的部分：
  · search_docs 成功
  · search_docs 成功
```

而本项目的设计文档自己写的是"**用已有证据给一个部分答案**"。

**打印工具名单不是部分答案——它是关于过程的报告，不是关于问题的回答。**
用户要的是"云台怎么接"，不是"你调了几次搜索"。

## 修复

四处，前三处治因，第四处补一个顺手发现的谎。

### 修复一：补上"打开文档"这个动作

新增第五个工具 `read_doc(doc_id, section, max_chars)`：

- **确定性**：给定 doc_id 就返回确定内容，没有相似度、没有随机性；
- 支持只写文件名（`face_tracking` → `zh/projects/face_tracking`），有歧义时列候选；
- 支持只读某一节；
- **和 `search_docs` 共用同一个引用编号池**——否则答案里的 `[3]`
  分不清是搜来的还是读来的，引用校验就无从做起。

修复后的同一条轨迹：

```
  ⏺ 第 1 轮 · 思考中…
    ✓ search_docs({'query': '二维云台 人脸跟踪 舵机', 'k': 10})
  ⏺ 第 2 轮 · 思考中…
    ✓ read_doc({'doc_id': 'zh/projects/face_tracking'})      ← 就是这一步
```

第二轮就打开了。**没有改提示词，没有换模型，没有加预算。**

### 修复二：给工具结果加一个"这次学到了什么"的字段

判断"有没有进展"最省事的做法是给 `content` 算哈希。**但那样会漏判**：
同一批片段在第二次检索时，结尾那行"（本次返回 5 个片段，编号从 6 到 10）"
的编号变了，于是**一模一样的证据看起来像新证据**。

所以给 `ToolResult` 加了一个类型化字段：

```python
evidence: tuple[str, ...] = ()   # 搜到的 chunk_id、查到的符号名、列出的模块名
```

循环据此判断：

```python
fresh = [e for e in evidence if e not in seen]
if fresh:
    seen.update(fresh)
    return 0                # 有新材料，计数归零
return current + 1          # 全是见过的
```

**关键设计**：`evidence` 为空表示"这个工具不产出材料"
（比如 `check_api_usage` 给的是判断而不是材料），
这种调用**既不算进展也不算原地打转**——否则连调两次自检就会被误判成卡住。

### 修复三：降级时补一次"最后一次发言"

预算耗尽时，把工具表清空（传 `[]`），要求模型用手上的材料作答：

```python
decision = self.model.decide(list(messages) + [Message("user", ask)], [])
```

**传空工具表是刻意的**：从**接口上**让它无法再调工具，
而不是在提示词里请求它别调。能靠结构约束的就别靠礼貌。

这一改的效果最大。同一个问题在预算耗尽时给出的答案开头是：

```
【预算已用尽，以下是基于已获取材料的回答】
（未完成的原因：轮次达到上限（12））
```

### 修复四：启动画面在说谎

查这件事的时候顺手发现：终端演示的横幅硬编码写着

```
检索 BM25 + 向量 + RRF
```

而当时的**内置默认配置**是 `retrievers: ["dense"]`——只跑稠密检索。
**启动画面在描述一套没有启用的配置。**

这和事故 07 是同一个病：说的和做的不一致，而且没人会去核对。
修法是让那一行从检索器对象本身取（`build_banner_stats`），
并把默认配置改成和项目推荐值一致（`["dense", "bm25"]`、`top_k: 5`）。

> **默认值就是大多数人会用的值**，所以它必须等于**推荐**的那套，
> 而不是最小的那套。想让读者看到的东西，和默认跑起来的东西，必须是同一个。

## 回归测试

**位置**：`tests/test_agent_progress.py`（18 条）

| 断言 | 锁住什么 |
| --- | --- |
| `test_read_doc_returns_the_whole_document_in_order` | **本事故的正身**：找到的文档能被完整读到 |
| `test_read_doc_shares_the_citation_pool` | 编号连续，引用不串题 |
| `test_read_doc_ambiguous_id_is_rejected_not_guessed` | 有歧义时列候选，不替模型猜 |
| `test_search_with_no_hits_is_a_failure` | "没找到"不能标成功（事故 07 同类） |
| `test_repeated_identical_evidence_stops_the_loop` | **没有新证据必须提前终止，而不是跑满预算** |
| `test_fresh_evidence_resets_the_counter` | 正常的多次检索不能被误判成卡住 |
| `test_tools_without_evidence_are_not_counted_as_no_progress` | 判断类工具不算原地打转 |
| `test_budget_exhaustion_answers_with_what_it_has` | 降级要给部分答案 |
| `test_degradation_never_calls_a_tool` | 收尾时工具表必须为空 |
| `test_degradation_falls_back_to_status_report_when_call_fails` | 收尾失败仍如实报告，绝不静默 |

两条最容易写错的，单独说：

```python
def test_fresh_evidence_resets_the_counter():
    """带回一个新片段就算有进展。**不能把正常的多次检索误判成卡住。**"""

def test_tools_without_evidence_are_not_counted_as_no_progress():
    """`check_api_usage` 这类工具给的是**判断**而不是**材料**。
    它既不算进展也不算原地打转——否则连调两次自检就会被误判成卡住。"""
```

**防误判和防浪费一样重要**：一个过于激进的"卡住"判定会把正确的多跳行为掐死，
而那比烧钱更难发现——因为烧钱看得见账单，掐死只是"答案变短了"。

**修复后实测**（`python -m maixrag demo "如何设计一个二维云台人脸跟踪系统"`）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 打不开文档时的行为 | 反复换措辞搜索 | 第 2 轮 `read_doc` 打开 |
| 工具的失败计数 | 全 `ok=True`，从不触发 | 空结果记 `not_found` |
| 原地打转 | 不可见 | 连续 3 次无新证据即终止并说明 |
| 预算耗尽 | 打印工具名单 | 给出带引用的部分答案 |
| 启动画面 | 声称 BM25+向量，实际只有向量 | 从检索器对象取 |

## 同类问题清单

| 变体 | 表现 | 判据 |
| --- | --- | --- |
| 只做分页不做跳转 | 用户翻到第 10 页仍找不到，其实有搜索 | 提供**两种**互补的动作 |
| 日志只说"成功" | 成功但结果为空，没人发现 | 记**数量**，不只记状态 |
| 重试逻辑按 `ok` 分支 | "成功但无进展"永远不触发重试上限 | 计数**新信息**，不只计数失败 |
| 降级只报状态 | "服务暂不可用"而不是上次的成功结果 | 降级要**给东西**，不只是**说情况** |
| 探针与真实路径不同 | 探针通、真实路径不通 | 自检必须走真实代码路径 |
| 横幅/文档写死数字 | 说的和跑的不是一套配置 | 画面上的每个数字都从对象取 |

**一条通用做法**：

> 让每个动作都报告**它带来了什么**，而不只是报告**它成没成功**。
> "成功了但什么也没带来"是最难被发现的一类浪费——
> 因为所有的灯都是绿的。

这条原则和另外两篇事故是同一条：

- [05 伪装成好消息的 0](./05-伪装成好消息的0.md)：指标必须暴露**覆盖面**
- [07 校验静默放行](./07-校验静默放行.md)：校验器必须报告**它检查了多少**

三者合起来是一句话：**"我做了什么"和"我做到了什么"必须分开表达。**

## 课后习题

**A1（复现）** 跑 `python scripts/diag_retrieval_miss.py`，确认检索是完美的；
然后注释掉 `cli.py` 里注册 `read_doc` 的那一行（或把 `cfg.agent.tools`
里的 `read_doc` 去掉），再跑一次 `demo` 问同一个问题。

- 验收：能得到"反复搜索直到预算烧光"，并说出**为什么每次都显示 ✓**
- 追问：如果只看 `✓`，你会先怀疑哪一层？为什么那是错的怀疑方向？

**B1（诊断）** 你的 RAG 服务日志里全是 `200 OK`，但用户投诉"答非所问"。
列出三种"每一层都成功、整体却失败"的可能，并说明各自怎么验证。

- 验收：至少一种必须和本事故同类（**工具/接口不够，而不是模型不够**）
- 提示：从"用户实际拿到的东西"倒推，而不是从日志正推

**C1（改造）** 给 `read_doc` 加一个能力：按**行号范围**或**关键词邻域**读取，
而不是整篇或整节。

- 验收：新增的 `evidence` 仍然正确，且引用编号仍然连续
- 追问：什么情况下"邻域读取"会反而**降低**答案质量？（提示：上下文被切断了）

**D1（判断）** 本事故的修复之一是"连续 3 次没有新证据就终止"。
这个阈值该取多少？说明你的判断依据，以及**取小了会怎样、取大了会怎样**。

- 验收：答案里要给出两种失效模式各自的**可观测症状**，
  而不只是"取中间值比较好"
- 参考：事故 06 的"预算要匹配任务深度"是同一个问题的另一个面
