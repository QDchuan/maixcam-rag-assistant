# 06 · 预算与任务不匹配

> **类别**：参数与调优
> **教的是**：参数要匹配任务，不是越大/越小越好
> **对应代码**：`maixrag/agent/loop.py` 的 `Budget`

---

## 症状

同一个问题、同一份语料、同一套工具：

**问题**：`MaixPy 里怎么做 YOLO 物体检测？给出完整例程`

**预算 4 轮的 agent**：

> 未能完成回答，原因是：轮次达到上限（4）
>
> 已完成的部分：
>   · search_docs 成功
>   · search_docs 成功
>   · lookup_api 成功
>   · search_docs 成功

**链式基线（L1，没有循环）**：

> 资料中没有给出 YOLO 物体检测的完整代码，因此无法提供可直接运行的完整示例。

**两个都没答出来。** 而且 agent 花的钱明显更多（4 次工具调用 + 4 次模型调用）。

**在这个配置下，agent 不如链式**——至少链式给了一个明确的答案，
agent 给的是"我没做完"。

## 它为什么危险

因为它会让人得出**完全错误的结论**。

如果你跑完这一轮评测，看到的是"agent 更贵、效果更差"，
自然会得出"agent 不适合这个场景"。

而真相是：**agent 在做正确的多跳推理，只是预算不够它做完。**

这个错误的方向是**最坏的一种**——它让你放弃了一个有效的方案，
而且理由是"数据支持的"。

> **用一个配置错的方案去和基准比较，得到的结论不是"这个方案不好"，
> 而是"这个方案在配置错的时候不好"。这两者差别巨大。**

## 怎么发现的

因为**轨迹里的每一步都是合理的**。

看一下 4 轮预算下它做了什么：

```
第1轮  search_docs("YOLO 物体检测 例程", k=8)
第2轮  search_docs("YOLOv5 YOLOv8 YOLO11 物体检测 代码 yolo = YOLOv5", k=10)
第3轮  lookup_api("maix.nn.YOLOv5")
第4轮  search_docs("yolov5.py 例程代码 detector = nn.YOLOv5 完整代码", k=10)
       → 撞上预算上限
```

这四步里**没有一步是浪费的**：

- 第 1 步：常规检索；
- 第 2 步：**自己改写了查询**（把类名加进去，扩大召回面）；
- 第 3 步：**切换到确定性工具**（查签名比继续检索更准）；
- 第 4 步：**用第 3 步学到的类名 `nn.YOLOv5` 去构造新的检索词**。

**第 4 步是关键**：它把"查签名"得到的信息反馈回了检索。
这是真正的多跳推理，而链式架构**结构上做不到这件事**。

所以我看的不是"它失败了"，而是"**它失败之前做的每件事都对**"。
这个观察直接指向了"预算不够"，而不是"方法不行"。

## 根因

预算默认值是 `max_turns=4`，是我按"保守一点"的直觉设的。

保守本身是对的——[`demo_budget.py`](../../scripts/demo_budget.py) 演示过
不设预算的 agent 会跑飞。但**保守的取值不能靠直觉**，它要匹配任务深度：

| 任务类型 | 需要几轮 | 理由 |
| --- | --- | --- |
| 单点事实查询（"某函数签名是什么"） | 1–2 轮 | 一次 lookup_api 就够 |
| 需要检索的概念题 | 2–3 轮 | 检索 → 可能再检索一次 → 答 |
| **多跳（先查 A 再用 A 查 B）** | **6–10 轮** | 每一步都可能需要修正 |

**默认值 4 覆盖了前两类，但对第三类不够。**

更深一层的问题：**"默认值"本身就是一个决策**，
而我把这个决策建立在直觉上，并且没有在评测里区分任务类型
（哪个 qtype 需要几轮）。

## 修复

两处：

### 1. 把预算暴露成可调参数

```bash
python -m maixrag --config configs/l2_hybrid.yaml agent "..." --max-turns 10
```

并且默认值改为按任务可调，而不是一个固定数。

### 2. 把"预算够不够"变成可观察的

评测报告里输出 agent 专属指标：

```
工具调用总数  88
其中失败      3
其中被拒      0
按工具分布    {'search_docs': 31, 'lookup_api': 25, 'check_api_usage': 21, 'list_api': 11}
平均每题工具调用  4.2 次/题
```

**平均 4.2 次/题，而预算是 10 轮** —— 这说明对多数题目预算充足；
而如果平均调用数逼近上限，就说明预算需要调大。

## 结果

**预算 10 轮下，同一道题**：

```
第1轮  search_docs("YOLO 物体检测 例程", k=8)
第2轮  search_docs("YOLOv5 YOLOv8 YOLO11 …", k=10)
第3轮  lookup_api("maix.nn.YOLOv5")
第4轮  search_docs("yolov5.py 例程代码 detector = nn.YOLOv5 …")
第5轮  check_api_usage(草稿代码…)          ← 写完自检
第6轮  lookup_api("maix.nn.YOLOv5.detect") ← 补缺失的签名
第7轮  check_api_usage(修正后代码…)        ← 再校验一次
第8轮  final
```

它的最终答案里有：

```python
from maix import camera, display, image, nn, app

detector = nn.YOLOv5(model="/root/models/yolov5s.mud", dual_buff=True)
cam = camera.Camera(detector.input_width(), detector.input_height(),
                    detector.input_format())
disp = display.Display()

while not app.need_exit():
    img = cam.read()
    objs = detector.detect(img, conf_th=0.5, iou_th=0.45)
    for obj in objs:
        img.draw_rect(obj.x, obj.y, obj.w, obj.h, color=image.COLOR_RED)
        label = detector.labels[obj.class_id]
        img.draw_string(obj.x, obj.y, f"{label}: {obj.score:.2f}",
                        color=image.COLOR_RED)
    disp.show(img)
```

**注意 `cam = camera.Camera(detector.input_width(), ...)`** ——
它主动让摄像头分辨率去匹配模型的输入格式。
这不是文档里逐字抄来的，是**理解之后写的**。

## 正确的结论

不是"agent 更好"，而是：

> **agent 的能力上限更高，但它要求预算与任务深度匹配。**
> 预算给少了，它比链式还不如（链式至少给了一个答案）；
> 预算给够了，它能做到链式做不到的事。

而"给多少才够"**只能靠评测回答**，不能靠拍脑袋。

**位置**：`scripts/demo_budget.py` 的三个场景 + `tests/test_agent_loop.py`

```python

def test_no_budget_means_runaway():
    """**刻意演示的错误：不设预算。**"""

def test_default_budget_is_conservative():
    """默认值就是大多数人会用的值——宽松的默认等于把"跑飞"设成默认行为。"""
```

两条测试锁住了两端：**预算太小会失败**（本篇），**预算缺失会跑飞**（demo 场景一）。
而默认值必须保守——所以真正的解法不是"把默认值调大"，
而是**让预算可调 + 让"够不够"可观察**。

## 同类问题清单

| 变体 | 表现 |
| --- | --- |
| `top_k` 太小 | 相关内容在索引里，但没进上下文 |
| `top_k` 太大 | 噪声淹没信号，还推高成本 |
| 超时太短 | 慢但正确的请求被判定为失败 |
| 重试次数太少 | 偶发失败被当成永久失败 |
| chunk 太大/太小 | 见 [02 有文档却召不回](./02-有文档却召不回.md) |
| 并发太高 | 触发限流，反而更慢 |
| 评测集太小 | 指标噪声大于信号 |

**一条通用做法**：**每一个"限制类参数"都要能被观察。**

- 预算 → 报告"平均消耗 / 上限"
- top_k → 报告"相关内容排第几"
- 超时 → 报告"P50 / P95 延迟"

**只看结果指标、不看资源指标，就无法区分"方法不行"和"参数不对"。**

## 课后习题

**A1（复现）** 用 4 轮和 10 轮分别跑 YOLO 那道题，对比轨迹：

```bash
python -m maixrag --config configs/l2_hybrid.yaml agent "MaixPy 里怎么做 YOLO 物体检测？给出完整例程" --max-turns 4
python -m maixrag --config configs/l2_hybrid.yaml agent "MaixPy 里怎么做 YOLO 物体检测？给出完整例程" --max-turns 10
```

- 验收：能指出 10 轮版本里**链式架构做不到**的那一步

**B1（诊断）** 你的 RAG 系统在"某个函数签名是什么"这类问题上表现很好，
但在"为什么我的摄像头读不到图像"这类问题上很差。
列出三种可能原因，并说明怎么区分。

- 验收：至少一种要指向"预算/轮次"而不是检索质量
- 提示：后者往往需要先查现象、再查相关 API、再查配置

**C1（改造）** 给评测报告加一个"预算使用率"指标（平均消耗 / 上限）。
跑一次全量评测，看它落在哪里。多少算"该调大"？

- 验收：给出一个判据，并说明为什么是这个数

**C2（改造）** 现在预算是全局的一个数。改成**按 qtype 给不同预算**

那么反过来——**怎么判断一个方案的失败是"配置不对"还是"方法不行"？**
