# 事故档案

> 这一层回答的是：**我遇到了一个现象，它是怎么回事。**

RAG 与 agent 工程里最难的部分，不是把东西搭起来，而是**东西安静地坏掉**的时候——
没有报错、没有异常、指标看起来还行。

这里记录了本项目在开发过程中**真实发生过的六次事故**。每一次都有完整的
症状 → 根因 → 修复 → 回归测试，而且都能被复现。

**为什么要公开写自己的失误**：因为"我们也踩过"比"你应该这样做"有用得多。
而且这六条覆盖了六种**不同类别**的判断力，不是六个孤立的知识点。

## 每篇的结构

六篇用同一套骨架，学会读一篇就会读全部：

```markdown
## 症状          能对号入座的现象，具体到能搜到
## 它为什么危险   不发现会怎样——这一节决定读者会不会继续读
## 怎么发现的     真实的发现过程，比结论更重要
## 根因          技术原因，配最小复现
## 修复          改了什么；有多解时说明为什么选这个
## 回归测试       文件名 + 断言。没有回归测试的修复不算修复
## 同类问题       这个坑还有哪些变体
```

**"怎么发现的"这一节是重点**：它教的是排查方法，而排查方法比结论更可迁移。

## 课后习题

读完六篇之后，试着做这几道（答案在 [`docs/exercises/answers.md`](../exercises/answers.md)）：

**B1（诊断）** 你在自己的 RAG 项目里发现：某个问题的答案明显有依据，
但你的评测报告说"召回率 0"。列出三种可能的原因，并说明怎么逐一排除。

**B2（诊断）** 你写了一个"检查代码里 API 是否存在"的工具，
上线后同事反馈它误报很多，于是大家都不用了。指出这个工具设计上的根本问题。

**D1（判断）** 事故 05 说明"指标会伪装成好消息"。
如果你只能给评测报告加**一个**字段来防止这种情况，你加什么？说明为什么它够用。

**D2（判断）** 事故 02 的修复让 signature 类召回 +50pt，但 concept 类 -12.5pt。
假设你不能同时优化两者，你会怎么选？说明你的判断依据。
