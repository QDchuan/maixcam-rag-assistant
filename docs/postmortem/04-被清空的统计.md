# 04 · 被清空的统计

> **类别**：状态与生命周期
> **教的是**：谁在什么时候被重置
> **对应代码**：`maixrag/agent/app.py` 的 `AgentApp.note_execution`

---

## 症状

主分支 agent 的评测报告里，"agent 专属指标"是这样的：

```
工具调用总数  2
按工具分布    {'search_docs': 2}
平均每题工具调用  0.1 次/题
```

**18 道题，一共只调用了 2 次工具。**

这个数字明显不对——就上一节手工跑的那一道 YOLO 题，
一次运行就调了 7 次工具。18 道题不可能只有 2 次。

## 它为什么危险

两个层面。

**第一，它让"agent 值不值"这个问题无法回答。**
工具调用次数正是 agent 的成本项。这个数字错了，
"agent 的收益是否值得它的成本"就失去了分母。

**第二，它是那种"看起来像真的"的错误。**
0.1 次/题 不是 0，也不是负数，它落在一个**貌似合理的范围**里。
如果不是我恰好记得"单题就调了 7 次"，这个数字会被当成真的用下去，
然后得出"agent 其实很省"这个完全错误的结论。

> **不合理但合理的数字，比明显错误的数字更危险。**

## 怎么发现的

因为**我记得一个具体的数**。

前面手工跑 YOLO 问题时，轨迹里有 7 条 `tool_result`。
那是亲眼看到的。所以报告上说"总共 2 次"时，我立刻知道不对。

**这里没有可复用的技巧，只有一条习惯**：
在看到聚合指标之前，先在一个具体样本上手工跑一遍、记住它长什么样。
**聚合指标的质量，取决于你有没有一个单样本的参照。**

## 根因

统计是从 `tools.history` 读的：

```python
def agent_stats(app):
    hist = app.tools.history          # ← 读这里
    return {"tool_calls": len(hist), ...}
```

而单题评测时，`history` 会被**逐题清空**：

```python
def answer(self, question):
    self.app.rag.reset_citations()
    self.app.tools.history.clear()    # ← 每道题开始前清空
    result = self.app.loop.run(question, ...)
```

清空本身是**正确**的：不清空的话，上一题的调用会串到下一题，
引用池也会串（表现为"引用精确率莫名其妙地高"）。

错的是**统计读了一个会被重置的数据源**。

```
每题开始   history.clear()      ← 统计的"账本"被清零
跑题       history 累积 1..7 条
跑完       agent_stats 读 history → 只剩最后一题的 7 条？
```

实际结果是 2 条，说明最后一题只调了 2 次。无论多少，
**它测的是"最后一题"，不是"全部 18 题"**。

## 修复

把统计和数据源分开：`history` 继续逐题清空（它是**当前题**的现场），
统计改成 `AgentApp` 上的**累计计数**：

```python
@dataclass
class AgentApp:
    total_tool_calls: int = 0
    total_tool_failures: int = 0
    total_denied: int = 0
    tool_counts: dict[str, int] = field(default_factory=dict)

    def note_execution(self, ex) -> None:
        self.total_tool_calls += 1
        self.tool_counts[ex.call.name] = self.tool_counts.get(ex.call.name, 0) + 1
        if not ex.result.ok:
            self.total_tool_failures += 1
        if ex.denied_by:
            self.total_denied += 1
```

修好后的真实数字：

```
工具调用总数  75
其中失败      6
其中被拒      0
按工具分布    {'lookup_api': 13, 'search_docs': 23, 'check_api_usage': 15, 'read_doc': 20, 'list_api': 4}
平均每题工具调用  4.2 次/题
```

**75 次，平均 4.2 次/题。** 而且注意 `check_api_usage` 被调了 15 次、`read_doc` 20 次——
那是 agent 在**主动自检**，是链式基线完全没有的行为。

## 回归测试

修复时加了一段文档字符串，写明这个坑出现过**两次**：

```python
def agent_stats(app: AgentApp) -> dict[str, Any]:
    """...
    **注意这里读的是累计计数而不是 `tools.history`。**
    单题评测时 history 会被逐题清空（避免上一题的调用串到下一题），
    所以从 history 读会把"18 题的统计"变成"最后一题的统计"——
    这个 bug 出现过一次，表现为 18 题只统计到 2 次工具调用。
    """
```

**"出现过两次"不是笔误**：第一次修在 `agent_stats`，
但 `_avg_tool_calls` 里**同样读的 `history`**，所以平均调用数那一路还是错的。
第二次修的时候，两个地方都写上了口径说明。

> ⚠️ **这一条的回归保护只有文档字符串，没有测试，此条待补。**
> `tests/` 下没有任何用例构造过 `AgentApp` / `AgentProfile`，
> 也没有任何用例读过 `total_tool_calls` / `agent_stats`——
> 也就是说「统计不要再从会被逐题清空的 `tools.history` 读」这件事，
> 今天只能靠人读那段文档字符串来保证。
> [`incidents.tsv`](../evidence/incidents.tsv) 这一行绑定的是
> `scripts/check_eval_consistency.py`，它查的是 `.md` 与 `.json` 是否自洽
> （另一类"产物被覆盖"的事故），
> **与本篇这条 bug 不是同一件事**。

> **教训**：同一个数据源被两处读取时，修一处不够。
> 修复时要问"还有谁在读这个"。

## 同类问题清单

| 变体 | 表现 |
| --- | --- |
| 计数器被重置 | 每个请求开始时清零，统计只反映最后一个请求 |
| 上下文管理器的作用域错 | `with` 块外的累积变量没有持久化 |
| 测试之间的状态泄漏 | 前一个测试的数据污染后一个（反向问题） |
| 缓存的 key 少了维度 | 不同配置命中同一个缓存条目 |
| 全局单例被多处修改 | 谁都能改，没人知道当前值是谁设的 |

**一条通用做法**：区分**「现场」**与**「账本」**。

- **现场**（`history`）：当前这一步需要看到的近期数据，随作用域清空是合理的；
- **账本**（`total_*`）：跨作用域累积的统计，绝不能挂在一个会被重置的对象上。

**混用这两者，就会出现本篇这种"账本被现场清零"的错误。**
