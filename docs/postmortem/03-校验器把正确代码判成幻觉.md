# 03 · 校验器把正确代码判成幻觉

> **类别**：校验与信任
> **教的是**：**假阳性比漏报更危险**
> **对应代码**：`maixrag/evaluation/harness.py` 的 `_symbol_is_valid`、`maixrag/corpus/pipeline.py` 的 `_flatten_aliases`

---

## 症状

主分支 agent 的评测报告里，有一道题（GPIO 点灯）的幻觉符号是：

```
maix.gpio.GPIO
maix.gpio.GPIO.toggle
maix.gpio.GPIO.value
maix.gpio.Mode.IN
maix.gpio.Mode.OUT
maix.pinmap.set_pin_function
```

看第一眼像是"模型编了一堆 API"。但**仔细看这些名字**——
`GPIO`、`Mode.IN`、`Mode.OUT`、`set_pin_function`——它们都太像真 API 了。

编造的 API 通常长得**似是而非**（`super_zoom`、`cv2_imread`）。
而这一批名字整齐得像是有出处的。

## 它为什么危险

因为**假阳性会摧毁信任，而失去信任的校验器比没有校验器更糟。**

推理链是这样的：

1. 校验器误报 → 使用者发现"我明明写对了，它说我错"
2. → 使用者不再相信校验结果
3. → 把校验关掉，或者学会忽略它的警告
4. → **于是真正的幻觉也一起被忽略了**

一个漏报的校验器只是"没帮上忙"。一个误报的校验器是**主动帮倒忙**：
它训练使用者忽略警告。

这是本篇最值得记住的一句话：

> **一个工具的误报率决定它会不会被使用；而没被使用的工具等于不存在。**

## 怎么发现的

从"这些名字太像真的"开始的。

如果只是扫一眼报告，会认为"agent 编了 6 个 API，幻觉率 0.039，需要加强提示词"。
但 `Mode.IN` / `Mode.OUT` 这种命名方式不像编造——编造者不会这么规整。

于是我去查**语料里是怎么写的**：

```bash
grep -n "import" corpus/raw/repo/peripheral/gpio.md
```

输出：

```python
from maix import gpio, pinmap, time, sys, err
```

**官方教程原文就是这么写的。** 也就是说 `from maix import gpio` 完全正确，
`gpio.GPIO` 完全正确，`gpio.Mode.OUT` 完全正确。

**是校验器错了，不是 agent 错了。**

## 根因

**API 文档的模块路径 ≠ 用户实际 import 的路径。**

| 来源 | 内容 |
| --- | --- |
| 文档页 URL | `maix/peripheral/gpio.html` |
| 从 URL 推出的模块名 | `maix.peripheral.gpio` |
| 于是符号登记为 | `maix.peripheral.gpio.GPIO` |
| **但教程里写的是** | `from maix import gpio` |
| **于是用户的代码里是** | `gpio.GPIO` → 解析为 `maix.gpio.GPIO` |
| **而白名单里没有这个** | → **判为幻觉** |

白名单只收了文档路径形式，所以**正确代码被系统性误报**。

这个错误还有一个隐蔽之处：它**只影响部分模块**。
`maix.camera.Camera` 恰好两种形式一致，所以不报错；
只有涉及子包（`peripheral.gpio`）的模块才会误报。
**部分模块误报比全部误报更难发现。**

## 修复

三处，前两处治标，第三处治本。

### 1. 生成扁平别名

规则来自语料自身的证据（教程里写 `from maix import gpio`），不是猜的：

```python
# 模块 maix.A.B 的扁平形式是 maix.B
# maix.peripheral.gpio.GPIO.get_mode  →  maix.gpio.GPIO.get_mode
out.add(".".join([parts[0], *parts[2:]]))
```

白名单 2996 → 4833 条。

### 2. 从语料里发现未文档化的模块

修完第 1 处后，自检又发现三类残留：

```
from maix import sdv1_5      （dlm_lora_sdv1_5.md）
from maix import sensevoice  （asr_sensevoice.md）
```

这些模块**真实存在、教程在用，但 wiki 上没有 API 页**——
所以从符号表里推不出来。加一步"从语料里扫 import 语句"补上。
白名单 4833 → 4868 条。

### 3. 加一道自检（这是治本的一处）

前两处都在修**已知**的漏项。治本的做法是**让"漏了什么"变得可见**：

```python
def check_roster_covers_corpus(roster, raw_repo) -> list[str]:
    """从教程原文里抽出 `from maix import X`，报告哪些 X 不在白名单覆盖范围内。"""
```

每次 `corpus build` 输出 `corpus/reports/roster_gaps.md`。

> **从"修好这一个 bug"变成"建立发现这类 bug 的机制"**，
> 这是这一处修复与前两处的本质差别。

## 回归测试

**位置**：`scripts/regress_symbol_false_positive.py`

把曾经被误报的正确代码固定成用例，并且**同时锁住两个方向**：

```python
MUST_PASS = [
    ("gpio 扁平导入（曾经被误报）", "from maix import gpio, pinmap\nled = gpio.GPIO(...)"),
    ("外设子包路径", "from maix.peripheral import gpio\n..."),
    ("camera 全限定名", "import maix.camera\n..."),
    ("常见组合导入", "from maix import camera, display, image, nn, app\n..."),
]

MUST_FAIL = [
    ("照搬 OpenCV", "...image.cv2_imread..."),
    ("照搬树莓派", "...camera.PiCamera()..."),
    ("编造实例方法", "...cam.super_zoom(3)..."),
]
```

**为什么两个方向都要锁**：修假阳性最容易的错法是"放得太宽"——
把校验放宽到不再能抓住真幻觉。所以**只测"不误报"是不够的**，
必须同时测"还能抓住幻觉"。修复误报不能以牺牲检出为代价。

运行：

```bash
python scripts/regress_symbol_false_positive.py
```

## 同类问题清单

凡是"自动判断对错"的工具都有这个风险：

| 变体 | 表现 |
| --- | --- |
| Lint 规则误报 | 团队把它加进 CI 的 `allow_failure`，等于没有 |
| 类型检查误报 | 到处加 `# type: ignore`，真错误也被忽略 |
| 测试不稳定 | 重跑一次就好了，于是没人看红色 |
| 安全扫描误报 | 告警疲劳，真漏洞被淹没 |
| LLM-as-judge 误判 | 分数不可信，于是没人用它做决策 |

**一条通用做法**：在做任何"自动判断"的工具时，
**先量它的误报率**，而且要有回归用例锁住已知的误报。

判断一个校验工具能不能用，问两个问题：

1. 它对**已知正确**的样本误报吗？（本项目这一篇）
2. 它对**已知错误**的样本漏报吗？（不能为了修 1 而牺牲 2）

## 课后习题

**A1（复现）** 跑 `python scripts/regress_symbol_false_positive.py`。
它打印的 7 条用例里，哪一条对应本篇事故？

- 验收：能说出当时误报的具体符号名，以及它在文档页里叫什么

**B1（诊断）** 你的同事写了一个"检查 SQL 语句里表名是否存在"的校验器，
上线后误报很多。列出这个校验器可能有的**三类**假阳性来源。

- 验收：每一类都要能说出"为什么会误报"和"怎么加回归用例"
- 提示：想一下"表名的写法"和"元数据来源"分别可能有什么问题

**C1（改造）** 给 `check_roster_covers_corpus` 增加一个检查：
把 `import maix.xxx` 形式（不带 `from`）也纳入扫描。跑一遍看有没有新缺口。

- 验收：能说出为什么 `from maix import X` 和 `import maix.X` 需要分开处理
- 相关：`maixrag/agent/tools.py` 里 `maix_aliases` 的四种导入形式

**C2（改造）** 现在 `_symbol_is_valid` 允许"前缀命中 + 后缀是常量形式"（枚举成员）。
构造一个**能骗过它**的幻觉符号，说明为什么这个规则是有必要的取舍。

- 验收：能说清"放行枚举成员"与"拦截编造方法"之间的张力
- 提示：看看 `_CONST_MEMBER` 的定义

**D1（判断）** 本篇说"假阳性比漏报更危险"。这个结论在什么情况下**不成立**？

- 验收：至少要给出一种"宁可误报也不能漏报"的场景，并说明判据
- 提示：想一想安全领域、医疗领域与开发工具领域的差别

**D2（判断）** 如果你只能给这个校验器加**一个**指标来证明它可用，
你加什么？（提示：不是准确率，因为本项目的事故说明"准确率"会掩盖问题）

- 验收：指标能区分"误报"与"漏报"，并且能随语料版本变化而被重新测量
