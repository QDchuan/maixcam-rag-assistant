# 证据层

> 这一层回答的是：**这个数字是怎么来的，我能自己验一遍吗。**

这是文档六层里最小的一层，但它撑着前面所有层的可信度。

---

## 为什么需要一层专门放"证据"

教学文档最常见的一种失效不是写错，是**写着写着和代码对不上了**。

而这种失效**完全无声**：读者看到"88 次工具调用 / 4.9 次每题"，
没法判断这是上周实测的、还是半年前的、还是当初就估的。
**一个无法被验证的数字，和一个编造的数字，在读者眼里没有区别。**

所以本项目的做法是把每条论断都变成一件**能跑的事**：

> **文档里的每一个数字，都能被一条命令复现。**

---

## 这里有什么

| 文件 | 内容 | 谁来校验 |
| --- | --- | --- |
| [`incidents.tsv`](./incidents.tsv) | 七次事故 → 各自的回归测试绑定 | [`scripts/check_evidence.py`](../../scripts/check_evidence.py) |
| `claims.tsv` | 论断 → 复现命令 → 期望形态 → 最后验证 | 待建（D5） |
| `ablation.md` | 消融结果的完整表格与原始产物 | 待建（D5） |

> 上面两个待建的文件**刻意不写成链接**。
> 指向一个不存在文件的链接，正是这一层要消灭的那种腐坏——
> 检查脚本 [`check_docs.py`](../../scripts/check_docs.py) 也会把它报成断链。
> 想建它们的时候再补链接。

### `incidents.tsv` 的列

```
id  类别  症状  回归测试  关键断言  复现命令  最后验证
```

`回归测试` 一列是 `路径::符号` 的形式，多个用逗号分隔：

```
tests/test_symbol_verification.py::test_bare_code_is_actually_parsed,
scripts/regress_check_api_usage.py::
```

符号为空表示"整个脚本就是回归测试"（脚本以退出码表达通过与否）。

## 为什么这张表需要工具校验

[事故档案](../postmortem/README.md) 里写了一句很强的话：

> **没有回归测试的事故文档，说明修复没有固化——那是文档在说谎。**

如果这句话只是写在文档里、没人检查，**它自己就成了一个反例。**
所以这里把它变成一条命令：

```bash
python scripts/check_evidence.py
```

它检查三件事：

1. 每条事故文档都在表里有对应行，反之亦然；
2. 表里引用的**测试文件存在**，且引用的**测试函数真的在那个文件里**；
3. 复现命令里提到的路径都存在。

**这三种腐坏都不会让任何东西报错。** 重命名一个测试函数、删掉一个脚本、
新增一条事故忘了进表——全部无声。而这张表的作用恰恰是"让人能去验证"，
**一个指向不存在文件的验证入口，比没有入口更糟。**

---

## 三条维护纪律

1. **数字变了就改文档，或者改数字的出处。** 不允许"文档里是旧的，代码里是新的"。
2. **不确定的数要标出来。** 本项目用三种标记：
   - `[本项目实测]` —— 有产物文件、能被复现命令重跑
   - `[厂商自测]` —— 来自官方文档，不是我们测的
   - `[推测]` —— 没有证据，明确承认
3. **产物文件只留一个可读入口。** 同一份结果同时有 `.json` 和 `.md` 时，
   两者迟早会不一致，而那时没人知道该信哪个。
   （本项目真出现过：一份 `--fake-chat` 复跑覆盖了 `.json`，
   与 `.md` 里的实测数字矛盾。处理方式是**删掉那份 `.json`**，
   而不是"以后再对齐"。）
