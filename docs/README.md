## 三条分支：目标不同，工程选择就不同

这个项目不是"同一个东西的三种写法"，而是**三个不同的目标**——
工程选择由目标推导，不由口味决定。

| 分支 | 目标 | 工程上的必然选择 | 状态 |
| --- | --- | --- | --- |
| **主分支** | **教学** | **从零构建**——过程本身就是目的 | ✅ 已完成 |
| **Harness 分支** | **应用价值** | **用成熟基座（DeepSeek Harness）** | ⏳ 待做 |
| **Skill 分支** | **普及** | **最轻形态**，任何桌面 Agent 装上即用 | ⏳ 待做 |

**写错的方式恰恰是**用一种分支的标准去评判另一种——说主分支"工程不成熟"、
说 Skill"功能太弱"，都是没看懂它们各自的目标。

## 这个项目最特别的一点

**它记录了自己犯过的错。**

大多数教学项目展示的是打磨过的正确路径。但 RAG 与 agent 工程里最难的部分，
恰恰是**东西安静地坏掉**的时候——没有报错、没有异常、指标看起来还行。

六次真实事故，每一次都有完整的症状 → 根因 → 修复 → 回归测试：

| 事故 | 教的是哪一类判断 |
| --- | --- |
| [静默的空结果](./postmortem/01-静默的空结果.md) | 安静的成功是假象 |
| [有文档却召不回](./postmortem/02-有文档却召不回.md) | 文档存在 ≠ 能被召回 |
| [校验器把正确代码判成幻觉](./postmortem/03-校验器把正确代码判成幻觉.md) | **假阳性比漏报更危险** |
| [被清空的统计](./postmortem/04-被清空的统计.md) | 状态生命周期 |
| [伪装成好消息的 0](./postmortem/05-伪装成好消息的0.md) | 指标会伪装成好消息 |
| [预算与任务不匹配](./postmortem/06-预算与任务不匹配.md) | 参数要匹配任务 |

**六条覆盖六种类别的判断力**，比任何"最佳实践清单"都有用——因为它们是真实发生的，
而且**每一条都能被复现**。

## 三个可以立刻跑的演示

不用配任何东西，`git clone` 之后就能跑：

```bash
python scripts/demo_planes.py     # 架构错：把服务放错平面
python scripts/demo_budget.py     # 工程错：不设预算的 agent 会跑飞
python scripts/demo_sandbox.py    # 安全错：权限越界，"拦住了≠拦对了"
```

它们对应的正是教学设计里的三个**故意写错**，分别埋在三类不同性质的错误上。

## 文档的维护纪律

文档最常见的死法不是写错，是**写着写着和代码对不上了**。

**本项目用一个原则对抗它**：

> **文档里的每一个数字，都能被一条命令复现。**

具体机制（见 [文档体系设计](./design/07-文档体系设计.md)）：
- 论断表 `evidence/claims.tsv` 记录"断言 → 复现命令 → 期望形态 → 最后验证"
- 每篇事故都绑定一个**真实存在的回归测试**
- **没有回归测试的事故文档，说明修复没有固化——那是文档在说谎**

## 课后习题

每一章都有习题，分四组：**复现 / 诊断 / 改造 / 判断**。

参考答案在 [`docs/exercises/answers.md`](./exercises/)（待写）。

**C 组（改造）是核心**：它逼你先写下预测，再验证。
"预测错了"恰恰是最有价值的学习时刻——而绝大多数教学文档不给你犯错的机会。

**D 组（判断）刻意没有标准答案**，只给判断依据。验收标准是
"你的答案里有没有代价分析和失效条件"——
**没有代价分析的方案描述，一律不算合格。**
