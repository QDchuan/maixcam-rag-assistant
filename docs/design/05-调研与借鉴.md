# 调研与借鉴

> 文档版本：v0.1（设计稿）
> 关联文档：[00 项目定位与教学大纲](./00-项目定位与教学大纲.md) · [01 系统架构设计](./01-系统架构设计.md) · [02 Skill 精简分支设计](./02-skill精简分支设计.md) · [03 评测与质量提升路线](./03-评测与质量提升路线.md)

本文档记录设计阶段的外部调研，以及**每条调研结论如何改变了设计**。它的存在有两个目的：

1. **可追溯**：读者能看到某个设计决定背后的依据，而不是"作者说的"。
2. **示范引用纪律**：本项目要求一切效果数字标注来源性质。这里就按这个标准做。

---

## 0. 证据分级（本项目对引用的一贯要求）

| 级别 | 含义 | 本项目如何处理 |
| --- | --- | --- |
| **一手实测** | 本项目自己在 MaixPy 语料上跑出来的数字 | 唯一可以作为结论的数字 |
| **独立研究** | 同行评议论文或有明确方法披露的公开研究 | 作为"值得一试的线索"，并标注适用域 |
| **厂商自测** | 厂商在自己数据集上的自测，无独立复现 | **必须标注 `[厂商自测]`，不得当作事实陈述** |
| **未核实** | 无法追溯来源 | 不引用 |

**为什么要这么严格：** 本项目的教学目标是培养判断力。如果自己的文档里到处是把厂商营销数字当事实用，那就自相矛盾了。

### 一个具体例子

某厂商工程博客给出过一组很有名的数字：加了上下文增强后，检索失败率分别降低 **35% / 49% / 67%**（三档分别对应上下文嵌入、加上下文 BM25、再加重排序）。同一篇文章还给出索引成本约 **$1.02 / 百万文档 token**。

这两个数字的实际情况是：**均来自该厂商在自有数据集上的自测，未找到独立复现。**

因此本项目的处理是：
- 可以引用，但必须标注为 `[厂商自测]`；
- **不作为技术选型的依据**；
- 恰恰相反——**鼓励读者在自己的语料上把这三个数字重测一遍**。这正是本项目把消融实验做成交付物的理由。

## 1. 改变设计的调研结论

按对设计的影响排序。

### 1.1 【影响最大】小语料可能不该用 RAG —— 以及实测后的修正

**结论**：一篇厂商工程博客提出，当知识库小于约 **20 万 token**（大致 500 页）时，可以直接把整个语料放进 prompt 并配合 prompt caching，跳过检索环节。

**性质**：`[厂商自测]` + 工程经验，非独立研究。

**为什么它重要**：这个量级与 MaixPy 文档处于同一数量级，所以"该不该检索"变成一个必须实测的问题。

**实测结果（本项目自己做的一手测量）**：

| 项 | 结果 | 性质 |
| --- | --- | --- |
| 中文教程字节数 | 713,520 字节（130 篇） | ✅ 实测 |
| 中文教程 token 估算 | 约 **20–22 万** | 估算（算式见 [00 文档 5.4](./00-项目定位与教学大纲.md)） |
| 加 API 参考 | 约 **26–33 万** | 估算 |
| 单模块（如 `peripheral`） | 约 **2 万** | 估算 |

**结论：整份中文教程已越过 20 万 token 阈值，但单模块远在阈值之内。**

**对设计的改变**：
- 新增 **L-1 全文上下文阶梯**，且必须拆成 **三档覆盖面**（单模块 / 全中文 / 加 API），而不是单一基线——因为答案随覆盖面改变；
- 新增脚本 `scripts/measure_corpus.py`，用于复现字节实测；
- 架构里为全文上下文模式增加 `retrieval.mode: none` 这个**显式开关**，而不是靠"把 top_k 调大"来模拟（见 [01 文档第 5 节](./01-系统架构设计.md)）。

**一次值得记录的估算纠错**：设计初稿凭直觉估计中文语料约 12–13 万 token，据此判定"全文上下文可行"；把算式摊开后发现该直觉把中文占比低估一半以上，真实量级在 **20 万以上**，**结论从"可行"翻转为"越线"**。这个纠错过程本身已写进教学正文——它是"估算必须标注、实测不可替代"最好的实例，也说明**为什么一个项目的第一批交付物应该是量尺**。

**待完成**：精确 token 数仍需用真实分词器确认（不同模型分词器不同）。

### 1.2 评测器应是课程主线，而非附录

**结论**：最小可信的评测体系应当包含——人工标注 gold chunk 的问答对（数十到上百条）、纯程序实现的 IR 指标（hit-rate / recall@k / MRR / nDCG，无模型参与、无 judge 偏差）、**一个** LLM-judge 的忠实度指标、**一个**确定性的代码正确性指标（AST + 符号存在性对照，不用 judge）。

**性质**：与主流评测框架（Ragas 等）的指标定义一致，属独立研究/公开工程实践。

**对设计的改变**：
- 强化了 [03 文档](./03-评测与质量提升路线.md) 已有的"两条轴分离"设计；
- 确认了"**能程序判的指标绝不交给模型判**"这一原则（03 文档第 4.2 节）；
- 确认了评测器必须**早于检索优化**交付（[04 文档](./04-教学交付物与里程碑.md) 的 M1）。

**注**：本项目在具体指标名与评测集规模上做了自己的取舍，见 03 文档。

### 1.3 稀疏检索对本场景不可替代

**结论**：厂商博客给出的典型例子恰好就是一个**标识符查询**——嵌入检索会返回泛泛的内容，而漏掉那个字面字符串。这与 MaixPy 的 `maix.image` / `find_blobs` / `nn.YOLOv5` 完全同构。

独立依据：BEIR 基准确立了 BM25 是一个很强的零样本基线，稠密模型在域外场景下常常打不过它。

**性质**：例子为 `[厂商自测]`；**BEIR 为独立同行评议研究**。

**对设计的改变**：
- 确认混合检索（BM25 + 稠密 + 融合）为默认方向（[01 文档 4.4 节](./01-系统架构设计.md)）；
- 强化了中文分词与英文标识符必须分开处理的方案（01 文档 4.3 节）——这是本场景最容易被通用方案坑掉的细节；
- 在评测里**必须按 qtype 分组**，才能看出稀疏检索的收益集中在标识符类问题上（[03 文档第 6.1 节](./03-评测与质量提升路线.md)）。

### 1.4 GraphRAG 不适用，而且"说它不适用"是更好的教学

**结论**：GraphRAG 原论文**自己**把适用范围限定在**全局性归纳与主题总结**（"这批材料的主题是什么"）且语料规模很大（百万 token 量级）的场景，**不是事实型查询**。它的索引成本极高（需要大量 LLM 实体抽取与社区摘要生成）。

**性质**：独立研究（论文自身的适用范围界定）。

**对设计的改变**：列入**非目标**，并在 [03 文档 5.2.1](./03-评测与质量提升路线.md) 专门说明理由。

**教学价值**：这是一个"技术有适用域，不能因为它有名就用"的绝佳案例。引论文自己的界定比我们主观判断更有说服力。

### 1.5 语义切分的增益与成本不相称

**结论**：有研究专门评估语义切分（用嵌入相似度找边界）是否值得其计算成本，结论是**成本与稳定增益不相称**。相对地，面向结构化文档的、按元素类型切分的方法有正面证据。

**性质**：独立研究。

**对设计的改变**：明确**不采用**语义切分，但在 [01 文档 4.2.2.1](./01-系统架构设计.md) 说明理由，并保留为对照项。

**教学价值**：技术文档的语义边界作者已用标题标出。这个判断本身就是一个可迁移的工程直觉。

### 1.6 防代码幻觉：分级校验

**结论**：代码幻觉有公开的命名分类法（映射 / 命名 / 资源 / 逻辑四类，通过执行来检测）。其中**命名与映射类**正是"编造 API"这一失败类型。由于 MaixPy 无法在笔记本上执行，可行的做法是分级：AST + 符号存在性检查（总能跑、确定性强、覆盖主要失败类型）→ 签名/参数校验 → 真实执行（真机或 mock shim）。

**性质**：独立研究（代码幻觉分类法）+ 本项目的工程推导。

**对设计的改变**：把原本的两级检查重构成**三级校验阶梯**，并明确各级的失败处理与投入产出比（[01 文档 4.5.3](./01-系统架构设计.md)）。

**保留判断**：本项目**不强制**引入该分类法的术语——对本项目而言，级别划分比分类学更重要。术语作为可选教学点给出。

### 1.7 Agent 循环要简单，而且要放在最后

**结论**：官方工程指南区分了**工作流**（提示链、路由、并行、编排者-工人、评估者-优化器）与**真正的 Agent 循环**（带环境反馈），并一贯建议优先选择简单方案。工具应当是**少数几个、粒度合适**的，而不是一堆薄的 API 包装。

**重要缺口**：**没有找到干净的独立证据表明，在小而结构良好的技术语料上，Agent 循环能胜过单次"检索-生成"。**

**性质**：官方工程指南属厂商观点，但其"优先简单"的原则与独立研究一致；后一条缺口是调研明确报告的**证据缺失**。

**对设计的改变**：
- Agent 默认**关闭**；
- 工具集按"确定性优先"设计，`lookup_api`（精确查表）被明确为最便宜可靠的工具（[01 文档 4.6.2](./01-系统架构设计.md)）；
- **把"Agent 是否更好"本身当作待评测的假设**，而不是既定结论。评测必须给出**分场景**的成对胜负（[03 文档第 9 节](./03-评测与质量提升路线.md)）。
- [00 文档第 8 节](./00-项目定位与教学大纲.md) 的非目标里明确写了"不承诺 Agent 一定更好"。

### 1.8 Self-RAG 需要训练，不是提示词技巧

**结论**：Self-RAG 要求**训练**模型输出反思标记，**不是**纯提示词可实现的方案。

**性质**：独立研究（论文方法）。

**对设计的改变**：列入非目标，并在 [03 文档 5.2.1](./03-评测与质量提升路线.md) 明确澄清这一常见误解。

### 1.9 查询改写技术都当作假设处理

**结论**：HyDE 报告的效果是相对**无监督**稠密检索器的提升，未必能推广到现代嵌入模型，也未必胜过稀疏检索在标识符查询上的表现；且每次查询多一次 LLM 调用。多查询/分解与元数据过滤是广泛记录的做法，但**没有**在 API 文档语料上做过隔离评估的强基准。

**性质**：独立研究，但**适用域不匹配**。

**对设计的改变**：L5 的定位改为**A/B 假设**而非"已知有效手段"（[03 文档 5.2.1](./03-评测与质量提升路线.md)）。

### 1.10 LLM-as-judge 的已知偏差

**结论**：强 judge 与人类的一致率可超过 80%（接近人类间一致水平），但论文明确记录了**位置偏差、长度偏差、自我增强偏差**与推理能力有限。实践规则：交换候选顺序、控制长度、避免生成者与 judge 同源而不加标注、先用约 30 条人工标注校准 judge。**代码正确性优先用 AST/执行，而不是 judge。**

**性质**：独立研究（同行评议）。

**对设计的改变**：确认并细化了 [03 文档第 7 节](./03-评测与质量提升路线.md) 的 judge 使用纪律（离散锚点、原子论断拆解、人工校准 10–20%、judge 版本固定）。

## 2. 竞品与生态位

调研了两个最常被引用的 RAG 教学项目：

| 项目 | 它有什么 | 它缺什么 |
| --- | --- | --- |
| [`langchain-ai/rag-from-scratch`](https://github.com/langchain-ai/rag-from-scratch) | 成体系的视频讲解 | 本质是播放列表的 README；**无评测、无 Agent 循环、无语料工程结构** |
| [`NirDiamant/RAG_Techniques`](https://github.com/NirDiamant/RAG_Techniques) | 42+ 个技术 notebook，**含评测**（RAGAS / DeepEval 等），含 self-RAG / CRAG / GraphRAG / agentic RAG | 无统一应用、无语料工程、无回归门禁 |

**⚠️ 许可约束（重要）**：`NirDiamant/RAG_Techniques` 使用**自定义非商业许可**。本项目**不得复制其代码**。可以引用其思路与链接，但实现必须自行完成。这条约束对开源教学项目是硬性的，记录在此以免后续误用。

**空缺**：没有找到同时具备以下四点的项目——**真实非玩具语料 + 语料工程作为一等公民（带出处与版本）+ 评测作为课程主线 + Agent 靠执行验证代码**。

本项目定位即填补这个空缺。

## 4. 调研的局限（必须声明）

诚实记录证据的边界，与引用纪律同等重要：

1. **没有找到任何在 MaixPy 类语料（边缘 AI 摄像头的 Python API 文档）上的已发表基准。** 因此所有"X 优于 Y"的说法都是**来自其他领域的先验**，不是本语料上的实测结果。**这恰恰是本项目把评测器做成交付物的根本理由。**
2. 某厂商的上下文检索数字与成本数字均为**自有数据集自测，未找到独立复现**。
3. 评测框架文档站多为 JS 渲染，指标**名称与定义**已核实，但个别实现细节未逐条验证。
4. Agent Skills 的格式契约（字段约束、目录约定、渐进式披露三阶段）**已对照规范与官方仓库一手来源核实**；但各客户端对标准的**实际兼容程度未逐个实测**。
5. 本文档中关于 MaixPy 语料的一切事实（页数、结构、版本、API 生成方式、站点与仓库差异）均通过 GitHub API 与文档站**直接核实**，不是估计。
6. 部分检索结果返回了 2026 年日期的材料。已确认当前系统日期为 2026-09-12，故此类日期并非异常；但本文档只采信**能追溯到一手来源**的内容。

## 5. 一句话总结

> 本项目可辩护的主张不是"我们用了混合检索 + 重排序 + GraphRAG"，
> 而是"**我们在一个真实的小型技术语料上测出了哪些技术活了下来，并把表放在这里**"。
>
> **先建量尺，最后才加 Agent。**
