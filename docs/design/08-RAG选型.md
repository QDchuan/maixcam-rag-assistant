# 08 · RAG 选型：把「不自研」这个决定真正做掉

## 0. 这份文档为什么存在

[`06`](./06-项目结构与两条分支.md) §3.3.1 已经写下了决定：

> **决定**：Harness 分支的 RAG **不使用本项目自研的 `maixrag`**，而是从开源平台挑选一个
> 工程上更成熟、效果更好的方案，与 DSH 整合。

下面还写着一句：**「这个选型留到主线告一段落之后再做」**。

实现 Harness 分支时，我做到了前半句（确实没用 `maixrag`），**却没有做这个选型** ——
改为自己手写了一条稠密检索（嵌入 + 余弦 top-k）。更糟的是 §3.6.1 里我给这次偏差
补了个技术理由（「稀疏那一路需要复刻 jieba 分词器」），把它记成了一次**务实的技术取舍**。

**那不是技术取舍，那是没做该做的决定。** 这份文档把那个决定补上。

## 1. 手写那条的实际能力边界（实测，不是推测）

拿真实语料量出来的：

| 查询 | 结果 |
| --- | --- |
| 整题：「设计一个人脸跟随系统」 | 6 条命中、5 个文档，**全部来自 `projects` / `vision`** |
| 子系统：「舵机 PWM 控制 占空比」 | 命中 `PWM`、`人脸追踪2轴云台`，**与整题查询重合 0 条** |
| 子系统：「串口通信 收发数据 uart」 | 命中 `UART 串口`、`maix.peripheral.uart` 等 4 个文档，**重合 0 条** |
| 子系统：「人脸检测 关键点」 | 命中 4 个文档，**重合 0 条** |

手写链路的全部能力是：**一句查询 → 一个向量 → 余弦 top-k**。

它没有：查询分解、多路召回、稀疏、融合、重排、多样性、覆盖度。

于是「怎么设计 X」这类题必然收敛到**那唯一一个看起来像整题的示例项目页**，
而真正的工程部件（PWM、UART、供电、机械）分散在完全不同的文档里，那条查询**一条都碰不到**。

用户的原话是准确的：「他全都是找二维云台的资料，但他却没有想到造舵机、通信这些东西。」

## 2. 需求：原有 5 条 + 实测新增 2 条

§3.3.1 原有（按重要性排序）：

1. 中文检索质量，尤其是**中英混合标识符**场景
2. **可替换性** —— 能否只换嵌入/重排而保留索引，能否自定义分块
3. 混合检索（稀疏 + 稠密 + 融合）与重排序是否内置或易接
4. 与 Node 侧的集成成本（原生 JS 优先，或提供稳定 HTTP 接口）
5. 许可证必须允许本项目使用

§1 的实测暴露了两条原需求没覆盖的：

6. **子问题分解** —— 能把「怎么设计 X」拆成若干面向，各自检索（这是 §1 里 0 重合的直接对症）
7. **覆盖度可回执** —— 检索结果要能回答「这个面向本地有没有证据」，让缺口**显形**

第 7 条是本项目一贯的手法：`check_api_usage` 让编造的符号显形，这一条让**漏掉的子系统**显形。
**能被看见的缺口才是缺口；静默的缺口是事故。**

## 3. 约束（不能违反前文的决定）

- §3.3.2：**单进程**。运行期不加第二个进程、不加端口、不加健康检查。
- 语料产物（`chunks.jsonl` / `api_symbols.jsonl` / `api_roster.txt`）**与检索实现无关**，
  必须能继续被复用 —— 这是当初设计对的地方，不能因为换实现就丢掉。

## 4. 候选与结论

| 候选 | 形态 | 混合 | 重排 | 子问题分解 | 单进程 Node | 许可 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| RAGFlow / Dify / FastGPT | 完整应用 | ✅ | ✅ | 部分 | ❌ 自带服务与存储 | 各异 | ✗ 我们已经有自己的壳，再套一层 UI |
| AnythingLLM | 完整应用（Node/Electron） | ✅ | ✅ | ✗ | ❌ 是产品不是库 | MIT | ✗ 同上 |
| Haystack / txtai | Python 框架 | ✅ | ✅ | 部分 | ❌ 要 HTTP sidecar | 宽松 | ✗ 违反 §3.3.2（sidecar 已被否决） |
| Qdrant / Chroma / LanceDB | 向量库 | — | — | ✗ | ✅ | 宽松 | ✗ 只是存储，不解决 §1 的病 |
| LightRAG / GraphRAG | 图式 | ✅ | 部分 | ✅ | 部分 | MIT | ✗ 索引期 LLM 成本高；语料是文档集不是实体图 |
| **LlamaIndex.TS**（`llamaindex`） | **TypeScript 框架** | ⚠️ 核心无稀疏 | ✅ | ✅ | ✅ | **MIT** | **候选（待补两条核验）** |

核对过的事实：`llamaindex` 当前版本 **v0.12.1**、许可 **MIT**；
配套适配器 `@llamaindex/openai`、`@llamaindex/ollama` 均在 npm 上可用（社区包 `@llamaindex/community` 已探明**不含** BM25/融合）。
**注意**：第一版这张表里「混合 ✅」是凭印象填的，见 §5 的核验表。

## 5. 结论：**候选收敛到 LlamaIndex.TS，但尚未定案**

> ⚠️ **本节经过一次核验，第一版的论据有一处是错的。**
>
> 第一版我写的是「LlamaIndex.TS 提供 `BM25Retriever`（稀疏）+ `QueryFusionRetriever`（融合）」——
> **那是凭印象写的，实际装包探过之后不成立。** 真实情况（`Object.keys()` 逐个核对，不是文档、不是记忆）：
>
> | 导出 | `llamaindex` v0.12.1 | `@llamaindex/community` v0.0.105 |
> | --- | --- | --- |
> | `BM25Retriever` | ❌ 没有 | ❌ 没有（该包总共只导出 6 个东西） |
> | `QueryFusionRetriever` | ❌ 没有 | ❌ 没有 |
> | `SubQuestionQueryEngine` | ✅ 有 | — |
> | `BaseRetriever` / `VectorStoreIndex` / `TextNode` | ✅ 有 | — |
> | `RetrieverQueryEngine` / `SimilarityPostprocessor` / `JinaAIReranker` | ✅ 有 | — |
>
> 也就是说：**核心给的是「向量检索 + 子问题分解 + 重排」，稀疏（BM25）与多路融合不在核心包里。**
>
> 这件事本身就是这个项目一直在讲的那个教训的又一次实例：
> **凭印象写下的技术论据，和被模型编造的 API 名字，是同一种病。**
> 我在一份专门用来纠正「凭印象做决定」的文档里，又一次凭印象写下了关键论据。

按目前已核验的事实，逐条重列：

| 需求 | 现状 |
| --- | --- |
| 1 中文 / 中英混合 | 由**我们自己的模型**（bge-m3 / bge-reranker-v2-m3）决定，框架不干预 —— ✅ 不受影响 |
| 2 可替换性 | 框架本身是抽象层 —— ✅ |
| 3 混合检索（稀疏 + 稠密 + 融合） | ⚠️ **核心只给稠密**。稀疏要么另配一个 BM25 实现，要么留在 Python 侧；融合要从 `BaseRetriever` 自己组 |
| 4 Node 集成 | ✅ TypeScript 原生，跑在同一个 Node 进程里，不新增进程 |
| 5 许可 | ✅ MIT（`llamaindex` v0.12.1） |
| 6 子问题分解 | ✅ `SubQuestionQueryEngine`（需要接一个 LLM —— 我们进程里就有） |
| 7 覆盖度回执 | ⚠️ 框架不给，要在它的多路结果之上自己汇总（这部分本来就该我们自己写） |

**因此第 5 节现在的状态是「候选」而不是「决定」**：

- 它满足第 4、5、6 条，这三条里第 6 条（子问题分解）正是 §1 实测那个 0 重合的直接对症；
- 它**不满足**第 3 条里的稀疏部分，需要额外补一个 BM25；
- 第 7 条无论如何都要我们自己写。

**下一步先补两条核验，再定案**：

1. 找一个能在 Node 侧用、许可合适的 BM25 实现（或确认稀疏继续留在 Python 侧的代价）；
2. 用真实语料跑一次对照：稠密-only vs 稠密+子问题分解，看**子系统查询与整题查询的重合度**是否从 0 抬起来 —— 那才是这个选型是否成立的判据，而不是候选表好不好看。


## 6. 接入形态

- 检索层跑在 **DSH 的 Node 进程里**，不新增进程（守住 §3.3.2）。
- 嵌入继续用**本机 Ollama + bge-m3**；重排用本机 bge-reranker-v2-m3。
- 索引仍由教学主线的 Python 管线产出；Node 侧只消费 `chunks.jsonl` 等中间产物。
- 对外契约不变：`/api/maixcam/*` 三条路由与三个 agent 工具（`search_docs` /
  `lookup_api` / `check_api_usage`）的名称与语义都不动，只换里面的实现。
  **这正是「语料与检索实现分开」当初的价值。**

## 7. 顺带把 §3.6.1 那个「分词器边界」解决掉

§3.6.1 记的是：`indexes/bm25.json` 是 jieba（`zh_identifier`）分词后的统计量，
要在 Node 里复用就得复刻分词器，所以运行期只走稠密。

**正确的做法不是复刻分词器，也不是放弃稀疏，而是：用框架自带的 BM25（自带分词），
从 `chunks.jsonl` 在 Node 侧重建稀疏索引。**

`indexes/bm25.json` 是**某个实现**的派生物；`chunks.jsonl` 才是与实现无关的中间产物。
当初把这两者分开，要的就是今天能这样换。§3.6.1 把一个**设计该有的自由度**当成了一次**妥协**。

## 8. 它怎么治那两个症状

| 症状（用户实测） | 机制（按已核验的导出） |
| --- | --- |
| 「全都是二维云台的资料」 | `SubQuestionQueryEngine`：把整题拆成「人脸检测 / 舵机控制 / 通信 / 供电 / 机械」逐个检索再汇总，不再由单一向量决定全部召回（**核心有此导出，已验证**） |
| 「他却没有想到造舵机、通信」 | 覆盖度回执：每个面向明确报「命中 N 条 / 本地无证据」，缺口必须写进回答，而不是静默跳过（**框架不给，我们自己写**） |
| 「AI 直接上网查的比 RAG 好」 | 本地语料是**产品文档**，强在「API 怎么用」，弱在「系统怎么搭」。见 §9 |

## 9. 风险与明确不做的事

- **框架与 Node 22 的兼容性**要在接入时实测，不能只在文档里假定。
- **不引入**它自带的 UI、存储层与服务封装 —— 我们只借检索机制。
- **不因为引入框架就放松硬纪律**：API 名字仍然只能来自本地语料并用 `lookup_api` 核对；
  `check_api_usage` 仍然在交付代码前跑。框架解决「召回」，不解决「忠实」。
- **语料缺口不是检索能补的**：这一条单独决策 —— 要么接受「设计类问题靠网络、API 类问题
  靠本地」的分工（网络结论必须标注「未本地核验」），要么真的补一批工程页进语料。
  **换任何框架都变不出语料里没有的工程经验。**

## 10. 实际落地的是哪一套（与上面候选的关系）

选型还在「候选」阶段时，先把**病**治住了。实际跑在应用里的是自建的混合检索，取舍如实写在这里：

| 能力 | 落地情况 | 为什么没等框架 |
| --- | --- | --- |
| 稀疏（BM25） | `lib/bm25.js`，从 `chunks.jsonl` 现建（3838 片 / 30091 词项 / 142 ms） | LlamaIndex v0.12 的核心包与 community 包都**没有** BM25（已探明）；但这不构成放弃稀疏的理由 —— 分词用「ASCII 整词 + 中文二元组」，不需要词典 |
| 融合 | RRF（按名次，因为余弦与 BM25 的分数不可比） | 融合逻辑本身只有二十行 |
| 子问题分解 | `search_docs(aspects)` + **前置闸门**：设计类问题不给 `aspects` 就不给结论 | `SubQuestionQueryEngine` 要接一个 LLM 与 query engine；而**模型自己就能做这个关联** —— 实测它自发打出过「总线舵机 串口舵机 舵机供电 外部电源 电压」 |
| 覆盖度回执 | `moduleCoverage()` + 每个面向报置信度 | 框架不给，本来就要自己写 |
| 相关性下限 | 最高余弦分三档，阈值 **0.60** 取自实测分布 | 同上 |

阈值不是拍出来的，是量出来的：

```
真有证据的面   0.733 ~ 0.807   人脸检测 / 舵机控制 / 串口通信 / 寻找色块
本地没有的面   0.524 ~ 0.561   供电与电流 / 机械结构 / 外壳防水 / 预算成本
```

**引进框架的真正价值在于不再手写。** 而这次的实测结论是：这几块里只有「子问题分解」值得借框架，
而它恰好是**模型自己能做**的那一块。所以当前形态是 ——
**机制自己写、关联交给模型、边界由工具报出来**。
