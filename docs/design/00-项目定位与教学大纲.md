## 1. 一句话定位

**一个以「MaixCAM 开发助手」为真实载体的 RAG 与 Agent 教学项目。读者跟着做完，能回答两个问题：怎么设计一个可靠的 AI 应用，以及怎么根据场景把 RAG 的质量提上去。**

它不是"又一个 RAG demo"。它有两重身份，且这两重身份必须同时成立：

| 身份 | 服务对象 | 成功标准 |
| --- | --- | --- |
| **真实工具** | **想用 MaixCAM 做项目的人** | 问它 MaixPy 的用法，给出的代码能跑，不是似是而非的 API |
| **教学材料** | 想学 RAG / Agent 的人 | 每一步为什么这么做、不这么做会怎样，都有可复现的证据 |

大多数教学项目死在第二重身份上：代码能跑，但读者不知道为什么这么写，换个场景就不会了。本项目的第一原则是——**每个设计决定都必须能挂到一次实验数据上**。

## 2. 项目背景

### 2.1 触发点：2025 年打电赛的一次真实经历

**2025 年**打电赛的时候，MaixCAM 还是很新的硬件——**那个时候模型完全没有它的知识**。

这不是"答得不够好"，而是一种很具体的失败模式：

- 让模型写 MaixPy 代码，它会给你**看起来很像**的 API——参数名对一半、返回值想当然、把 MaixPy 的接口和 OpenCV / 树莓派 / K210 时代的 MaixPy v1 混在一起；
- 代码读起来通顺，粘到 MaixVision 里直接报错，而且报错信息指不到问题根源；
- 模型还会"自信地"告诉你某个函数不存在是拼写问题，其实是它从来没见过这个函数。

这就是 **幻觉（hallucination）**。它的根因不是模型笨，而是**缺失的知识只有官方文档里有，而模型没见过官方文档**。

当时的应对方式是手工的：

```
遇到问题 → 去 wiki.sipeed.com 翻文档 → 自己判断该看哪几页
        → 把内容复制给 AI → AI 给建议 / 写代码
```

**这套手工流程，就是一次人工执行的 RAG。**

**把这个手工流程自动化、工程化，就是做这个项目的初衷。** 而"教学"这一部分是顺着它长出来的：
既然这条链路的每一步都能被测量，那它正好可以用来讲清楚 RAG 与 Agent 该怎么设计、怎么评估
——比另造一个玩具例子有说服力得多。

### 2.2 第二重背景：这是教学项目

文档在本项目里不是附件，是核心资产。这带来几个硬性约束：

- **文档质量 = 产品质量。** 语料的获取、清洗、切分、版本管理，必须作为一等公民讲，不能一句"我们用一个向量库"带过。
- **结论必须可复现。** "混合检索比纯向量好"这种话，本项目里不允许作为结论出现，必须给出对照实验和数字。评测集和评测脚本因此是**第一批交付物**，不是最后补的。
- **失败案例比成功案例值钱。** 教学材料要专门展示"朴素方案是怎么坏掉的"，因为读者在自己的项目里遇到的正是这些坏法。

### 2.3 为什么选 MaixCAM 做载体

| 特征 | 对教学的价值 |
| --- | --- |
| 知识高度集中，只有官方文档一个权威源 | 语料边界清晰，能讲清"语料决定上限" |
| 文档天然分两层：教程页 vs API 参考页 | 能讲清"不同问法需要不同知识层"，这是纯散文语料给不了的 |
| 全中文、Markdown 原文可获取 | 免去 PDF/OCR 的脏活，注意力集中在 RAG 本身 |
| 语料体量适中（实测 316 页 / 1.38 MB） | 单机可跑、评测跑得完、成本可忽略，适合教学 |
| 版本迭代快、API 会变 | 能讲清"语料版本固定"为什么是可靠性问题 |

## 3. 这个项目真正想教的三件事

### 目标一：设计可靠的 AI 应用

"可靠"不是"回答得漂亮"，而是**行为可预期、失败可解释**。具体到本项目，落成四条可检查的契约：

1. **有据可依**：结论必须能追到具体文档片段，并给出可点的出处。
2. **不知道就说不知道**：检索不到时明确拒答，而不是编一个像样的答案。
3. **不存在的 API 不出现**：代码里出现的 MaixPy 符号必须能在语料里找到依据。
4. **质量可回归**：任何改动都要过同一套评测，且能看到分数变化。

第 4 条最重要，也最常被教学项目忽略。**没有回归评测的 AI 应用不叫可靠，只叫"这次碰巧对"。**

### 目标二：根据场景提高 RAG 质量

这是本项目的技术主线。核心方法是**消融实验（ablation）**：从最朴素的 baseline 出发，一次只加一种技术，用同一套评测量化它的增益，并解释它在**什么场景下**有用、**什么场景下**是浪费。

要建立的关键判断力是：

- 检索和生成是**两个独立的失败点**，必须分开测。答得不好，可能是没检索到（召回问题），也可能是检索到了但没用上（生成问题），两者的修法完全相反。
- **没有银弹**。Rerank 对"用词不同、意思相同"的问法有效，对"函数名拼错"几乎无效——后者是稀疏检索的战场。
- **语料结构是被低估的杠杆**。在 MaixPy 这个场景里，把教程和 API 参考混在一个索引里，会同时伤害两类问题。

### 目标三：把 Agent 设计讲成人话

Agent 不需要神秘化。本项目的立场是：**Agent = 在循环里做决定的程序**。它和一条 `retrieve → prompt → generate` 的链式调用的区别只有一个——**决定是写死在代码里，还是由模型在运行时做出**。

这个区别带来的全部后果，项目都会演示一遍：能多轮检索、能自查、能承认失败，但也**更难评测、更慢、更贵、更容易跑飞**。教学上必须把代价一起讲，否则读者学到的是一种危险的乐观。

## 4. 两个交付分支

项目最终产出**两条分支**，覆盖两类不同的读者。

### 分支 A：Agent 版（主线）

读者自己设计并实现整个 AI 应用：语料管线、检索、Agent 循环、工具、评测、服务化。

- **谁用**：想学 RAG + Agent 设计与实现的开发者。
- **得到**：一个可改、可测、可解释的完整系统，以及一套能迁移到别的领域的工程方法。
- **代价**：要写代码、要配模型、要跑评测。

### 分支 B：Skill 版（裁剪）

**核心动机是裁剪。** 很多用户并不想自己设计 Agent 或 AI 应用——他们只想让手边的桌面 Agent 应用（Claude Code、Cursor、以及各种支持 skills 格式的桌面 Agent）**会用 MaixPy 文档**。

于是把分支 A 里真正产生价值的那一小块——**语料 + 检索 + 使用规程**——打包成一个自包含的 Skill，放进任何支持该格式的桌面 Agent 即可生效。

- **谁用**：只想解决问题的 MaixCAM 开发者；以及想学"如何把能力封装成可分发形态"的读者。
- **得到**：一个装上就能用的能力包，不需要写一行编排代码。
- **关键权衡**：**放弃了质量调优的主动权**。Agent 的检索策略由宿主应用决定，你只能通过语料的组织方式和规程文档去"引导"它。这是一个真实且常见的工程约束，项目会把它讲清楚，而不是假装它不存在。

两条分支共用**同一份语料管线**。这不是偷懒——是刻意的教学设计，让读者看到同一份资产如何服务两种截然不同的消费形态。

## 5. 语料底数（勘察结果，已核实）

> 本节数据来自 2026-08 的实际勘察，不是估计值。

### 5.1 数据源

| 来源 | 内容 | 用途 | 版本固定 |
| --- | --- | --- | --- |
| `github.com/sipeed/MaixPy` 的 `docs/doc/zh/` | 中文教程 Markdown 原文 | **主语料**，概念、流程、完整示例 | 固定到 commit |
| `wiki.sipeed.com/maixpy/api/` | API 参考（57 页） | **精确签名语料**，参数名/类型/返回值 | 按构建版本 |

**关键勘察结论：API 参考不在仓库的 Markdown 里。** 它由 `components/maix/gen_api.py` 从 C/C++ 头文件的 docstring 生成，随构建产出。因此：

- 教程语料走仓库 Markdown（干净、可 diff、可离线）；
- API 语料必须单独获取。已核实 release `v4.12.5` 的产物里**没有** `maixpy_*_doc.zip`（只有系统镜像和 whl），所以不能指望离线包，需要从文档站抓取或自行构建；
- 已核实文档站提供 `sitemap.xml`，语料边界可被程序精确枚举，不需要爬虫去猜。

### 5.2 规模（实测）

| 分区 | 页数 | 字节数 | 说明 |
| --- | --- | --- | --- |
| `/maixpy/doc/zh/` | 130 | 713,520 | 中文教程，**教学主语料** |
| `/maixpy/doc/en/` | 129 | 733,937 | 英文教程，与中文大体对应 |
| `/maixpy/api/` | 57 | 未测 | API 参考：31 个顶层模块页 + 子模块页，另含 2 个索引页 |
| **合计** | **316** | — | 不含 API 的字节合计为 1,447,457 |

> **一处已发现的计数差异（教学案例）**：文档站 sitemap 列出 `/doc/en/` 有 **130** 条，而仓库实测只有 **129** 个 `.md`。差异来源是站点上存在 `doc/en/no_translate.html` 这类非文档页面。管线在合并两个来源时**必须显式报告这类不一致**，而不是让两边各自为政——否则"到底有多少篇"这个最基本的问题都答不上来。

### 5.3 两处需要处理的一致性差异

勘察中发现文档站与仓库之间存在漂移，这本身就是很好的教学案例（**语料的真实状态永远是脏的**）：

1. 站点 sitemap 里存在但仓库 `docs/doc/zh/` 没有的页面：`vision/dual_buff.html`、`vision/customize_model_yolov5.html`、`vision/customize_model_yolov8.html`、`modules/acc.html`；
2. 仓库侧边栏列了 `vision/customize_model_yolo.md`，站点上对应的是 `vision/custmize_model.html`（注意拼写）。

**处理原则**：管线必须**显式报告差异**而不是静默丢弃。教学价值在于让读者看到"语料对齐"是一步需要主动做的工程动作。

### 5.4 语料体积实测（决定"要不要检索"的关键数字）

"全文塞进 prompt"是否可行，取决于语料有多大。设计阶段已用 GitHub git-trees API **精确测出**（同一份数据用两种独立方法交叉验证，逐字节一致）：

| 项 | 文件数 | 字节数 | 性质 |
| --- | --- | --- | --- |
| `docs/doc/zh`（中文教程） | **130** | **713,520**（约 697 KB） | ✅ 实测 |
| `docs/doc/en`（英文教程） | **129** | **733,937**（约 717 KB） | ✅ 实测 |
| **合计** | **259** | **1,447,457**（约 1.38 MB） | ✅ 实测 |

单篇最大：`peripheral/uart.md`（中文 29,906 字节 / 英文 32,368 字节）。中文前三为 `uart.md` 29,906、`pro/rvv.md` 24,542、`faq.md` 22,106 字节。

**token 估算**（把算式摊开，便于读者复核）：中文在 UTF-8 下 3 字节/字，中文约 1 token/字；英文与代码约 4 字符/token（即 1 字节 ≈ 0.25 token）。

| 覆盖面 | 估算 token | 是否在 20 万阈值内 |
| --- | --- | --- |
| 中文教程**单独**（713,520 字节，按中文占 40–70% 字节） | 约 **20–22 万** | ❌ **已越线** |
| API 参考单独（55 页，未实测） | 约 **5.5–12.5 万** | ✅ 可行 |
| 中文教程 + API 参考 | 约 **26–33 万** | ❌ 明显超出 |
| 中文 + 英文教程 + API 参考 | 约 **45–52 万** | ❌ 远超 |

> **字节数是实测的，token 是估算的，而且估算的敏感度很高。** 精确 token 数必须在实现阶段用真实分词器数出来——不同模型的分词器不同，会直接影响结论。测量脚本见 `scripts/measure_corpus.py`。

**这个结果把第一课的问题反过来了。** 我原本以为"小语料可以直接全塞"，实测发现**不是**：

- **整份中文教程就已经越线**（约 20 万 token 起），全文上下文不可行；
- 但**单个模块是可行的**——比如只把 `peripheral` 相关页面（10 篇、72 KB、约 2 万 token）塞进去，绰绰有余；
- 因此"该不该检索"的答案不是"该"或"不该"，而是**取决于你把多大范围装进去**。

**于是 L-1 这一课的正确形态是分层对比，而不是单一基线：**

| 变体 | 覆盖面 | 预期 |
| --- | --- | --- |
| L-1a | 单模块全文（如 `peripheral`，约 2 万 token） | 可行，且**零检索损失**，很可能优于检索 |
| L-1b | 全中文教程（约 20 万+ token） | 越线，成本高、可能触发截断 |
| L-1c | 中文教程 + API 参考（约 30 万 token） | 不可行 |

这个分层比"要不要上 RAG"这个二元问题有价值得多：**它教的是"如何找到最适合自己语料规模与成本预算的那个点"**。

> **诚实记录一次估算纠错**：设计过程中我先用"中文技术文档多半是代码和英文"的直觉估出 12–13 万 token，随后把算式摊开核算，发现该直觉把中文占比低估了一半以上，正确量级是 **20 万以上**——**结论从"可行"翻转为"越线"**。这正是本项目坚持"估算必须标注、实测不可替代"的原因，也是很好的一课：**在语料规模这类问题上一句话的直觉，偏差可以是两倍。**

## 6. 核心教学主线：一个场景驱动的能力阶梯

这是本项目的骨架。每一级只加**一个**变量，并给出该级的评测数字与失败案例。

| 级别 | 名称 | 新增内容 | 读者要学到 |
| --- | --- | --- | --- |
| **L-1** | 全文上下文阶梯 | 不检索，语料直接进 prompt + 缓存；分单模块 / 全中文 / 全量三档 | **"该不该上 RAG"取决于覆盖面，边界要测出来**（见 6.1） |
| **L0** | 无 RAG 基线 | 直接问模型 | 幻觉长什么样，建立"差"的参照 |
| **L1** | 朴素 RAG | 定长切分 + 单一向量检索 + 拼接生成 | 为什么它能改善，又为什么不够 |
| **L2** | 结构化语料 | 标题感知切分、按知识层打元数据、版本固定 | **语料工程是被低估的杠杆** |
| **L3** | 混合检索 | BM25 + 向量，融合排序 | 标识符/函数名场景为什么必须上稀疏检索 |
| **L4** | 结构感知检索 | 按问题类型路由到不同知识层，父文档回填 | 不同问法需要不同粒度 |
| **L5** | 查询改写 | 多查询、HyDE、指代消解 | 问法 ≠ 检索式，尤其多轮对话 |
| **L6** | 重排序 | 召回后精排 | 增益有多大、延迟代价是否值得 |
| **L7** | 上下文增强 | 给每个 chunk 补语境头 | 小语料上性价比极高的一招 |
| **L8** | 忠实生成 | 引用约束、拒答、符号白名单校验 | 把"有据可依"变成可强制执行的机制 |
| **L9** | Agent 化 | 多轮检索、按需调用、自查、执行反馈 | 什么时候值得上 Agent，代价是什么 |

**设计的两个要点：**

- **L-1 到 L8 是消融实验的阶梯**，可以逐级分离每种技术的贡献，生成一张"技术 → 增益"的对照表。这是全项目最有教学价值的产出物。
- **L9 不是更高一级，而是另一个维度**。它是把前九级的能力装进一个能自己做决定的循环里。教学上必须明确：Agent 化不必然更好，它换来的是灵活性，付出的是可控性。

### 6.1 为什么第一课是"该不该用 RAG"

业界有一条被广泛引用、但值得警惕的经验判断：**当知识库小于约 20 万 token（大致 500 页）时，可以把整个语料直接放进 prompt 并配合 prompt caching，跳过检索**。这个门槛的说法来自 Anthropic 自己的工程博客（见 [05 附录](./05-调研与借鉴.md)），是**厂商观点**，我们把它当作一个需要验证的假设，而不是结论。

MaixPy 的教程语料正好落在这个量级附近（实测约 20 万 token 起，见 [5.4](#54-语料体积实测决定要不要检索的关键数字)），所以这是一个**必须实测而不是假设**的判断点。于是本项目把"全文上下文"作为 L-1 级，并拆成三个覆盖面变体：

| 变体 | 覆盖面 | 要回答的问题 |
| --- | --- | --- |
| **L-1a** | 单模块全文（如 `peripheral`，约 2 万 token） | 小范围全塞，是否**优于**检索？（预期：是） |
| **L-1b** | 全中文教程（约 20 万+ token） | 越线之后，质量与成本各付出什么？ |
| **L-1c** | 中文教程 + API 参考（约 30 万 token） | 多源合并后是否彻底不可行？ |
| L-1a vs L0 | — | 把文档塞进去，幻觉能降多少？（RAG 相对"什么都没有"的价值上限） |

三档对照之后，读者拿到的不是"该不该用 RAG"的答案，而是**一条曲线**：覆盖面多大时，全文上下文开始不划算。这比二元结论有用得多。

**这一课的教学价值有三层：**

1. **避免默认假设。** 绝大多数 RAG 教学项目开篇就假定必须做 RAG，从不质问这个前提。"不做检索"在小覆盖面下是真实且常常更优的选项——它就是本项目背景故事里"把文档复制给 AI"那个原始动作的系统化版本。
2. **暴露真实的工程取舍。** 全文上下文的优势是**零检索损失**；代价是**每轮都付全量 token、且无法扩展到更大语料**。这个取舍（质量 vs 成本 vs 可扩展性）正是 RAG 存在的理由。
3. **教"边界意识"。** 答案是"看情况"时，教学的正确做法不是含糊过去，而是**把边界测出来**。

**本节已完成的实测纠错值得写进正文**：设计初稿凭直觉估计中文语料约 12–13 万 token、判定"全文上下文可行"；把算式摊开后发现真实量级在 **20 万以上**，结论翻转为"整体越线"。一个直觉判断偏差两倍，而它本会导致整个项目的技术路线判断出错。**这就是"实测不可替代"最好的实例。**

### 两条正交的评测轴（贯穿全项目）

| 轴 | 测什么 | 对应的失败 |
| --- | --- | --- |
| **检索轴** | 该出现的文档片段，有没有出现在 Top-K 里 | 召回失败 |
| **生成轴** | 给定了正确片段，答案是否忠实、是否可追溯 | 生成失败 |

**这是本项目要求学生建立的最重要的一个思维习惯**：分数掉了，先分清是哪条轴掉了。绝大多数 RAG 调优之所以低效，就是因为把这两个问题当成一个问题在修。

评测指标的具体选型、评测集怎么建、LLM-as-judge 的坑在哪，见 [03 评测与质量提升路线](./03-评测与质量提升路线.md)。

## 8. 明确的非目标

写清楚不做什么，和写清楚做什么一样重要：

- **不做微调。** 本项目聚焦检索增强，不涉及训练。理由：这是读者更常遇到的场景，且成本可控。
- **不做多模态。** MaixPy 文档里有大量图片，但本项目不处理图像检索。图片仅在语料清洗阶段处理。
- **不追求 SOTA。** 目标是"每一步都有依据"，不是刷榜。
- **不绑定特定厂商。** 走 OpenAI 兼容接口，读者可自由切换模型提供方。
- **不承诺 Agent 一定更好。** 相反，项目会明确给出"不该用 Agent"的场景。

## 9. 与同类教学项目的差异点

调研了两个最常被引用的 RAG 教学项目（详见 [05 附录](./05-调研与借鉴.md)），差异如下：

| 维度 | `langchain-ai/rag-from-scratch` | `NirDiamant/RAG_Techniques` | 本项目 |
| --- | --- | --- | --- |
| 形态 | 视频播放列表的 README | 42+ 个独立 notebook | **一个真实应用** |
| 语料 | 演示用小样本 | notebook 各自为政 | 真实、有版本、有脏数据、有两层知识结构 |
| 评测 | ❌ 无 | ✅ 有（RAGAS / DeepEval / GroUSE） | ✅ **第一批交付物**，两条轴分开测 |
| Agent 循环 | ❌ 无 | ✅ 有（self-RAG / CRAG / agentic RAG） | ✅ 有，且明确给出**不该用**的场景 |
| 回归门禁 | ❌ 无 | ❌ 无 | ✅ 有 |
| 代码可复用 | — | ⚠️ **自定义非商业许可，不可直接复用** | 自行实现 |

**空缺很清楚**：一个**真实非玩具语料 + 语料工程作为一等公民（带出处与版本）+ 评测作为课程主线 + Agent 靠执行来验证代码**四者兼备的项目，没有找到。

本项目就填这个空缺。同时也说明教学定位：不是把技术逐个演示一遍，而是**在一个真实场景里判断哪些技术真的活了下来**。
