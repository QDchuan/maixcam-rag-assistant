## 1. 为什么评测要单独成篇

**因为这个项目想教的核心能力，本质上是"如何在看不见的地方判断自己做得好不好"。**

RAG 和 Agent 与普通软件开发最大的区别是：**没有编译错误**。代码跑通了、输出了通顺的中文、看起来还挺专业——但它可能是错的。普通开发者最熟悉的那种"跑通即正确"的反馈回路在这里是失效的。

所以本项目的教学立场是：

> 没有评测的 RAG 调优，不叫工程，叫许愿。

这份文档要说清四件事：怎么把质量拆成可测的轴、评测集怎么建、指标怎么选、技术怎么逐级验证。

## 2. 两条轴：本项目最重要的一个思维模型

### 2.1 为什么要分轴

一个 RAG 系统回答错了，只有两种可能：

| 失败类型 | 现象 | 真正的病因 | 该改哪里 |
| --- | --- | --- | --- |
| **检索失败** | 正确的那段文档根本没被召回 | 语料、切分、检索器、查询理解 | L2 / L3 / L4 |
| **生成失败** | 正确片段在上下文里，模型却没用好 | 提示词、上下文组织、模型能力 | L5 |

**这两类失败的修法几乎没有交集。** 但现实中绝大多数人把它们混在一起处理：答错了就换嵌入模型、就上调 top_k、就加 rerank——纯属碰运气。

因此本项目要求：**所有评测报告必须并列展示两条轴的分数**。这是纪律，不是建议。

### 2.2 分轴之后自然得到的指标

两条轴交叉出一个非常有用的诊断指标：

```
检索命中 且 答案正确   → 正常
检索命中 但 答案错误   → 生成问题（改 L5）
检索未命中 但 答案正确  → 模型本来就会（说明这题没测到 RAG 的价值，标注时要注意）
检索未命中 且 答案错误  → 检索问题（改 L2 / L3 / L4）
```

第三格尤其值得注意：**如果一个评测集里大量问题模型不靠检索也能答对，这个评测集就是无效的。** 这直接决定了评测集的构建原则——见下一节。

## 3. 评测集构建

### 3.1 三条来源，一条原则

| 来源 | 做法 | 优点 | 风险 |
| --- | --- | --- | --- |
| **真实问题** | 收集实际开发中卡住过的问题 | 分布真实，最有价值 | 数量少，需要积累 |
| **文档反推** | 从文档章节反向生成问题 | 容易批量产出 | 容易生成"文档里有现成标题"的送分题 |
| **对模型施压** | 找出模型不检索时会答错的点，专门建题 | 精准命中幻觉区 | 需要先跑一遍 L0 基线 |

**一条原则**：每道题都必须标注 **ground-truth 依据片段**（`doc_id` + 该片段必须包含的关键字符串）。

没有 ground-truth 的题只能测生成轴，测不了检索轴。而检索轴恰恰是 RAG 特有的、最需要测的那一轴。

### 3.2 数据模型

```jsonc
{
  "qid": "q014",
  "question": "maix.image.Image 怎么转成灰度图？",
  "qtype": "signature",              // concept | signature | example | troubleshoot
  "difficulty": "medium",
  "ground_truth": {
    // 检索轴：这些页面/片段必须被召回
    "required_docs": ["api/maix/image"],
    "required_spans": ["to_grayscale", "Image::to_grayscale"],
    // 生成轴：答案必须/禁止包含的内容
    "must_contain": ["to_grayscale"],
    "must_not_contain": ["cv2.cvtColor", "image.gray()"]
  },
  "reference_answer": "……",          // 人工写的参考答案，用于 judge 校准
  "source": "real",                  // real | doc_derived | model_stress
  "notes": "模型常编造 image.gray()"
}
```

三个字段值得解释：

- **`must_not_contain`**：这是最有效的一类断言。防幻觉的能力，本质上体现在"不该出现的东西没出现"。`cv2.cvtColor` 这种错误特别典型——模型把 OpenCV 的习惯带进来了。
- **`qtype`**：所有指标都要能按 `qtype` 分组看。整体分数变好但 `signature` 类变差，是一个必须被发现的信号。
- **`source`**：按来源分组看分数，能识别出"送分题占比过高"这类评测集质量问题。

### 3.3 规模与配比

起步规模：**60 题**。这是"能看出趋势"与"人工标注可承受"之间的平衡点。

| qtype | 题数 | 说明 |
| --- | --- | --- |
| `concept` | 20 | 怎么用某个功能、概念解释 |
| `signature` | 15 | 函数签名、参数、返回值（**幻觉重灾区**） |
| `example` | 15 | 要一段可运行代码 |
| `troubleshoot` | 10 | 报错排查 |

配比不是均匀的：`signature` 与 `example` 合计占一半，因为这两类正是本项目要解决的真实痛点，也是幻觉最集中的地方。

### 3.4 评测集的质量检查（元评测）

评测集本身会坏。跑之前先做三项体检：

| 检查 | 方法 | 不合格的处理 |
| --- | --- | --- |
| **送分题比例** | 跑 L0（无 RAG）基线，筛掉模型裸答就对的题 | 替换或提高难度 |
| **标注一致性** | 两人独立标注 20% 样本，算一致率 | 低于 80% 则修订标注规范 |
| **可判定性** | 每条断言是否机器可判（字符串匹配 / 白名单校验） | 不可判的改成 `reference_answer` + judge |

**第一条最重要。** 一个模型不检索就能答对的题，在 RAG 评测里是噪音。它会让所有配置的分数都很好看，从而掩盖真实差异。

## 4. 指标选型

### 4.1 检索轴（不涉及模型调用，最便宜、最稳定）

| 指标 | 定义 | 为什么需要它 |
| --- | --- | --- |
| **Recall@K** | ground-truth 片段中被召回的比例 | **主指标**。RAG 的第一性要求是"该有的有没有进来" |
| **Hit Rate@K** | 至少命中一个相关片段的查询占比 | 直观、好解释，适合教学开场 |
| **MRR** | 第一个相关片段排名的倒数均值 | 衡量"位置"而非"有无" |
| **nDCG@K** | 考虑分级相关性的排序质量 | 有精细相关性标注时使用 |
| **Context Precision** | 上下文中相关片段占比 | 衡量"信噪比"，直接影响生成质量与 token 成本 |

**为什么 Recall@K 是主指标？** 因为在检索-生成架构里，**没召回的内容，生成阶段无论如何也救不回来**。它是最硬的上限约束。教学上要反复强调这一点：调检索时盯 Recall，其他指标都是次要的。

### 4.2 生成轴

| 指标 | 定义 | 实现方式 |
| --- | --- | --- |
| **Faithfulness（忠实度）** | 答案中的论断有多少能被给定上下文支撑 | 最优：把答案拆成原子论断，逐条判定。次优：整体打分 |
| **Citation Precision** | 引用的片段是否真的支撑所引用的论断 | **程序可判**（检查 `[n]` 与论断的对应） |
| **Citation Recall** | 有多少论断带了引用 | **程序可判** |
| **Hallucination Rate（符号级）** | 代码块中不存在于 API roster 的符号占比 | **程序可判，零成本，零歧义** |
| **Refusal Accuracy** | 该拒答的拒答了、不该拒答的没拒 | 需要标注"是否应该拒答" |

**这里有一个重要的实现建议**：能程序判的指标，一个都不要交给 LLM 判。

- 符号级幻觉率：查白名单，完全确定。
- 引用精确率/召回率：检查编号对应关系，完全确定。

只有 `Faithfulness` 和语义正确性才需要模型判断。**把 judge 的使用面压到最小，是整个评测体系可靠性的关键。** LLM-as-judge 不是免费的——它有成本、有延迟、有偏差（见第 7 节）。

### 4.3 运行指标

| 指标 | 单位 | 用途 |
| --- | --- | --- |
| 端到端延迟 | ms（P50 / P95） | 重排序、Agent 的代价 |
| Token 消耗 | 输入 / 输出分开 | 成本归因（上下文变长是隐性成本） |
| 单次成本 | 估算货币值 | 让读者建立成本直觉 |
| 检索调用次数 | 次 | Agent 效率 |
| 拒答率 | % | 与被测系统、与配置强相关 |

**没有运行指标的消融表是不完整的。** 一个技术把 Recall 从 62% 提到 68%、同时把 P95 延迟翻三倍、成本翻两倍——这不是"更好"，这是"更贵"。教学必须把权衡摆出来。

## 5. 消融实验方法论

### 5.1 五条纪律

1. **一次只改一个变量。** 改了切分又换嵌入模型，得到的任何数字都无法归因。
2. **同一评测集、同一随机种子、同一 judge 模型。** judge 换版本会导致分数不可比。
3. **改前先记基线。** 每级都要有前一级的数字做对照。
4. **记录延迟与成本。** 只记质量分数是半个结论。
5. **给出失效场景。** 每一项技术都要回答"它在什么情况下没用甚至有害"。

### 5.2 实验矩阵

每一级 = 一份配置 = 一次评测。注意 L2–L8 是在 L1 之上**逐级叠加**的，同时也支持**单独开关**（用于验证某一项的独立贡献）。

| 配置 | 相对上一级的变化 | 要回答的问题 |
| --- | --- | --- |
| `l0_no_rag` | 无检索 | 幻觉到底多严重？（基线参照） |
| `l1_baseline` | 定长切分 + 单一稠密检索 | 朴素 RAG 改善了多少？ |
| `l2_structured` | 标题感知切分 + 元数据 + 版本固定 | 语料工程的贡献有多大？ |
| `l3_hybrid` | + BM25 与 RRF 融合 | 稀疏检索在标识符查询上是否不可替代？ |
| `l4_routed` | + 查询分类路由 + 父文档回填 | 分层语料的价值能否兑现？ |
| `l5_query_rewrite` | + 多查询 / HyDE / 指代消解 | 问法差异带来的损失有多大？ |
| `l6_rerank` | + 重排序 | 增益 vs 延迟的真实曲线 |
| `l7_contextual` | + 语境头 | 小语料上的性价比之王？ |
| `l8_grounded` | + 引用约束 + 拒答 + 符号校验 | 幻觉率能压到多低？代价是什么？ |
| `l9_agent` | + Agent 循环 | 相对 L8 是否值得？ |

> **实现状态**：上面是目标矩阵（配置名即设计名的规划）。`configs/` 目前实际存在的是
> `l_minus1_full_context.yaml`、`l0_no_rag.yaml`、`l1_baseline.yaml`、`l2_hybrid.yaml`、
> `l3_dense_only.yaml`、`l3_bm25_only.yaml`——即 **L-1 到 L3 已落地**；
> `l2_structured` 在实现时合并进了 `l2_hybrid`，L4 以上还没有配置文件（见根 README「还没做的」）。

### 5.2.1 被排除的技术，以及为什么也要讲

教学项目容易犯一个错：只讲采用了什么。但**"为什么不用某项流行技术"同样是需要判断力的地方**，而且更能防止读者盲从。以下四项本项目**不实现**，但必须在正文里明确说明理由——否则读者会以为作者不知道。

| 技术 | 为什么不用 | 怎么写进教学 |
| --- | --- | --- |
| **语义切分**（嵌入相似度找边界） | 技术文档的语义边界作者已用标题标出；放着免费且确定的信号不用去花算力猜一个增益不稳定的边界，不划算（公开研究对它的增益评价不一致） | 保留为**对照项**，让读者自己跑出"多花钱没换来增益" |
| **GraphRAG** | 提出它的论文自己把适用范围限定在**全局性归纳与主题总结**（"这批材料的主题是什么"）且语料规模很大（百万 token 量级）的场景；**不是事实型查询**。而本项目恰恰全是事实型查询。同时它的索引成本极高（要跑大量实体抽取与社区摘要） | 引论文自己的适用范围界定，说明"技术有它的适用域"，并把它列入**非目标** |
| **Self-RAG** | 它需要**训练**模型输出反思标记，**不是纯提示词方案**。常见误区是把它当成一个可以 prompt 出来的技巧 | 明确澄清这一点。本项目不做训练，因此不实现 |
| **HyDE** | 报告的效果是相对**无监督**稠密检索器（Contriever）的提升，未必能推广到现代嵌入模型或稀疏检索；且每次查询多一次 LLM 调用 | **作为 A/B 假设**放进 L5，用本项目的数据说话，不预设它有效 |

**这一节的教学目标是建立一种态度**：读到一篇讲某项技术很有效的文章时，先问三个问题——它的适用场景和我一样吗？它的对照基线是什么？它的效果是在谁的数据上测的？

> **关于效果数字的纪律。** 本项目在引用任何外部效果数字时，必须标注来源性质。典型例子：某厂商工程博客给出的"检索失败率降低 35% / 49% / 67%"是**厂商在自有数据集上的自测结果**，未找到独立复现，因此只能作为"值得一试"的线索，**不能作为事实陈述**。教学材料里必须明确标注 `[厂商自测]`，并鼓励读者在自己的语料上重测——这正是本项目做消融实验的理由。

### 5.3 结果表模板

这是全项目最有价值的单张产出物。每行一次实验，必须能一眼看出质量、代价与结论。

| 配置 | Recall@5 | Hit@5 | MRR | Faithful | 引用召回 | **幻觉率** | 拒答准确 | P95 延迟 | 成本/次 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| l0_no_rag | — | — | — | 0.41 | — | **0.28** | — | 1.2s | ¥0.001 | 参照 |
| l1_baseline | 0.62 | 0.71 | 0.44 | 0.68 | 0.35 | 0.11 | 0.55 | 1.5s | ¥0.003 | — |
| l2_structured | 0.74 | 0.83 | 0.55 | 0.72 | 0.41 | 0.09 | 0.61 | 1.5s | ¥0.003 | 语料工程性价比最高 |
| l3_hybrid | 0.86 | 0.91 | 0.68 | 0.75 | 0.48 | 0.08 | 0.66 | 1.6s | ¥0.003 | **标识符题 +31pt** |
| … | | | | | | | | | | |

> 表中数字为示意，用于说明表的形状与信息密度，不是实测值。实际数字在实现阶段产出。

**表的读法教学**（这比表本身重要）：

- 看 `l2` 与 `l1` 的对比 → 语料工程的收益常被低估，因为它"不酷"；
- 看 `l3` 在整体上的小幅提升 → 容易被判断为"不值得"；**必须按 `qtype` 分组再看**，会发现 `signature` 类提升巨大而 `concept` 类几乎持平。这正是"根据场景提高 RAG 质量"的实操含义。
- 看 `l6` 的延迟列 → 判断是否值得上线；
- 看 `l8` 的幻觉率与拒答率 → 幻觉降下来了，但拒答率也上去了？这是典型的权衡，必须一起看。

## 6. 分组分析：让结论落到场景上

整体分数会骗人。必须做的三组切分：

### 6.1 按 qtype

```
             concept   signature   example   troubleshoot
l1_baseline    0.71      0.38        0.55       0.62
l3_hybrid      0.73      0.69        0.61       0.66
                          ↑↑↑
              稀疏检索的收益几乎全部落在这里
```

这种表格才能支撑"**在什么场景下该用什么技术**"的结论。它直接回答了用户提出的核心诉求。

### 6.2 按 difficulty

简单题上各配置拉不开差距是正常的。**技术的价值主要体现在难题上**，所以难题子集的分数才是区分度所在。

### 6.3 按 source

`model_stress` 类题目（专门针对幻觉区构建的）上，各配置的差距应该最大。如果没有差距，说明评测集没测到点子上。

## 7. LLM-as-Judge：能用，但要知道它的坑

`Faithfulness` 这类指标确实需要模型判断。但必须正视它的偏差：

| 偏差 | 表现 | 缓解手段 |
| --- | --- | --- |
| **位置偏差** | 偏好前一个候选 | 成对比较时交换顺序取平均 |
| **长度/啰嗦偏差** | 偏好更长的答案 | 控制长度，或显式惩罚冗余 |
| **自我偏好** | 偏好与自己同源的输出 | judge 与被测模型尽量不同源 |
| **分数坍缩** | 大量输出挤在 4/5 分，无区分度 | 用**原子论断拆解**替代整体评分 |
| **版本漂移** | 换了 judge 版本，历史分数不可比 | 固定并记录 judge 模型版本 |

### 本项目的具体做法

1. **优先程序判定。** 引用、符号幻觉这类能算的，绝不用 judge。
2. **拆原子论断。** judge 不问"这个答案忠实吗"（太主观），而问"论断 X 能被资料 Y 支撑吗"（可判）。
3. **离散锚点。** 用 0/1/2 三档并给出每档的具例，不用 1–10 分。
4. **人工校准。** 抽 10–20% 样本人工评一遍，与 judge 对齐；不一致率高就修 prompt，而不是放任。
5. **judge 也是被测系统的一部分。** judge 的 prompt 要入库、要版本化。

## 8. 可复现性

评测结果不可复现，等于没有评测。三条硬要求：

| 要求 | 做法 |
| --- | --- |
| **语料固定** | 记录 commit / 抓取时间 / 内容指纹；索引记录语料指纹，不匹配则拒绝评测 |
| **模型固定** | 记录被评模型与 judge 模型的确切名称与版本；生成结果落盘缓存 |
| **结果归档** | 每次评测输出完整 JSON + Markdown 报告，含配置快照与各项指标 |

**缓存是复现性的前提，也是成本的救命稻草。** 评测要反复跑（每次改一点东西都要重跑），没有以 `hash(配置 + 输入)` 为键的磁盘缓存，读者会在第一次认真调参时就被账单劝退。

## 9. Agent 版怎么评（L9）

Agent 不能只复用 L1–L8 的指标。新增：

| 指标 | 定义 | 为什么重要 |
| --- | --- | --- |
| **任务成功率** | 最终答案正确的比例 | 主指标 |
| **平均轮次** | 平均消耗的决策轮 | 效率 |
| **工具调用分布** | 各工具被调用的次数与成功率 | 诊断工具设计是否合理 |
| **预算耗尽率** | 因超出预算而降级的比例 | 预算设置是否合理 |
| **失败恢复率** | 遇到工具错误后仍成功的比例 | 鲁棒性 |
| **与链式的成对胜率** | 同一问题上 A/B 对比 | **核心结论**：Agent 到底值不值 |

**第 6 项是本项目要交付的关键结论之一。** 预期结果很可能是分场景的：

- 单点事实查询（"某函数签名是什么"）→ 链式更快更便宜，Agent 无优势；
- 多跳/需要澄清的问题（"我的摄像头读不到图，可能是什么原因"）→ Agent 明显更好。

**这个分场景结论本身，就是"什么时候该用 Agent"这个问题的答案。** 它比任何定性论述都有说服力。

## 10. Skill 分支怎么评（分支 B）

Skill 分支的检索策略由宿主 Agent 决定，本项目的可控面变小，因此**评测范式必须变**。

能做的是两件事：

1. **端到端对比。** 同一批问题，在宿主 Agent 上分别用「无 Skill」「基础语料版 Skill」「增强语料版 Skill」三套，做**成对胜负率**比较。
2. **语料质量独立评测。** 语料与索引仍可被本项目自己的评测器直接测（复用第 4.1 节的检索轴指标），这部分完全可控。

**教学要点**：这是"放弃控制权之后如何仍然保证质量"的真实案例——你无法控制 Agent 的检索策略，但你可以通过**语料的组织方式**（分文件、分模块、给好的摘要与索引）去引导它。这条结论对做 Skill / MCP / 工具分发的读者非常实用。

## 11. 每级的教学产出（对应大纲第 16–23 章）

每一级都要交付四样东西，缺一不可：

| 产出 | 作用 |
| --- | --- |
| 一份可运行的配置 | 读者能自己复现 |
| 一组对比数字 | 结论的依据 |
| 一个失败案例 | 展示这一级**没有**解决什么 |
| 一段失效场景说明 | 什么时候别用这招 |

**"一个失败案例"是刻意的要求。** 只展示成功的教学会培养出错误的乐观。每一级都应该留下"即使加了这一招，这类问题依然答错"的记录——这既诚实，也更有教学价值，因为它让读者知道质量提升是有边界的。

## 12. 小结：本项目的质量观

把这份文档压成五句话：

1. **先问"要不要检索"，再问"怎么检索"。** 小语料下"全文塞进 prompt"是一个真实且常常更优的选项，必须实测而非假设。
2. **先分清是检索错了还是生成错了**，再动手改。
3. **能程序判的指标不要交给模型判**，把 judge 的使用面压到最小。
4. **每一项技术都要给出增益、代价和失效场景**，不默认推荐；**被排除的技术也要给出理由**。
5. **质量提升的杠杆常常不在算法上，而在语料工程上**——这一点在 MaixCAM 这个两层结构的语料上会体现得特别清楚。

再加一条贯穿始终的纪律：

> **任何外部效果数字都必须标注来源性质（厂商自测 / 独立复现 / 理论分析），并鼓励读者在自己的语料上重测。** 本项目自己的结论必须来自本项目自己的评测。
