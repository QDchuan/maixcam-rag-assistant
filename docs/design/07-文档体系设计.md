## 0. 先说三条判断

在谈结构之前，先把"什么算好文档"定下来。否则结构设计没有判据。

### 判断一：本项目最稀缺的教学资产是**它自己的事故史**

绝大多数教学项目展示的是打磨过的正确路径。但 RAG 与 agent 工程里真正难的部分，
恰恰是**东西安静地坏掉**的时候——没有报错、没有异常、分数看起来还行。

本项目在开发过程中真实发生过六次这样的事故，而且每一次都有完整的
症状 → 根因 → 修复 → 回归测试：

| # | 事故 | 性质 |
| --- | --- | --- |
| 1 | 语料脚本报告"0 篇"，退出码 0 | 静默失败 |
| 2 | API 参考页没产出 chunk，signature 召回 0.000 | 语料工程的盲区 |
| 3 | 符号校验把 `maix.gpio` 判成幻觉 | **假阳性的危害大于漏报** |
| 4 | 88 次工具调用被统计成 2 次 | 状态生命周期 |
| 5 | 幻觉率 0.000，实际覆盖面 0/18 | **指标伪装成好消息** |
| 6 | 预算 4 轮的 agent 比链式还差 | 参数与任务深度不匹配 |

**这六条覆盖了六个不同类别。** 它们比任何"RAG 最佳实践清单"都值钱，
因为它们是真实发生的，而且每一条都能被复现。

所以文档体系要把**事故档案做成一等公民**，而不是藏在 commit message 里。

### 判断二：文档必须能被验证，否则一定会腐化

教学文档最常见的死法不是写错，而是**写着写着和代码对不上了**。
而一个教学项目里出现"文档说的和代码做的不一致"，是致命的——读者会失去全部信任。

本项目有一个别的教学项目通常没有的条件：**它自带评测器**。
所以它可以做到一件别人做不到的事——

> **文档里的每一个数字，都能被一条命令复现。**

这不是形容，是要用工具强制执行的（见第 4 节）。

### 判断三：读者不是一种人，所以需要阅读路径而不是线性目录

三条分支 × 不同起点，至少产生四种读者：

| 读者 | 想干什么 | 从哪进 |
| --- | --- | --- |
| 只想解决问题 | 让 AI 会写 MaixPy | 分支 C（Skill），几分钟 |
| 学 RAG | 掌握检索增强的质量方法 | 评测 → 语料 → 消融 |
| 学 Agent | 掌握 agent 设计与落地 | 主线导览 → 五块机制 |
| 想自己仿一个 | 从零写一个 agent 基座 | 主线导览 + 代码 |
| 排障 | 我的 RAG 效果不好 | **事故档案**（按症状查） |

**最后一行最容易被忽略，但它是文档实用性的关键。** 一个人遇到问题时，
不会从头读一本书；他会搜症状。所以事故档案要按**症状**组织，不是按时间。

## 1. 文档的四层结构

```
docs/
├── README.md              文档地图：四种阅读路径 + 现状
│
├── tutorial/              【学】线性主干，一章一个想法
│   ├── 00-导览.md             已存在
│   ├── 01-失败是什么样的.md
│   ├── 02-把手工流程变成系统.md
│   ├── 03-语料工程.md
│   ├── 04-检索与消融.md
│   ├── 05-评测.md
│   ├── 06-Agent-五块机制.md
│   └── 07-端到端.md
│
├── postmortem/            【查】事故档案，按症状组织
│   ├── README.md              症状索引表
│   ├── 01-静默的空结果.md
│   ├── 02-有文档却召不回.md
│   ├── 03-校验器把正确代码判成幻觉.md
│   ├── 04-被清空的统计.md
│   ├── 05-伪装成好消息的0.md
│   └── 06-预算与任务不匹配.md
│
├── reference/             【用】按需查阅，不承担教学
│   ├── cli.md                 命令与参数
│   ├── config.md              配置项
│   ├── architecture.md        分层与数据流
│   └── glossary.md            术语表
│
├── design/                【审】项目级决策与取舍（已存在）
│   └── 00..07.md
│
└── evidence/              【证】可验证的证据
    ├── claims.tsv             论断 → 复现命令 → 期望形态 → 最后验证时间
    ├── ablation.md            消融总表
    └── incidents.tsv          事故索引（症状 → 文件 → 回归测试）
```

### 1.1 四层各自的职责（边界必须清楚，否则会互相重复）

| 层 | 回答 | 面向 | 不做什么 |
| --- | --- | --- | --- |
| **tutorial** | "我该怎么做，为什么" | 学习中的读者 | 不做完整参数表 |
| **postmortem** | "我遇到这个症状，是怎么回事" | 排障中的读者 | 不教基础概念 |
| **reference** | "这个参数是什么" | 使用中的读者 | 不解释动机 |
| **design** | "当初为什么这么定" | 作者/评审者 | 不写操作步骤 |
| **evidence** | "这个数字怎么来的" | 怀疑的读者 | 不写叙述 |

**最容易犯的错是让 tutorial 变成 reference**——把所有参数都列进去，
结果既不能读也不能查。所以有一条硬规则：**tutorial 里不出现完整参数表，
只出现"这一章需要的那几个参数"，其余给出 reference 链接。**

## 2. 每章的固定骨架

一致性本身就是教学价值：读者学会"读一章的方法"后，后面每一章都能快速消化。

每一章必须有以下七节，**顺序固定**：

```markdown
## 1. 一句话结论
   给只想扫一眼的人。不超过三行。

## 2. 为什么需要这个
   从"没有它会怎样"讲起，不从定义讲起。
   落在本项目具体的问题上（MaixCAM 语料），不用通用例子。

## 3. 怎么做
   可运行的命令 / 可读的代码。每一步都能自己跑。

## 4. 亲眼看一次
   连到一个演示脚本或一条命令，读者跑完能看到东西。
   **这一节不能是"你应该会看到…"，必须是真实可跑的命令。**

## 5. 证据
   实测数字。没有数字的论断必须标注性质（[厂商自测]/[推测]/[本项目实测]）。

## 6. 失败的样子
   这一招什么时候不管用。**每章都必须有这一节，不许空着。**
   没有失败案例的章节，说明我们还没测够。

## 7. 自检
   读完的人怎么知道自己懂了：一个可做的小任务 + 一个明确的验收标准。
```

**第 6 节是这套骨架的核心。** 它强制每一章都留下"边界"，
而不是只讲好的一面——这正是本项目对其他一切外部数字的态度，
也应该体现在自己的文档里。

## 3. 事故档案：本项目最有价值的一层

### 3.1 为什么它值得单独一层

因为它回答的是**读者真正会遇到的时刻**。一个人不会在遇到问题时从头读书，
他会搜症状。而"症状 → 根因"的映射，恰恰是教学文档里最缺的东西。

### 3.2 每篇事故的固定结构

```markdown
## 症状
   读者能对号入座的现象。要写得具体到能搜到。
   （"报告里某个指标是 0.000，但看起来应该是正常的"）

## 它为什么危险
   这一节决定读者会不会继续读。要说清"如果不发现会怎样"。

## 怎么发现的
   真实的发现过程。**这一节教会读者怎么排查，比结论更重要。**

## 根因
   技术原因，配最小复现代码。

## 修复
   改了什么。如果有多解，说明为什么选这个。

## 回归测试
   文件名 + 断言。**没有回归测试的修复不算修复。**

## 同类问题清单
   这个坑还有哪些变体，读者在自己的项目里可能怎么遇到。
```

### 3.3 六篇的选题与顺序

按**排查思维**排序，不是按时间：

| 顺序 | 事故 | 教的是哪一类判断 |
| --- | --- | --- |
| 1 | 静默的空结果 | **失败必须显式**：安静的成功是假象 |
| 2 | 有文档却召不回 | **语料工程的盲区**：文档存在 ≠ 能被召回 |
| 3 | 校验器把正确代码判成幻觉 | **假阳性比漏报更危险** |
| 4 | 被清空的统计 | **状态生命周期**：谁在什么时候被重置 |
| 5 | 伪装成好消息的 0 | **指标必须暴露覆盖面** |
| 6 | 预算与任务不匹配 | **参数要匹配任务**，不是越大/越小越好 |

**这六条串起来是六种不同的判断力**，而不是六个孤立的知识点。

### 3.4 症状索引（`postmortem/README.md`）

这是这一层真正的入口。读者按现象查：

| 你看到的现象 | 去看 |
| --- | --- |
| 脚本跑完了但结果是 0 / 空的 | 01 |
| 检索的召回率明显偏低，但文档里明明有 | 02 |
| 某个指标是 0.000，看起来很好 | 05 |
| 代码校验报错，但我确信那段代码是对的 | 03 |
| 统计数字对不上（比预期少很多） | 04 |
| agent 有时候比不用 agent 还差 | 06 |

## 4. 课后习题：每一章都要有，而且分四组

习题不是装饰，它是第 2 节骨架里"自检"那一节的**落地形式**。
本项目有一件别的教学项目没有的条件：**习题可以要求读者真跑一遍，并对照期望结果。**

### 4.1 四组递进，对应四种能力

| 组 | 名字 | 考什么 | 验收方式 |
| --- | --- | --- | --- |
| **A** | 复现 | 能不能把环境跑通并看到现象 | **可自动校验**：给出期望输出，读者自己比对 |
| **B** | 诊断 | 给一个现象，能不能找到根因 | 能说出根因 + 指出对应的回归测试 |
| **C** | 改造 | 改一处东西，能不能预测后果 | **预测与实测一致**；不一致时能解释为什么 |
| **D** | 判断 | 没有唯一答案的取舍 | 答案里必须包含**代价**与**失效条件** |

**C 组是这套设计的核心**：它逼读者先写下预测，再验证。
"预测错了"恰恰是最有价值的学习时刻——而绝大多数教学文档不给你犯错的机会。

**D 组刻意不给标准答案**，只给"判断依据"。因为本项目要教的是判断力，
而判断力不能靠背答案获得。验收标准是"你的答案里有没有代价和失效条件"——
**没有代价分析的方案描述，一律不算合格。**

### 4.2 每题必须带的三样东西

```markdown
**C2. 把 chunk 的 max_tokens 从 500 调到 100，预测两条轴会怎么变，然后验证。**

- 提示：先想清楚"更小的 chunk"对召回和上下文各意味着什么
- 验收：预测与实测方向一致；若不一致，能说出是哪一步想错了
- 相关：`docs/tutorial/03-语料工程.md`、`postmortem/02`
```

三样：**提示**（卡住时看）、**验收标准**（怎么知道自己对了）、**相关链接**（去哪找依据）。

### 4.3 答案放哪

| 内容 | 放哪 | 理由 |
| --- | --- | --- |
| 提示 | 章节内 `<details>` 折叠 | 想自己想的读者可以不看 |
| A 组期望输出 | 章节内直接给出 | 它就是校验依据，藏起来反而没用 |
| B/C/D 组参考答案 | `docs/exercises/answers.md` | 单独一册，避免误读 |

`answers.md` 里每一题都写**推理链**，不只写结论——因为读者要学的是推理过程。

### 4.4 一条纪律：不出现"填空题"

不设计"填空"和"名词解释"这类题。本项目的读者是要**动手做 RAG 与 agent 的人**，
不是要考试的人。每一道题都必须对应一个真实会发生的工作场景。

---


**没有机制的纪律不会被执行。** 所以文档的每一条要求都要有工具兜住。

## 5. 防腐化机制（这一节是工程重点）

**没有机制的纪律不会被执行。** 所以文档的每一条要求都要有工具兜住。

### 5.1 四道自动检查

| 检查 | 抓什么 | 怎么实现 |
| --- | --- | --- |
| **链接与引用** | 内部链接失效、引用的文件/命令不存在 | 扫描 `](./x.md)` 与 `!` 引用的路径；扫描文档里的 `python -m maixrag <cmd>` 与命令表比对 |
| **代码块可运行** | 文档里的示例代码和代码库脱节 | 带 `<!-- run -->` 标记的代码块被抽出来真实执行 |
| **数字新鲜度** | 文档里的数字是旧版本跑出来的 | 论断表里的数字与 `eval/results/*.json` 的最新值比对，不一致就报"陈旧" |
| **论断有据** | 出现没有来源的效果数字 | 扫描文档里的百分比/倍数，要求同一行有 `[实测]`/`[厂商自测]`/`[推测]` 标记 |

### 5.2 论断表 `docs/evidence/claims.tsv`

这是把"文档里的每个数字都能复现"落成事实的手段：

```
claim_id	断言	复现命令	期望形态	最后验证
C-01	signature 类问题召回 0.000→0.500	maixrag corpus build && ...	recall 提升 ≥ 0.4	2026-09-12
C-02	agent 平均每题 4.9 次工具调用	maixrag agent-eval --max-turns 10	tool_calls/18 ≈ 4.9	2026-09-12
```

一个脚本（`scripts/check_docs.py`）做三件事：
1. 校验每条断言的命令在当前代码上**仍然存在**（子命令与参数名比对）；
2. 把 `[实测]` 数字与最新评测结果比对，不一致则标记为**待更新**；
3. 报告"最后验证"超过一定时间的条目。

> **为什么值得做这个**：这是本项目与其他教学项目最实在的差别。
> 别的项目说"我们的方法有效"，本项目能说"这条命令会打印出这个数字"。
> 而这个能力是现成的——评测器已经在了，只是还没把它和文档接上。

### 5.3 事故与回归测试的绑定

`docs/evidence/incidents.tsv`：

```
incident	症状	文档	回归测试
I-01	脚本报 0 篇但退出码 0	postmortem/01	fetch_repo_docs 的空结果断言
I-03	gpio 扁平导入被误判	postmortem/03	scripts/regress_symbol_false_positive.py
```

检查脚本验证：**每篇事故都有对应的回归测试，且那个测试存在**。
没有回归测试的事故文档，说明修复没有固化——那是文档在说谎。

## 6. 写作纪律（成文规则，写进 CONTRIBUTING）

| # | 规则 | 理由 |
| --- | --- | --- |
| 1 | **先说结论，再说理由** | 想扫一眼的人不该被逼着读三段 |
| 2 | **不用通用例子** | "假设你要做一个客服机器人"这类例子对本项目毫无价值，全部用 MaixCAM 的真实问题 |
| 3 | **每个论断标注性质** | `[本项目实测]` / `[厂商自测]` / `[推测]`，与 [05 附录](./05-调研与借鉴.md) 的证据分级一致 |
| 4 | **代码块必须能跑** | 不能跑的代码块要么标 `<!-- sketch -->` 并说明是伪代码，要么删掉 |
| 5 | **不复制 docstring** | 只给链接。重复是腐化的开始 |
| 6 | **失败案例与成功案例同等篇幅** | 只讲成功的教学会培养错误的乐观 |
| 7 | **一页一个想法** | 超过 300 行的页面，先问能不能拆 |
| 8 | **中文优先，术语保留英文** | 术语翻译会造成沟通成本；`embedding` 不译成"嵌入化"之类 |

**第 2 条值得单独强调**：教学文档最怕"通用化"。
一旦用"假设你在做电商客服"这种例子，读者就要做两次翻译（例子→自己场景），
而翻译过程正是理解流失的地方。本项目全部用 MaixCAM 的真实问题，
因为**这些问题是真实发生的**。

## 7. 分批交付计划

文档不能一次性写完——写完就跟不上代码，而且评审成本太高。

| 批次 | 交付 | 为什么这个顺序 |
| --- | --- | --- |
| **D1** | `docs/README.md`（地图与阅读路径）+ `postmortem/` 六篇 + 症状索引 | **事故档案先行**：它是最稀缺的资产，且不依赖其他文档 |
| **D2** | `docs/evidence/` + `scripts/check_docs.py` | 把"数字可复现"做成机制，后面所有文档都受益 |
| **D3** | `tutorial/` 补完 01–07 | 主干，依赖 D1/D2 的素材 |
| **D4** | `reference/` 四篇 + `CONTRIBUTING.md` | 收尾，且 reference 最容易由代码生成 |

**为什么事故档案放在最前面**：它是唯一**不会被代码改动淘汰**的内容——
接口会变、参数会变，但"静默失败很危险"这条判断不会变。
而且它现在的素材已经齐了（六次事故都有完整的 commit message 与回归测试）。

## 8. 需要你定的四件事

| # | 问题 | 选项 | 我的倾向 |
| --- | --- | --- | --- |
| 1 | 事故档案是否公开写自己的失误 | 全部公开 / 匿名化 / 只写技术不写过程 | **全部公开**——"我们也踩过"是教学价值最高的部分，而且是这个项目诚实的证明 |
| 2 | tutorial 与 design 是否合并 | 分开 / 合并 | **分开**，但 tutorial 每章末尾链回对应的 design 文档（讲"为什么这么定"） |
| 3 | `check_docs.py` 做到多重 | 只查链接 / 查链接+数字新鲜度 / 全做含代码块执行 | **查链接 + 数字新鲜度**；代码块执行放到之后（成本高、收益递增） |
| 4 | 是否给 tutorial 配可视化 | 纯文字 / 配生成的图表 | **配**：消融表已经有数据，生成一张图比写三段话有效；但排在 D3 之后 |
