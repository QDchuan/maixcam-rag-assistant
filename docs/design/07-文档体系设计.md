## 0. 先说三条判断

在谈结构之前，先把"什么算好文档"定下来。否则结构设计没有判据。

### 判断一：本项目最稀缺的教学资产是**它自己的事故史**

绝大多数教学项目展示的是打磨过的正确路径。但 RAG 与 agent 工程里真正难的部分，
恰恰是**东西安静地坏掉**的时候——没有报错、没有异常、分数看起来还行。

本项目在开发过程中真实发生过六次这样的事故，而且每一次都有完整的
症状 → 根因 → 修复 → 回归测试：

| # | 事故 | 性质 |
| --- | --- | --- |
| 1 | 语料脚本报告"0 篇"，退出码 0 | 静默失败 |
| 2 | API 参考页没产出 chunk，signature 召回 0.000 | 语料工程的盲区 |
| 3 | 符号校验把 `maix.gpio` 判成幻觉 | **假阳性的危害大于漏报** |
| 4 | 88 次工具调用被统计成 2 次 | 状态生命周期 |
| 5 | 幻觉率 0.000，实际覆盖面 0/18 | **指标伪装成好消息** |
| 6 | 预算 4 轮的 agent 比链式还差 | 参数与任务深度不匹配 |

**这六条覆盖了六个不同类别。** 它们比任何"RAG 最佳实践清单"都值钱，
因为它们是真实发生的，而且每一条都能被复现。

所以文档体系要把**事故档案做成一等公民**，而不是藏在 commit message 里。

### 判断二：文档必须能被验证，否则一定会腐化

教学文档最常见的死法不是写错，而是**写着写着和代码对不上了**。
而一个教学项目里出现"文档说的和代码做的不一致"，是致命的——读者会失去全部信任。

本项目有一个别的教学项目通常没有的条件：**它自带评测器**。
所以它可以做到一件别人做不到的事——

> **文档里的每一个数字，都能被一条命令复现。**

这不是形容，是要用工具强制执行的（见第 4 节）。

### 判断三：读者不是一种人，所以需要阅读路径而不是线性目录

三条分支 × 不同起点，至少产生四种读者：

| 读者 | 想干什么 | 从哪进 |
| --- | --- | --- |
| 只想解决问题 | 让 AI 会写 MaixPy | 分支 C（Skill），几分钟 |
| 学 RAG | 掌握检索增强的质量方法 | 评测 → 语料 → 消融 |
| 学 Agent | 掌握 agent 设计与落地 | 主线导览 → 五块机制 |
| 想自己仿一个 | 从零写一个 agent 基座 | 主线导览 + 代码 |
| 排障 | 我的 RAG 效果不好 | **事故档案**（按症状查） |

**最后一行最容易被忽略，但它是文档实用性的关键。** 一个人遇到问题时，
不会从头读一本书；他会搜症状。所以事故档案要按**症状**组织，不是按时间。

## 1. 文档的六层结构

```
docs/
├── README.md              文档地图：四种阅读路径 + 现状
│
├── concepts/              【懂】建立心智模型，不做操作
│   ├── 00-为什么需要RAG.md
│   ├── 01-RAG的完整链路.md
│   ├── 02-语料与切分.md
│   ├── 03-检索-稀疏与稠密.md
│   ├── 04-融合与重排序.md
│   ├── 05-生成与忠实性.md
│   ├── 06-Agent与链的区别.md
│   ├── 07-评测-两条轴.md
│   └── 08-权限与沙盒.md
│
├── tutorial/              【学】线性主干，一章一个想法
│   └── 00-导览.md             已存在（01..07 待写）
│
├── postmortem/            【查】事故档案，按症状组织
│   ├── README.md              症状索引表
│   └── 01..06.md              已完成
│
├── exercises/             【练】习题与答案，**物理分离**
│   ├── README.md              怎么用这套习题
│   ├── concepts/              概念类问答题
│   └── answers/               答案（含推理链与常见浅答案）
│
├── reference/             【用】按需查阅，不承担教学
│   ├── cli.md / config.md / architecture.md / glossary.md
│
├── design/                【审】项目级决策与取舍（已存在）
│   └── 00..07.md
│
└── evidence/              【证】可验证的证据
    ├── claims.tsv / ablation.md / incidents.tsv
```

### 1.1 为什么要有独立的 `concepts/` 层

这是从一个**设计缺口**补出来的：

> **读者得先有概念，才答得出概念题。**

原先我把"建立概念"混在 tutorial 里（一边讲概念一边做操作）。但那有问题：
tutorial 是**线性**的，读者要跳到第五章才能理解第三章提到的"融合"是什么；
而概念应该是可以**单独查阅、随时回看**的。

拆成两层，职责不同：

| | concepts | tutorial |
| --- | --- | --- |
| 回答 | **这东西是什么、为什么长这样、由哪些部分组成** | 你该怎么做、为什么这么选 |
| 形式 | 概念图、术语、边界、常见误解 | 命令、代码、实测数字 |
| 读法 | 可跳读、可查阅 | 按顺序走 |
| 删掉它 | 读者知道怎么做，但不知道自己在做什么 | 读者懂了原理，但做不出来 |

**两层的交叉引用是双向的**：概念文档末尾链到对应 tutorial 章节与习题；
tutorial 章节开头链回概念文档。

### 1.2 各层职责（边界必须清楚，否则会互相重复）

| 层 | 回答 | 面向 | 不做什么 |
| --- | --- | --- | --- |
| **concepts** | "这是什么，为什么这样" | 建立认知 | 不做操作步骤 |
| **tutorial** | "我该怎么做，为什么" | 学习 | 不做完整参数表 |
| **postmortem** | "我遇到这个症状，是怎么回事" | 排障 | 不教基础概念 |
| **exercises** | "我到底懂没懂" | 自检 | **不引入新知识** |
| **reference** | "这个参数是什么" | 使用 | 不解释动机 |
| **design** | "当初为什么这么定" | 评审 | 不写操作步骤 |
| **evidence** | "这个数字怎么来的" | 验证 | 不写叙述 |

**最容易犯的错是让 tutorial 变成 reference**——把所有参数都列进去，
结果既不能读也不能查。所以有一条硬规则：**tutorial 里不出现完整参数表，
只出现"这一章需要的那几个参数"，其余给出 reference 链接。**

## 2. 每章的固定骨架

一致性本身就是教学价值：读者学会"读一章的方法"后，后面每一章都能快速消化。

每一章必须有以下七节，**顺序固定**：

```markdown
## 1. 一句话结论
   给只想扫一眼的人。不超过三行。

## 2. 为什么需要这个
   从"没有它会怎样"讲起，不从定义讲起。
   落在本项目具体的问题上（MaixCAM 语料），不用通用例子。

## 3. 怎么做
   可运行的命令 / 可读的代码。每一步都能自己跑。

## 4. 亲眼看一次
   连到一个演示脚本或一条命令，读者跑完能看到东西。
   **这一节不能是"你应该会看到…"，必须是真实可跑的命令。**

## 5. 证据
   实测数字。没有数字的论断必须标注性质（[厂商自测]/[推测]/[本项目实测]）。

## 6. 失败的样子
   这一招什么时候不管用。**每章都必须有这一节，不许空着。**
   没有失败案例的章节，说明我们还没测够。

## 7. 自检
   读完的人怎么知道自己懂了：一个可做的小任务 + 一个明确的验收标准。
```

**第 6 节是这套骨架的核心。** 它强制每一章都留下"边界"，
而不是只讲好的一面——这正是本项目对其他一切外部数字的态度，
也应该体现在自己的文档里。

## 3. 事故档案：本项目最有价值的一层

### 3.1 为什么它值得单独一层

因为它回答的是**读者真正会遇到的时刻**。一个人不会在遇到问题时从头读书，
他会搜症状。而"症状 → 根因"的映射，恰恰是教学文档里最缺的东西。

### 3.2 每篇事故的固定结构

```markdown
## 症状
   读者能对号入座的现象。要写得具体到能搜到。
   （"报告里某个指标是 0.000，但看起来应该是正常的"）

## 它为什么危险
   这一节决定读者会不会继续读。要说清"如果不发现会怎样"。

## 怎么发现的
   真实的发现过程。**这一节教会读者怎么排查，比结论更重要。**

## 根因
   技术原因，配最小复现代码。

## 修复
   改了什么。如果有多解，说明为什么选这个。

## 回归测试
   文件名 + 断言。**没有回归测试的修复不算修复。**

## 同类问题清单
   这个坑还有哪些变体，读者在自己的项目里可能怎么遇到。
```

### 3.3 六篇的选题与顺序

按**排查思维**排序，不是按时间：

| 顺序 | 事故 | 教的是哪一类判断 |
| --- | --- | --- |
| 1 | 静默的空结果 | **失败必须显式**：安静的成功是假象 |
| 2 | 有文档却召不回 | **语料工程的盲区**：文档存在 ≠ 能被召回 |
| 3 | 校验器把正确代码判成幻觉 | **假阳性比漏报更危险** |
| 4 | 被清空的统计 | **状态生命周期**：谁在什么时候被重置 |
| 5 | 伪装成好消息的 0 | **指标必须暴露覆盖面** |
| 6 | 预算与任务不匹配 | **参数要匹配任务**，不是越大/越小越好 |

**这六条串起来是六种不同的判断力**，而不是六个孤立的知识点。

### 3.4 症状索引（`postmortem/README.md`）

这是这一层真正的入口。读者按现象查：

| 你看到的现象 | 去看 |
| --- | --- |
| 脚本跑完了但结果是 0 / 空的 | 01 |
| 检索的召回率明显偏低，但文档里明明有 | 02 |
| 某个指标是 0.000，看起来很好 | 05 |
| 代码校验报错，但我确信那段代码是对的 | 03 |
| 统计数字对不上（比预期少很多） | 04 |
| agent 有时候比不用 agent 还差 | 06 |

## 4. 习题体系：两个轴，四类题

### 4.1 为什么是两个轴

我最初按**"要做什么动作"**分了一组题（复现 / 诊断 / 改造 / 判断）。
那个划分能用，但它漏掉了一个更重要的维度：**考的是什么知识。**

补上第二个轴之后，得到一张 2×2：

|  | **概念**：框架 · 流程 · 算法 · 术语 | **工程**：局限性 · 选型 · 取舍 · 排障 |
| --- | --- | --- |
| **动手**<br>（跑命令、改代码） | **复现题**<br>跑通一遍流程、实现一个算法 | **改造题**<br>改一个参数、修一个 bug、做一次取舍实验 |
| **问答**<br>（把一件事说清楚） | **概念问答**<br>"RAG 的完整链路是什么"<br>"BM25 的 IDF 为什么要修正" | **工程问答**<br>"什么时候不该用 rerank"<br>"这个场景你选 dense 还是 hybrid" |

**"诊断"落在工程列**：它同时需要动手（去查）与工程判断（怎么排除），
所以它是"改造题"的一个变体，而不是独立一类。

### 4.2 为什么"工程问答"是这个项目最该考的东西

因为这个项目的主张不是"我用了混合检索 + 重排序"，而是
**"我测出了哪些技术活了下来，并把表放在这里"**。

而"哪些活下来了"这个判断，只有靠**工程问答**才能考出来：

| 概念问答能考 | 工程问答才能考 |
| --- | --- |
| RRF 是什么、为什么不需要量纲归一 | 什么情况下**不该**用 RRF |
| BM25+ 的 IDF 为什么恒正 | 小语料下 BM25 和 dense 你选哪个，为什么 |
| rerank 能提升精度 | rerank 的延迟代价什么时候不值 |
| agent 能做多跳 | 什么问题**不该**交给 agent |

**右列的每一道题都没有唯一正确答案**，它的验收标准是
**"你的答案里有没有代价分析和失效条件"**。

### 4.3 概念文档负责**提出**问题，习题负责检验**你能不能回答**

这是从一次设计缺口补出来的机制。

原先我把概念文档写成"讲解"，把习题写成"检验"——两者是**断开的**：
读者读完概念，不知道哪些地方是重点；做题时又想不起概念文档在哪。

改成这样：

```markdown
（概念文档 03-检索-稀疏与稠密.md 的末尾）

## 这一章留下的问题

读到这里，你应该能回答下面这些问题。**答不出来说明前面没读透。**
答案在 exercises/answers/03-检索-稀疏与稠密.md。

1. 为什么"函数名精确匹配"这类查询，稠密检索经常输给 BM25？
2. BM25 的 IDF 在什么情况下会变成负数？为什么那是问题？
3. 如果只用稠密检索，你会怎么发现"某类查询一直召回失败"？

（对应的 tutorial 章节与动手题也在这里给出链接）
```

**概念文档负责提出问题，习题负责检验答案。** 这样：

- 读者读概念时就知道**哪些是重点**（就是被问到的那些）；
- 做习题时知道**依据在哪**（概念文档的链接）；
- 而这两处的链接是**双向**的，不会脱节。

### 4.4 问答题与答案必须物理分离

**问答题的全部价值在于"先自己想"。** 答案放在题目下面，
读者会在读到问题的同一秒看到答案，思考过程根本不会发生。

所以：

```
docs/exercises/
├── README.md                怎么用这套题（含"不要提前翻答案"的说明）
├── concepts/                概念类问答（按章节分文件）
│   ├── 00-为什么需要RAG.md
│   ├── 03-检索-稀疏与稠密.md
│   └── ...
└── answers/                 答案（同名文件）
    ├── 00-为什么需要RAG.md
    ├── 03-检索-稀疏与稠密.md
    └── ...
```

**但不能藏得太深**——找不到答案会让人放弃。所以每道题后面都给一行：

```markdown
> 参考答案：[`exercises/answers/03-检索-稀疏与稠密.md`](../exercises/answers/03-检索-稀疏与稠密.md) 第 1 题
```

**分离但不难找**，这是这条规则的全部要求。

### 4.5 答案要写成什么样

两类问答的答案结构**不一样**，因为它们的评判标准不一样。

#### 概念类答案：给推理链，不只给结论

```markdown
### Q1. 为什么"函数名精确匹配"这类查询，稠密检索经常输给 BM25？

**答案**：因为稠密检索把文本压成语义向量，而**罕见字符串在这个压缩中损失最大**。
"maix.camera.Camera" 这类标识符在训练语料里出现极少，嵌入模型没有为它学过
一个好位置，于是它与"摄像头"、"Camera" 等常见词的向量距离反而不如词面匹配可靠。
BM25 不做语义压缩，它按词是否出现来打分，所以标识符的字面命中几乎是必然的。

**如果你答到了**：语义压缩 / 标识符罕见 / 词面 vs 语义 —— 说明你理解了这一层。
**如果你答成**："因为 BM25 更准" —— 那是把结论当原因，需要回去读 03 章。
```

**"如果你答到了 X" / "如果你答成 Y"** 是这个答案设计的关键：
它不只判断对错，还**诊断读者理解到了哪一层**。

#### 工程类答案：给判断依据 + 一个示范回答 + 常见浅答案

```markdown
### Q4. 什么问题不该交给 agent？（工程类，无唯一答案）

**判断依据**（这三条都要考虑到才算合格）：
1. 任务需要几步 —— 单步能答的，链式更快更便宜；
2. 失败代价 —— agent 可能跑飞，代价高的场景不该交给它；
3. 可验证性 —— 结果能不能被程序校验（不能的话 agent 的自检也没用）

**一个示范回答**：
单点事实查询不该交给 agent。"某函数的签名是什么"用 lookup_api 一次查表就够，
而 agent 会花 4-5 轮；我们实测 agent 平均 4.9 次工具调用/题，
在 signature 类问题上这 4.9 次里大部分是浪费的。

**常见的浅答案**（以及为什么浅）：
- "简单问题不该用 agent" —— 没有定义什么叫"简单"，也没说代价有多大；
- "agent 太贵了" —— 只说了成本，没说清在什么条件下贵是值得的；
- "看情况" —— 对，但等于没说；合格的答案要给出判据。
```

**"常见的浅答案"这一节是工程类答案的核心。**
它通过对比教学——读者能看到"我那个答案为什么不够好"。

### 4.6 四类题的定位与验收

| 类型 | 位置 | 数量建议 | 验收标准 |
| --- | --- | --- | --- |
| **复现题** | 各 tutorial 章节末 | 每章 1–2 | **可自动校验**：运行命令，输出与期望一致 |
| **改造题** | 各 tutorial 章节末 | 每章 1–2 | **预测与实测一致**；不一致时能解释为什么 |
| **概念问答** | `exercises/concepts/` | 每章 3–5 | 答案覆盖到"推理链"的关键环节 |
| **工程问答** | `exercises/concepts/` | 每章 2–3 | 答案含**代价分析**与**失效条件** |

**改造题是四类里学习效率最高的**：它逼读者先写下预测再验证。
"预测错了"恰恰是最有价值的学习时刻——而绝大多数教学文档不给你犯错的机会。

### 4.7 每条习题必须带的三样东西

```markdown
**C2. 把 chunk 的 max_tokens 从 500 调到 100，预测两条轴会怎么变，然后验证。**

- 提示：先想清楚"更小的 chunk"对召回和上下文各意味着什么
- 验收：预测与实测方向一致；若不一致，能说出是哪一步想错了
- 依据：[`concepts/02-语料与切分.md`](../concepts/02-语料与切分.md)、[`postmortem/02`](../postmortem/02-有文档却召不回.md)
```

**提示**（卡住时看）、**验收标准**（怎么知道自己对了）、**依据**（去哪找答案）。

### 4.8 一条纪律：不出现填空题与名词解释

本项目的读者是要**动手做 RAG 与 agent 的人**，不是要考试的人。

所以不设计"填空"和"请解释什么是 X"这类题。
每一道题都必须对应一个**真实会发生的工作场景**——
要么是"你会怎么做"，要么是"这个现象说明了什么"。

**没有机制的纪律不会被执行。** 所以文档的每一条要求都要有工具兜住。

## 5. 防腐化机制（这一节是工程重点）

**没有机制的纪律不会被执行。** 所以文档的每一条要求都要有工具兜住。

### 5.1 四道自动检查

| 检查 | 抓什么 | 怎么实现 |
| --- | --- | --- |
| **链接与引用** | 内部链接失效、引用的文件/命令不存在 | 扫描 `](./x.md)` 与 `!` 引用的路径；扫描文档里的 `python -m maixrag <cmd>` 与命令表比对 |
| **代码块可运行** | 文档里的示例代码和代码库脱节 | 带 `<!-- run -->` 标记的代码块被抽出来真实执行 |
| **数字新鲜度** | 文档里的数字是旧版本跑出来的 | 论断表里的数字与 `eval/results/*.json` 的最新值比对，不一致就报"陈旧" |
| **论断有据** | 出现没有来源的效果数字 | 扫描文档里的百分比/倍数，要求同一行有 `[实测]`/`[厂商自测]`/`[推测]` 标记 |

### 5.2 论断表 `docs/evidence/claims.tsv`

这是把"文档里的每个数字都能复现"落成事实的手段：

```
claim_id	断言	复现命令	期望形态	最后验证
C-01	signature 类问题召回 0.000→0.500	maixrag corpus build && ...	recall 提升 ≥ 0.4	2026-09-12
C-02	agent 平均每题 4.9 次工具调用	maixrag agent-eval --max-turns 10	tool_calls/18 ≈ 4.9	2026-09-12
```

一个脚本（`scripts/check_docs.py`）做三件事：
1. 校验每条断言的命令在当前代码上**仍然存在**（子命令与参数名比对）；
2. 把 `[实测]` 数字与最新评测结果比对，不一致则标记为**待更新**；
3. 报告"最后验证"超过一定时间的条目。

> **为什么值得做这个**：这是本项目与其他教学项目最实在的差别。
> 别的项目说"我们的方法有效"，本项目能说"这条命令会打印出这个数字"。
> 而这个能力是现成的——评测器已经在了，只是还没把它和文档接上。

### 5.3 事故与回归测试的绑定

`docs/evidence/incidents.tsv`：

```
incident	症状	文档	回归测试
I-01	脚本报 0 篇但退出码 0	postmortem/01	fetch_repo_docs 的空结果断言
I-03	gpio 扁平导入被误判	postmortem/03	scripts/regress_symbol_false_positive.py
```

检查脚本验证：**每篇事故都有对应的回归测试，且那个测试存在**。
没有回归测试的事故文档，说明修复没有固化——那是文档在说谎。

## 6. 写作纪律（成文规则，写进 CONTRIBUTING）

| # | 规则 | 理由 |
| --- | --- | --- |
| 1 | **先说结论，再说理由** | 想扫一眼的人不该被逼着读三段 |
| 2 | **不用通用例子** | "假设你要做一个客服机器人"这类例子对本项目毫无价值，全部用 MaixCAM 的真实问题 |
| 3 | **每个论断标注性质** | `[本项目实测]` / `[厂商自测]` / `[推测]`，与 [05 附录](./05-调研与借鉴.md) 的证据分级一致 |
| 4 | **代码块必须能跑** | 不能跑的代码块要么标 `<!-- sketch -->` 并说明是伪代码，要么删掉 |
| 5 | **不复制 docstring** | 只给链接。重复是腐化的开始 |
| 6 | **失败案例与成功案例同等篇幅** | 只讲成功的教学会培养错误的乐观 |
| 7 | **一页一个想法** | 超过 300 行的页面，先问能不能拆 |
| 8 | **中文优先，术语保留英文** | 术语翻译会造成沟通成本；`embedding` 不译成"嵌入化"之类 |

**第 2 条值得单独强调**：教学文档最怕"通用化"。
一旦用"假设你在做电商客服"这种例子，读者就要做两次翻译（例子→自己场景），
而翻译过程正是理解流失的地方。本项目全部用 MaixCAM 的真实问题，
因为**这些问题是真实发生的**。

## 7. 分批交付计划

文档不能一次性写完——写完就跟不上代码，而且评审成本太高。

| 批次 | 交付 | 为什么这个顺序 |
| --- | --- | --- |
| **D1** ✅ | `docs/README.md` + `postmortem/` 六篇 + 症状索引 | **事故档案先行**：最稀缺，且不依赖其他文档 |
| **D2** | `concepts/` 九篇 + 每篇末尾的「这一章留下的问题」 | **概念层必须先于习题**：读者得先有概念，才答得出概念题 |
| **D3** | `exercises/`（问答题 + 答案）+ `README.md` | 依赖 D2 提的问题——**问题由概念文档提出，习题负责检验** |
| **D4** | `tutorial/` 01–07 + 章末复现题与改造题 | 主干，依赖 D2（概念）与 D1（事故素材） |
| **D5** | `evidence/` + `scripts/check_docs.py` | 把"数字可复现"做成机制，越早越好（见下方说明） |
| **D6** | `reference/` 四篇 + `CONTRIBUTING.md` | 收尾，reference 最易由代码生成 |

### 7.1 关于 D5 的位置（一个真实的取舍）

原计划把 `check_docs.py` 放在 D2，理由是"机制要先于正文"。
**重新想过之后，这里有个矛盾**：

- 放太早：还没有文档可检查，工具写完没东西验证；
- 放太晚：正文已经积了一批不一致，补检查时要回头改。

**折中方案**：D2、D3 写完时，`check_docs.py` **只做链接与引用检查**（那时已经
有 20+ 篇文档可查）；等 D4 的 tutorial 写完、数字大量出现时，
再加"数字新鲜度"检查。

> 这条取舍本身是个好例子：**工具与内容谁先，取决于"有多少内容可验证"**，
> 不是取决于"机制重要不重要"。机制当然重要，但一个空跑的机制
> 既不能发现问题，也不能证明自己有用。

### 7.2 为什么 `concepts/` 排在习题前面

因为**问答题的问法取决于概念文档的结构**。

举例：`concepts/03-检索-稀疏与稠密.md` 的末尾会提出三个问题，
而 `exercises/concepts/03-检索-稀疏与稠密.md` 就是那三个问题（加答案）。
如果先写习题，就要现编问题；先写概念，问题会**自然地从讲解里长出来**——
读者读完概念时想追问的那些点，就是最好的问答题。

**这正是"提问之后，自然而然就可以有问答题了"的工程实现。**

## 9. 一句话总结

> **这套文档的设计目标不是"讲清楚这个项目"，而是"让读者在自己项目里遇到同样问题时能想起这里"。**
>
> 所以它按**症状**组织入口、按**判断**组织内容、按**可复现**组织证据——
> 而这三件事，本项目恰好都有真实素材。
