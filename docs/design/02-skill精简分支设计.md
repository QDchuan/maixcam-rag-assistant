## 1. 这个分支存在的理由

主线项目（分支 A）要求读者自己设计并实现整个 AI 应用。但有一类用户的需求完全不同：

> "我不想设计 Agent，我只想让手边这个桌面 Agent 会用 MaixPy 文档。"

这就是**裁剪**：把主线里真正难以替代、且可以独立分发的那一小块——**语料 + 检索 + 使用规程**——打包成一个自包含的 Skill，装到任何支持该格式的桌面 Agent 上即可生效。

**这一分支的教学价值不在于"多一个交付形态"，而在于它把一个真实的工程约束摊开来讲：当你放弃了对自己 AI 应用的控制权，质量还剩下多少保证手段？**

## 2. 先确认格式：Agent Skills 的制度事实

设计前先核实了格式，以下为已验证的事实（来源见文末）：

### 2.1 最小契约

```
skill-name/
├── SKILL.md              # 必需
│   ├── YAML frontmatter  # name、description 必需
│   └── Markdown 正文     # 使用说明
└── 捆绑资源（可选）
    ├── scripts/          # 确定性/重复性任务的可执行代码
    ├── reference/        # 按需加载的补充文档
    └── assets/           # 模板、素材
```

最小可用示例（官方 template 原文）：

```markdown
---
name: template-skill
description: Replace with description of the skill and when Claude should use it.
---

# Insert instructions below
```

frontmatter 字段（约束为规范原文要求，不是约定俗成）：

| 字段 | 必需 | 约束 | 说明 |
| --- | --- | --- | --- |
| `name` | 是 | **≤ 64 字符**；仅小写字母、数字、连字符；首尾不能是连字符 | 技能标识符，也是目录名 |
| `description` | 是 | **≤ 1024 字符** | **触发机制本身**：既说做什么，也说什么时候用 |
| `license` | 否 | — | 许可声明 |
| `compatibility` | 否 | **≤ 500 字符** | 所需工具与依赖，很少用到 |
| `metadata` | 否 | 字符串映射 | 自定义元数据 |
| `allowed-tools` | 否 | — | **规范中标记为实验性**，本项目不使用 |

**`description` 的 1024 字符上限是一个硬约束，会直接影响设计。** 本项目的技能需要在描述里覆盖多类触发语境（设备名、库名、报错、例程……），必须在这个上限内把话说完。这本身就是一次真实的工程取舍：**触发覆盖度 vs 描述精度**。写超了不会被截断——技能直接不合规。

### 2.2 两条设计约定（官方明确写出，对本分支影响很大）

**约定一：`description` 承担全部触发判断，正文不承担。**

> "All 'when to use' info goes here, not in the body."

这意味着**可用性设计 = 写 description**。写不好 description，技能装上了也不会被触发。

**约定二：官方承认存在「欠触发」（undertrigger）倾向，建议描述写得"主动"一点。**

> "currently Claude has a tendency to 'undertrigger' skills... please make the skill descriptions a little bit 'pushy'"

这对本分支有直接后果：`description` 里必须把**用户会说的话**显式列出来（"MaixCAM"、"MaixPy"、"报错"、"例程"等），否则用户提了相关需求也不会触发技能。这是本项目可以量化验证的一个点（见第 6 节）。

**约定三：渐进式披露（progressive disclosure），共三个阶段。**

| 阶段 | 加载什么 | 对本项目的含义 |
| --- | --- | --- |
| **发现（Discovery）** | 启动时**只预加载**全部技能的 `name` + `description` | 这两行决定了技能会不会被用上；剩下的内容不占上下文 |
| **激活（Activation）** | 任务匹配后，读入**完整 SKILL.md** | 正文必须精简——它每次被激活都会占用上下文 |
| **执行（Execution）** | 按需读取 `references/` 下的文件、运行 `scripts/` 下的代码 | **140 多篇文档只能放在这一层**，由 Agent 按需取用 |

**这个三阶段模型直接决定本分支的目录设计**：SKILL.md 必须薄（只放触发描述与工作规程），语料与索引必须厚（放在被按需加载的位置）。把文档硬塞进 SKILL.md 会同时违反规范意图和上下文经济性。

**关于安装位置**：规范规定了技能目录的发现规则，Claude Code 支持个人级（`~/.claude/skills/<name>/`）、项目级（`.claude/skills/<name>/`，可随仓库提交）、以及插件与托管配置等多种来源，并存在优先级。对本项目的影响是：**技能目录必须能整体移动**——不能依赖绝对路径、不能在安装时写死位置。`scripts/` 里的脚本要能通过环境变量或相对定位找到 `index/`，这样用户放到任何位置都能用。这是"可分发"与"能跑起来"之间的一个小但真实的工程要求。

## 3. 核心设计张力

这条分支的全部设计由此展开：

| | 分支 A（主线） | 分支 B（Skill） |
| --- | --- | --- |
| 检索策略 | 我决定 | **宿主 Agent 决定** |
| 引用强制 | 代码校验 | 只能靠规程劝说 |
| 符号校验 | 程序拦截 | 只能提示 Agent 自查 |
| 拒答策略 | 阈值触发 | 只能明确要求 |
| 可移植性 | 低（要部署） | **高（放到目录里就行）** |
| 质量下限 | 可保证 | **不可保证** |

**一句话概括：分支 B 用质量的确定性，换了可移植性。**

教学上必须诚实地说出这一点，而不是把它包装成"轻量版主线、效果一样"。真实的工程世界里，这种取舍无处不在。

那么剩下的问题就是：**在放弃了控制权之后，还有哪些杠杆可以拉高质量下限？** 这就是下面三层的设计目标。

---

## 4. 三层杠杆（按"对宿主 Agent 的要求"从低到高排列）

### 第一层：语料结构（零运行时代码，对任何支持该格式的 Agent 都生效）

这是**最重要的一层**，因为它不依赖宿主 Agent 的任何特殊能力——只要它能读文件就能受益。

| 手段 | 做法 | 为什么有效 |
| --- | --- | --- |
| **知识层物理分离** | `docs/tutorial/` 与 `docs/api/` 分目录存放 | 教程与 API 参考混在一起会互相干扰；物理分离让 Agent 的文件浏览与 grep 天然按层定位 |
| **命名带语义** | `docs/api/maix.image.md`、`docs/tutorial/vision__yolov5.md` | 让 Agent 仅凭文件名就能判断该不该读 |
| **每页加元信息头** | 页面顶部固定格式的 YAML 头：模块、类型、官方链接、最后核对日期 | 给 Agent 提供"这是什么、权威性如何、去哪核对" |
| **提供地图** | `reference/doc_map.md`：按模块列出全部页面 + 一句话摘要 | **渐进式披露的入口**。Agent 先读地图再定位，而不是盲目 glob |
| **保留官方章节归属** | 从官方 sidebar 提取的章节路径写进元信息头 | 复用官方自己的知识组织，免费获得强先验 |

**"提供地图"是本层最关键的一招。** 它把"140 个文件"变成"一个可导航的目录"，这直接契合 Agent 的阅读习惯：先看索引，再按需深入。它也让渐进式披露真正可用。

### 第二层：预构建索引 + 检索脚本（要求宿主 Agent 能执行命令）

语料躺在那儿，Agent 未必能找到——它可能用 grep，对中文和语义召回都很弱。

因此随包提供一个**预构建索引 + 一个极简检索脚本**：

```
scripts/
├── search.py        # 检索入口：一条命令返回排序后的片段
├── lookup_api.py    # 精确查符号签名（确定性查表，不走向量）
└── README.md        # 怎么调、参数是什么
index/
├── chunks.jsonl     # 切分结果（复用主线 L2 产物）
├── bm25.pkl         # 稀疏索引
├── vectors.npy      # 稠密向量（可选，见下）
└── meta.json        # 语料版本、模型、切分参数指纹
```

设计要点：

1. **索引是预构建的，不是运行时建的。** 用户装 Skill 不该等索引构建，更不该为了检索去配 API Key。这决定了嵌入向量的获取方式（见下）。
2. **`lookup_api.py` 是关键工具。** 对"这个函数签名是什么"这类问题，一次精确查表远胜语义检索。它不需要任何模型，完全确定性，而且直接针对幻觉重灾区。
3. **向量索引作为可选增强。** 两种方案：
   - **方案甲（推荐默认）**：随包分发预计算的向量，或用一个无需 Key 的本地小嵌入模型。**零配置**是第一优先级。
   - **方案乙**：若用户自己配了嵌入接口，则走远端嵌入。质量更好，但要配置。
   分支 B 的默认必须是方案甲——**"零配置可用"是这个分支存在的意义**。若要配置 Key，用户不如直接用分支 A。
4. **`meta.json` 记录语料指纹**，脚本启动时自检。语料与索引不匹配就明确报错，而不是给出错误结果。

### 第三层：规程（写进 SKILL.md 的"使用纪律"）

分支 A 里由代码强制执行的约束，在这里只能靠**自然语言规程**。这是本分支最需要教学解释的部分。

SKILL.md 正文要包含的规程（示意结构）：

```markdown
## 回答 MaixPy 问题的工作流程

1. 先判断问题类型：
   - 问某个函数/参数的用法 → 属于"签名类"，**必须先跑 lookup_api.py**
   - 问怎么实现某功能 → 属于"概念类"，检索教程层
   - 要一段能跑的代码 → 属于"示例类"，优先找现成例程

2. 检索资料。用 scripts/search.py；若结果为空，换关键词再试一次。

3. **写代码前必须核对符号。** 代码中用到的每个 maix.* 符号，
   都要在 reference/api_roster.md 里存在。**不确定的一律不用，
   宁可告诉用户"文档中没有这个 API"。**

4. 回答必须标出处（页面路径），便于用户核对。

5. **资料没覆盖的，直接说没有。** 不要根据其他框架（OpenCV、
   Raspberry Pi、K210 时代的 MaixPy v1）的习惯去猜 MaixPy 的 API。
```

三条比正文更隐蔽、但同样重要的设计：

| 设计 | 说明 |
| --- | --- |
| **把"不该做什么"写具体** | "不要照搬 OpenCV 习惯"比"不要编造 API"有效得多——前者可执行，后者是口号 |
| **给承认无知一个出口** | 第 5 条明确授权 Agent 说"文档没覆盖"。这在分支 A 里是代码里的 `refused` 字段，在这里只能靠措辞 |
| **给判断提供决策树** | 让 Agent 按问题类型选语料层，是把分支 A 的"查询路由"降级成文字规程 |

**规程的表达方式要"可执行"，不要"讲道理"。** 例如：

- ❌ "请确保引用准确"——无法执行
- ✅ "每个 `maix.*` 符号必须能在 `reference/api_roster.md` 中检索到"——可执行、可自查

---

### 额外层（可选）：MCP 形态

如果宿主要求更强的能力边界，同一份资产还能以 MCP server 形态提供（把 `search.py` / `lookup_api.py` 包装成工具）。

**本轮不设计，仅在文档里指出存在这条路径**，避免范围蔓延。并且要在教学上说明：MCP 会重新引入"要配置、要运行服务"的成本，与"零配置"这一分支初衷相冲突——所以它是可选项，不是默认。

## 5. 目录结构（最终形态）

```
skill/maixcam-maixpy/
├── SKILL.md                      # 触发描述 + 使用规程（精简，遵守渐进式披露）
├── reference/
│   ├── doc_map.md                # 语料地图：模块 → 页面 → 一句话摘要
│   ├── api_roster.md             # 全部 API 符号白名单（自查用）
│   ├── common_pitfalls.md        # 常见错误与版本差异（高频幻觉点）
│   └── version.md                # 语料版本、覆盖范围、已知缺口
├── docs/
│   ├── tutorial/                 # 中文教程 Markdown（整理后，带元信息头）
│   └── api/                      # API 参考（整理后，带签名）
├── scripts/
│   ├── search.py
│   ├── lookup_api.py
│   └── README.md
└── index/
    ├── chunks.jsonl
    ├── bm25.pkl
    ├── vectors.npy               # 可选
    └── meta.json
```

**`docs/` 是流水线生成的，不是手写的。** 这一点很重要：它保证分支 B 与分支 A 共用同一份语料管线，语料修一次两边都受益，也避免了"文档两处维护、慢慢分叉"这一最常见的腐化方式。

## 6. 怎么评（与主线的评测差异）

分支 B 无法测检索策略（不由我们决定），所以评测范式必须变。详见 [03 文档第 10 节](./03-评测与质量提升路线.md)。要点：

| 能测 | 怎么测 |
| --- | --- |
| **触发准确率** | 构造一批"应该触发"和"不该触发"的提示词，看 Skill 是否被加载。**这是本分支特有且必须测的指标**，直接对应官方说的 undertrigger 问题 |
| **语料检索质量** | 复用主线的检索轴评测器直接测 `index/`（这部分完全可控） |
| **端到端胜负率** | 同一批问题，在宿主 Agent 上对比「无 Skill」/「基础版」/「增强版」三套，做**成对比较**并交换顺序消除位置偏差 |

**"触发准确率"值得单列。** 它是分支 B 最容易失败的地方，也是最容易被忽视的地方：技能做得再好，没被触发就等于不存在。官方文档承认了欠触发倾向并建议 description 写"主动"，本项目正好可以量化验证这条建议是否真的有效——这是一个很漂亮的教学实验。

## 7. 主动放弃了什么（必须明说）

诚实是这一分支教学价值的一部分。对照分支 A：

| 能力 | 分支 A | 分支 B | 后果 |
| --- | --- | --- | --- |
| 查询路由 | 代码实现 | ❌ 只能靠规程引导 | 复杂问法可能检索不到正确知识层 |
| 混合检索 | 代码实现 | ⚠️ 索引里有，但用不用由 Agent 决定 | Agent 可能根本不去调 `search.py` |
| 重排序 | 可配置 | ❌ | 排序质量下降 |
| 引用校验 | 程序强制 | ❌ 只能"要求" | 引用可能缺失或错误 |
| 符号白名单拦截 | **第一级校验，可阻断** | ⚠️ 降级为 Agent 自查 | **幻觉无法被拦截，只能被降低概率** |
| 签名/参数校验 | 第二级校验 | ❌ | 参数用错无法被发现 |
| 真实执行验证 | 第三级校验（可选） | ❌ | — |
| 拒答 | 阈值触发 | ❌ 只能"要求" | 可能硬答 |
| 消融评测 | 完整 | ❌ | 无法自己调优 |
| 零配置可用 | ❌ 要部署 | ✅ | — |
| 跨宿主可移植 | ❌ | ✅ | — |

**最值得讲的一行是第一级校验（符号白名单）。** 在分支 A 里，一个新出现的、不存在的 API 会被程序拦下来；在分支 B 里，最好的结果也只是"Agent 读了白名单后决定不用它"。**从"拦截"到"降低概率"，这是控制权转移带来的质变**，而不是量变。

教学结论：**Agent Skills 这类分发形态的价值在于覆盖面和零门槛，不在于质量上限。** 如果一个场景对正确性要求极高（比如生成要直接烧进设备运行的代码），该上的还是分支 A。

## 8. 与主线共用什么

| 共用 | 说明 |
| --- | --- |
| **语料管线（L1 + L2）** | 完全共用。分支 B 的 `docs/` 是管线的一个输出目标 |
| **索引格式（L3）** | 共用，只是打包分发而非本地构建 |
| **API roster** | 共用。分支 A 用于代码拦截，分支 B 用于 Agent 自查 |
| **评测集** | 共用。分支 B 的语料质量评测直接复用 |
| **切分参数** | 共用 |

**这套共用关系本身就是一个教学点**：一个系统里真正值得沉淀、值得打包分发的资产，是**语料与其索引**，而不是编排代码。编排代码换一种宿主形态就得重写，而语料是可以复用的。

## 9. 未决问题（需评审确认）

| # | 问题 | 说明 |
| --- | --- | --- |
| 1 | **语料分发是否合规** | 与 [01 文档第 10 节](./01-系统架构设计.md) 同一个问题。**仓库侧已明确**：`sipeed/MaixPy` 为 Apache 2.0，教程语料可分发（保留版权声明、标注修改、附许可文本）。**站点侧 API 语料仍需确认**，本分支对它更敏感——因为它涉及再分发。选项：只分发脚本由用户自行生成 / 分发整理后的语料并附许可与出处 / 只存链接 |
| 2 | 包体积上限 | 教程约 130 篇 + 索引，需要实测；若超限则考虑分模块拆成多个 Skill |
| 3 | 是否需要预计算向量 | 取决于是否找到无需 Key 的可靠本地嵌入方案；找不到就只发 BM25 索引（对标识符类查询其实已经够用） |
| 4 | 英文语料是否一并分发 | 130 篇 en 文档体积翻倍，价值待确认 |
| 5 | 是否同时提供 MCP 形态 | 建议本轮不做，仅留口子 |
