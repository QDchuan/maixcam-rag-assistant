## 1. 架构目标与设计原则

### 1.1 目标

一套代码同时满足两个约束：

- **能跑**：真实可用，回答 MaixPy 问题并给出可运行代码；
- **能教**：每一层的内部机制对读者可见、可替换、可测量。

### 1.2 六条设计原则

| 原则 | 含义 | 具体做法 |
| --- | --- | --- |
| **不藏魔法** | 核心链路自己实现，不用重型框架封装 | 检索、融合、提示词组装、Agent 循环全部自写；只在解析、分词、HTTP 等外围用库 |
| **评测先行** | 先有量尺，再有优化 | 评测集与评测器是第一批交付物，早于任何检索优化 |
| **两条轴分离** | 检索失败与生成失败分开测量 | 指标按轴组织，报告并列展示 |
| **可配置化消融** | 每种技术是开关，不是散落的硬编码 | 一个实验配置对象描述一整条链路 |
| **失败显式** | 不静默降级、不吞异常 | 语料差异、空检索、校验失败都要产出可见的结构化事件 |
| **版本可复现** | 语料与索引都记录来源版本 | 语料固定 commit；索引元数据记录语料指纹 |

### 1.3 为什么不用框架编排

教学项目的核心矛盾是"开箱即用"和"看得见内部"的取舍。本项目选择**看得见**：

- 读者能读到一个 200 行的检索实现，而不是一个 `VectorStoreIndex.from_documents()`；
- 消融实验可以精确到"融合算法换掉"这一层，框架往往把这一层锁死；
- 出现质量问题时，能定位到具体环节，而不是"框架里某个环节"。

代价是要自己写更多代码。本项目的判断是：**这些代码正是要教的内容本身**，不是额外负担。

## 2. 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│  L7 接入层        CLI  ·  本地 API 服务                        │
├──────────────────────────────────────────────────────────────┤
│  L6 Agent 层      工具集 · 决策循环 · 预算与终止 · 失败恢复     │
├──────────────────────────────────────────────────────────────┤
│  L5 生成层        提示词组装 · 引用约束 · 拒答 · 输出校验       │
├──────────────────────────────────────────────────────────────┤
│  L4 检索层        查询分析 · 稠密/稀疏检索 · 融合 · 重排序      │
├──────────────────────────────────────────────────────────────┤
│  L3 索引层        向量索引 · BM25 索引 · 元数据过滤 · 持久化    │
├──────────────────────────────────────────────────────────────┤
│  L2 语料处理层    文档模型 · 切分 · 元数据标注 · 代码/签名抽取  │
├──────────────────────────────────────────────────────────────┤
│  L1 语料获取层    Markdown 快照 · API 页抓取 · 版本固定 · 差异报告│
├──────────────────────────────────────────────────────────────┤
│  L0 基础设施      配置 · 模型客户端 · 缓存 · 日志 · 评测器      │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向严格向下**。上层不直接访问模型客户端或文件系统，必须经过下层的抽象。这样做的直接好处是：消融实验可以在任意一层替换实现，而不牵动其他层。

**横切关注点：评测（L0）。** 评测器不是最上层，而是基础设施层。它必须能被任意一层调用（例如单独测检索器），这也是"两条轴分离"在架构上的体现。

## 3. 核心数据模型

整个系统的数据契约只有四个对象。把它们定清楚，后面每一层都只是这四个对象之间的变换。

### 3.1 `Doc` —— 一篇文档

```python
@dataclass(frozen=True)
class Doc:
    doc_id: str            # 稳定 ID，如 "zh/vision/yolov5"
    source: str            # "repo" | "api"
    kind: str              # "tutorial" | "api_ref"
    module: str            # 粗粒度模块，如 "vision" / "peripheral" / "mllm"
    title: str             # 页面标题
    url: str               # 可点的官方地址
    version: str           # 语料版本（commit 或 tag）
    chapters: list[str]    # 来自侧边栏的章节路径，如 ["AI 视觉", "YOLO 物体检测"]
    raw: str               # 清洗后的正文
```

`chapters` 字段值得强调：它来自官方侧边栏，是**官方自己的知识组织方式**。把官方分类直接变成检索元数据，是成本极低、收益明显的做法——因为它免费提供了"这个概念属于哪个板块"的先验。

### 3.2 `Chunk` —— 一个可检索单元

```python
@dataclass(frozen=True)
class Chunk:
    chunk_id: str
    doc_id: str
    text: str              # 用于嵌入与展示的正文
    heading_path: list[str]  # ["YOLO 物体检测", "准备模型"]
    kind: str              # "prose" | "code" | "signature" | "table"
    parent_id: str | None  # 父章节 chunk（用于父文档回填）
    ordinal: int           # 在文档内的顺序
    meta: dict             # 继承自 Doc 的 module/chapters/version/url
```

**`heading_path` 是设计里最关键的一个字段。** 它同时解决三个问题：

1. **语境丢失**：一个 200 字的片段脱离标题就没有意义。检索时把标题路径拼在正文前面一起嵌入，命中率显著改善（L7 会单独量化这一步的贡献）。
2. **可解释性**：答案里能说清"依据来自《YOLO 物体检测》的『准备模型』一节"，比给一个文件路径有用得多。
3. **加权**：标题命中可以作为排序特征，这是免费的信号。

**`kind` 字段支撑"结构感知检索"。** 教程页的散文、可运行代码、API 签名，是三类不同的东西，混在一起检索会互相干扰。分开存、分开召回、按问题类型加权，是 L4 的核心手段。

### 3.3 `RetrievalResult` —— 检索结果

```python
@dataclass(frozen=True)
class RetrievalHit:
    chunk: Chunk
    score: float
    rank: int
    retriever: str         # "dense" | "bm25" | "fused" | "reranked"
    scores_by_stage: dict  # 各阶段分数，用于调试与教学展示
```

`scores_by_stage` 是为教学加的：读者能亲眼看到"一个片段在稠密检索排第 30，稀疏检索排第 2，融合后排第 1"，这比任何文字解释都直观。

### 3.4 `Answer` —— 最终答案

```python
@dataclass(frozen=True)
class Answer:
    text: str
    citations: list[Citation]      # 结构化引用，不是正文里的字符串
    refused: bool                  # 是否明确拒答
    refusal_reason: str | None
    verification: VerificationReport  # 校验结果
    usage: Usage                   # token / 耗时 / 成本
    trace: list[Event]             # 完整执行轨迹
```

`refused` 是一个一等字段，不是靠文本里有没有"我不知道"来猜。**拒答是一种正常输出，不是异常**，这个建模选择会影响整个系统的错误处理风格。

## 4. 各层详细设计

### 4.1 L1 语料获取层

#### 4.1.1 两条获取通道

| 通道 | 目标 | 方式 | 输出 |
| --- | --- | --- | --- |
| 仓库通道 | 中文教程 Markdown | 固定版本下载仓库快照，取 `docs/doc/zh/` | `corpus/raw/repo/` |
| 站点通道 | API 参考（31 个顶层模块 + 子模块，共 55 页正文） | 按 `sitemap.xml` 枚举后抓取 | `corpus/raw/api/` |

**版本固定策略**

- 仓库通道：默认固定到 tag（当前为 `v4.12.5`），并在清单里同时记录 commit 与抓取时间。用 tag 而不是分支，因为分支会漂移。
- 站点通道：站点无法固定版本，因此**必须记录抓取时间与页面内容哈希**，并允许与上一次抓取做 diff。
- 允许配置为"跟随最新"，但会打印显著警告并在索引元数据里标记为 `unpinned`。教学上要让读者意识到这是一个真实的风险取舍。

**为什么必须离线缓存。** 语料抓一次就落盘，后续所有处理只读本地。理由有三个：可复现（评测结果不会因为上游文档改了而漂移）、可离线（教学环境可能没网）、可 diff（能看出上游改了什么）。

#### 4.1.2 差异报告（必须有）

勘察已确认文档站与仓库之间存在漂移（存在站点有、仓库无的页面，也存在拼写不同的页面名）。管线**必须**产出 `corpus/reports/diff.md`，显式列出：

- 站点有、仓库无的页面；
- 仓库有、站点无的页面；
- 同名但内容哈希不同的页面。

不静默丢弃任何页面。这是教学点：**语料对齐是要主动做的工程动作。**

> **一个已实际发生的教训（写进教学正文）**：实现语料体积测量脚本时，因为把 `git/trees/<sha>?recursive=1` 返回的 `path`（**相对于子树根**，根目录文件不带前缀）误当成仓库全路径来过滤，脚本**安静地报告了"0 篇、0 字节"**，退出码仍是 0。没有异常、没有警告——如果没人核对数字，这个结果会被当成"语料为空"。
>
> 事后在脚本里加了防御：**空结果必须显式失败**（非零退出码 + 明确错误信息），而不是安静地返回 0。
>
> 这是"失败显式"这条设计原则的由来，也是很好的教学案例：**静默的空结果比抛异常危险得多。** 一个 RAG 系统如果检索不到内容却照常生成答案，用户拿到的就是一个自信的错误答案——这和"脚本报告 0 篇"是同一种病。

#### 4.1.3 API 语料的抽取

API 参考页是结构化 HTML，需要从里面抽出：

- 模块名与模块简述；
- 类/函数名；
- Python 签名（页面里有 `py_def`，来自构建时的 stub 解析）——这是**最精确的签名来源**；
- 参数表、返回值、异常。

产物是 `corpus/processed/api_signatures.jsonl`，每行一个符号。同时汇总出一份**符号白名单（API roster）**，供 L5 的幻觉校验使用。

> 教学提示：这份白名单是本项目"防幻觉"能力的物理基础。没有它，"代码里的 API 必须存在"就只能靠模型自觉。它也从侧面说明了为什么 API 语料值得单独工程化。

### 4.2 L2 语料处理层

#### 4.2.1 文档解析

用 AST 级解析（`markdown-it-py`）而不是正则。要正确处理：

| 元素 | 处理方式 |
| --- | --- |
| 标题 | 构建 `heading_path`，同时决定切分边界 |
| 围栏代码块 | 独立成 `kind="code"` 的 chunk，保留语言标记 |
| 表格 | 独立成 `kind="table"`，**不切开**（切开的表格对模型毫无价值） |
| 图片 | 记录 alt 与路径，正文中替换为占位说明，不参与检索 |
| 相对链接 | 解析成绝对 URL，既用于引用，也用于构建文档间关系 |
| 提示块 / 注意块 | 保留标记，这类内容常包含"坑"，检索价值高 |

#### 4.2.2 切分策略

采用**两级切分**，而非固定长度：

1. **第一级：按标题结构切。** 每个标题段是一个候选 chunk。这一步保证语义完整。
2. **第二级：对超出预算的段再切。** 按段落边界切，并保留重叠；**代码块与表格不参与二次切分**。

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `max_tokens` | 500 | 单 chunk 上限 |
| `min_tokens` | 80 | 低于此值的段与相邻兄弟段合并，避免碎片 |
| `overlap_tokens` | 80 | 二次切分时的重叠 |

**切分粒度必须由评测决定，不能凭感觉。** 因此切分器暴露 `strategy` 参数，L2 的消融实验会给出"定长 256 / 定长 512 / 标题感知"的对照数据。

#### 4.2.2.1 为什么不做"语义切分"

有一种流行做法是**语义切分**：用嵌入相似度找语义边界，在相似度骤降处切开。本项目**不采用**，理由要讲清楚，否则读者会以为是遗漏：

| | 标题感知切分（本项目） | 语义切分 |
| --- | --- | --- |
| 依据 | 文档自身的结构（免费、确定） | 嵌入相似度的相对变化（要算、有噪声） |
| 成本 | 零额外调用 | 每篇文档一遍嵌入计算 |
| 依据强度 | 结构是作者给的，可靠 | 公开研究显示**增益不稳定，与计算成本不相称** |
| 可解释性 | 边界就是标题，读者能核对 | 边界是阈值产物，难解释 |

关键差别在于：**技术文档的语义边界，作者已经用标题标出来了。** 放着作者给的、免费且确定的信号不用，去花算力猜一个可能更差的边界，是没有道理的。这条结论对学生文档（如论文、手册）尤其成立。

本项目把它作为**对照项**保留在配置里，让读者自己跑出"多花的钱没换来增益"这个结论——这比直接告诉他们更有说服力。

#### 4.2.3 语境头（Contextual Header）

每个 chunk 在喂给嵌入模型时，实际嵌入的不是 `text`，而是：

```
[文档] MaixPy / AI 视觉 / YOLO 物体检测
[章节] 准备模型
[类型] 教程
---
<正文>
```

这个头**只用于嵌入与召回**，展示给用户和模型时另行裁剪，避免污染答案。L7 会量化这一步的独立贡献——在小规模技术语料上，它通常是性价比最高的一招，因为它几乎不增加成本。

#### 4.2.4 代码资产单独抽取

教程里的代码块是可运行的示例，是最有价值的资产。处理方式：

- 每个代码块成为独立 chunk，带 `kind="code"`；
- 同时抽成一个可检索的 `examples` 集合，并尽力提取出它所演示的 API 符号（用白名单做符号匹配）；
- 保留其所在章节的 `heading_path` 与前后各一段说明文字作为语境。

这样"想找一段用摄像头拍照的示例代码"这类需求可以走精确的示例检索，而不是跟散文一起混检。

### 4.3 L3 索引层

设计上刻意选择**最简单、最透明的实现**，因为教学目标是让人看懂。

| 索引 | 实现 | 理由 |
| --- | --- | --- |
| 稠密 | NumPy 矩阵 + 归一化向量的内积 | 语料约数千个 chunk，暴力检索毫秒级；不需要 ANN 库，且矩阵运算完全透明 |
| 稀疏 | BM25（`rank_bm25` 或自写） | 算法短小、可读，是教学重点 |
| 元数据 | 内存字典 + 持久化 JSONL | 支持 `module` / `kind` / `version` 过滤 |

**关于中文与标识符的分词——这是本场景特有的关键细节。**

中文需要分词（`jieba`），但 MaixPy 的查询里混着大量英文标识符，分词器会把它们切碎：

```
"maix.image.Image 怎么转灰度"
    ✗ 被切成 maix / image / Image / 怎么 / 转 / 灰度
    ✓ 应该保留 maix.image.Image 作为一个整体
```

处理方案（BM25 索引同时建两个字段，检索时都匹配）：

1. 用 `jieba` 对中文部分分词；
2. 用正则单独抽取 `[A-Za-z_][A-Za-z0-9_.]*` 形式的标识符，**作为不可分割的 token**；
3. 把 `maix.image.Image` 这类点分标识符额外生成其末段（`Image`）作为一个弱 token，提高模糊命中率；
4. 为 `jieba` 挂自定义词典，把高频 MaixPy 术语（`MaixCAM`、`YOLO`、`AprilTag`、`MaixVision` 等）注册为词。

**这是"场景决定 RAG 质量"的一个典型例子**：通用的中文分词方案在这个场景下会直接损失掉最重要的一类查询信号。

**索引元数据**记录：语料 commit / 抓取时间 / 嵌入模型名与版本 / 切分参数 / chunk 总数。索引与配置不匹配时必须报错，而不是给出静默错误的结果。

### 4.4 L4 检索层

这是质量提升的主战场，也是消融实验的主要对象。

#### 4.4.1 查询分析

在检索之前，先给查询分类并抽取结构：

```python
@dataclass
class QueryPlan:
    raw: str
    normalized: str
    qtype: str                # "concept" | "signature" | "example" | "troubleshoot"
    identifiers: list[str]    # 抽出的 API 符号
    filters: dict             # 推断的元数据过滤条件
    retrievers: list[str]     # 本次要启用的检索器
    weights: dict             # 各检索器与各 kind 的权重
```

分类规则**先用手写规则**（简单、可解释、够用），并保留一个"可选模型分类"的开关供对比。教学上要强调：**能用规则解决的就不要上模型**，因为规则可调试、零延迟、零成本。

不同 `qtype` 对应不同策略：

| qtype | 例子 | 策略 |
| --- | --- | --- |
| `concept` | "怎么找色块" | 偏教程语料，偏散文 chunk |
| `signature` | "`find_blobs` 的参数有哪些" | **强制召回 API 签名语料** |
| `example` | "给我一段摄像头拍照的示例" | 偏代码 chunk |
| `troubleshoot` | "报错找不到摄像头" | 偏 FAQ / 教程，召回面放宽 |

#### 4.4.2 检索器

统一接口，便于替换与组合：

```python
class Retriever(Protocol):
    name: str
    def retrieve(self, plan: QueryPlan, k: int) -> list[RetrievalHit]: ...
```

已规划的检索器：`DenseRetriever`、`BM25Retriever`、`MetadataRetriever`（按过滤器直取）、`ParentExpander`（父文档回填包装器）、`Reranker`（精排包装器）。

包装器模式让"父文档回填"和"重排序"成为可插拔装饰器，消融时只需改配置。

#### 4.4.3 融合

默认用 **RRF（Reciprocal Rank Fusion）**：

```
score(d) = Σ_r  w_r / (k + rank_r(d))
```

选 RRF 的理由：它只用排名、不用原始分数，因此**不需要处理不同检索器分数量纲不一致的问题**。这是工程上最省事且稳健的选择。同时保留加权分数融合作为对比选项，教学上用来展示"量纲归一化"这个坑。

#### 4.4.4 重排序

两档实现，供对比：

- **Cross-encoder**：精度好、延迟可控，但要引入本地模型依赖；
- **LLM 重排**：直接用已配置的对话模型打分，零额外依赖，但慢且贵。

默认关闭重排序。**它在 L6 才被打开**，并被要求给出"增益 vs 延迟"曲线——这是本项目的教学立场：不默认推荐任何技术。

### 4.5 L5 生成层

#### 4.5.1 提示词结构

上下文以**带编号的结构化块**给出，而非拼接成一大段文本：

```
[1] 来源：MaixPy 文档 / AI 视觉 / YOLO 物体检测 (https://...)
    章节：准备模型
    正文：...

[2] 来源：MaixPy API / maix.image
    签名：find_blobs(thresholds, roi=None, x_stride=2, ...) -> list
    正文：...
```

编号是**引用机制的载体**：模型被要求用 `[1]` 形式标注依据，从而使引用可被程序校验，而不是靠事后字符串匹配。

#### 4.5.2 结构化输出

要求模型返回 JSON（OpenAI 兼容接口的 `response_format`）：

```json
{
  "answer": "……",
  "citations": [1, 3],
  "confidence": "high",
  "unsupported": ["这部分资料未覆盖"]
}
```

`unsupported` 字段是刻意设计的：**给模型一个"承认资料不足"的正式出口**。经验上，模型编造内容常常是因为没有被提供一个体面的方式说"我不知道"。

#### 4.5.3 输出校验（`VerificationReport`）

采用**三级校验阶梯**，从最便宜、最确定的一级开始。这个阶梯的用意是：**能用程序判的绝不交给模型，能在本地判的绝不上设备。**

| 级别 | 校验 | 成本 | 能抓住什么 |
| --- | --- | --- | --- |
| **第一级** | AST 解析 + 符号存在性（对照检索到的上下文与 API roster） | 零成本、纯本地、完全确定 | **主要的幻觉类型**：编造不存在的 API、写错函数名 |
| **第二级** | 签名/参数校验（对照抽取出的 API 签名：参数名、个数、顺序） | 零成本、纯本地 | 函数存在但用法错误——参数名对不上、漏传必填项 |
| **第三级** | 真实执行（真机，或在电脑上用 mock 的 `maix` shim 跑一遍） | 高成本、需环境 | 逻辑错误、运行时才暴露的问题 |

分级的意义在于**投入产出比**：第一级几乎零成本，却覆盖了本项目背景故事里的核心痛点（"写不出能用的代码"主要就是 API 编造）。第三级最有说服力，但 MaixPy 跑不到笔记本上，只有真机或精心构造的 shim 才能执行，所以它是可选的、最后的防线，而不是默认手段。

**第一级的具体做法**：从答案的代码块中抽出所有 `maix.*` 形态的符号，逐个查 API roster；不在名单里的，标记为幻觉嫌疑。这把"模型会不会瞎编"这个模糊问题，变成了一个确定的程序问题。

**三级的失败处理也不同**（逐级放宽）：

| 级别 | 检出后 | 理由 |
| --- | --- | --- |
| 第一级 | **阻断**并要求重修，仍失败则拒答 | 信号确定，误报率低 |
| 第二级 | 警告并在答案中标注 | 签名抽取可能有解析误差，不宜硬阻断 |
| 第三级 | 记录并可提示，不阻断 | 环境差异可能造成误报 |

第一级的失败处理见上表。与此并行的还有两项**可程序判定**的检查，同样零成本：

| 检查 | 做法 | 失败处理 |
| --- | --- | --- |
| **引用有效性** | 每个 `[n]` 是否指向真实存在的上下文块；是否有论断完全无引用 | 标出无依据的句子 |
| **拒答一致性** | 若检索为空但模型给了肯定回答，判为可疑 | 触发重试或降级为"资料不足" |

> **术语对齐（可选教学点）**：这套分类与 CodeHalu 提出的代码幻觉分类法（映射 / 命名 / 资源 / 逻辑四类，见 [05 附录](./05-调研与借鉴.md)）可以对应上。第一级主要抓**命名与映射**类幻觉，第二、三级才触及**资源与逻辑**类。想让读者建立更系统的认知时，可以引入这套术语；不想引入新概念时，本项目的三级阶梯已自成体系。**对本项目而言，分类法不是必需的，级别划分才是。**

#### 4.5.4 拒答策略

拒答触发条件（任一满足）：

- 检索结果为空，或最高分低于阈值；
- 校验发现全部论断都无引用支撑；
- 符号检查发现关键代码含不存在符号且重试后仍存在。

拒答时**仍然返回检索到的相关片段**，并说明"资料里没有直接答案，但以下是相关章节"。这比一句冷冰冰的"我不知道"有用得多，也是"好产品"与"安全阀"的区别。

### 4.6 L6 Agent 层

#### 4.6.1 从链到循环

链式版本（L1–L8）的决策是写死的：检索 → 拼提示词 → 生成。Agent 版把决策交给模型：

```python
@dataclass
class AgentState:
    messages: list[Message]
    budget: Budget              # 剩余轮次 / token / 工具调用次数
    evidence: list[RetrievalHit]
    events: list[Event]         # 结构化轨迹，用于评测与回放
    last_error: str | None
```

循环：

```
while not done and budget.remaining > 0:
    action = model.decide(state)      # 返回 工具调用 或 最终答案
    if action is tool_call:
        result = tools.run(action)    # 失败时把错误写进 state，而不是抛异常
        state.observe(result)
    else:
        return answer(action)
```

**`budget` 是一等公民。** 没有预算的 Agent 在生产里是事故。本项目把轮次、token、工具调用次数全部纳入预算，并用尽时走"降级为基于已有证据的答案"，而不是静默失败。

#### 4.6.2 工具设计

按 harness 的思路，工具要**粒度合适、描述准确、执行廉价**：

| 工具 | 用途 | 关键设计 |
| --- | --- | --- |
| `search_docs(query, filters?)` | 主检索入口 | 暴露 `qtype` 等过滤参数，让 Agent 能做定向检索 |
| `get_page(doc_id)` | 取整页 | 当片段不足以回答时，让 Agent 能读全文 |
| `lookup_api(symbol)` | 精确查符号签名 | **最便宜、最可靠的工具**；查到即权威 |
| `check_api_usage(code)` | 校验代码里的符号 | 把校验能力交给 Agent 自主调用 |
| `list_module(module)` | 列模块成员 | 帮助 Agent 在不确定时先探索 |

`lookup_api` 值得单独讲：对"这个函数签名是什么"这类问题，**一次精确查表胜过一整轮向量检索**。它体现了 Agent 设计的核心判断——**能用确定性工具解决的，不要交给概率性检索**。

#### 4.6.3 失败恢复

| 失败 | 处理 |
| --- | --- |
| 检索空结果 | 提示 Agent 改写查询或扩大范围；记录一次事件 |
| 工具报错 | 错误作为观察结果回灌，不中断循环；连续同类错误 3 次则中止 |
| 超出预算 | 用已有证据生成"部分答案"，并显式说明未完成的部分 |
| 校验失败 | 允许一次自修机会；仍失败则降级为拒答 |

#### 4.6.4 可回放性

所有 `Event` 结构化落盘，支持：

- **回放**：用同一轨迹复现一次运行，用于调试与教学演示；
- **评测**：Agent 的评测必须能看轨迹，否则无法解释"为什么这次成功了"。

### 4.7 L7 接入层

| 形态 | 用途 |
| --- | --- |
| **CLI** | 主要教学交互形态。子命令见下表 |
| **本地 API 服务** | 最小可用服务化示例；也是 Skill 分支可选的后端 |
| **对比报告** | 消融实验的产出，Markdown 表格 |

CLI 命令规划：

```
maixrag corpus build      # 抓取 + 解析 + 切分 + 产出差异报告
maixrag index build       # 建向量与 BM25 索引
maixrag ask "..."         # 单次问答
maixrag agent "..."       # Agent 模式问答（带轨迹）
maixrag eval --config X   # 跑评测
maixrag ablate --configs A,B,C   # 批量跑配置，产出对比表
```

## 5. 配置设计

**一个配置对象描述一整条链路**，这是消融实验能够机械化的前提。

```yaml
corpus:
  version: "v4.12.5"
  sources: [repo, api]
  pin: true

chunking:
  strategy: heading        # fixed | heading
  max_tokens: 500
  min_tokens: 80
  overlap_tokens: 80
  contextual_header: true  # L7 开关

index:
  embedding:
    provider: openai_compatible
    base_url: ${EMBED_BASE_URL}
    model: ${EMBED_MODEL}
  sparse:
    enabled: true
    tokenizer: zh_identifier

retrieval:
  retrievers: [dense, bm25]
  fusion: rrf
  top_k: 20
  rerank:
    enabled: false
    backend: cross_encoder

generation:
  model: ${CHAT_MODEL}
  citation_required: true
  symbol_check: true
  refuse_threshold: 0.35

agent:
  enabled: false
  max_turns: 6
  tools: [search_docs, lookup_api, check_api_usage, get_page]
```

约定：**每一级消融 = 一份配置**。`configs/full_context_baseline.yaml`、`configs/l1_baseline.yaml` 到 `configs/l9_agent.yaml` 是可执行的教学大纲——读者跑一遍配置序列，就复现了整条能力阶梯。这可能是整个项目最优雅的一处设计。

`full_context_baseline.yaml` 与其余配置在结构上有一处本质差异，值得单独指出：

```yaml
# configs/full_context_baseline.yaml —— 不做检索
retrieval:
  mode: none          # 关键开关：整条检索层被旁路
generation:
  context_strategy: full_corpus   # 语料全文注入
  prompt_cache: true              # 配合 prompt caching 控制成本
```

**它需要 `retrieval.mode: none` 这个开关，而不是"top_k 设得很大"。** 这个区别很重要：前者表达的是"我们决定不检索"，后者是"我们检索了但取得很多"——在报告里这两者必须能被区分开，否则数据无法解读。

## 7. 基础设施（L0）

| 组件 | 设计 | 教学要点 |
| --- | --- | --- |
| **配置** | 单一配置对象 + 环境变量插值 + 显式校验 | 配置错误要早失败，且报错要指出是哪个字段 |

| **缓存** | 以 `hash(模型名 + 输入)` 为键的磁盘缓存 | 评测要重复跑很多次；没有缓存，评测成本会劝退 |
| **日志与轨迹** | 结构化 JSON 事件流 | 可回放、可统计，是调试 Agent 的唯一现实手段 |
| **密钥** | 只从环境变量读，永不写入配置或日志 | 顺带教一个安全习惯 |
| **可观测** | 每次问答记录：检索耗时、召回数、token、成本、是否拒答 | 这组数据是消融表的数据来源 |

## 8. 关键工程决策与取舍

把重要取舍摊开写，本身就是教学内容。

| 决策 | 选择 | 放弃 | 理由 |
| --- | --- | --- | --- |
| 检索实现 | 自写 + NumPy 暴力检索 | ANN 库（FAISS 等） | 语料小，暴力够快；透明的实现更有教学价值 |
| 编排 | 自写 Agent 循环 | LangChain / LlamaIndex | 需要精确控制每一层以做消融 |
| 嵌入 | OpenAI 兼容接口 + 可选本地模型 | 绑定单一厂商 | OpenAI 兼容是事实标准，切换成本最低 |
| 向量库 | 落盘矩阵 | 独立向量数据库 | 单机、零运维、无外部依赖 |
| 语料版本 | 固定 tag，可切最新 | 始终跟随最新 | 可复现性优先；同时提供"跟随最新"的显式选项 |
| 分词 | jieba + 标识符保留 | 纯 jieba 或纯空格 | 本场景的查询必然混中英文标识符 |
| Agent 默认 | **关闭** | 默认开启 | 多数问题链式调用就够；默认 Agent 是过度设计 |
| 重排序默认 | **关闭** | 默认开启 | 有延迟代价；必须先看到增益数据再决定 |

## 9. 测试策略

| 层次 | 方式 | 说明 |
| --- | --- | --- |
| 单元 | 纯函数优先 | 解析、切分、分词、融合算法都是纯函数，易测 |
| 契约 | 固定小语料 + 断言 | 切分结果、召回结果的快照测试 |
| 离线集成 | 假模型客户端（固定回复） | **不依赖网络和 API Key 就能跑通全链路**，这是教学项目能被跑起来的前提 |
| 评测回归 | 指标不低于基线阈值 | 改动的门禁 |
| Agent | 脚本化的假模型 + 轨迹断言 | 验证预算、失败恢复、终止条件 |

**"无密钥可跑通"是一个硬性要求。** 教学项目最大的流失点就是"读者卡在配置 API Key 上"。假模型客户端让读者在拿到 Key 之前就能把整个系统跑一遍。

## 11. 与 Skill 分支的关系

Skill 分支（[02 文档](./02-skill精简分支设计.md)）复用本架构的 **L1 + L2 + L3 + 一个精简的 L4**，去掉 L5–L7 的编排，把 L5 的约束改写成**给宿主 Agent 的自然语言规程**。

这个复用关系是刻意的教学安排：读者会亲眼看到，一个系统里真正难以替代、值得打包分发的资产，是**语料与其索引**，而不是编排代码。
