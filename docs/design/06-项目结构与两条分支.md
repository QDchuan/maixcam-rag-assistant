## 0. 对 v0.1 的修正

v0.1 我写成了"把整个 RAG 管线重构成 DSH（Harness）插件"。**那是错的**，原因有两个：

1. **没必要。** DSH 本身已经很完整，用现成的就行；为了插件化去重构一个能跑的教学管线，是把手段当成了目的。
2. **丢了教学价值。** 如果一切都用现成的，读者学不到"这套东西是怎么设计出来的"。而那恰恰是这个项目最想教的部分。

修正后的结构是**两条分支**：一条用现成的，一条自己仿写。

## 1. 三条分支：目标不同，工程选择就不同

这是整个项目的骨架。**三条分支不是"同一个东西的三种写法"，而是三个不同的目标**，而工程选择是从目标推导出来的——不是由口味决定的。

| 分支 | 目标 | 一句话 | 工程上的必然选择 | 读者得到什么 |
| --- | --- | --- | --- | --- |
| **A 主分支** | **教学** | 自己从零写一个 agent（仿 Harness 思想） | **从零构建**——因为过程本身就是目的，用现成的就学不到了 | 理解 agent 是怎么被设计出来的 |
| **B Harness 分支** | **应用价值** | 做一个真能用的 MaixCAM 开发助手 | **用成熟基座（DSH）**——从零构建在这里是浪费 | 一个可以真的拿去用的助手 |
| **C Skill 分支** | **普及** | 让任何桌面 Agent 都能用上这个助手 | **最轻形态**——不做 agent，不装环境 | 在任意 AI 上用上 MaixCAM 助手 |

### 1.1 为什么这个三分法值得单独讲

因为它示范了一条常被忽视的判断力：

> **同一个能力（MaixCAM 领域的检索与防幻觉），交付形态可以有多种，选哪种取决于你的目标，而不是取决于哪种更"高级"。**

- 想学 → 从零写，哪怕写得糙。**糙是特性，不是缺陷**，因为它让每个设计决策都暴露出来。
- 想做产品 → 用成熟基座。**不要重复造轮子**，把精力放在领域能力上。
- 想扩大覆盖 → 做最轻的形态。**降低使用门槛比增加功能重要**。

三种选择都是对的，因为目标不同。而写错的方式恰恰是：**用一种分支的标准去评判另一种分支**——
说主分支"工程不成熟"，或说 Skill 分支"功能太弱"，都是没看懂它们各自的目标。

### 1.2 三条分支共享什么

```
┌─────────────────────────────────────────────────────────────────┐
│  共享底座（三条分支都用）                                          │
│                                                                  │
│  maixrag/            语料管线 · 检索 · 校验 · 评测（Python）       │
│  eval/               评测集与两轴指标                              │
│  corpus/             语料快照与产物                                │
│                                                                  │
│  ↑ 这一层刻意保持"框架无关"：它不 import 任何 agent 框架。          │
│    理由：评测器如果被编排框架绑住，就不再是量尺。                    │
└─────────────────────────────────────────────────────────────────┘
```

| 共享项 | 为什么必须共享 |
| --- | --- |
| 语料管线 | 一份语料三处维护必然分叉 |
| API 符号白名单（1898 个符号） | 它是防幻觉的物理基础，三条分支都需要 |
| **评测集与评测器** | **最关键**：如果每个分支各有一套评测，就无法比较；而"能比较"正是这个项目的教学主线 |
| 检索算法 | A 用 Python 实现（可读），B 用 JS 实现（可用），两者应给出**可比较的结果**——这本身就是一次交叉验证 |

**最后一条是个额外的教学机会**：同一套算法在两套语言里实现，如果结果显著不同，说明有一边实现错了。
这是"用第二个实现验证第一个实现"的实践。

## 2. 分支 A：主分支（自己从零仿写）

### 2.1 定位

> **按 Harness 的设计思路，自己写一个 agent。写得不那么完善没关系——这个分支的价值在于把设计决策暴露出来。**

它是"原理项"，不是"使用项"。所以取舍标准完全不同：

| | 分支 A（仿写） | 分支 B（用现成） |
| --- | --- | --- |
| 判断标准 | **这个设计决策讲清楚了吗** | 好用吗、稳吗 |
| 可以粗糙的地方 | 错误处理、并发、边缘情况 | 不行，必须可靠 |
| 必须精致的地方 | **契约边界、可替换点、为什么这么分层** | 用户看不到的部分无所谓 |

### 2.2 要仿写的核心机制（按重要性排序）

这些都是从 DSH 的机制里提炼的，不是凭空想的：

| # | 机制 | 为什么它是核心 | 教学产出 |
| --- | --- | --- | --- |
| 1 | **服务注册表** | 能力之间靠注册表解耦，而不是靠 import | 一个 40 行的 `Registry`，读者能一眼看完 |
| 2 | **插件生命周期** | 每个副作用必须可撤销（disposer） | 挂载/卸载一个有工具的插件，观察副作用全部消失 |
| 3 | **工具注册与执行管线** | 工具是"能力"的标准暴露面 | 注册一个检索工具，被 agent 调用 |
| 4 | **提示词装配** | 提示词是**拼**出来的，不是写死的字符串 | 多个来源各自贡献一段，可增删 |
| 5 | **agent 循环** | 决策由模型做还是写死，是链与循环的唯一区别 | 同一任务，链式 vs 循环式对比 |
| 6 | **预算与终止** | 没有预算的 agent 在生产里是事故 | 轮次/token/工具调用三重预算 |
| 7 | **权限与沙盒** | 能力边界、范围边界、审批边界 | 故意做错一次：让 agent 去写工作区外的文件，看它怎么被拦住 |

**第 1 项里包含「两个平面」**：注册表天然带出"共享的放全局、单次的放隔离域"这个划分。
自己仿写时**故意先写错一次**，让读者看到第二个会话挂载失败的现场，再修——
这比直接告诉他们规则有效得多。**这个演示已经做完了**，见 `scripts/demo_planes.py`。

**第 7 项是被刻意保留在教学范围内的**，理由见 2.3.1——它是这一轮范围调整中
唯一新增的机制。

### 2.3 仿写范围

**要仿写**（七项，按依赖顺序）：

| # | 机制 | 为什么它是核心 |
| --- | --- | --- |
| 1 | 服务注册表 | 能力靠名字解耦，而不是靠 import |
| 2 | 插件生命周期 | 每个副作用必须可撤销 |
| 3 | 工具注册与执行管线 | 工具是"能力"的标准暴露面 |
| 4 | 提示词装配 | 提示词是**拼**出来的，不是写死的字符串 |
| 5 | agent 循环 | 决策由模型做还是写死，是链与循环的唯一区别 |
| 6 | 预算与终止 | 没有预算的 agent 在生产里是事故 |
| 7 | **权限与沙盒** | **AI 应用的核心设计问题，不是附属品** |

#### 2.3.1 为什么权限与沙盒必须在教学主线里

很多教学项目把权限当成"生产环境的杂事"跳过。**那是个错误判断。**

一个会执行命令、读写文件、访问网络的 agent，如果没有能力边界，
它的错误就不再是"回答得不好"，而是"删了不该删的东西"。
**这是性质上的差别，不是程度上的差别。**

本项目在真实开发过程中就亲历过这个差别，而且完全可以复现：

> 同一条联网命令，在受限沙盒里因为拿不到 TLS 凭证而失败
> （`SEC_E_NO_CREDENTIALS`），在放开权限后成功返回 200。
> **同一次操作，只因为权限不同，结果完全不同。**

这不是理论，是现场。所以权限要分三层讲：

| 层 | 问题 | 本项目里的实例 |
| --- | --- | --- |
| **能力边界** | 这个 agent 能做什么 | 能读文件吗？能执行命令吗？能联网吗？ |
| **范围边界** | 能做到多大范围 | 只能写工作区，还是整块磁盘 |
| **审批边界** | 什么情况下必须问人 | 这是最后一道闸，也是唯一一道 |

#### 2.3.2 明确不仿写（并说明真实系统为什么必须有）

| 不仿写 | 真实系统为什么必须有 |
| --- | --- |
| 会话持久化与恢复 | 否则进程重启后上下文全丢；但教学项目用内存 + JSONL 就够 |
| 子 agent 委派 | 长任务需要并行与隔离；但会显著推高理解成本 |
| 前端框架 | **可以用插件形式加上**——它属于应用形态，不属于 agent 原理，所以不放在教学主线 |

**「明确不做什么」本身就是教学内容**：成熟系统的完整度是靠大量工程堆出来的，
教学项目不该假装能复刻。


### 2.4 分支 A 的接口

```python
# 仿写的注册表：能力靠名字注册，靠名字解析
class Registry:
    def provide(self, name: str, obj) -> Disposer: ...
    def get(self, name: str): ...
    def require(self, name: str): ...   # 缺失时显式失败，不返回 None

# 插件契约：一个函数，拿到 ctx，注册自己的东西，返回清理函数
class Plugin(Protocol):
    name: str
    def apply(self, ctx: Context) -> Disposer: ...
```

## 3. 分支 B：Harness 分支（用 DSH 作为 AI 应用的基底）

### 3.1 定位（一次重要的理解修正）

我之前写的是"**给 DSH 加一个 RAG 插件**"。**那理解错了。**

正确的定位是：

> **把 DeepSeek Harness 作为这个 AI 应用的基底，在它之上做我们自己的 AI 应用——MaixCAM 开发助手。**

区别是根本性的：

| | ✗ 加插件（我原先的理解） | ✅ 以它为基底做应用（正确理解） |
| --- | --- | --- |
| DSH 的角色 | 被扩展的一方 | **底座**：agent 循环、工具系统、模型路由、持久化、前端 |
| 我们做的 | 一个 RAG 插件 | **一个完整的 AI 应用** |
| 交付物 | 一个插件包 | 一套可用的 MaixCAM 助手应用（配置 + 能力 + 界面） |
| 读者学到的 | 怎么写插件 | **怎么用一套成熟的 agent 基座把自己的能力做成产品** |

**这个定位的价值在于**：读者不需要从零实现 agent 循环、工具调度、会话管理、前端——直接用 Harness 提供的。他要做的是**把 MaixCAM 这个领域能力接进去**：语料、检索、防幻觉校验、回答纪律、领域界面。

这也正是实际工程里最常见的形态：**底子是成熟的，差异化在你接进去的领域能力上。**

### 3.2 应用由哪几块组成

一个"以 DSH 为基底的 AI 应用"包含以下内容。这是本分支的交付清单：

| 块 | 内容 | DSH 里对应什么 | 我们写什么 |
| --- | --- | --- | --- |
| **领域能力** | 检索、查签名、防幻觉校验 | Host 平面服务 | 一个 RAG 服务实现 |
| **Agent 人格与工具** | MaixCAM 助手的回答纪律 + 三个工具 | Agent Preset | 一份 preset 组合 |
| **领域界面** | 检索轨迹、消融对比、语料地图 | Client 插件 + Slot | 前端面板 |
| **配置面** | 语料版本、top_k、检索策略 | `settings` 服务 | 设置分区 |
| **数据面** | 语料与索引产物 | 构建期产出 | Python 管线（已就绪） |

### 3.3 关键设计决定

#### 3.3.1 RAG 不自研，从开源方案里挑一个（已决定）

**决定**：Harness 分支的 RAG **不使用本项目自研的 `maixrag`**，而是从开源平台挑选一个
**工程上更成熟、效果更好**的方案，与 DSH 整合。

**理由**（与「目标决定工程选择」这条主线一致）：
- 这一分支的目标是**应用价值**，不是教学。自研 RAG 在这里没有任何好处；
- 自研的检索链（BM25 + 向量 + RRF）是**教学参考实现**，它的价值在于可读、可拆解，
  而不是在于效果。生产系统里该用经过大量场景验证的方案；
- 复用成熟方案能把精力集中在**领域能力**上（MaixPy 语料、防幻觉校验、回答纪律），
  那才是这个应用真正的差异化所在。

**选型标准**（按重要性排序，都是工程指标）：
1. 中文检索质量，尤其是**中英混合标识符**场景（本项目实测证明这是最容易翻车的地方）；
2. **可替换性**——能否只换嵌入/重排而保留索引，能否自定义分块；
3. 混合检索（稀疏 + 稠密 + 融合）与重排序是否内置或易接；
4. 与 Node 侧的集成成本（原生 JS 优先，或提供稳定 HTTP 接口）；
5. 许可证必须允许本项目使用。

**与共享底座的关系**：语料管线（Python）仍然保留——它产出的
`chunks.jsonl` / `api_symbols.jsonl` / `api_roster.txt` 是**与检索实现无关的中间产物**（索引本身在 `indexes/` 下，那是可重建的派生物），
任何开源方案都可以从这里接入。**这正是把"语料"与"检索实现"分开的价值。**

> **这个选型留到主线告一段落之后再做**，因为它是应用工程问题，不影响教学主线的推进。

#### 3.3.2 构建期产物 + 运行时直读

不管最终用哪个开源方案，"重活在构建期、轻活在运行期"这条仍然成立：

| | 原先设想：HTTP sidecar | 现在：构建期产物 + 运行期直读 |
| --- | --- | --- |
| 运行时进程 | 2 个 | 1 个 |
| 新失败模式 | "服务没起来" | 无 |
| 负面代价 | 端口、生命周期、健康检查都要管 | 语料更新要重新构建 |

接口是三个文件：

```
corpus/processed/chunks.jsonl      切分结果（含 heading_path 与 meta）
indexes/bm25.json        BM25 统计量
corpus/processed/api_symbols.jsonl API 符号与精确签名（防幻觉白名单）
```

> **教学点**：构建期 vs 运行期的划分，是让系统变简单的最有效手段之一。
> 代价是数据有一份拷贝，且更新语料要重新构建。

我原先设计的是"Python 跑 HTTP 服务，Node 插件调它"。**现在改掉**，理由如下：

| | 原先：HTTP sidecar | 现在：构建期产物 + 直读（**采用**） |
| --- | --- | --- |
| 运行时进程 | 2 个 | **1 个** |
| 新失败模式 | "服务没起来" | 无 |
| 前端可视化 | 要经 HTTP 转发 | 可在 Node 侧直接读轨迹 |
| 副作用 | 端口、生命周期、健康检查都要管 | 无 |
| 代价 | — | 检索逻辑要用 JS 写一份 |

最后那条代价**可接受**，因为两个分支的分工本来就是这样：

- **Python 侧负责"造"**：抓语料、切分、抽 API 符号、建索引、跑评测。这些是离线的一次性工作。
- **Node 侧负责"用"**：在 Harness 里检索、融合、查签名、校验符号。这些是运行时的轻量逻辑。

**接口是三个文件，而不是一个 HTTP 契约**：

```
corpus/processed/chunks.jsonl      切分结果（含 heading_path 与 meta）
indexes/bm25.json        BM25 统计量（df / 文档长度 / 参数）
corpus/processed/api_symbols.jsonl API 符号与精确签名（防幻觉白名单）
```

Node 侧不需要重新实现分词与索引构建，只需要实现**查询**——那只有几十行。

> **教学点**：这是"构建期 vs 运行期"的经典划分。把重活放在构建期、把轻活放在运行期，
> 是让系统变简单的最有效手段之一。代价是数据有一份拷贝，且更新语料要重新构建。

### 3.4 平面归属（一条硬约束）

```
Host 平面
  └─ RAG 服务（读预构建产物，实现检索 / 查签名 / 校验）
        · 必须在 Host，只能在 Host 注册一次

Agent Preset 平面（= MaixCAM 助手这个应用本身）
  ├─ tool: search_docs        → RAG 服务
  ├─ tool: lookup_api         → RAG 服务
  ├─ tool: check_api_usage    → RAG 服务
  └─ prompt section           → MaixCAM 助手的回答纪律

Client 插件
  └─ 领域界面面板
```

**"RAG 服务必须在 Host 平面"是机制要求，不是风格选择。** DSH 规定：发布服务的行不能裸放在 preset 里，
否则第二个会话挂载时会在同一符号上撞名，挂载被拒绝。

这条值得单独教：**"一切皆插件"不等于"什么都往 preset 里塞"。** 平面判断是这个架构里最容易错、也错得最隐蔽的一步。

补充两条落地时才看清的细节：

- **"必须在 Host"有一个官方出口：`isolate` realm。** 如果一个服务确实只归某一个 agent 用、
  外面没人读，preset 里可以把它包在 `cordis:group` + `isolate: { <服务名>: true }` 里挂载，
  每个 preset 各得一份实例，就不会撞名。随包交付的 `minimal` preset 就是这么处理
  `terminals` 的。所以规则的准确说法是：**"别把服务发布进根 realm"，而不是"别写进 preset"。**
- **实际做法**：这一分支的检索是**宿主组装**里的一行（写进 profile 的 `cordis.patch.yml`），
  发布在根 realm —— 因为这个进程就是那个应用，整个进程只有一个消费者。
  哪天要和别的领域共用一个进程，就该把它挪进 preset 的 `isolate` realm，并把
  §3.2 里那两个工具一起搬过去。

### 3.5 前端可视化

在 Harness 里前端也是插件（Client 插件 + Slot）。三个面板按性价比排序：

| 面板 | 价值 | 数据来源 | 优先级 |
| --- | --- | --- | --- |
| **检索轨迹** | 教学 + 调试 + 演示，三合一 | `scores_by_stage`（已在数据模型里） | **高** |
| 消融对比表 | 展示 L-1→L9 的两轴曲线 | 评测报告 JSON | 中 |
| 语料地图 | 教程层/API 层分布 | 语料统计 | 低 |

**检索轨迹面板性价比极高**：它把"为什么这条片段被选中"从黑箱变成可见的东西，而"看不见"正是 RAG 难教、难调的根源。

### 3.6 落地记录

上面是设计。下面是**实际做出来的部分**，以及做的过程中被事实修正的地方。

交付在 [`harness/`](../../harness/README.md)：

| 块 | §3.2 里的设想 | 实际落地 |
| --- | --- | --- |
| 数据面 | 构建期产物 | ✅ 直接复用主线产物（`chunks.jsonl` / `vectors.npy` / `api_symbols.jsonl` / `index_meta.json`） |
| 领域能力 | Host 平面服务 | ✅ `dsh-maixcam-shell` 宿主半边：加载 + 校验语料，三条 `/api/maixcam/*` 路由，两个 agent 工具 |
| 领域界面 | Client 插件 + Slot | ✅ 品牌三处 + 「MaixCAM 知识库」面板（`sidebar.panellist` + `main`） |
| Agent 人格与工具 | Agent Preset | ✅ `maixcam-assistant` preset（`standard` 的副本，**只改 `persona` 那一行**）+ 两个工具 |
| 配置面 | `settings` 服务 | ❌ 未做，目前配置写在 profile 补丁行里 |

一条接口上的硬事实：**这个分支没有第二个进程**。壳是一个 dsh profile 里的插件包，
宿主半边在同一个 Node 进程里，浏览器半边手写在 `exports["./client"]` 里，
**没有构建步骤**。

#### 3.6.1 对 §3.3.2 的一处修正：稀疏检索没法"只有几十行"

§3.3.2 当初写的是「Node 侧不需要重新实现分词与索引构建，只需要实现**查询** —— 那只有几十行」。
**这句话对稠密成立，对稀疏不成立。**

`indexes/bm25.json` 里的 `df` / `tf` 是按 `zh_identifier` 分词后的词条统计，而那个分词器
是 jieba 分中文词的（实测词表里有 `资源` `汇总` `寻找` `色块` 这样的多字词，共 13367 个词条）。
要在 Node 里用这份索引，就得先复刻分词器 —— 要么背一份词典，要么引一个原生扩展，
两条路都不划算。

所以运行期实际走的是**稠密那一路**：

```
问题 → 嵌入服务（本机 Ollama，bge-m3，OpenAI 兼容 /embeddings，1024 维）
     → 与 vectors.npy 逐行余弦 → top-k
```

嵌入模型本身就是一个成熟组件，运行期只写"调用 + 余弦"，这仍然符合 §3.3.1「RAG 不自研」。
稠密 + 稀疏的融合与重排留在后面。

> **教学点**：**构建期与运行期的边界，会跟着实现语言一起移动。**
> "运行期很轻"这个判断，取决于运行期能不能用上构建期那份**分词约定**。
> 换语言就等于要重新满足这个约定 —— 这才是 HTTP sidecar 当初真正的吸引力所在
> （不是"服务化"，而是"不用把分词器搬过去"）。

#### 3.6.2 语料与索引对不上时，拒绝服务而不是降级

语料（`chunks.jsonl`）与向量（`vectors.npy`）是**两份可能各自更新的产物**，而向量是
按 `chunk_id` 顺序存的。两者一旦错位，检索会安静地返回牛头不对马嘴的片段 —— 不报错，
只有错答案，而且错得很像对的。

所以加载时逐条核对 `vectors_meta.chunk_ids[i] === chunks[i].chunk_id`，不一致就抛错，
`/api/maixcam/search` 返 503 并说明原因，**不返回空结果**。空结果会被模型读成
"知识库里没有"，然后继续凭记忆回答 —— 那正是这个项目要治的病。

同一条道理也用在工具上：检索不可用时工具抛「知识库不可用：<原因>」，
而不是返回一个空列表。

#### 3.6.3 实测教训一：占了座位，但什么都没发生

`single` 座位的选举规则是「按优先级排序后，**第一个**存活的条目获胜」——
**数字越小越优先**。

而外壳默认的品牌（侧栏的鱼形标志与 `LOCAL BUILD` 标签）**不是兜底渲染，
而是一个 `priority: 0` 的在册占位者**。所以往 `sidebar.brand.mark` 登记自己的组件时：

- 不给优先级 → 并列 0，先登记的默认占位者赢，我们的组件**根本不渲染**；
- 而且**不报任何错**，页面看起来像"这次改动没生效"。

实测：`priority: -1` 赢，`priority: +1` 输。而 `conversation.hero.brand.mark` 原本没人占，
不给优先级也能赢 —— 于是"填座位"和"换座位"这两件事看起来一模一样，直到你发现前者静默失效。

> **教学点**：界面扩展最难的从来不是"怎么画"，而是"我画的东西到底有没有被渲染"。
> **一个不报错的失败，比一个报错的失败贵得多。**

#### 3.6.4 实测教训二：前端的反馈必须自己拿得到

如果验证前端的方式是"叫用户刷新页面、肉眼看、再口述回来"，一轮要几分钟，
而且看不清"是哪个座位没占上"。这个分支因此带了一个工具：

```bash
node harness/tools/eyes.mjs --url "$URL" --text --shot out.png
node harness/tools/eyes.mjs --url "$URL" --eval "document.querySelector('.dsh-mx-name')?.innerText"
```

它起一个无头 Chrome、用 DevTools 协议连上、把"文本 / 元素几何 / 截图"拿回来。
配合 `dsh web --port 0 --no-open`（会打印一个带 token 的 URL）就能起一个**只给自己看**的
验证实例，和用户正在用的那个互不打扰。

上面那个优先级坑就是它一次实验定位的，没有麻烦任何人。

> **这条比它看起来重要。** §3.6.3 那种"静默失效"，
> 在没有自带反馈回路的时候几乎不可能被发现 —— 你只会反复跟用户说"你再刷一下看看"。

#### 3.6.5 agent 那一侧：改动只有一段话

`harness/maixcam-assistant/agent.cordis.yml` 是随包 `standard` preset 的**副本**，
全文件只改了一处 —— `persona` 那一行。其余 17 行（shell、文件、技能、目标、计划、
压缩、委派、联网、交付）原样保留。

这就是 §3.1「以 DSH 为基底做应用」最直接的证据：**agent 平面上真正属于这个应用的，
只有一段提示词。** 那段提示词要治的正是这个项目的起点：

| 纪律 | 治的是什么 |
| --- | --- |
| 先查再答（`search_docs`） | 凭记忆编 API |
| 先核对再用（`lookup_api`） | 写出看起来很合理的名字 |
| 答必带出处 | 「根据文档」这种无法核对的引用 |
| 查不到就说不知道 | 用编造的代码把空白填上 |

**为什么复制而不是从零写**：一份复制的组合**开箱就是能挂载的**。从零写的组合通常
会忘记某个 group realm，或者把一个消费者行留在它的提供者 realm 外面 ——
而那类错误在挂载时才会以"某行没有激活"的形式出现（见 §3.4）。

**为什么纪律写在 `persona` 的配置里，而不是另写一个本地提示词插件**：
preset 目录不在 `profiles/` 下面，Node 的 `node_modules` 向上查找够不到
`@deepseek-ai/*`，所以 preset 自带的 `.js` 必须零依赖。声明式地写在 `persona`
配置里既不需要依赖，用的又和随包 preset 是同一个机制。

#### 3.6.6 实测教训三：`parameters` 不是 JSON Schema，工具会静默消失

这一处**第一次端到端实测才发现**，而且发现的方式值得记下来。

当时两个检索工具注册在宿主平面，路由一切正常、知识库面板一切正常。然后起一个会话、
把 preset 选成「MaixCAM 开发助手」、问一句「怎么寻找色块」，模型的第一段思考是：

> "I have hard discipline instructions: I must first search the local knowledge base with
> `search_docs` and `lookup_api`. **But wait — those tools are not in my available tool list!**"

原因是 `defineTool` 的 `parameters` 是一张**扁平的「参数名 → 规格」表**：

```js
parameters: { query: { type: 'string', description: '…', required: true } }
```

而不是 JSON Schema 的 `{ type: 'object', properties: {…}, required: […] }`。
写成后者**不报错** —— 路由照常工作，界面照常工作，只有 agent 看不见这两个工具。
模型只好自己去找替代路径：它读了 `maixrag/cli.py` 和 `ragtools.py`，
自己写了四个探针脚本去调 Python 检索链。

> **教学点**：这是本分支第三个「不报错的失败」，性质完全相同 ——
> 座位优先级要**渲染**才看得见；工具 schema 要**模型真的调一次**才知道没注册；
> 语料错位要**两次独立构建**才撞得上。
> 三者的共同点是：**"我改完了"和"它生效了"之间，永远隔着一次实跑。**
> 而反馈回路（§3.6.4）决定了你能不能自己发现它 —— 那一次实测如果没有自验实例，
> 结论会是"功能做好了"，而真相是"模型根本用不到"。

### 5.1 第一个真实的消融结果（本项目自己的实测数字）

底座跑通后，评测器立刻抓到了一个**设计缺陷**并验证了修复效果。这是全项目第一个真实的消融实验。

**发现**：`signature` 类问题（"某函数的参数是什么"）召回率 **0.000**。
**根因**：API 参考页当时只被用来生成符号白名单，**没有产出可检索的 chunk**。
而教程层不会系统性地写出函数签名——所以这类问题在语料里根本没有答案可召回。

**修复**：让每个 API 符号渲染成一个 chunk（限定名 + 精确签名 + 说明 + 参数表）。

**结果**（同一评测集、同一配置、只改语料这一项）：

| qtype | 修复前 | 修复后 | 变化 |
| --- | --- | --- | --- |
| **signature** | **0.000** | **0.500** | **+50 pt** |
| example | 0.250 | 0.750 | +50 pt |
| troubleshoot | 0.000 | 1.000 | +100 pt |
| **concept** | 0.625 | **0.500** | **−12.5 pt** |
| 总体 Recall@5 | 0.556 | 0.611 | +5.5 pt |

chunk 总数：1940 → **3838**（新增 1898 个 signature chunk）。嵌入维度 1024（bge-m3）。

### 5.2 这个结果为什么值得单独讲

**它同时证明了四件事**，而且每一条都是靠数字而不是靠论述：

1. **只看总分会把结论看反。** 总体 +5.5 pt 听起来不痛不痒；分组之后才看到
   一类问题 **+50 pt**、另一类 **−12.5 pt**。这正是"必须按 qtype 分组"的实证。
2. **语料工程是被低估的杠杆。** 没改任何检索算法，只改了"语料里有没有东西可召回"，
   就让一整类问题从 0 变成 0.5。**检索算法再好，也救不回语料里不存在的内容。**
3. **加语料层不是免费的。** 新增的 1898 个 API chunk 抢占了 Top-5 名额，
   把概念类问题需要的教程散文挤了出去——这是 concept 下降的直接原因。
4. **这就给了 L4（查询路由）一个可测的动机。** 既然两类问题需要不同的知识层，
   那就应该**按问题类型把检索导向对应的层**，而不是让它们在一个池子里互相挤。
   这是一个有明确预期的下一步实验。

> **一个诚实的说明**：以上数字是**检索轴**的，用真实嵌入（bge-m3）测出。
> 生成轴需要对话模型，而提供的 DeepSeek key 在评测中途失效（401），
> 因此生成轴的数字尚未测得。这也促使我们把 `--fake` 拆成 `--fake-embed`
> 与 `--fake-chat`——**检索轴本来就不需要模型**，应该能单独测量。

### 5.3 两条轴的第一次真实分离（全项目最有价值的单个结果）

接上真实对话模型（DeepSeek）后，评测跑出了一个把项目核心论点演活的结果。

**问题**：`MaixPy 里怎么做 YOLO 物体检测？给出完整代码`

**模型的实际回答**（节选）：

> 资料中没有给出 YOLO 物体检测的完整代码，因此无法提供可直接运行的完整示例。
> …由于资料中未包含具体的 `maix.*` API 名称、参数和示例代码，**按规则我不能凭其他框架
> （OpenCV、K210 时代 MaixPy v1 等）的习惯推测 API**。请查阅…官方文档。

**依据**：`zh/vision/segmentation`、`zh/ai_model_converter/maixcam`、`zh/vision/yolo_world`…

**诊断**：

| 轴 | 表现 | 结论 |
| --- | --- | --- |
| **生成轴** | **优秀**——不编造 API、明确拒答、引用规范 | 提示词纪律生效 |
| **检索轴** | **失败**——真正含 YOLO 检测例程的 `zh/vision/yolov5` 没被召回 | **根因在这里** |

**为什么这个结果最有价值**：它把项目的核心论点变成了可观察的事实——

> **答得不好有两种原因：没召回（检索失败），或召回了没用上（生成失败）。两者的修法完全相反。**

这里生成侧表现优秀，问题 100% 在检索。**如果只看"答案里没有代码"就判断模型不行，
就会去调提示词、换模型——全部调错方向。**

### 5.4 为什么 `yolov5` 没被召回（一个有依据的猜测）

直接验证 BM25 时已经看到同一个现象：查 `YOLOv5 物体检测`，返回的是
`online_converter` 和 `README_MaixCAM`，而不是 `zh/vision/yolov5`。

最可能的原因是 **BM25 的高频词问题**：`YOLO`、`物体检测` 在整个语料里出现频率很高
（README、其他视觉文档都提到），导致 IDF 偏低，于是"专讲这件事的那一篇"反而赢不了
"顺带提到这件事的一大堆"。

> **一个必须澄清的点**：这与我之前写的"BM25+ 修正了负 IDF"**并不矛盾**。
> 修正只保证 IDF **不为负**（不再给正确文档扣分），但它**无法让高频词变得有区分力**。
> 高频词的区分力问题需要另外的手段解决，例如标题/小节路径加权、字段化 BM25（title 字段单独算分）。

**这给了下一个实验一个明确、可证的动机**：给标题与 `heading_path` 加权，
预期能显著改善 `signature`/`example` 类里那些"专讲某件事"的文档的排名。

### 5.5 一个被修正的误导性指标

完整两轴报告里，"**符号级幻觉率 = 0.000**"看起来是好消息。但诊断脚本
（`scripts/inspect_eval.py`）打出了真相：

```
符号被检查到的题数  0/18  (0%)
⚠️ 没有任何题目被检查到符号——幻觉率 0.000 不具参考意义
```

**0.000 有两种完全不同的含义**："真的很好"或"几乎没测到东西"。这里的真相是后者，
而且原因是 5.3 里那个检索失败——模型没拿到任何 API 资料，于是按纪律**不写代码**，
自然也就没有符号可检查。

**修正**：新增诊断脚本，把每条指标"实际覆盖了多少题"打出来。
**指标必须能暴露自己的覆盖面，否则它会伪装成好消息。** 这条已写进项目纪律。
