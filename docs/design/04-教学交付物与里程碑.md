## 2. 里程碑

### 2.0 前置：合规确认（**阻塞项，动代码前必须完成**）

| 事项 | 说明 |

### M1：语料 + 评测地基

**为什么评测在这一批：** 它必须在任何检索优化之前存在。否则第一批优化就只能靠感觉——而那正是本项目要反对的做法。

| 任务 | 验收标准 |
| --- | --- |
| **语料体积实测** | 用 `scripts/measure_corpus.py` 复现字节数（zh 130 篇 / 713,520 字节已实测），并用**真实分词器**数出 token，替换设计阶段的估算。设计阶段估算为中文教程约 20–22 万 token，**已判定整体越线**（见 [00 文档 5.4](./00-项目定位与教学大纲.md)） |
| 语料抓取（仓库 + 站点） | 产出快照与 `manifest.json`，记录 commit / 抓取时间 / 内容指纹 |
| 差异报告 | `reports/diff.md` 显式列出站点与仓库的差异；不静默丢弃 |
| 文档解析与结构化 | 标题层级、代码块、表格、图片、链接均被正确识别 |
| 切分（标题感知 + 代码块独立） | 快照测试通过；代码块与表格未被切开 |
| API 签名抽取 + 符号白名单 | 覆盖全部 31 个顶层模块（55 个 API 正文页）；白名单可精确匹配 |
| 基础索引（向量 + BM25） | 可构建、可持久化、可校验指纹 |
| **评测集（60 题）** | 四类 `qtype` 齐备；每题有 ground-truth 片段 |
| **评测器（两轴）** | 检索轴指标可算；生成轴指标可算；**评测报告并行展示两条轴** |

**M1 完成即验证的结论**：语料统计（页数、字节数、token 数、chunk 数、代码块数、符号数）+ 差异报告。这些是后续一切对比的基准。

> **语料体积实测要单独列一项**，因为它是唯一一个**可能改变项目技术路线**的测量。设计阶段已完成字节实测并做出 token 估算，结论是**整份中文教程已越过 20 万 token 的全文上下文阈值，但单模块远在阈值之内**。因此 L-1 必须以**三档覆盖面**（单模块 / 全中文 / 加 API）的形式对比，而不是单一基线。精确 token 数仍需用真实分词器确认。

### M2：L-1 + L0 + L1 基线

| 任务 | 验收标准 |
| --- | --- |
| **L-1 全文上下文基线** | `retrieval.mode: none` 走通；配合 prompt caching；记录 token 成本与延迟 |
| L0 无 RAG 基线 | 跑出幻觉基线数字（这是全项目的参照点） |
| L1 朴素 RAG | 定长切分 + 单一稠密检索 + 拼接生成，端到端可跑 |
| 提示词与结构化输出 | 引用编号机制可用；拒绝回答可结构化返回 |
| 评测集体检 | 用 L0 筛掉"不检索也能答对"的送分题 |
| 离线集成测试 | **无 API Key 也能跑通全链路**（假模型客户端） |

**M2 完成即验证的结论**：
1. **L-1a/b/c 三档覆盖面 vs L1——检索架构在多大的语料范围上开始占优**（本项目的第一课；设计阶段已确认整体越线，但仍需测出"边界在哪"以及单模块下全文上下文是否确实更优）；
2. 朴素 RAG 相对 L0 改善了多少（两条轴分别看）。

### M3：质量提升阶梯（L2–L8）

每一级交付**四样东西**（见 [03 文档第 11 节](./03-评测与质量提升路线.md)）：可运行配置、对比数字、一个失败案例、失效场景说明。

| 级别 | 核心验证问题 |
| --- | --- |
| L2 结构化语料 | 只改切分与元数据，两条轴各变化多少 |
| L3 混合检索 | **按 `qtype` 分组**，稀疏检索在标识符类问题上的不可替代性 |
| L4 结构感知检索 | 分层语料 + 路由能否兑现增益 |
| L5 查询改写 | 多轮指代消解带来的改善 |
| L6 重排序 | 增益 vs 延迟的实际曲线 |
| L7 上下文增强 | 小语料上的性价比 |
| L8 忠实生成 | 幻觉率能压到多低，拒答率付出多少 |

**M3 的核心产出是一张表**：技术 → 增益 → 代价 → 失效场景。这是全项目最有教学价值的单一交付物。

### M4：Agent 版（L9）

| 任务 | 验收标准 |
| --- | --- |
| 工具集 | ≥4 个工具，含确定性的 `lookup_api` |
| 决策循环 | 预算（轮次/token/工具调用）可控，耗尽时优雅降级 |
| 失败恢复 | 空检索、工具报错、校验失败均有明确路径 |
| 轨迹落盘与回放 | 可复现一次运行 |
| Agent 评测 | 任务成功率、平均轮次、预算耗尽率、失败恢复率 |
| **成对对比** | **与链式版本的分场景胜负结论**：什么时候 Agent 值、什么时候不值 |

**M4 完成即验证的结论**：`什么时候不该用 Agent` 这一章的证据。预期是分场景的（单点事实查询链式更好；多跳/需澄清问题 Agent 更好）。

## 3. 学习路径建议

面向不同读者，给出三种用法（写进项目 README）：

| 路径 | 适合谁 | 怎么走 | 预计投入 |
| --- | --- | --- | --- |
| **A. 只想要工具** | 只想解决 MaixCAM 问题的开发者 | 直接用 Skill 包（M5 产物），不看代码 | 几分钟 |
| **B. 学 RAG** | 想掌握检索增强 | M1 → M2 → M3，重点看消融表与失效场景 | 数天 |
| **C. 学 Agent 设计** | 想掌握 AI 应用架构 | M1 → M3（快过）→ M4 → 读设计文档 01 | 数天 |

**路径 A 的存在很重要。** 它让这个项目对"不关心教学"的人也有真实价值——这是项目能持续维护的前提。

---

## 4. 每一批的验收纪律

三条贯穿所有里程碑的硬要求：

1. **能离线跑通。** 每批都必须能在无网络、无 API Key 的情况下完成冒烟测试（假模型客户端 + 本地缓存）。这是教学项目最大的流失点。
2. **结论必须有数字。** 不允许出现"效果更好"这类无数值、无对照的表述。
3. **失败案例必须留档。** 每一级都要记录"加了这一招之后，哪类问题依然答错"。

## 5. 风险登记

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **语料再分发合规** | 高（阻塞） | 前置确认（见 2.0）；保守方案：只分发脚本 |
| **语料体积的结论改变教学重心** | 中 | 设计阶段已确认：整份中文教程越过 20 万 token 阈值（估算 20–22 万），单模块远在阈值内。因此 L-1 从"单一基线"改为"三档覆盖面对比"。**这不是失败，是更好的教学材料**——教的是边界而非结论 |
| 站点抓取结构变化 | 中 | API 抓取器要可测；失败时明确报错而非静默产出空语料 |
| 上游文档漂移导致评测不可复现 | 中 | 语料版本固定 + 索引指纹校验 |
| 评测 Judge 成本超出预期 | 中 | 磁盘缓存 + 尽量用程序判定替代 judge |
| 教学项目常见病：只有成功案例 | 中 | 每级强制交付失败案例（第 4 节纪律 3） |
| Agent 结论不达预期（不一定更好） | 低 | **这本身就是有价值的结论**，如实交付 |
| 误用非商业许可的代码 | 中 | `NirDiamant/RAG_Techniques` 为自定义非商业许可，**禁止复制代码**，只可引用思路（见 [05 附录](./05-调研与借鉴.md)） |
| 范围蔓延（想加 UI / 微调 / 多模态 / GraphRAG） | 中 | 见 [00 文档第 8 节](./00-项目定位与教学大纲.md) 非目标，一律拒绝 |
