# 01 · RAG 的完整链路

> **这一章要建立的认知**：RAG 不是"把文档变成向量然后问模型"这一个动作。
> 它是一条**七段的链**——而这条链有两个独立的失败轴，和一个硬上限：
> 检索决定模型能看到什么，**没召回的内容，生成阶段无论如何救不回来**。
>
> 相关：[tutorial 00 主线导览](../tutorial/00-主线导览.md) ·
> [事故 02 有文档却召不回](../postmortem/02-有文档却召不回.md) ·
> 习题：[`exercises/concepts/01-RAG的完整链路.md`](../exercises/concepts/01-RAG的完整链路.md)

---

## 1. 一句话

**链路的前半段（语料 → 索引 → 检索 → 融合）回答"模型能看到什么"，
后半段（生成 → 校验）回答"模型怎么用看到的东西"。**

前四环错了，后三环再强也没有意义。

## 2. 它在链路中的位置

```
MaixPy 语料（教程 Markdown + API 参考页）
   ↓
① 语料获取    快照 + commit + 差异报告
   ↓
② 解析切分    prose / code / table / signature
   ↓
③ 索引        BM25（稀疏） + 向量（稠密）
   ↓
④ 检索        该出现的那几段，进 Top-K 了吗      ┐
   ↓                                            │ 检索轴
⑤ 融合重排    RRF 融合 · rerank 精排             ┘
   ↓
⑥ 生成        带编号的上下文 → 引用 → 答案       ┐
   ↓                                            │ 生成轴
⑦ 校验        符号白名单 · 引用有效性 · 拒答一致性┘
   ↓
答案（含引用、校验报告、拒答标记）
```

整条链就是这一章，每个环节的契约如下——**注意最后一列，它才是各环设计成这样
的真正原因**：

| 环 | 输入 | 输出 | 下游要它做什么 |
| --- | --- | --- | --- |
| ① 语料获取 | 仓库 tag / 文档站 | 落盘快照 + commit + 差异报告 | 让"这批语料是哪一版"可回答 |
| ② 解析切分 | 原始 Markdown / HTML | `Doc` → `Chunk` | **提供可被召回的最小单位**——索引里没有就没得检索 |
| ③ 索引 | `Chunk` 集合 | BM25 索引 + 向量矩阵 | 把"相关"变成一次可排序的计算 |
| ④ 检索 | 一个查询 | k 个片段 + 分数 + 名次 | 把候选压到能塞进上下文的规模 |
| ⑤ 融合重排 | 多路检索结果 | 一个统一排名 | 决定"谁进 Top-K"——名额是零和的 |
| ⑥ 生成 | 带编号的上下文块 | 答案 + 引用编号 | 让每句论断都能追到某一块 |
| ⑦ 校验 | 答案 + 上下文 + 符号白名单 | `VerificationReport` | 把"有据可依"从口号变成可执行检查 |

**两个必须记住的约束：**

1. **检索是一次筛选，不是一次判断。** 它决定模型能看到什么。
2. **没召回的内容，生成阶段救不回来。** 所以召回率是主指标（见 [07 评测](./07-评测-两条轴.md)）。

## 3. 为什么需要它（没有它会怎样）

从失败讲起。在 MaixCAM 这个场景里，链路上任何一环坏掉，读者看到的现象**长得一模一样：
答案里没有能跑的代码**。

- 语料层坏了：站点的 API 参考页抓下来了、1898 个符号也抽出来了，但它们被当成
  "校验用的元数据"，**没有产出任何一个可检索的 chunk**。于是"`find_blobs` 的参数有哪些"
  这类问题在语料里根本没有答案可召回——这是 [事故 02](../postmortem/02-有文档却召不回.md)。
- 切分层坏了：代码块被按段落切开，`yolov5.py` 的例程被切成两半，
  检索到了也只有半段可用。
- 检索层坏了：查"MaixPy 里怎么做 YOLO 物体检测"，BM25 返回的是
  `online_converter` 和 `README_MaixCAM`，而真正专讲这件事的 `zh/vision/yolov5` 没进 Top-K。
  根因是 `YOLO`、`物体检测` 在全语料高频、IDF 偏低，**"顺带提到"的一堆赢过了"专讲它"的那一篇**。
- 生成层坏了：正确片段就在上下文里，模型却凭 OpenCV 的习惯写了 `cv2.cvtColor`
  ——评测集里"`maix.image.Image` 怎么转灰度"那一题的 `must_not_contain`
  正是 `cv2.cvtColor` 和 `image.gray()`。

所以链路的第一个用处不是"组织代码"，是**把"答得不好"拆成几个可分别排查的位置**。
不拆，读者能做的只有一件事：把所有环节一起换一遍。

### 3.1 两条轴：两类不同的病，修法几乎不交集

这是本项目最重要的一个思维模型（设计论证见 [03 评测与质量提升路线](../design/03-评测与质量提升路线.md)）：

| 失败类型 | 现象 | 该改哪里 |
| --- | --- | --- |
| **检索失败** | 该出现的那几段文档，根本没进 Top-K | ①②③④⑤：语料、切分、索引、检索器、融合 |
| **生成失败** | 正确片段已经在上下文里，模型却没用上 | ⑥⑦：提示词、上下文组织、引用与校验 |

**这两类失败的修法几乎没有交集。** 而现实中绝大多数调优把它们当成一个问题处理：
答错了就换嵌入模型、就上调 top_k、就加 rerank——纯属碰运气。

分轴之后还会自然得到一个诊断格（第 4 节有一个真实例子）：
**检索没命中，答案却对了**——说明模型不靠检索本来就会，这道题不能留在评测集里，
它会把所有配置的分数都垫高。

### 3.2 链路是有上限的

这是这一章第二个必须记住的判断：

> **召回决定了答案的质量天花板。** 生成阶段只能在召回结果之内做到最好。

所以本项目把 `Recall@K` 定成**主指标**，而不是精确率、也不是延迟。
原因不是它更"科学"，而是它是**结构性上限**——其他环节的表现，全都发生在这个上限之内。

## 4. 本项目的实测证据

### 4.1 两条轴的第一次真实分离

问题：**"MaixPy 里怎么做 YOLO 物体检测？给出完整代码"**

模型（链式基线）的实际回答：

> 资料中没有给出 YOLO 物体检测的完整代码，因此无法提供可直接运行的完整示例。
> ……按规则我不能凭其他框架（OpenCV、K210 时代 MaixPy v1 等）的习惯推测 API。

| 轴 | 表现 | 结论 |
| --- | --- | --- |
| **生成轴** | **优秀**——不编造 API、明确拒答 | 提示词纪律生效了 |
| **检索轴** | **失败**——真正含例程的 `zh/vision/yolov5` 没被召回 | 根因在这里 |

**如果只看"答案里没有代码"就判断模型不行，就会去调提示词、换模型——全部调错方向。**
[本项目实测]

### 4.2 一次语料层改动，两类问题一涨一跌

同一份教程语料（119 篇文档 · 3838 chunk，其中 605 代码 / 67 表格 / 1898 signature），
只改**语料层这一项**（让 API 参考页产出可检索 chunk），同一评测集 18 题：

| qtype | 修复前 | 修复后 | 变化 |
| --- | --- | --- | --- |
| **signature** | **0.000** | **0.500** | **+50 pt** |
| example | 0.250 | 0.750 | +50 pt |
| troubleshoot | 0.000 | 1.000 | +100 pt |
| **concept** | 0.625 | **0.500** | **−12.5 pt** |
| 总体 Recall@5 | 0.556 | 0.611 | +5.5 pt |

三件事同时成立，而且只有分组才看得出来：

1. 没动任何检索算法，一整类问题从 0 变成 0.5——**语料工程是被低估的杠杆**；
2. 新增的 1898 个 API chunk 抢占了 Top-5 名额，把概念类需要的教程散文挤了出去
   ——**加语料层不是免费的**；
3. 总分 +5.5 pt 对这两件事都没有信息量。**必须按 qtype 分组。** [本项目实测]

### 4.3 同一个 0.000，两种完全不同的含义

完整两轴报告里"符号级幻觉率 0.000"看起来是好消息。诊断脚本
（`scripts/inspect_eval.py`）打出的是：

```
符号被检查到的题数  0/18  (0%)
⚠️ 没有任何题目被检查到符号——幻觉率 0.000 不具参考意义
```

原因就是 4.1 那个检索失败：模型拿不到 API 资料，按纪律不写代码，自然**没有符号可检查**。
修掉检索问题之后，真实数字是 **18/18 覆盖、幻觉率 0.000**——这一次它是真的。

> **0.000 有两种含义：真的很好，或几乎没测到东西。**
> 区别不在数字，在覆盖面。详见 [事故 05](../postmortem/05-伪装成好消息的0.md)。[本项目实测]

### 4.4 链路后段的性质变化（agent）

把第 ④ 环从"一次检索"换成"模型自己决定检索几次"之后，18 题用了 **88 次工具调用**
（平均 4.9 次/题；`search_docs` 31 / `lookup_api` 25 / `check_api_usage` 21 / `list_api` 11）。
同一个 YOLO 问题，8 轮循环给出了完整可运行代码，并且自己校验过两次。

但要注意一把尺子的边界：**agent 在检索轴上的数字反而更差**
（Recall@K 0.611 → 0.556，MRR 0.453 → 0.352）——因为检索轴的 `Recall@K` 只看**第一次
检索的前 5 个片段**，而 agent 的证据是在第 2、3 次检索里累积起来的。

> 所以"链式 vs agent 不能用同一把检索尺子比"。真正量 agent 需要"累积证据"口径的检索指标，
> 这是本项目一个**明确的待办**，不是已解决的问题。[本项目实测]

### 4.5 链路各环当前的状态

① 语料获取已产出差异报告；② 切分用标题感知（有意不做语义切分）；③ 索引是手写 BM25
（用 BM25+ 的 `ln((N+1)/df)` 保证 IDF 恒正）+ bge-m3（1024 维，本地 Ollama）向量；
④⑤ 的**融合与重排序消融（L3/L6）与查询路由（L4）尚未跑**；⑥⑦ 的生成轴已测，
引用精确率 0.889 / 符号级幻觉率 0.000（覆盖 18/18）。

**没跑过的那几环，本项目不给结论。** [设计判断]（依据：[06 项目结构与两条分支](../design/06-项目结构与两条分支.md)）

## 5. 关键术语

| 术语 | 一句话 |
| --- | --- |
| **chunk** | 索引与召回的最小单位；切分粒度决定了一段话还能不能被完整召回 |
| **qtype** | 问题类型：`concept` / `signature` / `example` / `troubleshoot`；**所有指标都要能按它分组** |
| **Recall@K** | 该被召回的片段里，有多少真的进了前 K 个。**主指标** |
| **MRR** | 第一个相关片段排名的倒数均值——衡量"位置"而不是"有无" |
| **RRF** | 只用**名次**、不用原始分数的融合方式，因此不需要处理各检索器分数量纲不一致 |
| **rerank** | 召回之后再用更贵的模型精排一次；默认关闭，要先看到增益再决定 |
| **引用（citation）** | 答案里的 `[n]` 指向上下文块，使论断可被程序校验 |
| **拒答（refusal）** | 一种正常输出，不是异常：语料里的确没有就说没有 |
| **符号白名单** | 1898 个真实存在的 MaixPy 符号 / 4868 条，是符号级幻觉检查的物理依据 |

## 6. 常见误解

这一节是这一章最重要的部分——**建立认知主要靠纠正错误认知**。

### 误解一："RAG 就是把文档塞进向量库"

这句话漏掉了链路的**整个前半段**。向量库只是第 ③ 环的一个实现细节。

真正的因果链是：**检索只能召回索引里有的东西，索引里只有切分产出的 chunk。**
所以语料覆盖面、解析完整性、切分粒度、元数据正确性，任何一项错了，向量检索都救不回来。

本项目的事故 02 是这句话最直接的证伪：API 参考页抓下来了、1898 个符号抽出来了、
白名单也建好了——**它们没产出任何可检索 chunk**，`signature` 类召回 0.000。
把 top_k 从 5 调到 50 也不会有任何变化，因为索引里没有东西可检索。

这个误解之所以常见，是因为它**在 demo 上完全成立**：语料干净、切分随便、
问题都是自然语言，于是整条链看起来就是"塞进去 + 搜出来"。它只在真实的、
两层结构的技术语料上塌掉。

### 误解二："效果好就是整体都好"

总分 0.556 → 0.611 听起来是"小幅优化"。分组之后真相是
**一类问题 +50 pt，另一类 −12.5 pt**。总分把两件方向相反的事平均成了一件事。

这个误解的危险不在于算错，而在于**它让回归变得不可见**：只看总分的团队会认为
"这次改动无害"，然后带着 concept 类的退化继续上线。

所以本项目有一条纪律：**所有评测报告必须并列展示两条轴，并且按 `qtype` 分组。**
这不是建议，是纪律。

### 误解三："调优就是换模型或调 top_k"

换嵌入模型和调 top_k 都发生在链路的一个点上，而链路有七个环节。
更关键的是：**换模型会一次改掉整条链的表现，于是任何数字都无法归因**
——这正是消融实验要禁止的"一次改两个变量"。

本项目把链路做成 L1→L9 的**能力阶梯**，每一级只加一个变量、配一份配置，
就是为了让"这个技术到底贡献了多少"成为一个可回答的问题。

在 MaixCAM 这个语料上，最大的杠杆甚至不在算法里：只改语料层就换来一整类问题 +50 pt，
而没动一行检索代码。**你只盯着模型和 top_k，就永远看不到这件事。**

### 误解四："某个指标是 0.000，说明这块没问题"

符号级幻觉率 0.000 曾经是"防幻觉机制完全成功"的表象，真相是**检查了 0/18 题**。
而且它不是一个孤立的测量事故：**它是第 ④ 环检索失败的"下游症状"**。

这个误解之所以常见，是因为比率型指标在代码里天然会写成"没有样本时返回 0.0"
——避免了除零，语义上也说得通"没有发现幻觉"。**它把"没有证据"和"证据表明没问题"
编码成了同一个数字。**

同类变体：空集合的平均值、被过滤成空集的样本、被 skip 的测试。

### 误解五："加语料一定是好事"

这次改动让两类问题大涨、一类问题下跌。原因是**Top-K 名额是零和的**：
多出来的 1898 个 API chunk 挤掉了概念类问题需要的教程散文。

所以"加语料"的正确说法是"**加了一类知识层，并接受它挤占另一类的名额**"。
这也直接给出了下一个实验的动机：既然两类问题需要不同的知识层，
就应该按问题类型把检索**路由**到对应的层，而不是让它们在一个池子里互相挤
（本项目把这叫 L4 查询路由，见 [事故 02](../postmortem/02-有文档却召不回.md) 的 C1 改造题）。

## 7. 这一章留下的问题

读到这里，你应该能回答下面这些问题。**答不出来说明前面没读透。**

答案在 [`exercises/answers/01-RAG的完整链路.md`](../exercises/answers/01-RAG的完整链路.md)。

1. 链路的七个环节，哪些属于检索轴、哪些属于生成轴？为什么这两类失败的修法几乎不交集？
2. 为什么本项目的**主指标是召回率**，而不是精确率或延迟？用"上限"这个词解释。
3. 加 API 语料层换来 `signature` +50 pt、同时付出 `concept` −12.5 pt。
   说清这个代价的机制是什么（提示：Top-K 名额是零和的）。
4. 一份报告写"符号级幻觉率 0.000"。列出至少两种它可能什么都没测到的情况，
   以及你要求报告额外给出哪个数字。

**动手题**（见 [tutorial 00 主线导览](../tutorial/00-主线导览.md)）：按顺序跑
`corpus adopt → corpus build → index build`，再用 `--fake-chat` 问一次
"MaixPy 里怎么做 YOLO 物体检测？"，观察链路每一环在报什么数字——看清楚问题是从
哪一环开始出现的。

## 8. 一句话总结

> **链路的前半段决定模型能看到什么，后半段决定模型怎么用它。**
> **答得不好时，先分清是哪半段坏了——因为它们的修法几乎不交集；
> 而无论修哪一段，没被召回的内容，生成阶段永远救不回来。**
