# 02 · 语料与切分

> **这一章要建立的认知**：RAG 的质量上限不是检索算法定的，是**语料层**定的。
> 而语料工程的核心动作只有两个——**分层**（哪些知识归哪一层）与**按结构切**（边界在哪）。
>
> 相关：[tutorial 03 语料工程](../tutorial/03-语料工程.md)（待写）· [事故 02](../postmortem/02-有文档却召不回.md) ·
> 习题：[`exercises/concepts/02-语料与切分.md`](../exercises/concepts/02-语料与切分.md)

## 1. 一句话

**语料工程决定"检索能召回什么"，切分决定"召回得到的东西能不能用"。**

两件事都比换检索算法便宜，也都比换检索算法有效——[事故 02](../postmortem/02-有文档却召不回.md) 里一行检索代码都没改。

## 2. 它在链路中的位置

```
用户问题 → [语料与切分：分层 / 解析 / 按结构切 → chunk] → 索引 → 检索 → 重排序 → 生成 → 答案
                        ↑ 本章
```

**输入**：119 篇中文教程 Markdown（仓库）+ 56 页 API 参考 HTML（文档站）
**输出**：3838 个 chunk（prose 1268 / code 605 / table 67 / signature 1898），每块带 `heading_path`、`kind`、`doc_id`
**下游要它做什么**：给每个 chunk 一个**可被检索的身份**——能被打分、能被排序、能被放进上下文

> **最后一件事解释了这一环为什么这样设计**：**没被切成 chunk 的内容，在检索器眼里根本不存在。**
> 所以切分不是预处理，它是**检索空间的构造**——切出什么形状，检索器就只能在这个形状上找东西。

## 3. 为什么需要它（没有它会怎样）

不从"切分是什么"讲起，从一次真实的失败讲起。第一份检索轴评测报告按问题类型分组是这样的：

```
| qtype        | n | Recall@K |
| ------------ | - | -------- |
| concept      | 8 | 0.625    |
| example      | 4 | 0.750    |
| signature    | 4 | 0.000    |   ← 完全为 0
| troubleshoot | 2 | 1.000    |
```

`signature`——"`find_blobs` 的参数有哪些"这类问题——**一次都没命中过**。

而语料里明明有 API 参考页：文件在磁盘上，符号抽出来 1898 个，白名单也建好了。
去索引里一查：**API 层产出的 chunk 数是 0。**

根因是一个听起来很合理的直觉："API 文档就是签名列表，用户问签名时模型直接答就行，不需要检索。"
**它错在**：模型得**先读到**签名才能答；签名不在检索结果里，模型只能凭记忆猜——
而那正是符号白名单要防的幻觉。API 层被当成"校验用的元数据"，而不是"可检索的内容"。

**这就是不做语料工程的代价**：文档存在 ≠ 能被召回。

## 4. 本项目的实测证据

### 4.1 语料分两层，混在一起会互相伤害

MaixPy 的语料天然是两层，不是我们切的，是上游就这样组织的：

| 语料层 | 规模 | 回答什么 | chunk 形态 |
| --- | --- | --- | --- |
| 教程层 | 119 篇中文教程 | "怎么实现某个功能" | 散文 / 代码 / 表格 |
| API 层 | 56 页 API 参考 | "这个函数的签名是什么" | 每个符号一个 chunk |

**两层都必须工程化，缺一层就有一类问题归零** [本项目实测]：
教程层**不会系统性地写出函数签名**，所以只有教程层时，`signature` 类问题在语料里根本没有答案可召回。
但也**不能因此以为"塞进同一个索引"是免费的**。见下。

### 4.2 加 API 层 chunk 的完整代价（本项目最重要的单组实测数字）

同一评测集、同一配置、**只改语料这一项**，真实嵌入（bge-m3，1024 维）的检索轴结果 [本项目实测]：

| qtype | 加 API chunk 之前 | 之后 | 变化 |
| --- | --- | --- | --- |
| **signature** | **0.000** | **0.500** | **+50 pt** |
| example | 0.250 | 0.750 | +50 pt |
| troubleshoot | 0.000 | 1.000 | +100 pt |
| **concept** | 0.625 | **0.500** | **−12.5 pt** |
| 总体 Recall@5 | 0.556 | 0.611 | +5.5 pt |

chunk 总数 **1940 → 3838**（新增 1898 个 signature chunk）。三个必须同时看到的结论：

1. **只看总分会把结论看反**：分组后才看到 +50 pt 与 −12.5 pt 同时存在。
2. **语料工程是被低估的杠杆**：没碰检索算法，只让语料里"有东西可召回"，一整类问题从 0 变成 0.5。
3. **加语料层不是免费的**：新增的 1898 个 API chunk 抢占了 Top-5 的**同一批名额**，
   把概念类问题需要的教程散文挤了出去——这是 `concept` 下降的直接原因。

> 第 3 点直接给出了 L4 查询路由的实验动机：既然两类问题需要不同的知识层，
> 就该按问题类型把检索导向对应的层，而不是让它们在一个池子里互相挤。

### 4.3 切分：按标题切，代码块与表格绝不切开

默认切分器（`maixrag/corpus/chunker.py`）是**两级**的 [设计判断]：

1. **第一级按标题结构切**：每个标题段是一个候选 chunk，`heading_path` 是它的身份。
2. **第二级只对超出预算的段再切**：按段落边界装箱并保留重叠；
   **代码块与表格不参与二次切分**——各自独立成段，且绝不切开。

这条纪律不是洁癖："切开的表格对模型毫无价值"——一张参数表被从中间截断后，
剩下的半张表**连列名都没有**，模型读到的是一堆无主的单元格。

实测可见它的后果：`max_tokens` 默认 500，但语料里**有 17 个 chunk 越过 500** [本项目实测]，
最长的两个是一张 1223 token 的表格（`zh/projects/README#h5.1`）和一个 1152 token 的代码块
（`zh/source_code/build#h9`）。**它们没有被切开，因为切了更糟。**

顺带一个从真实数据里看到的形态：3838 个 chunk 的 token 中位数是 **45**，p25 是 **27**，均值 78.8。
绝大多数 chunk 远小于 500——**切分粒度实际由文档的标题结构决定，而不是由 `max_tokens` 决定。**

### 4.4 为什么不用语义切分

语义切分（用嵌入相似度找边界，在相似度骤降处切开）是流行做法。本项目**不做** [设计判断]：

| | 标题感知切分（本项目） | 语义切分 |
| --- | --- | --- |
| 依据 | 文档自身的结构 | 嵌入相似度的相对变化 |
| 成本 | 零额外调用 | 每篇文档一遍嵌入计算 |
| 依据强度 | 结构是作者给的，确定 | 增益不稳定，与成本不相称（公开研究评价不一致） |
| 可解释性 | 边界就是标题，读者能核对 | 边界是阈值产物，难解释 |

关键差别在于：**技术文档的语义边界，作者已经用标题标出来了。**
放着作者给的、免费且确定的信号不用，去花算力猜一个可能更差的边界，不划算。
本项目把它保留为**配置里的对照项**，让读者自己跑出"多花的钱没换来增益"这个结论。

## 5. 关键术语

| 术语 | 一句话 |
| --- | --- |
| **语料层（corpus layer）** | 一类知识来源；本项目是教程层与 API 层 |
| **chunk** | 可检索的最小单元，打分与上下文装载都以它为单位 |
| **标题感知切分** | 以文档标题树为切分依据，而不是固定的 token 数 |
| **原子块（atomic block）** | 代码块与表格：独立成 chunk，且绝不二次切开 |
| **`heading_path`** | 从顶层标题到当前节的路径，既是展示信息也是检索元数据 |
| **重叠（overlap）** | 二次切分时相邻块共享的尾部，防止答案落在切缝上 |
| **signature chunk** | API 层的 chunk（限定名 + 签名 + 说明 + 参数表） |

## 6. 常见误解

这一节是这一章最重要的部分——**建立认知主要靠纠正错误认知**。

### 误解一："切得越小越精确"

小 chunk 的**打分**确实更聚焦，但它买到的是精确度，付出的是**可用性**：

- 代码块被切散 → 召回的是函数的下半截，跑不起来；
- 表格被截断 → 召回的是半张无列表格，模型读不懂；
- 散文被切碎 → `heading_path` 指不到它属于哪一节，语义完整性和标题一起丢掉。

**为什么这个错法很常见**："小块 = 更精确"在纯散文语料上确实常常成立，
而绝大多数 RAG 教程用的就是纯散文语料。一旦语料里有代码和表格（技术文档必然有），这条经验就反过来了。

### 误解二："语料越多越好"

本项目付过学费的一条：语料从 1940 涨到 3838 个 chunk，`signature` 类 +50 pt，`concept` 类 **−12.5 pt**。

**为什么这个错法很常见**："多召回一点总没坏处"听起来无害。
但 Top-K 名额是**零和的**——新 chunk 进来，就一定有旧 chunk 被挤出去。
"越多越好"只在**新内容确实有答案、且不会挤掉别的答案**时才成立。
正确的问法不是"还能不能加语料"，而是"**加了以后谁被挤出去了**"。

### 误解三："文档放进库里就能被召回到"

[事故 02](../postmortem/02-有文档却召不回.md) 的全部内容就是这一条：
API 页面抓下来了、文件在磁盘上、符号抽了 1898 个，`signature` 召回率**仍然是 0.000**。

**为什么这个错法很常见**："库里有没有"是你能打开文件夹确认的，而"能不能被召回"只能靠评测发现。
**前者看起来像证据，后者才是证据。** 一旦你去看文件夹，就会得出"语料没问题"，
然后去调检索算法——全在错的方向上。

排查顺序：**先查这个 doc_id 在索引里存在吗，再查它进过 Top-K 吗、排第几，最后才怀疑检索算法。**

### 误解四："语义切分更先进，早晚要上"

"先进"不是判据。判据是**你的语料里有没有一个免费的、确定的边界信号**。

MaixPy 的文档是作者手写标题的技术文档——**边界信号就在那里，而且不要钱**。
语义切分真正不可替代的场景是**没有结构的长文本**（会议记录、访谈稿）。
把它的适用场景和你的语料对齐一下，再决定要不要花那份算力。

### 误解五："chunk 大小调一个参数就行了"

`max_tokens` 不是切分粒度的旋钮。本项目实测：3838 个 chunk 的 token **中位数是 45**，远低于 500 的上限。
`max_tokens` 只对"某一节本身就超长"的情况生效。
如果你想要"每个 chunk 都差不多大"，那你需要的不是调参，而是**放弃按结构切**——而那正是本项目明确不选的路。

## 8. 一句话总结

> **语料工程是那个"不酷但便宜"的杠杆：分好层，按作者给的标题切，代码与表格不许切开。
> 代价是零和的——加语料之前，先问清楚被挤出去的是谁。**
