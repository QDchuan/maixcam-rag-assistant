# 06 · Agent 与链的区别

> **这一章要建立的认知**：链与 agent 的差别不在"聪不聪明"，而在**决策由谁做**——
> 链的决策写死在代码里，循环的决策由模型在运行时做。
> 这个区别不带来"更强的链"，它带来**四类全新的工程问题**。
>

## 1. 一句话

**链把"下一步做什么"写进代码；循环把它交给模型在运行时决定。**

所以循环不是"更聪明的链"，而是**多出四件必须工程化的事**：
可插拔（能力怎么解耦）、可描述（模型怎么知道有什么能力）、
可停止（预算）、可约束（权限）。

## 2. 它在链路中的位置

链与循环不是两个并列的模块，而是**两种编排方式**：循环把链的每一环
变成了它可以调用的工具。

```
链式（决策写死）：
  问题 → [检索] → [拼提示词] → [生成] → 答案
          ↑ 走哪条路、走几步，全由代码决定

循环（决策在运行时）：
  问题
   ↓
  ┌───────────────────────────────────────┐
  │  [决策：模型]  ← 本章                  │
  │      ↓                                │
  │   工具调用 ⇄ search_docs / lookup_api  │
  │              check_api_usage / list_api│
  │      ↑ 观察结果（失败也是观察结果）    │
  │      ↓                                │
  │   预算检查：轮次 / 工具调用 / token    │
  └───────────────────────────────────────┘
   ↓
  答案（+ 轨迹 + 预算消耗）
```

**输入**：一个问题 + **一份工具注册表**（模型能看见的能力清单）
**输出**：答案 + 完整轨迹（每轮调了什么、结果如何）+ 预算消耗

**下游要它做什么**：**下游要能判断"这次值不值"。** 链式的成本是固定的
（1 次检索 + 1 次生成），循环的成本是不确定的——**不确定就必须被度量**。
这就是为什么 `RunResult` 里带着 `events` 与 `budget` 快照，而不是丢进日志。

> 代码位置：`maixrag/agent/loop.py`（循环与预算）、`maixrag/agent/tools.py`（工具）

## 3. 为什么需要它（没有它会怎样）

### 3.1 一条具体的链会在哪里卡住

本项目真实的问题：**"MaixPy 里怎么做 YOLO 物体检测？给出完整例程"**。
链式的第一跳命中的是教程散文与说明文字，**没有任何一段完整例程**，
于是它只有两个选择：拒答，或者编。它真实的回答是

> 资料中没有给出 YOLO 物体检测的完整代码，因此无法提供可直接运行的完整示例。

**这已经是最好的结果了**——它没有幻觉。但对用户来说，
"资料里没有"和"这个系统没用"是同一件事。

**链式为什么救不回来**：问题不在检索质量，也不在提示词，而在结构——
它只有一次检索机会，**看见结果之后不能改检索词**；链里只有"检索"一类动作，
没有确定性工具可切（`lookup_api("maix.nn.YOLOv5")` 根本不存在）；
自然也拿不到"先查 A、再用 A 的结果去查 B"这种多跳。
**这三条都不是配置问题，是结构性缺失。**

### 3.2 一个反直觉的失败

同一个问题，第一次跑 agent（预算 4 轮）`[本项目实测]`：

```
未能完成回答，原因是：轮次达到上限（4）
已完成的部分：search_docs 成功 ×3 · lookup_api 成功 ×1
```

**它比链式更差**——链式至少给了一个明确的答案。看到这个结果，
最自然的结论是"agent 不适合这个场景"，而真相是
**agent 在做正确的多跳推理，只是预算不够它做完**（见 [事故 06](../postmortem/06-预算与任务不匹配.md)）。

### 3.3 于是这个区别带来四类新问题

不是"更强的链"，而是四件**链里根本不存在**的事。

| 新问题 | 机制 | 代码 | 不解决会怎样 |
| --- | --- | --- | --- |
| **可插拔** | 服务注册表 + 插件生命周期 | `registry.py` | 换一个检索实现要改所有 import 它的地方 |
| **可描述** | 工具注册与执行管线 | `tools.py` | 模型不知道有什么能力，或选错能力 |
| **可停止** | 循环 + 三条预算线 | `loop.py` | 一台会自己花钱的机器 |
| **可约束** | 权限与沙盒 | `sandbox.py` | 错误从"答得不好"变成"删了不该删的东西" |

## 4. 本项目的实测证据

### 4.1 4 轮预算：失败，但每一步都对

同一道 YOLO 题，4 轮预算下的真实轨迹 `[本项目实测]`：

```
第1轮  search_docs("YOLO 物体检测 例程", k=8)
第2轮  search_docs("YOLOv5 YOLOv8 YOLO11 物体检测 代码 yolo = YOLOv5")  ← 自己改写查询
第3轮  lookup_api("maix.nn.YOLOv5")                                    ← 切到确定性工具
第4轮  search_docs("yolov5.py 例程代码 detector = nn.YOLOv5 完整代码")  ← 用学到的类名重检索
       → 撞上预算上限
```

**四步里没有一步是浪费的**，第 4 步尤其关键：它把第 3 步查签名得到的
`nn.YOLOv5` 反馈回了检索——这是链式**结构上做不到**的多跳。
所以判据不是"它失败了"，而是"**它失败之前做的每件事都对**"，
这个观察直接把结论指向"预算不够"，而不是"方法不行"。

### 4.2 10 轮预算：8 轮给出可运行代码，并自检两次

同一道题，预算调到 10 `[本项目实测]`：第 1–4 轮同上，接着

```
第5轮  check_api_usage(草稿代码…)          ← 写完自检
第6轮  lookup_api("maix.nn.YOLOv5.detect") ← 补缺失的签名
第7轮  check_api_usage(修正后代码…)        ← 再校验一次
第8轮  final
```

它的代码里主动让摄像头分辨率去匹配模型的输入格式
（`camera.Camera(detector.input_width(), detector.input_height(), …)`）——
这不是文档里逐字抄来的，是理解之后写的。**同一份语料，链式给不出这一行。**

### 4.3 agent 的真实成本

同一批 **18 题**，agent 用了 **88 次工具调用** `[本项目实测]`：
`search_docs` 31 · `lookup_api` 25 · `check_api_usage` 21 · `list_api` 11，
平均 **4.9 次/题**（预算是 10 轮，说明对多数题目预算充足）。两个要点：

1. **这就是代价。** 链式固定 1 次检索 + 1 次生成，agent 是平均 4.9 次工具调用
   加对应轮次的模型调用。**这个代价必须由"答得更好"来偿还**，不能默认它值得。
2. **`check_api_usage` 被调了 21 次**——agent 在主动自检。但因果顺序要看清：
   不是"用了 agent 所以更可信"，而是因为**自检被注册成了模型可主动调用的工具**；
   链式想要这个能力，得把它变成一次固定步骤。

> **测量局限（必须说明）**：上面两段对比是定性的。在检索轴上 agent 的数字
> 反而更差（Recall@K 0.611 → 0.556）`[本项目实测]`，但那把尺子只看
> **第一次检索的 Top-5**，而 agent 是多次检索、累积证据的——**它量不了 agent**。
> 详见 [tutorial 00 · 4.3](../tutorial/00-主线导览.md)。

### 4.4 结论的正确写法

不是"agent 更好"，而是：

> **agent 的能力上限更高，但它要求预算与任务深度匹配。**
> 预算给少了，它比链式还不如；预算给够了，它做到链式做不到的事。
> 而"给多少才够"只能靠评测回答，不能靠拍脑袋。

## 5. 关键术语

| 术语 | 一句话 |
| --- | --- |
| **链（chain）** | 编排路径写死在代码里的流水线：检索 → 拼提示词 → 生成 |
| **循环（loop）** | 每轮由模型决定"再调一次工具"还是"给最终答案" |
| **agent** | 本项目**特指这个循环的运行时决策**，不是产品类别，也不是"自主智能" |
| **工具（tool）** | 能力对模型的标准暴露面：名字 + 描述 + 参数，模型据此选择 |
| **观察结果** | 工具返回值回灌给模型的那段内容；失败也是观察结果，不是异常 |
| **预算（budget）** | 一次运行的花费上限，三条线：轮次 / 工具调用次数 / token |
| **轨迹（trace）** | 结构化事件流；调试 agent 的唯一现实手段 |
| **优雅降级** | 预算耗尽时用已有证据给"部分答案"并说明缺什么，绝不静默失败 |
| **多跳（multi-hop）** | 先查 A、再用 A 的结果去查 B；链式结构上做不到 |

## 6. 常见误解

这一节是这一章最重要的部分——**建立认知主要靠纠正错误认知**。

### 误解一："agent 就是链加了个循环，肯定更好"

两半都错。前半句忽略了量级：加一个循环意味着能力必须**可插拔**、工具必须
**可描述**、循环必须**可停止**、调用必须**可约束**——链里这四件事一件都不存在。

后半句有实测反例：**预算 4 轮时，agent 在 YOLO 题上输给链式**。
这个误解之所以常见，是因为大多数 agent 教程只演示成功案例，
**从不展示"同一套代码在预算不足时更差"**。

### 误解二："预算设大点总没错"

错的方向有两个，而且是**相反**的两个：

| 预算 | 失效方式 | 用户看到什么 |
| --- | --- | --- |
| 太小（4 轮） | 多跳做不完 | "我没做完"（**显式失败**，可诊断） |
| 等于没设 | 停不下来 | 每次都"成功"、只是没有进展（**无声失败**） |

第二种更危险。跑 `python scripts/demo_budget.py` 的场景一：上限设成
30 轮 / 9999 次工具调用，它会一轮一轮烧下去，**每次工具调用都"成功"，
只是返回"找到 0 个片段"**——没有报错、没有异常，真实场景里这就是账单。

所以"默认值必须保守"不等于"该用的时候要用小值"：
**预算不是安全阀，它是任务与成本之间的谈判。**

### 误解三："agent 可以自己搞定一切"

四个前提缺一不可：能力**被注册成工具**（没注册的能力，模型不知道它存在）；
描述**写清什么时候用**（本项目因此**当场拒绝注册空描述的工具**——
没描述的工具体等于不存在）；**有停止条件**（否则不是"自主"，是跑飞）；
**在权限边界内**（否则它的错误不再是"答得不好"，而是"删了不该删的东西"，
这是性质上的差别）。

这四条**没有一条是模型能力的问题**。这也正是本项目的主线立场：
**"自主"不是免费得到的属性，是被这四块机制框出来的。**

### 误解四："agent 的指标和链式可以直接比"

检索轴的 `Recall@K` 只看第一次检索的前 5 个片段。链式只有一次检索，
那把尺子对它是完整的；agent 的正确文档出现在第 2、3 次检索里，
那把尺子**只量到了它的第一步**。

所以 `0.611 → 0.556` 不能读成"agent 更差"，只能读成**"这把尺子量不了它"**。
想真正量 agent，需要"累积证据"口径的检索指标——这是明确的待办，不是已解决的问题。

### 误解五："链和循环是两套实现，代码要写两份"

链与循环**复用同一个检索层**。循环做的事只是"把链的每一步变成工具调用"，
它不重写检索、融合、生成——那些代码一行都没动。这也解释了本项目为什么
把工具设计看得这么重：**工具的设计质量直接决定 agent 的实际能力上限**。

   并解释为什么四类问题**不能靠"更强的模型"解决**。

   说明你放弃的那两种失效在你的场景里代价多大。
3. 你怎么判断"一次 agent 的失败"是预算不够，还是方法不行？给出可操作的判据
   （不是"多试几次"）。

**链式结构上做不到**的那一步。

## 8. 一句话总结

> **链把决策写进代码，循环把决策交给模型——这不是能力的升级，是责任位置的转移。**
> 转移之后，"它会不会停下来、它能不能做这个、它该不该做这个"全部从编译期问题
> 变成运行时问题。四块机制就是这四个问题的答案，而预算是一等公民：
> **没有预算的循环不是更灵活的链，是一台会自己花钱的机器。**
