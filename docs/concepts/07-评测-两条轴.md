# 07 · 评测：两条轴

> **这一章要建立的认知**：RAG 没有编译错误，"跑通了"不是证据。
> 唯一能回答"改动改好没有"的方法，是**把质量拆成两条互不相干的轴分别测**，
> 并让每条指标暴露自己**覆盖了多少题**。

## 1. 一句话

**评测的任务是：把"答得好不好"拆成两条轴——检索轴（该召回的进没进 Top-K）
与生成轴（给了正确片段有没有用好）——并让每条轴都能被程序判定。**

两类失败的修法几乎没有交集，所以必须分开报，不能合成一个总分。

## 2. 它在链路中的位置

```
              ┌──────────── 本章管的就是这一整圈 ────────────┐
              ↓                                              │
用户问题 → [检索] → [融合/重排] → [生成] → 答案                 │
              ↑                        ↑                     │
         检索轴测这里              生成轴测这里                │
              └──────────►  [评测器]  ◄───────────────────────┘
                               ↓
                 两条轴报告 + 按 qtype 分组 + 每条指标的覆盖面
                               ↓
                 决定下一步改 L2/L3/L4（语料与检索）还是 L5（生成）
```

**输入**：评测集（每题带 ground-truth 的 `required_docs` / `required_spans`，
以及生成轴的 `must_contain` / `must_not_contain`）+ 待评配置的一次运行结果。

**输出**：两轴总览分数、按 qtype（`concept` / `signature` / `example` /
`troubleshoot`）的分组、每题明细，以及**每条指标覆盖了多少题**。

**下游要它做什么**：它是**唯一有资格说"该改哪一环"的装置**——消融实验要判断
"这一招值不值"，回归门禁要判断"有没有把别处弄坏"，两者都要**归因**。
这就是报告必须**两轴并列**的原因（[设计文档 03 第 2 节](../design/03-评测与质量提升路线.md)）。

## 3. 为什么需要它（没有它会怎样）

普通软件有一条极强的反馈回路：**编译不过就是错了，测试红了就是错了**，
强到足以形成"没报错 ≈ 没问题"的习惯。RAG 把这条回路整根抽掉了：
输出永远通顺，退出码 0；错误不会让任何东西变红，它只会**安静地**变成一句很客气的话。

**现场一，答案错了但读起来正常。** 问题 `q005`"MaixPy 里怎么做 YOLO 物体检测？
给出完整例程"，链式基线（L1）的回答是"资料中没有给出完整代码，因此无法提供
可直接运行的完整示例"。挑不出语言毛病——但它是**失败的结果**：
同样的问题、同样的语料，10 轮预算的 agent 给出了可运行代码。

**现场二，数字错了但落在合理范围里。** [事故 04](../postmortem/04-被清空的统计.md)
里，18 道题的工具调用被统计成 **2 次**（0.1 次/题）——不是 0、不是负数，
所以像真的，直到有人记得"单跑一道 YOLO 题就调了 7 次"。

**没有这一环，"调优"不成立**：你无法区分自己在改善系统，还是在许愿。

## 4. 本项目的实测证据

**(a) 报告的 judge 一栏是 `(未使用)`** `[本项目实测]`
（`eval/results/rag_L1_rag[rrf_dense+bm25].md`，18 题 / Top-K=5）

引用精确率 0.889、引用召回率 0.889、禁止项触发 0.000、符号级幻觉率 0.000、
拒答率 0.000——**全部由程序算出**，没有一个需要模型打分。

**(b) 第一个消融：总体 +5.5pt 掩盖了两类相反的变化** `[本项目实测]`

同一评测集、同一配置，**只改语料这一项**（给 API 参考页产出可检索 chunk）：

| qtype | n | 改前 | 改后 | 变化 |
| --- | --- | --- | --- | --- |
| signature | 4 | 0.000 | 0.500 | **+50 pt** |
| example | 4 | 0.250 | 0.750 | +50 pt |
| troubleshoot | 2 | 0.000 | 1.000 | +100 pt |
| **concept** | 8 | 0.625 | **0.500** | **−12.5 pt** |
| **总体 Recall@5** | 18 | 0.556 | 0.611 | **+5.5 pt** |

**只看总体，这是"小幅有效"；按 qtype 看，是"两类大幅改善、另一类被拖累"。**
而且实跑只有 **18 题**（设计稿定 60 题），`signature` 仅 4 题——一分之差就是 25 pt：
分组数字要看**方向**，不看小数位。

**(c) 主指标为什么是召回率** `[本项目实测]`

L1 报告里 q005（YOLO 例程，`example` 类）召回率 **0.00**，模型因此按纪律拒答——
生成轴的"符号级幻觉率 0.000"其实是这次**检索失败的下游症状**。
**没召回的内容，生成阶段救不回来；它还会伪装成生成阶段的好消息。**
改前的 signature 类也是 **0.000**：检索是硬上限。

**(d) 让覆盖面可见** `[本项目实测]`

`scripts/inspect_eval.py` 对每条指标打出覆盖题数，抓到的第一个现场：

```
  **符号被检查到的题数  0/18  (0%)**
  ⚠️ 没有任何题目被检查到符号——幻觉率 0.000 不具参考意义
```

修掉检索问题后，同一个数字变成 **16/18，幻觉率仍为 0.000**——
**这次它是真的，因为覆盖面接近满的（16/18，余下 2 题没有符号可检查）。**

## 5. 关键术语

| 术语 | 一句话 |
| --- | --- |
| **检索轴** | 该出现的片段有没有进 Top-K；失败叫召回失败 |
| **生成轴** | 上下文里已有正确片段时，答案是否忠实、可追溯 |
| **Recall@K** | ground-truth 片段中被召回的比例——本项目的主指标 |
| **符号级幻觉率** | 代码里不存在于 API 白名单的符号占比，**程序可判** |
| **覆盖率** | 一条指标实际在多少道题上有样本（分母），必须随指标一起报 |

## 6. 常见误解

### 误解一："跑通了就是对的"

**错在哪**：把"没有编译错误/没有异常"当成正确性证据。RAG 里这个信号几乎不存在——
错答案和对话式拒答在日志里长得一模一样。

**为什么常见**：日常开发里"没报错"确实几乎等于"没问题"，习惯迁移过来就失效了。
修法不是"更仔细一点"，而是**让失败变成显式的**：空结果必须是一个错误，
不是一个答案（[事故 01](../postmortem/01-静默的空结果.md)）。

### 误解二："整体分数提升就说明改动有效"

**错在哪**：总分会把方向相反的变化**平均掉**：总体 Recall@5 **+5.5 pt**，
底下是 signature **+50 pt** 与 concept **−12.5 pt**。跨形态比较更是如此：
agent 是累积检索的，`Recall@K` 只量到它第一步——早期实测 agent 0.556 < 链式 0.611，
补上 `read_doc` 之后又变成 **0.667 > 0.611**。**同一个口径，偏差会翻转**，
因为它数的是"命中片段数"，而"什么算命中"会随被测对象改变（见
[tutorial 07 · 失败一](../tutorial/07-端到端.md)）。

**为什么常见**：报告默认只算总分，总分也是唯一被写进简报的那个数；
分组需要预设——**没人会主动去看一个他没想到要看的切面**。

### 误解三："LLM 打分方便，全都交给它"

**错在哪**：引用编号对不对、符号在不在白名单里，都是**确定的程序问题**，
交给 judge 只引入位置偏差、长度偏差、分数坍缩。本项目两份真实报告里 judge
都是"`(未使用)`"，数据模型里 `faithfulness` 是 `float | None`
（定义在 `maixrag/evaluation/harness.py` 的 `GenerationMetrics`）——
**没测就是 None，不是 0**。

**为什么常见**：它最省事，很多框架也把它当默认。但另一面是：
**程序判定也不是免检的**。[事故 03](../postmortem/03-校验器把正确代码判成幻觉.md)
里，校验器把 `from maix import gpio` 产生的 `maix.gpio.GPIO` 判成幻觉，
白名单从 2996 补到 4868 条才修好——**误报率必须被量出来**。

### 误解四："0.000 的幻觉率说明防幻觉成功"

**错在哪**：0.000 有两种含义——**真的很好**，或者**几乎没测到东西**。
两者在报告里长得一模一样，却指向完全相反的行动。本项目真的踩过：
符号被检查到的题数 **0/18**，而且这个 0.000 是**检索失败的下游症状**。

**为什么常见**：指标把"没有证据"和"证据表明没问题"编码成同一个数字
（没有样本时返回 `0.0`）。这不是算错，是**报告设计的缺陷**——
修法不是改公式，而是让分母必须出现（[事故 05](../postmortem/05-伪装成好消息的0.md)）。

## 7. 这一章留下的问题

读到这里，你应该能回答下面这些问题。**答不出来说明前面没读透。**

答案在 [`exercises/answers/07-评测-两条轴.md`](../exercises/answers/07-评测-两条轴.md)。

1. 为什么"检索命中但答案错误"和"检索未命中且答案错误"必须分开统计？
   合成一个"答对率"会丢掉哪个关键信息？
2. `0.000` 在什么条件下是"真的很好"，什么条件下是"没测到东西"？
   报告里该用什么字段区分这两者？
3. 引用精确率、符号级幻觉率都能程序判，`faithfulness` 不能。
   你交给 judge 的清单是什么？**判据**是什么？
4. 一个改动让总体 Recall@5 +5.5 pt，但 concept 类 −12.5 pt。
   如果你的用户里 80% 问的是概念类问题，你会怎么处理？（必须含代价分析）

**动手题**见 [tutorial 00 主线导览 · 4.5](../tutorial/00-主线导览.md)：
跑一次链式基线、一次 agent 评测，再用 `scripts/inspect_eval.py` 看每条指标覆盖了多少题。

## 8. 一句话总结

> **RAG 没有编译错误，所以"跑通了、输出通顺、看起来专业"都不是证据。
> 唯一的证据是：两条轴分开测、按 qtype 分组看、每条指标自带分母——
> 而主指标只有一个，就是该召回的东西有没有进 Top-K。**
