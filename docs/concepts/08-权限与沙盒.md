# 08 · 权限与沙盒

> **这一章要建立的认知**：权限不是给 agent 加一层保险，它决定**这个 agent 存在的形态**——
> 能做哪类事、能对多大范围做、做之前要不要问人。
>
> 相关：[tutorial 00 主线导览 · 2.5](../tutorial/00-主线导览.md) ·
> [事故 01 静默的空结果](../postmortem/01-静默的空结果.md) ·
> 习题：[`exercises/concepts/08-权限与沙盒.md`](../exercises/concepts/08-权限与沙盒.md)

## 1. 一句话

**权限层回答的不是"它答得好不好"，而是"它能不能做这件事"。**

三层边界各答一问：能做哪类事（能力）、能做到多大（范围）、什么必须问人（审批）。
贯穿三层的是同一条原则：**拿不准就拒绝**。

## 2. 它在链路中的位置

```
用户问题
   ↓
[agent 循环] ← 模型决定下一步（见 06 章）
   ↓ 产生一次工具调用
[工具执行管线]
   1. 工具存在吗
   2. 参数合法吗
   3. 权限：能力 → 范围 → 审批   ← 本章
   4. 真正执行
   ↓ denied / 结果
[结果回灌给模型] → 下一轮
```

**输入**：一次工具调用（工具名 + 参数）、当前策略，以及这个工具**自己声明**的
`requires` 与 `path_params`。
**输出**：放行，或者一条 `denied` 分类的结果。
**下游要它做什么**：把"不能做的事"变成**模型能看见的一次失败**，而不是异常，也不是静默成功。

最后一件事决定了这一环的形状：

1. **检查必须在执行之前。** 事后检查只能告诉你损失有多大——所以越界调用是"根本没有执行"，
   而不是"执行后报错"。
2. **顺序是能力 → 范围 → 审批。** 前两层是确定规则，最后才轮到打扰人的那层；
   反了会让一次本来就会被能力边界拒掉的调用先去弹一次审批窗口，白打扰人一次。

## 3. 为什么需要它（没有它会怎样）

从一次真实的失败讲起。`scripts/demo_sandbox.py` 场景一：`write_file` 写一个
**工作区之外**的路径，结果成功。真实场景里，这就是"删了不该删的东西"那一步。

| | 回答类错误 | 权限类错误 |
| --- | --- | --- |
| 表现 | 答错、答偏、拒答 | **动了不该动的东西** |
| 可回滚 | 重问一次 | 删掉、覆盖的可能回不来 |
| 谁先发现 | 用户读答案时 | 事后 |

**这是性质上的差别，不是程度上的差别**——所以它不在"生产环境再补"的清单里。

更隐蔽的是：没有权限层时，问题不报错，只会消失。本项目工具层的默认策略是"放行一切"，
装配时没传策略用的也是完全不限制的那一档。**"忘了配权限"不会让程序崩，
只会让它安静地什么都能做**——与 [事故 01](../postmortem/01-静默的空结果.md) 同一个形状。

## 4. 本项目的实测证据

**一、同一调用，装上策略后被拦住，而且根本没有执行** [本项目实测]

同一个 `write_file`、同一个越界路径，换成"只能读写工作区"后是拒绝，执行记录为空
（`scripts/demo_sandbox.py` 场景一 vs 场景二）。

**二、三种绕过方式，字符串前缀判断全部放行** [本项目实测]

| 绕过方式 | 形态 | 字符串前缀 | 规范化 + 解析链接 |
| --- | --- | --- | --- |
| 兄弟前缀目录 | `<base>/workspace-evil/x.txt` | 放行 | **拦住** |
| 两点向上穿越 | `workspace/../secret.txt` | 放行 | **拦住** |
| 符号链接逃逸 | `workspace/link -> <base>` | 放行 | **拦住** |

第一条最关键：那个路径**确实**以 `<base>/workspace` 开头。正确做法是**先 `resolve()`
规范化并解析符号链接，再用 `relative_to` 做包含判断**（它正确处理分隔符边界，
`workspace-evil` 不以 `workspace/` 开头）。**"拦住了"和"拦对了"是两回事。**

**三、失败关闭的落点** [本项目实测]

没有审批人时，需要审批的能力（演示里是 `net`）判为拒绝并标记"需审批"，而不是放行；
路径解析失败同样判为不允许。理由一句话：一个"没人问就放行"的默认实现，
会让所有审批在无人值守时静默通过——那正好把这一层作废。

**四、同一条命令，权限不同结果完全不同** [本项目实测]

受限环境里因为拿不到 TLS 凭证而失败（`SEC_E_NO_CREDENTIALS`），放开权限后成功返回 200
（记录见 [设计 06 · 2.3.1](../design/06-项目结构与两条分支.md)）。

**五、测试里的显式跳过** [本项目实测]

项目 228 个测试（227 通过 + 1 显式跳过），跳过的正是符号链接逃逸那条：
Windows 上建符号链接需要额外权限。做法是**显式跳过，而不是把没验证过的结论当通过**。

> ⚠️ **边界说清**：两轴评测里**没有权限轴**，所以这一层没有 Recall@K 那样的数字。
> 上面给的是可复现现场与断言，不是"权限层覆盖率"。这是范围取舍，不是遗漏。

## 5. 关键术语

| 术语 | 一句话 |
| --- | --- |
| **能力边界** | 能做哪类事：读 / 写 / 执行 / 联网，工具用 `requires` 声明 |
| **范围边界** | 能做到多大：可读、可写的根目录 |
| **审批边界** | 什么必须问人：判定不自行决定，把请求交出去 |
| **失败关闭** | 拿不准就拒绝：没人可问、解析失败、类型不对 |
| **规范化（resolve）** | 折成唯一路径形式，并解析符号链接 |
| **`path_params`** | 工具显式声明哪个参数是路径；靠猜参数名是漏洞的常见来源 |
| **审计** | 第四层：记录每次拒绝与放行。本项目**没做**，真实系统必须有 |

## 6. 常见误解

这一节是这一章最重要的部分——**建立认知主要靠纠正错误认知**。

### 误解一："权限是生产环境的事，教学或原型不用管"

错在把权限想成程度问题：好像原型只是少一层保险，以后补上就行。
**它改变的是错误的形式**。本项目自己就是反例：它在开发期就撞见过"同一条命令，
权限不同、结果完全不同"。原型阶段照样会撞上这种事。

### 误解二："加了白名单就安全了"

白名单只回答第一层。它不回答"能写多大范围"，也不回答"谁批准"——
一个只允许 `fs:write` 的策略仍然能覆盖工作区外的文件，场景一就是活证。

白名单还有实现陷阱：**匹配方式决定它是否真的成立**。本项目命令白名单用的是字符串前缀
匹配，就代码事实而言，`ls` 开头的任意命令形态都会被放行。要不要做命令解析属于工程细节
取舍 [设计判断]；但"有白名单"和"白名单拦得住"不是同一句话。

### 误解三："路径检查用 startswith 就行"

这是三种绕过方式全部放行的原因。`startswith` 比的是**字符串**，越界检查判的是
**目录包含关系**。差别就在一个字符上：`/workspace-evil` 以 `/workspace` 开头，
却不以 `/workspace/` 开头。

这个错误特别常见，因为**它看起来是对的**：代码读起来完全合理，
测试如果只测"工作区内的正常路径"，它会一路通过。

### 误解四："没人审批就默认放行，等有人了再问"

这会把审批层做成摆设：无人值守时（脚本、评测、后台任务），所有需要审批的操作静默通过，
**甚至不出现在日志里**。正确方向是失败关闭：没人可问就拒绝，并显式标记为"需审批"。

### 误解五："拒绝得越多越安全"

拦过头同样是坏设计。[事故 03](../postmortem/03-校验器把正确代码判成幻觉.md) 的结论
在权限层同样成立：**假阳性比漏报更危险**。一个动不动就拒绝正常操作的权限层会被绕过
或关掉，那时真正的边界也没了。判据不是拒绝得多不多，而是**每次拒绝都说得出是哪一层的
哪条规则**——所以本项目把当前策略做成了人能读出来的形式。

## 8. 一句话总结

> **权限层不是"回答得好不好"的补丁，它决定这个 agent 能做什么。
> 三层各管一件事，而贯穿三层的是同一条原则：拿不准就拒绝。
> 最危险的不是拦不住，而是"以为拦住了"——字符串前缀就是那个假象。**
