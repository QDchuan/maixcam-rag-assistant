# 04 · 融合与重排序

> **这一章要建立的认知**：融合与重排序不是"让检索更准"的魔法，它们做的是同一件事——
> **分配 Top-K 的名额**；而名额怎么分必须由数据决定，不能靠"加一层总没坏处"。
>
> 相关：[tutorial 04 检索与消融](../tutorial/04-检索与消融.md)·
> [事故 02 有文档却召不回](../postmortem/02-有文档却召不回.md) ·

## 1. 一句话

**融合：把两份榜单合成一份，让"两个检索器都说好"的片段拿到名额。**
**重排序：先用快而粗的方法捞一大池，再用慢而准的方法把池子重新排队。**

两者**不增加知识**，只改变"谁能进上下文"。

## 2. 它在链路中的位置

```
用户问题
   ↓
[查询分析] ← 本章不涉及
   ↓
┌────────────────────────────────────┐
│  L4 检索层                          │
│   ├─ 稀疏 BM25 → 榜单 A（无界分）   │
│   └─ 稠密 向量 → 榜单 B（0–1 分）   │
│           ↓                        │
│     融合（RRF / 加权） ← 本章上半   │
│           ↓  候选池（本项目取 20）  │
│     重排序（rerank）   ← 本章下半   │
└────────────────────────────────────┘
   ↓  最终 Top-5
[生成] / [agent 工具 search_docs] → 答案
```

**输入**：多份各自排好序的榜单，每个片段带 `rank` 与原始 `score`
**输出**：一份统一排名的 Top-K 名单
**下游要它做什么**：生成层只有 K 个名额。**没进这 K 个名额的片段，下游再强也看不见。**
所以这一环是**名额分配**：召回决定池子里有没有正确答案，融合与重排决定它能不能排上来。

## 3. 为什么需要它（没有它会怎样）

### 3.1 两个检索器的盲区不重合，只用一个一定会漏

上一章的实测已把这件事摆出来。查询 `maix.camera.Camera`：BM25 前三名全在
`vision/camera`，一次命中；稠密检索给出的却是 `vision/line_tracking`、`vision/qrcode`、
`vision/find_barcodes`——**完全找不到方向**（稠密那侧用的是**假嵌入**，不能代表真实嵌入）。

反方向同样真实。YOLO 那题里 `zh/vision/yolov5` 是唯一系统讲这件事的页面，却**没进 Top-5**；
查 `YOLOv5 物体检测` 时 BM25 返回的是 `online_converter`、`README_MaixCAM` 这些
**顺带提到**它的页面。对此的解释是有依据的猜测 [推测]：`YOLO`、`物体检测` 在语料里太常见、
IDF 偏低，于是"专讲这件事的那一篇"赢不过"顺带提到的一大堆"。

**两种失败方向相反**：稀疏输在"词太常见"，稠密输在"字符串太罕见"。
**这就是融合的动机——不是更先进，而是不让某类查询掉进对方的盲区。**

### 3.2 融合：只用排名，不用分数（RRF）

本项目默认用 RRF：

```
score(d) = Σ_r  w_r / (k + rank_r(d))
```

它只读 `rank`、不看原始分数，因此**不需要处理不同检索器的量纲差异**——
稠密分数在 0–1、BM25 分数无界，两者相加本身没有意义，而 RRF 里只有名次。

`k`（默认 60）起**平滑**作用：它压低了"第 1 名"相对"第 2 名"的权重差距，k 越大越趋于平权。
它换来这条性质：

> **"多个检索器一致认可"比"单一检索器的极端排名"更重要。**

### 3.3 加权分数融合：一个必须亲手踩一次的坑

把分数加权相加看起来更"信息充分"，它确实用上了分数里的强度信息。问题是**量纲**：
BM25 对一次罕见词命中可以打几十分，稠密相似度最多 1.0——直接相加时
**BM25 单方面主导排序**，稠密那一侧等于没参与。

常见的补法是各自归一化，而归一化方式本身又是会影响结果的参数。本项目的实现是
**在各自榜单内除以最高分**再加权：量纲被压平了，代价是对"该榜单最高分是谁"极其敏感——
**一个离群的极端高分会把同榜单其他候选压到接近 0，等于让这个检索器在融合里失效。**

本项目把它**作为对照保留**（`fusion: weighted`），不默认使用，教学价值就是让读者自己
踩一次"分数不能直接加"。

### 3.4 重排序：召回要广度，精排要精度

融合之后池子里通常已有正确答案，只是排得不够前。这时做的不是"再检一遍"，
而是**换一个更贵的打分方式重新排队**：

| 阶段 | 方法 | 特点 | 目标 |
| --- | --- | --- | --- |
| 召回 | BM25 / 向量 | 快、粗；查询与文档**各自独立**编码 | **广度**：别漏 |
| 精排 | cross-encoder / LLM 打分 | 慢、准；查询与文档**互相看见** | **精度**：排对 |

两档精排都规划了（后者零额外依赖但慢且贵），但**默认关闭**（`rerank.enabled: false`）——
它换来"可能更靠前的排序"，付出的却是每次查询的确定性延迟：
**增益必须先被看到，才轮得到决定要不要付这个代价。**

## 4. 本项目的实测证据

**已经跑通的**（检索轴报告 RRF over dense+bm25，见 `eval/results/rag_L1_rag[rrf_dense+bm25].md`）：
Recall@K **0.611**、Hit Rate@K 0.667、MRR 0.453、Context Precision 0.267（均 [本项目实测]）；
分组后 `concept` 0.500、`signature` 0.500、`example` 0.750、`troubleshoot` 1.000 [本项目实测]。
**最弱与最优差了一倍**，所以要优化的不是总分，而是被拖住的那一类。

**名额的零和性有直接测到的证据** [本项目实测]：加 API 层之后，signature 召回
0.000 → 0.500（+50 pt），concept 却 0.625 → 0.500（−12.5 pt），总体只从 0.556 走到 0.611
（+5.5 pt）——新增的 1898 个 signature chunk **抢占了 Top-5 名额**。
**融合与重排做的正是同一件事——分名额。**

**已经测到的部分** [本项目实测]——这是本项目 L3 消融的结果，纯检索轴、同一评测集：

| 配置 | Recall@K | MRR |
| --- | --- | --- |
| 只 dense | 0.611 | **0.557** |
| 只 bm25 | 0.444 | 0.335 |
| **RRF 融合** | **0.611** | **0.453** |

**融合没有提升 Recall，MRR 还夹在两者中间。** 这是个诚实的、有点失望的结果
（报告在 `eval/results/rag_L1_rag[rrf_dense|rrf_bm25].md`）。

它正好印证了本章开头那句话：**融合做的是"分名额"**。当两路检索器的强项重叠时，
融合拿不到额外收益；而当一路明显更弱（这里是 bm25，0.444）时，
按排名平等的 RRF 会把弱路的错误也平权地抬进来，于是 MRR 反而下降。

> **所以"默认选 RRF"是 [设计判断]，不是实测结论。** 依据是它的性质
> （只用排名、不引入归一化环节），而不是"它一定更好"。

**还没测到的部分：**

- **重排序的"增益 vs 延迟"曲线没有数字。** 报告里 P50 的 4,622 ms 是端到端（含生成）的数，
  **不能当作检索耗时**。
- **rerank 目前只有配置字段，没有实现**——`RerankConfig` 定义在 `maixrag/config.py`，
  但 `maixrag/retrieval.py` 里没有任何代码产出 `retriever="reranked"`。
  所以本章的 rerank 讨论是**设计层面的**，不是已落地的能力。
- 外部最有名的那组数字（上下文增强三档让检索失败率降低 35% / 49% / 67%）是 **[厂商自测]**，
  未找到独立复现，因此**不作为选型依据**。

**一处实现取舍** [设计判断]：融合前每路各取 `max(k, 20)` 个候选——池子太浅时融合会退化成
随便挑一个；这也划出了 rerank 的边界：**它只能在池子里重排。**

## 5. 关键术语

| 术语 | 一句话 |
| --- | --- |
| **融合（fusion）** | 把多份榜单合成一份统一排名的名单 |
| **RRF** | Reciprocal Rank Fusion：只用名次算分，`Σ w_r/(k+rank_r)` |
| **`k` / `w_r`** | RRF 的平滑常数（默认 60，越大越平权）与每路权重（默认全 1） |
| **量纲** | 分数的取值范围（稠密 0–1，BM25 无界）；不一致时不能直接相加 |
| **候选池（pool）** | 融合与精排的处理范围，本项目取 `max(k, 20)` |
| **精排 / rerank** | 召回之后用更贵的模型对候选重新排序 |
| **cross-encoder** | 查询与文档一起进模型打分；比双塔式相似度准，但慢 |
| **共模错误** | 两个检索器因同一个原因同时判错——融合消不掉这种错 |

## 6. 常见误解

### 误解一："融合就是把分数加起来"

分数不能直接加，因为两个检索器的分数**不在同一个坐标系里**：稠密相似度 0.82 与
BM25 的 31.4 之间没有可加性。可加的是"名次"（RRF）或"归一化后的相对强度"（加权融合）。

这个错法常见，因为它符合直觉——两路都给出分数，加起来天经地义。后果是
**其中一个检索器被静默架空**：报告里 fusion 那一栏看起来正常，实际稠密那侧已不影响排序。

### 误解二："rerank 一定更好，所以先开上再说"

rerank 是**用延迟买精度**，至少有三个前提：①正确片段**已经在候选池里**——没召回的东西
精排排不出来；②池内排序**确实需要被纠正**；③增益**被自己测出来过**，不是"别人说好"。
本项目默认关闭，正是因为第 ③ 条还没满足。

这个错法普遍，是因为 rerank 在外部材料里几乎总以"提升了多少"的形式出现，
而它的延迟与成本很少被并列写在旁边。

### 误解三："两个检索器都排第一，那它肯定最相关"

RRF 的平滑确实在奖励这种一致性，但一致性**不等于正确**：

- **共模错误**：两个检索器被同一个因素带偏。YOLO 那题里 `物体检测` 在多篇文档中高频出现，
  稀疏与稠密都可能把它当强信号，于是**一起**把"顺带提到"的页面顶上去。
- **"第一"只是在各自池子里第一**，而两个池子由同一个查询产生，共享同一个错误前提。
- **它仍可能进不了最终 Top-K**：名额有限，别的片段在两路都排第二、第三，靠累积分数反超。

所以融合的产出应当被当作**候选**，而不是**判决**——这正是重排序存在的位置。

## 8. 一句话总结

> **融合与重排序都在分同一个东西——Top-K 的名额。**
> 融合用"名次"投票，绕开了量纲这个坑；重排序用更贵的模型重新排队，买精度、付延迟。
> **两者都只能在池子里工作**：池子里没有的答案，任何排序技巧都救不回来。
