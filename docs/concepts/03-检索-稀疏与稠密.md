# 03 · 检索：稀疏与稠密

> **这一章要建立的认知**：检索不是"把文档变成向量然后算相似度"。
> 它是**两种互补的信号**——词面匹配与语义匹配——以及知道什么时候该信哪一个。
>
> 相关：[tutorial 04 检索与消融](../tutorial/04-检索与消融.md)·
> [事故 02 有文档却召不回](../postmortem/02-有文档却召不回.md) ·
> 习题：[`exercises/concepts/03-检索-稀疏与稠密.md`](../exercises/concepts/03-检索-稀疏与稠密.md)

## 1. 一句话

**检索的任务是：从一堆片段里，找出对回答这个问题有用的那几个。**

而"有用"有两种完全不同的判据，这就是这一章的全部内容。

## 2. 它在链路中的位置

```
用户问题
   ↓
[查询分析] ← 本章不涉及
   ↓
┌─────────────────────────────┐
│  检索                        │  ← 本章
│   ├─ 稀疏（BM25）：按词匹配   │
│   └─ 稠密（向量）：按语义匹配 │
│          ↓                   │
│       融合（下一章）          │
└─────────────────────────────┘
   ↓
[重排序] → [生成] → 答案
```

**输入**：一个查询（可能已经是改写过的）
**输出**：k 个片段 + 每个片段的分数
**下游要它做什么**：把这些片段塞进模型的上下文，让模型基于它们作答

> **一个必须记住的约束**：检索是**一次筛选**，不是一次判断。
> 它决定"模型能看到什么"。**没进上下文的片段，后面的环节再强也救不回来。**
> 这就是为什么召回率是主指标（见 [07 评测](./07-评测-两条轴.md)）。

## 3. 两种判据

### 3.1 稀疏检索：按"词出现没出现"打分

**代表**：BM25。它的核心是三个直觉：

1. 一个词在**这篇文档里出现得多**，这篇文档就更相关（词频 tf）；
2. 一个词在**所有文档里出现得少**，它的区分力就强（逆文档频率 idf）；
3. 一篇**很长的文档**天然会包含更多词，所以要惩罚它（长度归一化）。

把这三条写成一个公式就是 BM25：

```
score(q,d) = Σ_t  IDF(t) · (tf(t,d)·(k1+1)) / (tf(t,d) + k1·(1-b+b·|d|/avgdl))
```

**它的关键特性是"字面"**：把文档切成词，看词对不对得上。
所以它对 `maix.camera.Camera` 这种**精确字符串**极其敏感，也对拼写错误极其脆弱。

### 3.2 稠密检索：按"意思像不像"打分

**做法**：用一个嵌入模型把查询和文档都变成向量，算余弦相似度。

**它的关键特性是"语义"**：它不看词，看的是"这两段话在说同一件事吗"。
所以：

- 能匹配"怎么拍照" ↔ "camera 用法"（词面完全不同）；
- 但**对罕见字符串会失灵**：`maix.image.Image.to_grayscale` 这类标识符
  在训练语料里出现太少，嵌入模型没为它学过一个好位置。

### 3.3 一个必须看清的事实：两者不是替代关系

| 查询类型 | 稀疏 | 稠密 |
| --- | --- | --- |
| `maix.camera.Camera 的参数` | **强**（字面命中） | 弱（标识符罕见） |
| `拍一张图存起来` | 弱（"拍照"没出现） | **强**（语义相近） |
| `报错找不到摄像头怎么办` | 中 | 中 |
| `find_blobs` | **强** | 弱 |

**没有哪一种是"更好的检索"**，只有"这个查询更适合哪一种"。

## 4. 本项目的实测证据

这不是理论推演。本项目在真实语料（MaixPy 文档，3838 个 chunk）上跑出来过。
下面两组是**真实嵌入**（bge-m3，1024 维）下的实际排名，可以用
`python scripts/demo_retrieval.py -k 3 --query "<查询>"` 逐字复现：

**查询 `find_blobs thresholds 色块`**

```
[bm25]                                     [dense]
1. zh/vision/find_blobs#h3.1   code        1. zh/vision/find_blobs#h3.8   prose
2. zh/vision/find_blobs#h2     prose       2. zh/vision/find_blobs#h2     prose
3. zh/vision/find_blobs#h3.8   prose       3. zh/vision/find_blobs#h14.1  table
```

**查询 `maix.camera.Camera`**

```
[bm25]                                     [dense]
1. api/maix.camera.Camera      signature   1. api/maix.camera.Camera      signature
2. api/maix.webrtc.WebRTC.bind_camera      2. api/camera.Camera           signature
3. api/maix.rtsp.Rtsp.bind_camera          3. api/maix.video.Video        signature
```

**第一篇是稀疏检索占优**——查询里有精确标识符，BM25 一次命中；稠密那边则**分散**在
同名符号的其他写法上（`api/camera.Camera`、`api/maix.video.Video`）——
**它给的是"语义相近的邻居"，不是"这个符号本身"。**

> ⚠️ **这两组数字的边界**：
> ① 它们的 `chunk_id` 形如 `<doc_id>#h<序号>`，是**标题感知切分**的编号；
> 早期版本用的是 `#code` / `#prose` 这种按类型的编号，两者不可混读。
> ② 稠密那一侧**只有真实嵌入的排名才是结论**。哈希词袋（假嵌入）的排名
> 证明的只是"管线通了"；本项目早期记录过一组假嵌入的结果（那时稠密的
> 前三名会跑到 `vision/line_tracking`、`vision/qrcode` 这种完全无关的页面上），
> 那组数字**不能代表真实嵌入**——现在 `demo_retrieval.py` 载入的索引就是真实
> bge-m3，所以**磁盘上已经没有能重建那组假嵌入数字的入口**。
> 这正是为什么**换掉假嵌入之前，所有检索数字都没有意义**。

## 5. 关键术语

| 术语 | 一句话 |
| --- | --- |
| **召回（recall）** | 该找到的片段，有多少真的进了 Top-K |
| **精确（precision）** | 进 Top-K 的片段，有多少真的相关 |
| **Top-K** | 取前 K 个片段放进上下文 |
| **tf / idf** | 词频 / 逆文档频率，BM25 的两个核心量 |
| **嵌入（embedding）** | 把文本变成向量，让"语义距离"可计算 |
| **余弦相似度** | 两个向量的夹角——方向上像不像，与长度无关 |
| **混合检索** | 同时用稀疏与稠密，再融合（见下一章） |

## 6. 常见误解

这一节是这一章最重要的部分——**建立认知主要靠纠正错误认知**。

### 误解一："稠密检索更先进，所以应该只用它"

"先进"不是判据。**判据是"你的查询属于哪一类"**。

MaixPy 文档的查询里混着大量 API 标识符（`maix.camera.Camera`、`find_blobs`），
而这些正是稠密检索最弱的地方。只看"哪种更先进"会直接砍掉一半的检索能力。

### 误解二："BM25 是上个时代的东西，用它是开倒车"

BM25 有一个稠密检索很难替代的性质：**确定性**。
词在文档里出现了就是出现了，没有"大概"。

对"这个函数名存不存在"这类问题，确定性比语义相似更有价值。

### 误解三："召回率低就加大 top_k"

加大 top_k 只会让更多**不该进的片段**进上下文，把噪声也带进去。
召回率低通常是**语料层的问题**而不是参数问题——
本项目的 [事故 02](../postmortem/02-有文档却召不回.md) 就是：
`signature` 类召回 0.000，根因是"API 文档根本没产出 chunk"，
把 top_k 从 5 调到 50 也没用。

### 误解四："向量库里没结果就是没相关内容"

`[]` 有两种含义：**"确实没有"** 或 **"有，但没被召回到"**。
这两者在代码里长得一样，但处理方式完全相反。

这是 [事故 01](../postmortem/01-静默的空结果.md) 的主题：
**空结果必须是一个错误，不能是一个答案。**

## 8. 一句话总结

> **稀疏看"词对不对得上"，稠密看"意思像不像"。
> 没有哪个更好，只有哪个更适合你这一类查询——
> 而"你这一类查询"是什么，必须靠评测分组看出来，不能靠猜。**
