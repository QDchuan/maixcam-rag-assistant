### 概念类答案：给推理链，不只给结论

**Q1. 报告只留一个"答对率"，会永久丢失哪一类归因？**

答错只有两种可能：**正确片段没进 Top-K**（检索失败，改语料 / 切分 / 检索器 / 查询理解），
或者**正确片段在上下文里而模型没用**（生成失败，改提示词 / 上下文组织 / 模型能力）。
这两类失败的修法几乎没有交集——所以合成一个数之后，你丢掉的不是精度，而是**"该改哪一环"这个判断**。
L1 报告里 q005（YOLO 例程，`example` 类）就是这个现场的标本：它检索轴的召回率是 **0.00**，
模型因此按纪律拒答，而生成轴的"符号级幻觉率 0.000"看起来完全正常。
**这个 0.000 是检索失败的下游症状**（[`concepts/07`](../concepts/07-评测-两条轴.md) 第 4 节 (c)）。
一旦只报"答对率"，这个症状会被读成"答得不好 → 去调生成"，方向从一开始就是错的。
再补一步：分轴之后还有第三个格子——**检索未命中但答案正确**，那不是好消息，
它说明这题模型裸答就会，在 RAG 评测里是噪音（[design/03 · §2.2](../../design/03-评测与质量提升路线.md)）。

如果你答到了：两类失败修法不交集 / 一个数会把方向相反的病因平均掉 / 还要识别"检索没中也能答对"这一格 ——
说明你理解了这一层。
如果你答成："因为一个数字信息量少" —— 那是把"信息少"当原因，需要回去读
[`concepts/07`](../concepts/07-评测-两条轴.md) 第 1 节与 [design/03 · §2.1](../../design/03-评测与质量提升路线.md)。

**Q2. 为什么"跑通了"不是证据，失去了什么？**

普通软件有两条极强的反馈回路：**编译不过就是错了**、**测试红了就是错了**。
它们强到足以养成一个习惯——"没报错 ≈ 没问题"。RAG 把这两条一起抽掉了：
输出永远是通顺的中文、退出码 0，错误不会让任何东西变红，只会**安静地**变成一句很客气的话。
本项目有一份完整的现场：链式基线（L1）被问"MaixPy 里怎么做 YOLO 物体检测？给出完整例程"，
回答是"资料中没有给出完整代码，因此无法提供可直接运行的完整示例"——
按提示词的拒答纪律，这句话**是对的**；同一个问题，10 轮预算的 agent 给出了可运行代码
（[`concepts/07`](../concepts/07-评测-两条轴.md) 第 3 节现场一 · [tutorial 00 · §4.1](../../tutorial/00-主线导览.md)）。
所以"跑通"这个信号在本项目里唯一还能证明的事情是"管线接通了"，
它证明不了质量——也就无法在"换 embedding"和"改提示词"之间给出任何方向。
失去它之后，判断依据只剩一个：**先把质量拆成两条轴各自测出数字，再按 qtype 分组看是哪一类变了**。
对照条款就在 [tutorial 05 · §2](../../tutorial/05-评测.md)：在没建量尺之前，
只看总分 0.556 会让人同时去换嵌入模型、调 top_k、加 rerank，**三个方向全错**。

如果你答到了：编译/测试这两条回路消失 / 错误变成通顺的输出 / 于是只能靠分轴 + 分组恢复归因 ——
说明你理解了这一层。
如果你答成："RAG 的答案不好验证，所以要人工看看" —— 人工看既不可复现也不可分组，
不是这条回路的替代品，需要回去读 [`concepts/07`](../concepts/07-评测-两条轴.md) 第 3 节。

**Q3. 哪三条指标完全由程序算出，`faithfulness` 的类型说明了什么？**

三条程序可判的指标：

1. **符号级幻觉率** —— "代码里出现的 `maix.*` 符号在不在 API 白名单里"是一次集合查询，**确定**；
2. **引用精确率** —— 答案里的 `[n]` 有没有落在实际给它的上下文条数内，是编号对应检查，**确定**；
3. **引用召回率** —— 答案里出现的每个 `[n]` 标记有没有对应的结构化引用，同样是编号检查，**确定**。

它们合起来的价格是零：不调用模型、没有位置偏差、没有版本漂移，重跑结果一致。
数据模型里的 `faithfulness` 是 `float | None`，**默认是 `None` 而不是 `0.0`**
（[`maixrag/evaluation/harness.py`](../../../maixrag/evaluation/harness.py) 的 `GenerationMetrics`；
L1 报告头部写着 `judge 模型：(未使用)`）。
这个类型选择本身是一条纪律：**没测就是 None，不是 0**——
"没有证据"和"证据表明没问题"不能被编码成同一个数字。
再补一层边界，否则这个答案只答对了一半：**程序判定也不是免检的**。
[事故 03](../../postmortem/03-校验器把正确代码判成幻觉.md) 里校验器把 `from maix import gpio`
产生的 `maix.gpio.GPIO` 判成幻觉，白名单从 **2996 条补到 4868 条**才修好。
所以交给 judge 的清单其实很短（只有 `faithfulness` 这类语义忠实度），
而白名单那类程序判定要额外维护一件事：**把自己的误报率量出来**。

如果你答到了：确定性 vs 判断 / `float | None` = 没测不是 0 / 程序判定也要量误报率 ——
说明你理解了这一层。
如果你答成："能程序算的就不该用 LLM，因为 LLM 不准" —— 这句话把 LLM 的偏差当成了唯一原因，
漏掉了"程序判定也会假阳性、而且假阳性比漏报更伤信任"这一层，需要回去读
[`concepts/07`](../concepts/07-评测-两条轴.md) 第 6 节误解三和 [design/03 · §7](../../design/03-评测与质量提升路线.md)。

**Q4. "不检索，把语料整篇塞进 prompt"这条路在本项目成立吗？边界由什么决定？**

这条路**被实现了**（`context_strategy: full_corpus`，检索侧 `mode: none`），
见于 [`configs/l_minus1_full_context.yaml`](../../../configs/l_minus1_full_context.yaml)。
但它的定位不是"更优方案"，而是**零检索损失的上界参照**：
如果连"把资料全给模型"都答不对，那问题就不在检索上，而在生成或语料上。
它成不成立由**语料的规模量级**决定，而这个量级在本项目里被记在配置文件头：
中文教程 **130 篇 / 713,520 字节 / 约 20.8 万 token**——
**已经越过 20 万 token 的可行区间**，所以 L-1b（全量，约 30 万 token）**必然截断**且成本高；
而单模块全文（约 2 万 token）那一路（L-1a）"大概率优于检索"，但也只是大概率，必须实测。
越过边界之后的失败形态很关键：不是报错，而是**截断**——
被截掉的部分等于从来没进过上下文，于是它退化成一个更隐蔽的检索失败。
这也正是为什么 [design/03 · §12](../../design/03-评测与质量提升路线.md) 把它列为第一条要求实做的事情：
**先问"要不要检索"，再问"怎么检索"**，小语料下"全文塞进 prompt"是一个真实且常常更优的选项，
但必须用本项目自己的实测数据说话。

如果你答到了：有这条配置 / 它的作用是上界参照 / 边界是 token 预算 / 越界后是静默截断 ——
说明你理解了这一层。
如果你答成："上下文窗口够大就可以不检索" —— 窗口够大只是必要条件；
"20.8 万 token 在 20 万 token 的区间里意味着什么"这一步没走，
需要回去读配置文件头的实测背景与 [design/03 · §12](../../design/03-评测与质量提升路线.md)。

### 工程类答案：判断依据 + 示范回答 + 常见浅答案

**Q5. 三个并排的 0.000，哪些能采信？核对动作是什么？**

判断依据（这几条都要考虑到才算合格）：

1. **先看分母，再看数值** —— 每一行都要问"它是在几道题/几个样本上算出来的"；
2. **区分"测到了没触发"与"压根没测到"** —— 前者的分母是 18，后者是 0；
3. **追它的上游** —— 一个 0.000 可能是检索失败的下游症状，而不是防幻觉机制的成功；
4. **结论必须是"报告该怎么改"，不只是"这个数不能信"** —— 让分母出现在报告里，而不是改公式。

一个示范回答：

> 这三行里我能立刻采信 `触发禁止项比例 0.000`：`must_not_contain` 是纯子串检查，
> 18 道题每道都跑了，分母是 18，所以 0.000 的含义是"没有任何答案写进了 `cv2.VideoCapture`
> 这类禁止项"——它有明确的分母。
> `错误率 0.000` 同理，分母是 18 次运行。
> **不能采信的是 `符号级幻觉率 0.000`**：它的分母是 `symbol_checked`，
> 而**链式融合那份报告**的 `幻觉符号` 一列 18 题全是 `-`——符号被检查到的题数 0/18，
> **一个符号都没检查过**。（同一目录下的 `agent_loop.json` 则是 16/18，所以这句话
> **只对报告本身成立，不能对"符号级幻觉率"这个指标一概而论**。）
> 更进一步，这个 0.000 不是"防幻觉成功"，而是**下游症状**：
> q005 召回率 0.00，模型按纪律拒答，**没有代码也就没有符号可检查**。
> 我的核对动作就是跑 `scripts/inspect_eval.py`，看"符号被检查到的题数"那一行；
> 覆盖率是 0 时它会直接打印 ⚠️。修的动作不是改指标公式，而是让分母进报告：
> 修掉检索问题之后，同一个位置变成 **18/18，幻觉率仍然是 0.000**——
> **这次它是真的，因为覆盖面是满的。**
> 数字没变，结论反了；区别只在分母。

常见的浅答案（以及为什么浅）：

- **"0.000 就是没有幻觉，是好消息"** —— 报告里没有任何字段能区分"检查了 0 个"和"检查了 200 个全过"，这就是它危险的**全部原因**；
- **"幻觉率公式没有分母"** —— 不准确。公式的分母是 `symbol_checked`，问题是这个分母在真实数据上等于 0；说错这一点，就会去改公式而不是去补覆盖率；
- **"没有样本时应该返回 `None` 而不是 `0.0`"** —— 这个方向有道理，但题问的是"怎么判断、怎么核对"；而且它不是免费的：`None` 会让"分数低于阈值就报警"这类自动门禁崩掉，所以**给人和给程序的两个消费者要分开处理**（[事故 05 · D1](../../postmortem/05-伪装成好消息的0.md)）。

**Q6. 怎么判断"是送分题在稀释差异"？哪些信号能看出来？**

判断依据（这几条都要考虑到才算合格）：

1. **给出"送分题"的可操作定义** —— 不是"简单题"，而是**不检索也能答对的题**；
2. **说清它的危害机制** —— 它给每个配置都 +1，分母变大、差值不变，配置间差异被稀释；
3. **区分报告内可见信号与必须另跑基线的信号** —— 前者是 `召回率 0.00` 且答案照样通过、以及 `source` 分组；后者是 L0（无 RAG）基线；
4. **给出现状** —— 这个体检在本项目**还没做**，别把"设计里有"说成"已经做过"。

一个示范回答：

> 送分题的定义要卡死：**模型不检索就能答对的题**。它在 RAG 评测里是噪音，
> 因为它对每个配置的贡献都一样，把真实差异稀释掉。
> 报告里能直接看出来的信号有两个：
> ① **逐题明细里召回率 0.00、但答案照样不是拒答** —— 检索一个都没中，答案却过了生成轴的断言，
> 说明这题不靠资料也能答（[tutorial 05 · §6 ②](../../tutorial/05-评测.md)）；
> ② **按 `source` 分组**：`doc_derived` 类是送分题高发区，而 `model_stress` 类专挑模型裸答就会错的点，
> 比例失衡会直接反映在分组分上，`_agg` 的 `by("source")` 是现成的。
> 但"模型裸答就会"这件事报告判不了，必须另跑一次 **L0 基线**
> （`python -m maixrag --config configs/l0_no_rag.yaml eval --level no_rag`）做对照。
> **现状要诚实说**：18 题的 `source` 全是 `real`，L0 这一路体检本项目还没做——
> 所以严格讲，这个评测集有没有送分题，现在还没有被检查过。
> 要修的话，顺序是先体检、再替换或提高难度；**不要因为"召回 0"就删题**——
> 检索没召回和不检索也能答对是两件事，前者可能是检索 bug 或语料缺口，删题会把真问题盖住。

常见的浅答案（以及为什么浅）：

- **"跑一下 L0 基线就行"** —— 说了手段没说判据：L0 跑完要看哪一列、报告里哪个字段是预警信号、以及怎么和现有 18 题对上；
- **"召回率 0 的题就是送分题，删掉"** —— 召回 0 至少有三种成因（语料没有、断言太松、检索配置），直接删题是掩盖问题，不是体检；
- **"题太难/太简单"** —— 没有判据。"难"不可操作，"不检索也能答对"可操作——这就是 L0 基线存在的全部理由。

**Q7.（无唯一答案）API chunk 让 signature/example/troubleshoot 大涨、concept 下跌，而用户 80% 问概念类，你怎么处理？**

判断依据（这几条都要考虑到才算合格）：

1. **收益落在谁身上、代价落在谁身上** —— 分开算，不能用总体 +5.5 pt 抵消；
2. **样本量与置信度** —— `signature` 只有 4 题，一题之差就是 25 pt，+50 pt 的置信度本来就很低；
3. **评测集配比与真实流量的错位** —— 题面说的是"你的用户里 80%"，而评测集里 `concept` 是 8/18（约 44%）；
4. **有一个可回退的中间态，且它的代价被写出来** —— 分索引/独立名额（L4 查询路由）、按 qtype 路由、或只给 signature 类查询开 API chunk；
5. **给出失效条件** —— 你选的方案在什么情况下会退化回今天这个互相挤的状态。

一个示范回答：

> 先算账：这次改动给语料加的是 API 参考页 chunk（chunk 总数 1940 → 3838，
> 新增 1898 个），收益集中在 `signature`（0.000→0.500）与 `example`（0.250→0.750），
> 代价落在我 80% 流量所在的 `concept`（0.625→0.500）——
> 根因是新增的 API chunk **抢占了 Top-5 名额**，把概念类问题要的教程散文挤了出去。
> 所以我不会把它当"小幅有效"上线，也不会直接回退，因为 signature 是幻觉重灾区。
> 我第一步做的不是改代码，而是**修评测集**：`signature` 只有 4 题，
> 那 +50 pt 可能就是一道题；`concept` 只有 8 题，却对应 80% 的真实流量——
> 配比和流量不一致时，任何基于分组分的决定都不可靠。先补题、重跑，看 concept 的下降是否稳定。
> （补题与补跑这一段的数字我这里没有实测过：`signature` 与 `concept` 的题数来自
> `eval/datasets/seed.jsonl` 的 4/8 配比，补题后的结果 **[未实测，需你运行确认]**。）
> 如果稳定，我选 **L4 查询路由**：让 API chunk 与教程 chunk 各自保留名额，
> 而不是统一排名后取前 5。代价是多一套候选池和一个查询分类器，
> 且分类错了就退化成今天这个互相挤的状态——这是这个方案的失效条件。
> 如果不想付分类器的代价，退一步的便宜做法是只给 `signature` 类查询开 API chunk，
> 代价是对"问签名但用自然语言表达"的查询会漏（`concept` 与 `signature` 的边界本来就模糊）。
> 判据是"收益落在谁身上、代价落在谁身上、两边的题数与流量各是多少"——
> 不是总体 +5.5 pt。

常见的浅答案（以及为什么浅）：

- **"总体是 +5.5 pt，所以有效，上"** —— 总分会把方向相反的变化平均掉，这正是这道题存在的理由；
- **"两个都要，做路由"** —— 方向对，但"做路由"是方案描述而不是判断：没说清多出来的代价由谁承担（分类器 + 两套候选）、也没给出失效条件；
- **"先修 signature，因为它是幻觉重灾区"** —— 这是价值排序，不是这道题的约束；题面给的是**流量分布**，而流量在 concept 那一侧。

### 动手题答案

**H1. 覆盖率体检一次现有报告**

操作步骤（**先知道一件事**：`eval/results/` 里现在**只留着** `agent_loop.json`、
`rag_L1_rag[rrf_dense].json`、`rag_L1_rag[rrf_bm25].json`——融合那一份
`rag_L1_rag[rrf_dense+bm25]` **只有 `.md`，没有 `.json`**。而 `inspect_eval.py` 读的是 **json**，
所以要么用下面这条命令，要么自己跑一次 `eval` 把它生成出来）：

```bash
python scripts/inspect_eval.py "eval/results/agent_loop.json"
```

注意两点：`inspect_eval.py` 不传参数时挑**最新**的 `.json`，所以这里必须显式给路径；
另外 `eval` 按 `{level}_{profile}.md/json` 覆盖同名文件，
**跑任何一次评测前先备份 `eval/results/`**（[tutorial 05 · §6 ①](../../tutorial/05-评测.md)）。

期望结果（按 [`scripts/inspect_eval.py`](../../../scripts/inspect_eval.py) 的逻辑 + 磁盘上这份 json 现读）：

- 脚本会在生成轴那一段打印 `**符号被检查到的题数  k/18  (p%)**`；
  当 `k == 0` 时，它还会多打印一行
  `⚠️ 没有任何题目被检查到符号——幻觉率 0.000 不具参考意义`。
- 这份 json 读出来是 **`k = 16`，即 16/18 (89%)**，`符号总数 101`、`幻觉符号数 0`、
  `拒答题数 8/18`——也就是说它**有**分母，`符号级幻觉率 0.000` 在这一份上是可以采信的。
- 真正"没有分母"的那一份是**链式**的融合报告
  [`eval/results/rag_L1_rag[rrf_dense+bm25].md`](<../../../eval/results/rag_L1_rag[rrf_dense+bm25].md>)：
  它的「逐题明细」里 `幻觉符号` 一列 18 题全是 `-`，`符号级幻觉率 0.000` 站在一个空分母上。
  **这一份没有配套的 `.json`**，所以你只能从 `.md` 读它——这也正是"报告要把分母写进去"的理由。
- ⚠️ 一个实测中会撞上的坑：`eval/results/` 下同一份配置的 `.md` 与 `.json` 可能是**两次不同的运行**
  （`agent_loop.json` 的 `agent_stats` 写 75 次工具调用，而 `.md` 与 tutorial 07 记的是 88 次）。
  所以报数时要**连总数一起报**，例如"符号被检查到的题数 X/Y"。
  **[未实测，需你运行确认]**
- 结论：`符号级幻觉率 0.000` **不总是**"几乎没测到东西"——
  它有分母时是可信的（16/18），没分母时才是假的好消息；链式那份就是后者。
  而两份报告里的 `触发禁止项比例 0.000` 分母都是全部 18 题（每道题都做了子串检查），
  所以那一行可以采信。**两个 0.000 在报告里长得一模一样，区别只在分母。**

一份可核对的现场记录见 [事故 05 · 怎么发现的](../../postmortem/05-伪装成好消息的0.md)：
覆盖率修满之后，同一个数字变成 `18/18，幻觉率仍为 0.000`——这次它是真的。

**H2. 给 `Report` 加"覆盖题数"**

操作步骤：

1. 先写预测（动键盘之前）：`符号级幻觉率` 那一行会显示 **`0/18`**——
   因为它的分母是"符号被检查到的题数"，不是"全部题数"。
   如果你猜 `18/18`，那说明你把分母当成了总题数；跑一次就知道错在哪一步。
2. 改 [`maixrag/evaluation/harness.py`](../../../maixrag/evaluation/harness.py) 的 `Report._agg`：
   每一条比率除了值，还要能拿到它的**分子与分母**。
   这里有一个必须分清的口径——`_agg` 里已经有一个筛选条件
   `with_ctx = [r for r in rows if r.gen.symbol_checked or r.ret.n_hits]`，
   它是用**"或"**连起来的：有召回片段的题也算进 `with_ctx`。
   但 `hallucination_rate` 真正有效的分母只应该是 **`symbol_checked > 0` 的题数**。
   这两个口径今天不相等，动手时最容易在这里混。
3. 改 `Report.to_markdown`：把每行渲染成 `值 (k/n)`。
   分母的口径按指标分两类：
   - `recall` / `hit_rate` / `mrr` / `context_precision` / `citation_precision` / `citation_recall` / `must_not_violation` / `refusal_rate` → 分母是**全部题数**；
   - `hallucination_rate` → 分母是**符号被检查到的题数**（`symbol_checked > 0`）；`citation_*` 若要更严，可再把"有引用的题数"一并打出来。

期望结果：

- 报告里不再出现没有分母的比率（这是验收的硬标准）；
- 链式融合那份（`eval/results/rag_L1_rag[rrf_dense+bm25].md` 的「逐题明细」里
  `幻觉符号` 一列 18 题全是 `-`）：`符号级幻觉率 0.000 (0/18)`；
- agent 那份（`eval/results/agent_loop.json`，现读 `k = 16`）：`符号级幻觉率 0.000 (16/18)`；
- 文档记录里"修过检索之后"的那一次：`符号级幻觉率 0.000 (18/18)`——
  三个数字相同、结论却不一样，**这正是加这一列的全部意义**。
  这个 `18/18` 来自 [事故 05 · 修复](../../postmortem/05-伪装成好消息的0.md) 的记录，
  我没有在本机复现它。**[未实测，需你运行确认]**

> ⚠️ 两条口径提醒：**"哪一份报告是'修过之后'的"会随语料配置改变**，
> 而 `k/18` 里的 `k` 也**会随你用的生成模型改变**（假模型不写代码 → `k` 接近 0）。
> [tutorial 05 · §7](../../tutorial/05-评测.md) 讲的是"给 `required_docs` 改错一个字符、

> 这条本身值得记：验收时先确认"我这份报告对应哪一次语料构建、哪一个生成模型"，再对数字，
