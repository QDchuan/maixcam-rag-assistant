# 参考答案 · 01 RAG 的完整链路

答案分两类来写，因为它们的评判标准不一样：

- **概念类（Q）**：给推理链，不只给结论。末尾两行是**理解状态诊断**（你答到了哪一层）。
- **工程类（E）**：给判断依据 + 一个示范回答 + 常见的浅答案。这类题**没有唯一正确答案**，
  验收标准是"你的答案里有没有代价分析和失效条件"。

## 一、概念问答

### Q1. 链路的七个环节里，哪些属于检索轴、哪些属于生成轴？为什么这两类失败的修法几乎不交集？

**推理链**：先把七环按"它交付给下游的是**依据**还是**成品**"分一遍。① 语料获取 → ② 解析切分 → ③ 索引 →
④ 检索 → ⑤ 融合重排，这五环交付的都是"模型能看到什么"——检索轴；⑥ 生成 → ⑦ 校验交付的是
"模型怎么用看到的东西"——生成轴。分轴之后，两类失败的现象就分开了：检索失败是**该出现的那几段根本没进 Top-K**，
生成失败是**正确片段已经在上下文里、模型却没用上**。修法不交集的根源是它们的**可控变量完全不重叠**：
检索轴要动的是语料覆盖面、切分粒度、索引、融合权重，改这些不会让模型更听话；生成轴要动的是提示词、
上下文组织、引用约束、符号校验与拒答阈值，改这些也不会把一段没被召回的文档变出来。所以同一个"答案里没有能跑的代码"，
在两条轴上是两个病，而且 [concepts 01 · 4.1](../concepts/01-RAG的完整链路.md) 那个 YOLO 例子证明
它们会同时以相反的面貌出现：生成轴优秀（明确拒答、不编造 API），检索轴失败（真正含例程的 `zh/vision/yolov5` 没进 Top-K）。

**如果你答到了**：按"交付依据 / 交付成品"划分七环 / 两类失败的现象不同 / 可控变量不重叠 —— 说明你理解了这一层。
**如果你答成**："检索是找资料、生成是写答案，所以修的地方不一样" —— 那是把流程复述了一遍，
没有回答"为什么不交集"；回去读 [concepts 01 · 3.1](../concepts/01-RAG的完整链路.md) 的两轴表，
注意它列的是**该改哪里**而不是**在做什么**。

### Q2. 为什么本项目的主指标是召回率，而不是精确率或延迟？请用"上限"这个词解释。

**推理链**：RAG 是"检索-生成"两段式，生成阶段只能读到进上下文的那 K 个片段，所以
**召回率决定的是答案质量的天花板，其他环节的表现全都发生在这个上限之内**。精确率衡量的是
"已经进 Top-K 的片段里有多少真相关"——它只在**已召回的那部分**里算，天花板再低它也可能很漂亮；
延迟衡量的是"这次请求多慢"，是逐次与累计成本，跟"资料有没有到模型眼前"无关。
用一个具体数字看：本项目链式基线的报告里 `Recall@K = 0.611`
（[`eval/results/rag_L1_rag[rrf_dense+bm25].md`](<../../eval/results/rag_L1_rag[rrf_dense+bm25].md>)），
意思是每道题标注的"必须被召回的页面"里，大约 39% **从来没有出现在模型眼前**——
这部分不是提示词、模型或校验能补的，因为它们连输入都没有。这就是"主指标"的含义：
它不是一个分数排名里的第一名，而是**结构性上限**。

**如果你答到了**：检索-生成的结构决定生成只能在上限内发挥 / 精确率只衡量已召回部分 / 延迟属于成本不属于质量 —— 说明你理解了这一层。
**如果你答成**："因为召回率更基础 / 更科学" —— 那是把结论当原因（[concepts 01 · 3.2](../concepts/01-RAG的完整链路.md)
用的词是"结构性上限"）；也有人会答成"精确率不重要"，那又过头了：精确率直接决定
**信噪比与 token 成本**，它只是不当主指标，不是不看。

### Q3. 加 API 语料层换来 `signature` +50 pt、同时付出 `concept` −12.5 pt。这个代价的机制是什么？

**推理链**：机制是 **Top-K 名额零和**。改动是让 API 参考页产出可检索 chunk，
chunk 总数从 1940 涨到 3838，多出来的正是 1898 个 `signature` chunk
（[`corpus/reports/stats.md`](../../../corpus/reports/stats.md)）。
但检索时最后只取前 K 个（本项目 K=5），而这 5 个名额来自**一个共享的排名池**——
API chunk 与教程散文在同一个池子里竞争。API chunk 对"函数签名/参数"这类查询的信号极强，
于是一次占掉好几个名额，把概念类问题本来能排在第 5、6 名的教程散文挤了出去。
所以 `signature` 能 +50 pt（它终于有东西可召回了），`concept` 反而 −12.5 pt（它的名额被占了）。
同一份报告里总分只动 +5.5 pt，正是因为它把两件方向相反的事平均成了一件事
（[concepts 01 · 4.2 / 误解二](../concepts/01-RAG的完整链路.md)）。

> 一个必须说清的边界：那次消融实际同时改了两个变量——chunk 数变化，也顺带改变了
> BM25 的文档长度归一化与语料统计。按消融纪律"一次只改一个变量"，
> 因此不能把 `concept` 的跌幅**全部**归因于名额竞争。
> 另外还要区分"没召回"与"召回了没排上"：`concept` 里有些题（见 [concepts 01 · 4.1](../concepts/01-RAG的完整链路.md)）
> 从一开始就没命中，属于另一类故障。

**如果你答到了**：Top-K 名额零和 / 1898 个新增 chunk 与教程散文共享同一个池子 / 有借有还的净效果被总分掩盖 —— 说明你理解了这一层。
**如果你答成**："加语料总是有代价的" —— 那是把结论当原因，没说出代价的机制；
更危险的答法是"因为向量空间被稀释了"——听起来高级，但它解释不了 BM25 那一侧同样出现的名次变化，
而且它把"名额被占"（池子层面）说成了"表示变差"（模型层面），这是两回事。

### Q4. 一份评测报告写着"符号级幻觉率 0.000"。列出至少两种它其实什么都没测到的情况，并说明你会额外要哪个数字。

**推理链**：符号级幻觉率是 `不存在的符号数 / 被检查到的符号总数`，而代码里那一步通常会写
"分母为 0 时返回 0.0"——**它把"没有证据"和"证据表明没问题"编码成了同一个数字**。
至少两种什么都没测到的情况：
1. **分母本身就是 0**：模型压根没输出代码（本项目第一次就是这样——模型拿不到 API 资料，
   按纪律不写代码，于是没有符号可检查）。[`scripts/inspect_eval.py`](../../scripts/inspect_eval.py) 打出的正是
   `符号被检查到的题数 0/18 (0%)`；
2. **只有个别题贡献了分母、其余全没测到**：比如 18 题里只有 1 题写了代码，
   这 1 题又刚好没错，0.000 就成了"18 题都没问题"的假象；
3. **检查器因过滤/异常把样本丢掉了**：只能拿到空的或错误的符号引用集合，等于没检查。
你会额外要的数字是**这道指标的覆盖面**——具体说，就是"符号被检查到的题数 n/18"
（以及它派生的、只在被检查的题上算的那个幻觉率）。它够用，是因为它把"0.000"劈成两种互斥的解释：
真的很好，或几乎没测到东西。

**如果你答到了**：说出分母为 0（模型没写代码）/ 说出部分覆盖 / 要的是覆盖率或样本数而非另一个比率 —— 说明你理解了这一层。
**如果你答成**："我要看幻觉的例子里有哪些" —— 那说明你还停在"有没有抓到"，
没意识到抓不到的原因可能是**根本没看**；回去读 [concepts 01 · 误解四](../concepts/01-RAG的完整链路.md) 与
[事故 05 伪装成好消息的 0](../../postmortem/05-伪装成好消息的0.md)。
注意这个 0.000 在本项目里不是一次孤立的测量事故，**它是第 ④ 环检索失败的下游症状**——
这正是"先分清哪半段坏了"的用处。

## 二、工程问答

### E1. 两份评测报告总分都是 Recall@5 = 0.611，但 MRR 一个是 0.557、一个是 0.453。你会从哪一环开始查、先改什么？

**判断依据（这几条都要考虑到才算合格）**：

1. **先对齐口径，再比数字。** 两份报告必须同语料、同评测集、同 K、同嵌入模型，
   否则差异不来自被测变量。本项目这两份报告的唯一差别就是 `retrieval.retrievers`
   （`[dense]` 对 `[dense, bm25]`），配置见 [`configs/l3_dense_only.yaml`](../../configs/l3_dense_only.yaml)
   与 [`configs/l2_hybrid.yaml`](../../configs/l2_hybrid.yaml)，所以差别可以归因到第 ⑤ 环的融合。
2. **按环节的顺序逐环排除，而不是跳到最贵的那一环。** 语料→索引→切分→检索→融合，
   每环的故障形态不同：语料是"索引里根本没有这个 doc_id"（[事故 02](../../postmortem/02-有文档却召不回.md)），
   检索是"候选池里有、但排序不对"，融合是"候选池里有、两路各自都排得不错、合起来反而掉出 Top-K"。
3. **必须按 `qtype` 分组看，不能只看总分。** 总分相同直接掩盖了方向相反的两种变化。
4. **改动要与现象同层。** MRR 掉、Recall 没掉，说明"该召回的还在池子里，只是位置往后挪了"，
   这指向排序而不指向覆盖——所以不该先去动语料。

**一个示范回答**：

我会先从第 ⑤ 环（融合）查起，而不是先怀疑语料或换嵌入模型。理由是三件事同时成立：
两份报告 `Recall@K` 都是 0.611，说明**覆盖没有变**；`Hit Rate@K` 都是 0.667；
但 `MRR` 从 0.557 掉到 0.453、`Context Precision` 两份都是 0.267。召回没掉、位置掉了一档半，
这是排序质量问题，而这里唯一被动过的就是融合。按 `qtype` 分组再看方向：
`concept` 0.500 → 0.500、`signature` 0.500 → 0.500、`troubleshoot` 0.500 → 1.000，
而 `example` 从 **1.000 掉到 0.750**——融合把一整个 `example` 题（`q005`，YOLO 例程，标注文档就是
`zh/vision/yolov5`）从 dense 的第 5 名挤出了 Top-5。机制在
[`maixrag/retrieval.py`](../../maixrag/retrieval.py)：两路先各取 20 个候选，再按
`score(d) = Σ_r 1/(rrf_k + rank_r(d))` 重排取前 5；`zh/vision/yolov5` 在 dense 排第 5（贡献约 1/66）、
在 BM25 排第 6（贡献约 1/67，两路合计约 0.030），而两路都排 10–20 名的片段各自拿到约两份
1/7x 的分数（合计约 0.05–0.06），叠加后反超了它——**单路已经进榜的片段，融合可以把它挤出去**
（名次数据见 [tutorial 04 · 4.2 / R2](../../tutorial/04-检索与消融.md)）。
所以我的第一刀是**只动融合这一环**：先按 `qtype` 决定权重，或先把 `pool`/`rrf_k` 这类融合参数做成可消融的开关，
而不是去换嵌入模型——换模型会一次改掉整条链，之后任何数字都无法归因
（[concepts 01 · 误解三](../concepts/01-RAG的完整链路.md)）。代价是：融合参数的调优本身也有过拟合
这份 18 题评测集的风险（`concept` 8 / `example` 4 / `signature` 4 / `troubleshoot` 2，
每类只有 2–8 题），所以我会同时保留只 dense 这一路做对照。
**边界**：融合与重排序的消融（L3/L6）与查询路由（L4）在本项目**尚未跑**
（[concepts 01 · 4.5](../concepts/01-RAG的完整链路.md)），所以上面这个结论是"该查哪一环"的判断，
不是"改了就能涨"的承诺——**没跑过的环节，本项目不给结论**。

**常见的浅答案（以及为什么浅）**：

- **"两份都是 0.611，说明没差别，不用管"** —— 只看总分。总分把 `example` 的 −25 pt
  和 `troubleshoot` 的 +50 pt 平均成了一件事，于是回归变得不可见。
- **"MRR 低就是排序不好，加个 rerank 就行"** —— 跳过了"先定位到哪一环"这一步，
  而且 rerank 在本项目默认关闭、要先看到增益与延迟曲线才决定；先加最贵的一招等于用钱换掉归因能力。
- **"Recall 没变，说明检索已经做到底了"** —— 把"召回是主指标"误读成"只有召回值得看"。
  `example` 那一类在这两份报告之间是实打实地退化了一整题。
- **"调大 top_k 就都回来了"** —— 这只改变尺子的量程（见 E2），不改排序质量；
  而且它会把 Context Precision 一起拉低，代价是 token。

### E2. 把 `retrieval.top_k` 从 5 调到 50，什么条件下有用、什么条件下浪费——你怎么判断？

**判断依据（这几条都要考虑到才算合格）**：

1. **先回答"索引里有没有可召回的东西"。** 分母里有货，加大 K 才可能命中；
   分母里没有（或没产出可检索 chunk），K 调多大都一样。
2. **区分"没召回"和"召回了没排上"。** 前者要动语料/切分，后者才轮到 K 与融合。
3. **看别被自己的尺子骗了**：检索指标本身就是"前 K 个"里算的，K 一变，
   和旧基线的对比口径就不同了。
4. **算代价**：多塞进上下文的片段会改变 Context Precision 与 token 成本，
   本项目的一条纪律是"没有运行指标的消融表是不完整的"。

**一个示范回答**：

判断顺序是**先看分母、再看代价，最后才动 K**。第一步查"这个 doc_id 在索引里存在吗"：
`signature` 类曾经是 0.000（[`eval/results/rag_L1_rag[rrf_bm25].md`](<../../eval/results/rag_L1_rag[rrf_bm25].md>)
里 `signature | 4 | 0.000 | 0.000`），根因是 API 参考页**没产出任何 chunk**——
这种时候把 top_k 从 5 调到 50，"什么都不会发生，因为索引里没有东西可检索"
（[concepts 01 · 误解一](../concepts/01-RAG的完整链路.md)）。修完语料层之后，
同一个 `signature` 行变成 **0.500**（[`eval/results/rag_L1_rag[rrf_dense+bm25].md`](<../../eval/results/rag_L1_rag[rrf_dense+bm25].md>)），
而这一涨**没动一行检索代码、也没动 K**。反过来说，K 真正有用的场景是"已经在候选池里、只是排在第 6–20 名"：
本项目 `zh/vision/yolov5` 在只跑 dense 时正好是**第 5 名**——它是踩着线进来的，
任何一个把名次往后推一点点的改动都会让它掉出去，这时扩大 K 或调整融合都有真实作用。
代价这边：K 从 5 到 50 意味着上下文里多塞 10 倍片段，精确率会被稀释
（当前 `Context Precision` 只有 0.267，即上下文里约四分之三的片段与标注无关），
注入的 token 与延迟一起上涨。所以我的做法是**先在报告里按 `qtype` 分组确认退化发生在哪一类**，
再用 `inspect_eval.py` 确认覆盖面，最后才用一次带 K 变量的消融去回答"值不值"——
而不是把 K 当成一个可以随手拧大的旋钮。

**常见的浅答案（以及为什么浅）**：

- **"K 越大召回越高，当然调大"** —— 这句话在**同一个 K 口径下**才成立；
  换 K 重跑等于换了一把尺子，直接和旧基线比是口径不一致。
- **"召回低就是参数没调好"** —— 本项目最贵的一次教训恰恰相反：根因在语料层，
  而"总分只有 +5.5 pt"这件事本身还在掩盖它。
- **"调大 K 只是慢一点"** —— 没说清慢多少、贵在哪，也没提 Context Precision 与幻觉风险；
  没有代价分析的方案描述，在这套题里一律不算合格。

### E3. 如果只能给评测报告加一个字段，来防止"0.000 伪装成好消息"，你加什么？为什么它够用？

**判断依据（这几条都要考虑到才算合格）**：

1. **这个字段要能区分"真的很好"与"几乎没测到"**，也就是必须暴露**分母**，
   而不是再加一个比率（比率会重复同一个毛病）。
2. **它要能覆盖所有比率型指标**，而不只治好一处：符号幻觉有"被检查的题数/符号数"，
   引用有"有引用的题数"，拒答有"该拒答的题数"。
3. **它必须是报告的一等公民**（进入汇总层，出现在 markdown 里），
   否则没人会去翻 JSON 明细，等于没加。

**一个示范回答**：

我会给**每一个比率型指标配一个覆盖计数字段**，字段形如 `checked_items / total_items`
（对符号幻觉就是"符号被检查到的题数"）。理由是它把 0.000 劈成两种互斥解释，
而这个区分只能用分母做：本项目真实发生过的一次是
`符号被检查到的题数 0/18 (0%)`（[`scripts/inspect_eval.py`](../../scripts/inspect_eval.py) 的输出），
修完检索之后覆盖率变成 **18/18**，同一个 0.000 才是真的
（[事故 05](../../postmortem/05-伪装成好消息的0.md)）。
代价与边界也要说清：这个字段只暴露"测了多少"，**不保证标注本身是对的**——
覆盖率 18/18 但仍可能因为标注错误而给出一个假的 0.000；
所以它是必要不充分条件，配额上还要配"人工抽检 10–20% 样本"。
如果只能给**绝对一个**数字，我选"符号被检查到的题数"，因为本项目最贵的那次误判就发生在这里。

**常见的浅答案（以及为什么浅）**：

- **"加一个置信度字段"** —— 主观量、不暴露覆盖面，0.000 照样可以是"没测到"。
- **"加错误率"** —— 报告里本来就有（本项目 `错误率 0.000`），但它同样不回答
  "幻觉率的分母覆盖了什么题"。
- **"多加几行日志"** —— 日志不是报告字段：不进汇总层的证据，在下一次汇报里不会出现，
  于是同一个坑会再踩一次。

### H1. 验证"这篇文档确实在语料里"，再用两份配置跑同一道题

**操作步骤**：

```powershell
# ① 语料里到底有没有这一篇（只读，不改任何东西）
(Get-Content corpus/processed/chunks.jsonl -Encoding UTF8 |
  Where-Object { $_ -match '"doc_id": "zh/vision/yolov5"' }).Count

# ② 只 dense：读现成的向量索引，重新跑一遍检索轴评测（不重建索引）
python -m maixrag --config configs/l3_dense_only.yaml eval --level rag --fake-chat

# ③ dense + bm25 走 RRF 融合
python -m maixrag --config configs/l2_hybrid.yaml eval --level rag --fake-chat

# ④ 看覆盖面（可选，但强烈建议）
python scripts/inspect_eval.py
```

> 两条纪律：**别跑 `index build --rebuild`**——一次 `--fake --rebuild` 会把 1024 维真实向量索引
> 覆盖成 256 维假索引（[tutorial 02 · 6.2](../../tutorial/02-把手工流程变成系统.md) 里记着这次事故）；
> 想只看检索轴就用 `--fake-chat`，它只把对话模型换成空客户端，嵌入仍是真实的。

**期望结果（以下数字我都已在本仓库的文件里核对过）**：

1. `doc_id` 为 `zh/vision/yolov5` 的 chunk 是 **12** 条（`#h0`…`#h10.1`，其中 kind 为 `code` 的 2 条）。
   也就是说这一篇**确实在语料里、确实产出了可检索 chunk**。
2. `q005`（YOLO 例程）在现成的三份报告里的数字：

   | 跑法 | 报告 | `q005` 召回率 | `q005` 首位命中 | `example` 分组 |
   | --- | --- | --- | --- | --- |
   | 只 dense | `rag_L1_rag[rrf_dense].md` | **1.00** | **5** | 1.000 |
   | dense + bm25 融合 | `rag_L1_rag[rrf_dense+bm25].md` | **0.00** | **—**（没进 Top-5） | 0.750 |
   | 只 bm25 | `rag_L1_rag[rrf_bm25].md` | **0.00** | **—** | 0.750 |

   所以"消失"发生在**第 ⑤ 环融合**，而**不是**语料缺失——同一个现象看起来一模一样，
   病根却完全不同，这正是这一章要练的判断。
3. 名次层面的现场：`python scripts/demo_retrieval.py --query "MaixPy 里怎么做 YOLO 物体检测？给出一个完整例程。" -k 20`
   会把同一查询在三个检索器下的名次打出来——**dense 第 5 / bm25 第 6 / 融合掉到第 12**。
   注意 bm25 不是"没找到"，是**排在第 6、刚好在 Top-5 之外**；而融合后再退到第 12，
   连扩大 K 到 12 才能勉强看到它。机制在 [`maixrag/retrieval.py`](../../maixrag/retrieval.py)：
   `HybridRetriever` 让两路各取 **20** 个候选（`pool = max(k, 20)`），再用
   `1/(60 + rank + 1)` 累加后取前 **5**。它排 dense 第 5（贡献约 1/66）、bm25 第 6
   （贡献约 1/67，两路合计约 0.030）；而两路都在 10–20 名的片段各自拿到约两份 1/7x 的分数
   （合计约 0.05–0.06），叠加后反超了它——**融合不是取并集，它是一次重新排序**，
   于是单路已经进榜的片段会被挤出去。
   （这正是 [tutorial 04 · R2](../../tutorial/04-检索与消融.md) 记录过的同一类现象。）

**你自己跑第 ②③ 步时**：报告会落到 `eval/results/`，文件名由
`{level}_{profile.name}` 拼成；若你跑的配置与现成报告同名，会覆盖掉那份报告——
建议先备份，或换一份配置文件名。**这两个数字我没有亲手重跑确认**，
它们是 `eval/results/` 里现成报告的值——**其余数字同样以你机器上的输出为准**。
（名次那一组来自 [tutorial 04 · 4.2 / R2](../../tutorial/04-检索与消融.md) 与
[`scripts/demo_retrieval.py`](../../scripts/demo_retrieval.py)，我也未亲自重跑。）

### H2. 把评测的 K 从 5 改成 50，先写下预测再跑

**操作步骤**：

```powershell
# 先写预测（三行）：Recall@K 会怎么动、Context Precision 会怎么动、成本会怎么变
python -m maixrag --config configs/l2_hybrid.yaml eval --level rag --fake-chat --top-k 50
```

**期望结果与推理依据**：

- **`Recall@K` 会不降反升，而且这是定义决定的**：检索指标算的是"前 K 个片段里，
  ground-truth 命中了几项"，K 从 5 涨到 50，命中机会只增不减。
  所以这个上升**不代表检索变好了**，只代表尺子的量程变大了。
- **`Context Precision` 大概率下降**：它是"取回的片段里命中的占比"，
  多出来的 45 个片段里大部分与标注无关（当前 K=5 时它只有 0.267）。
- **"拿这次的 `Recall@50` 去比上次的 `Recall@5` 基线，这个对比成立吗"——不成立。**
  两份报告题目头里都会写明 `Top-K`（现成那三份都写着 `Top-K：5`），
  K 不同就是口径不同；要对比就必须固定 K，只改被测的那一个变量
  （[design 03 · 5.1](../../design/03-评测与质量提升路线.md) 的五条纪律）。
- **这个实验的正确用法**：它恰恰是 E2 的反面教材——想靠调 K 涨分，
  涨的是尺子不是系统；真正该先做的是查"索引里有没有可检索的 chunk"。

**我未实测的部分**：`--top-k 50` 这一次的 Recall / Context Precision 具体数值、
以及它是否会覆盖你现有的报告文件，**[未实测，需你运行确认]**。
上面对**方向**的判断来自评测器的实现
（[`maixrag/evaluation/harness.py`](../../maixrag/evaluation/harness.py) 的 `evaluate_retrieval`：
`top = hits[:k]`，召回按 `required_docs` 在 `top` 中的命中比例算），
以及现成报告里 K=5 时的实测值（Recall@5 **0.611** / Context Precision **0.267**）。
