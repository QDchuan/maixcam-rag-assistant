## 一、概念问答

### Q1. 问「怎么列出 MaixCAM 上可用的摄像头设备？」稠密检索容易翻车，问「maix.camera.list_devices」几乎必中——从"文本被压成向量之后发生了什么"说清前一问为什么输给 BM25。

稠密检索把整段文本压成一个 1024 维向量（本项目用 bge-m3），"语义"被保住了，
但**罕见字符串在这种压缩里损失最大**：`list_devices` 这类标识符在自然语言语料里出现极少，
嵌入模型没为它学过一个稳定的方向，于是"摄像头设备"这种口语说法与它之间
没有一条可靠的向量近邻关系；而"泛泛讲摄像头"的教程散文反而更靠近这个问题。
第二个失效叠加在上面：查询里最像答案的词其实是**语义化表达**（"列出可用的摄像头设备"），
而答案所在的 chunk（`api/maix.camera.list_devices`）的正文是
`maix.camera.list_devices` + `def list_devices()` + `List all supported camera devices.`——
它的英文说明和中文口语之间没有共同 token，也没有共同措辞习惯；
查询被分词成 `maixcam / 怎么 / 列出 / 上 / 可用 / 的 / 摄像 / 像头 / 摄像头 / 设备`，
而文档里既没有"摄像头"也没有"设备"。
BM25 不看语义，只看"词在不在"：一旦查询里带上标识符，它字面命中几乎是必然的；
而它在语义化提问下的失败不是"排错了"，是**根本没有可打的词**——本项目实测这个词面复现是：
查询 `怎么列出 MaixCAM 上可用的摄像头设备？` 走 BM25 时，
`api/maix.camera.list_devices` **不在前 20**；把查询换成 `maix.camera.list_devices`，它**排第 1**。
这正是"没有哪个更好，只有哪个更适合这一类查询"的现场。

**如果你答到了**：语义压缩导致罕见字符串信息损失 / 标识符在训练语料里罕见 / 词面命中 vs 语义相近 ——
说明你理解了这一层。
**如果你答成**："因为 BM25 更准" 或 "稠密检索就是不行" —— 那是把结论当原因，
没有指出失效的机制；回去读 [`concepts/03`](../concepts/03-检索-稀疏与稠密.md) 第 3.2、3.3 节，
再看第 4 节那两组真实排名。

### Q2. BM25 的 IDF 在什么情况下会变成负数？为什么那是问题？本项目怎么绕开它——绕开之后还有哪一类查询治不好？

经典 BM25 的 IDF 是 `ln((N - df + 0.5) / (df + 0.5))`，
它在 **`df > N/2`（某个词出现在超过一半的文档里）** 时为负——因为 `ln` 的参数小于 1。
负 IDF 的后果不是"这个词没用"，而是**方向反了**：一个包含该词的文档会被扣分，
于是"专讲这件事的那一篇"反而排在"完全不提这件事的文档"后面；
在极小语料（N=50、一个词出现在 40 篇里）上这几乎是必然发生的。
本项目采取的做法是**直接换公式**：`maixrag/indexing/bm25.py` 的 `BM25Params.idf_plus`
打开时用 `ln((N+1)/df)`，因为 `df ≤ N`，结果恒 ≥ 0，从根上消除负 IDF
（`search()` 里还有一道 `if idf <= 0: continue` 的兜底，负 IDF 的词根本不参与打分）。
**这里要诚实**：按本机当前索引算，`N = 3838`，`df` 最高的词是 `item`（**1743**，
出现在 45.4% 的文档里），**还没有跨过 N/2 这条线**，经典式子给出的仍是 +0.18 而不是负数；
所以在本项目这份语料上，修正的收益主要不是"救回一个负数"，而是把高频词的权重压到合理量级
（`item` 的 idf_plus 是 **0.7896**，经典式子是 0.1839，两者都为正——所以在这个语料上，
修正改变的是量级，不是符号）。[实测，本机实跑]
顺带一个能看出"语料形态会反过来塑造 IDF"的细节：这份语料里 `df` 排前列的词是
`item`(1743)、`description`(1680)、`type`(1594)、`false`(1553)、`static`(1489)、`def`(1452)——
**全是 API 参数表头里的词**，因为 1898 个 signature chunk 每一块都重复了同一张表头；
如果哪天有人把 API 层关掉，这一批词的 `df` 会整体塌下来，**索引的统计量跟着语料一起变**。[实测，本机实跑]
**但"不为负"不等于"有区分力"**，这才是重点：`yolo` 的 `df = 59`、`idf ≈ 4.18`，
`检测` 的 `df = 144`、`idf ≈ 3.28`，而 `rtsp` 的 `df = 21`（`idf ≈ 5.21`）、
`yolov5` 的 `df = 23`（`idf ≈ 5.12`）——**高频词的 IDF 天然就小，这是 IDF 的定义，不是 bug**。
所以它治不好"最该排第一的那一篇稳定地排在第 3–10 名"这类问题（本项目里就是
`zh/vision/yolov5` 在查询 `YOLOv5 物体检测` 下排第 6，被一堆"运行例程"章节压住），
那一类要靠字段化 / 标题加权 / 查询理解，而不是"把 IDF 修得不负"。

**一个容易混的实现细节**：同一个"BM25+ 修正"在仓库里出现过两种写法——
`bm25.py` 模块 docstring 引用的是论文原始形式 `ln(1 + (N - df + 0.5)/(df + 0.5))`，
而 `_idf()` 里实际算的是 `ln((N + 1) / df)`（docstring 的正文解释也写的是这一版）。
两者在 N 远大于 1 时几乎同值（以 `item` 为例：前者 0.78932、后者 0.78960），
都恒正、都属 BM25 家族，所以**结论不受影响**；但做实验时仍要认**代码里实际那一版**，
不要拿论文公式手算去解释报告里的小数差异——那是两回事。

**如果你答到了**：`df > N/2` 时 `ln` 的参数小于 1 / 负 IDF 会让排序方向反过来 /
BM25+ 的修正只是保证非负、不解决区分力 —— 说明你理解了这一层。
**如果你答成**："IDF 是负数说明这个词是停用词，去掉就好" —— 方向对了半截，
但把**修公式**和**丢词**混成了一件事：本项目修完公式后**保留**这些词，
因为对高频领域词直接丢弃会同时丢掉它们的召回贡献；回去读
[`concepts/03`](../concepts/03-检索-稀疏与稠密.md) 第 3.1 节与
[tutorial 04 · 6 ③](../../tutorial/04-检索与消融.md)。

### Q3. 五条真实查询逐条判断该偏稀疏还是偏稠密，并给出判据；至少一条说明"两边都不稳、得靠别的环节"。

判据只有一条：**这条查询里有没有罕见字符串，以及答案所在的文档里有没有出现它**。
把它套到五条上：

| 查询 | 该偏谁 | 理由 |
| --- | --- | --- |
| `maix.camera.Camera 的构造函数有哪些参数？` | **稀疏** | 查询里带点分标识符；分词器把它整体保留成一个 token，字面命中即得分。稠密侧对这个罕见过长的名字没有稳定位置 |
| `拍一张图存起来` | **稠密** | 口语动词"拍/存"，文档里写的是 `read()` / `save()` / 摄像头示例；两侧没有共同 token，BM25 打不出分 |
| `YOLOv5 物体检测` | **都不稳** | 查询词是**该领域的通用高频词**，IDF 天然小，BM25 会把它让给"顺带提到的一大堆"；`物体检测` 被分词切成 `物体` + `检测`，整体 token 的 `df = 0`。稠密侧则可能被"AI 视觉总览"这类泛化文档吸走 |
| `MaixCAM 2 和 MaixCAM Pro 有什么区别？` | **都不稳** | 型号名是真实字符串（`MaixCAM2` 在领域词典里、`MaixCAM-Pro` 也注册了），字面能打在两边；但答案分散在跨页面文档里，这一条靠的是**多文档召回 + 重排**，不是某一路检索器变强 |
| `报错找不到摄像头怎么办` | **都不稳 / 偏稠密** | "报错""怎么办"是排障措辞，文档里是症状描述；两边都只能算中等。真正的修法通常是**放宽候选池 + 让 fusion/rerank 参与**，而不是换单路 |

**关键点：这五条里有两到三条，换检索器是解决不了的。** 第三、四条要的是
"领域词加权 + 多文档召回"，第五条要的是"候选池 + 融合/重排"——
它们都不在"稀疏还是稠密"这个二选一的维度上。

**如果你答到了**：判据落在"罕见字符串 / 共同 token"上 / 认出 `YOLOv5 物体检测` 是高频词问题 / 至少一条指向检索之外的环节 ——
说明你理解了这一层。
**如果你答成**："短的用 BM25，长的用稠密" 或者 "混合检索全都用就行了" ——
前者是按形式（长度）而不是按信号选型；后者承认了问题但没给出任何判据，
而概念文档 3.3 那张表的意义恰恰是"混合也要知道每一路在为什么贡献"；
回去读 [`concepts/03`](../concepts/03-检索-稀疏与稠密.md) 第 3.3 节与
[design/01 · 4.4.1](../../design/01-系统架构设计.md)（按 `qtype` 分策略那张表）。

### Q4. 3000 chunk 的中文散文语料，只上稠密可以吗？换成 MaixPy 文档（119 篇教程 + 56 页 API，3838 chunk）答案会不会变？

不可以一刀切，因为**稀疏检索相对稠密多买到的是"确定性"，而不是"语义"**——
它保证"文档里写了这个字符串"这件事一定可以被检索到，代价是它对措辞变化极其脆弱。
所以判据是：**你的查询里有多少条需要那个确定性**。

- 第一种语料（几乎全是中文散文、查询都是"怎么做 X"）：不需要确定性，
  BM25 的主要贡献退化成"把专有名词和数字当锚点"，收益小但仍非零；
  这时候先上稠密、把稀疏留作对照是合理的第一步。
- 第二种语料（本项目）：**答案会变**。因为 3838 个 chunk 里有 **1898 个是 signature chunk**
  （占近一半），而它们的内容就是标识符 + 签名 + 说明 + 参数表；
  评测集里 `signature` 那一组（4 题）问的正是 `api/maix.camera` 这类 doc_id，
  而这类 query–doc 的词面几乎完全重合。反过来，本项目 `signature` 组在只跑 bm25 的报告里是
  **0.000**、只跑 dense 的报告里是 **0.500**——**注意这个方向**：
  单看这一格，本项目当时的稠密那一侧并没有输；数字要一起读，
  只跑 BM25 那份（`eval/results/rag_L1_rag[rrf_bm25].md`）的 `signature = 0.000`
  **不能**被写成"BM25 赢了"。

**这条题的真正答案不是"选哪个"，而是"你的语料里标识符占比多少、查询里标识符占比多少"。**
本项目两边的占比都不低，所以默认是混合 + 融合；你的第一种语料两边都低，稠密单跑是合理起点。

**如果你答到了**：把"确定性"与"语义"分开 / 用量化事实（1898/3838 是 signature）支撑 / 指出第二问答案会变且方向可能反直觉 ——
说明你理解了这一层。
**如果你答成**："我的语料没有标识符，所以用稠密" —— 结论不算错，
但它只答了"哪种技术更先进"，没有回答判据；合格的答案要说清
**"什么时候会出现标识符类的查询"**，而不是"语料里有没有标识符"；
回去读 [`concepts/03`](../concepts/03-检索-稀疏与稠密.md) 误解一、误解二，
以及 [`design/05 · 1.3`](../../design/05-调研与借鉴.md)（稀疏检索对本场景不可替代）。

## 二、工程问答

### Q5. q004「怎么列出可用的摄像头设备」在只 dense、只 bm25、融合三份报告里全部未命中。列出排查步骤。

判断依据（这几条都要考虑到才算合格）：
1. **先分清"没召回"和"不存在"**——两者在报告里长得一样，本项目的通用排查路径是
   "先在索引里找这个 doc_id 在不在 → 再看它排第几 → 最后才怀疑检索算法"
   （[`postmortem/02`](../../postmortem/02-有文档却召不回.md) 的"一条通用排查路径"）；
2. **要同时看语料侧和索引侧**——chunk 建出来了不等于进了索引，本项目真的踩过
   "文档在磁盘上、白名单 4868 条、signature chunk 一个都没有"（事故 02）；
3. **要能区分三种失效**：语料里没有 / 语料里有但检索器没召回 / 召回了但排不进 Top-K；
4. **要对齐口径再下结论**——"只跑 BM25"的数字只能在 `retrievers: [bm25]` 那份配置里读，
   在融合配置的 `[bm25]` 那一列读出来的是候选池里的排名，不是最终榜单。

一个示范回答：
这道题我按四步走。第一步，确认"该被召回的东西"是什么：`eval/datasets/seed.jsonl` 里 q004 的
`ground_truth.required_docs` 是 `api/maix.camera`，`required_spans` 是 `list_devices`。
第二步，去 `corpus/processed/chunks.jsonl` 里找它在不在——**在**，
`chunk_id = api/maix.camera.list_devices`，`kind = signature`，正文是
`maix.camera.list_devices` / `def list_devices()` / `List all supported camera devices.` /
参数表一行。所以这既不是事故 02 那种"语料里没有"，也不是切分把信息切散了。
第三步，看它排第几：用 `scripts/demo_retrieval.py`（它只载入已有索引，秒级返回），
查询 `怎么列出 MaixCAM 上可用的摄像头设备？`，**dense 把它排在第 17**
（这个数字引自 [tutorial 04 · 6 ①](../../tutorial/04-检索与消融.md) 对同一题的记录），
**BM25 的前 20 里根本没有它**——我自己在本机只重跑了 BM25 这一侧：
它在 BM25 前 20 之外，而把查询换成 `maix.camera.list_devices` 后它**排第 1**（[实测，本机实跑]；
`demo_retrieval.py` 的 dense 一列依赖本机真实嵌入客户端，我没有在本轮重跑）。
这说明失效在"查询与文档没有共享词面"这一环：查询被分词成
`maixcam / 怎么 / 列出 / 上 / 可用 / 的 / 摄像 / 像头 / 摄像头 / 设备`，
而文档里既没有"摄像头"、也没有"设备"，只有 `list_devices` 与英文说明。
第四步，结论：这不是"加大 `top_k`"能修的（`top_k` 只会把噪声一起放进来），
也不是融合能修的（融合只能在候选池里重排，池子里没有的答案任何融合都救不回来——
请对照 `zh/vision/yolov5` 与 q004 的差别：前者在名次上被挤掉，后者根本没进池子）。
落点有二：① **查询理解**——把"列出可用的摄像头设备"识别成"要找 `list_devices` 这类符号名"，
走强制 API 召回；② **语料层**——给每个 signature chunk 补一条中文可检索的说明
（现在 `list_devices` 的 `summary` 是英文 `List all supported camera devices.`，
中文提问没有任何词面可打）。这两条都比"换嵌入模型"更直接命中问题。
**[未实测，需你运行确认]**：dense 侧的"第 17"来自 tutorial 04 的报告记录，我本轮没有重跑 dense；
你自己跑时若 `corpus/` 与 `indexes/` 不是同一份语料，名次会变——
那属于环境问题（[tutorial 04 · 3.1](../../tutorial/04-检索与消融.md) 讲过怎么对齐）。

常见的浅答案（以及为什么浅）：
- "把 `top_k` 从 5 加到 50" —— 没查语料、没查名次，直接改参数；
  概念文档误解三说的就是这个，事故 02 里 `top_k` 调到 50 也救不回来；
- "换个更强的 embedding 模型" —— 没先确认答案是不是在索引里、以及失败在词面还是语义这一环；
  在"查询与文档没有共享词"的情况下换模型是赌博；
- "融合两路应该就能捞回来" —— 混淆了"被挤掉"和"没进候选池"；
  融合只重排候选池，池子里没有的答案它看不见（[tutorial 04 · 6 ①](../../tutorial/04-检索与消融.md)）。

### Q6. 总分没动、用户说"签名类最近老答不对"。要加什么切法、什么字段，才能在下一次改动时立刻发现"某一类查询一直在召回失败"？

判断依据（这几条都要考虑到才算合格）：
1. **分组要有客观来源**——本项目的切法是评测集自带的 `qtype`
   （`concept` / `example` / `signature` / `troubleshoot`，写在 `eval/datasets/seed.jsonl` 每道题上），
   不是出题人临时挑的；
2. **每条指标要带分母（覆盖率）**——否则"0.000"和"没测到"在报告里是同一个数字
   （[`postmortem/05`](../../postmortem/05-伪装成好消息的0.md) 与
   [`concepts/07`](../concepts/07-评测-两条轴.md) 误解四）；
3. **失败要能落到"语料 / 检索 / 生成"哪一层**——报告里至少要能回答"这个 doc_id 在索引里存在吗"；
4. **要能分辨"排得不够前"和"根本没进池子"**——前者动融合/重排/加权，
   后者只能动语料或查询理解。

一个示范回答：
我会加三层，而不是加一个分数。第一层是**按 `qtype` 分组的表**——本项目的报告已经有它
（`maixrag/evaluation/harness.py` 的 `Report.by` 就是为这个写的），
数字直接从 `eval/results/` 的三份报告里读：`signature` 在只跑 BM25 那份里是 **0.000**
（4 题），在只跑 dense 那份里是 **0.500**，融合那份是 **0.500**。
第二层是**覆盖率字段**：`scripts/inspect_eval.py` 会对每条指标打出"覆盖了多少题"，
它抓到的第一个现场就是"符号被检查到的题数 0/18"，于是那个 0.000 立刻被标成不具参考意义。
第三层是**逐题明细 + 目标名次**：报告里的逐题表已经给了每题的召回率与首位命中，
再往前一步是让脚本对每个 `required_docs` 打出"是否在索引里 / 排名第几"——
这一步把"语料没有"和"排不上来"分开。
为什么单看总分不行，本项目有两次现成的实证：一次是语料层消融，
`signature` **+50 pt**、`concept` **−12.5 pt**、总体只有 **+5.5 pt**（事故 02）；
另一次是 dense / bm25 / 融合三方对比，总体 0.611 / 0.444 / 0.611，
融合与单路 dense **总分打平**，底下却是"救回一题、弄丢两题"
（`q016` 从第 6 抬到第 2，`q005` 从第 5 掉到第 12）。
**总分会把方向相反的变化平均掉**，所以它永远发现不了"某一类在持续失血"。
另外我要给一个诚实的边界：18 题里 `signature` 只有 4 题，**一题就是 25 pt**，
所以分组表看方向、不看小数位，想让结论稳定得先把评测集扩到设计稿的 60 题。
**[未实测，需你运行确认]**：`eval/results/` 里那三份报告是之前跑出来的快照，
你自己重跑时若语料或配置变了，具体小数会变；"按 qtype 分组 + 报覆盖率"这个做法不变。

常见的浅答案（以及为什么浅）：
- "加一个总分报警阈值" —— 总分不变恰恰是这次事故的症状，报警器永远不会响；
- "看用户的反馈就行" —— 反馈能告诉你"有问题"，但告诉不了你"问题在 4 类查询的哪一类、
  以及是哪一层"；没有分组，你无法把反馈变成可复现的实验；
- "加一个 LLM judge 打质量分" —— 先不说 judge 的偏差，它回答的还是"答案好不好"，
  而这里要查的是"该召回的东西进没进 Top-K"；这两件事分属两条轴
  （[`concepts/07`](../concepts/07-评测-两条轴.md) 第 2 节）。

### Q7.（取舍题）两周工时：继续做稀疏侧（字段化 BM25 / 标题加权 / 分词与词典），还是换成更强的 embedding？

判断依据（这几条都要考虑到才算合格）：
1. **先定位失效环节**——是"该进池子的没进"（语料/查询理解）、"进了池子排不上"（加权/重排）、
   还是"排序对了但没进 Top-K"（`top_k` / 名额分配）；三者的修法不共享；
2. **按 qtype 算收益，而不是按总分**——同一改动对不同类别的方向可能相反；
3. **算代价**：换 embedding 要重建整个向量索引（本项目 3838 chunk）、要重跑全部评测、
   且**会让所有历史数字失效**；字段化 BM25 是纯本地的、可增量验证的；
4. **样本量的边界**——18 题、每类 2–8 题，一组差一题就是 12.5–50 pt，
   不足以支撑"某一路整体更强"的结论；
5. **要说出失效条件**——你选的那条路在什么情况下会不划算。

一个示范回答：
我先把"要改善哪一类"钉死：用户抱怨的是 `signature` 类。它的现状是
只跑 dense **0.500**、只跑 bm25 **0.000**、融合 **0.500**，而这类问题的答案就是
1898 个 signature chunk 里的某一条——**答案在语料里，问题是"能不能被排进前 5"**。
这两周我投**稀疏侧**，理由是三点。第一，失败环节是"语料里有、但排不进"而不是"没有"：
`q002`（`Camera` 构造参数）在只 dense 时召回率 1.00、首位命中第 2（`eval/results/rag_L1_rag[rrf_dense].md` 逐题表），
说明答案确实在索引里、也确实能被排上来；而 `q004` 在 dense 下只排到第 17、
BM25 前 20 里根本没有它——**这说明问题一半在词面、一半在名额分配**，
而这两件事都便宜：`heading_path` 里 `api/maix.camera` 的标题就是 `["camera","Camera"]`，
把它拼进 `chunk.text` 前部或做字段化加权，就是直接给"标题命中的 chunk"加分，
不需要动索引结构之外的东西（[tutorial 04 · C1](../../tutorial/04-检索与消融.md) 就是这道实验）。
第二，代价不对称：换 embedding 要把 3838 个 chunk 全部重新嵌入、重跑三份报告，
还会把现在这批数字全部作废——在 18 题的评测集上，你没法区分"新模型更好"和"这一版运气更好"。
第三，我承认这个选择的**失效条件**：如果排查后发现失败集中在"用户用口语描述、
而语料只有英文符号名"（比如 `list_devices` 的 summary 是英文），
那么字段化加权救不了它——那属于**语料层要补中文说明**，或者**查询理解要做标识符抽取**，
两周预算就应该改成"给 signature chunk 补中文说明 + 重跑"，
而不是继续在 BM25 的权重上打磨。
**结论：先做字段化 BM25（一周内可验证），同时用同一条命令把对照留在同一把尺子上；
只有在"口语提问占比高、且语料补中文也补不动"时，才把预算转向 embedding。**

常见的浅答案（以及为什么浅）：
- "换 bge-m3 之外的更强模型，稠密一路就能救 signature" —— 没有看现状：
  只 dense 的 `signature` 已经是 **0.500**，而 `q004` 的失败是"查询与文档没有共享词"，
  更强的语义模型不会让 `list_devices` 这个字符串出现在查询里；
- "两个都做" —— 两周预算下等于两个都不做；取舍题要的是**先做哪个、以及什么条件下换**；
- "先扩评测集再说" —— 方向不错（18 题确实太少），但它不能回答"这两周投在哪"；
  合格的答案要给出"在现有样本量下，我仍然敢下注的那一个方向"以及它的代价。

## 三、动手题答案

### H1. 用 IDF 表与分词结果验证"BM25 对高频领域词失灵"

**操作步骤**（工作目录是仓库根）：

```bash
# 1) 先看查询被切成什么——这一步不能省
python -c "import sys;sys.stdout.reconfigure(encoding='utf-8');from maixrag.corpus.tokenize import tokenize_query;print(tokenize_query('YOLOv5 物体检测'))"

# 2) 载入语料、建一份内存 BM25，打印若干词的 (df, idf)
python -c "import sys,pathlib;sys.stdout.reconfigure(encoding='utf-8');from maixrag.builders import load_corpus;from maixrag.config import Config;from maixrag.indexing.bm25 import BM25Index,debug_idf_table;cfg=Config.load('configs/l2_hybrid.yaml',project_root=pathlib.Path.cwd());chunks,_,_=load_corpus(cfg);idx=BM25Index.build(chunks);print('N=',idx.size,'avgdl=',round(idx.avgdl,2));[print(f'{t:<14} df={d:<6} idf={i:.4f}') for t,d,i in debug_idf_table(idx,['yolo','检测','物体检测','rtsp','yolov5','camera','list_devices','find_blobs'])]"
```

**我在本机（`corpus/processed/chunks.jsonl` 现存的 3838 个 chunk、`configs/l2_hybrid.yaml`）
跑出来的结果**——这一组是我实测的，可以直接对照：

| 词 | df | idf |
| --- | --- | --- |
| `yolo` | 59 | 4.1754 |
| `检测` | 144 | 3.2832 |
| `物体检测` | **0** | 0.0000 |
| `rtsp` | 21 | 5.2084 |
| `yolov5` | 23 | 5.1175 |
| `camera` | 207 | 2.9202 |
| `list_devices` | 15 | 5.5449 |
| `find_blobs` | 11 | 5.8551 |

`N = 3838`、`avgdl = 46.51`。[实测，本机实跑]

**期望结果与解释**：
1. `物体检测` 的 `df = 0`：分词器把 `物体检测` 切成 `物体` + `检测`（`tokenize_query('YOLOv5 物体检测')`
   给出 `('yolov5', '物体', '检测', '5')`），所以"整体 token"在语料里一次都没出现。
   **这不是检索失败，是检索单元不存在**——验证 IDF 之前必须先验证分词。
2. `yolo`（df=59）与 `rtsp`（df=21）的 idf 是 4.18 vs 5.21，**稀有词的区分力更强**。
   在 BM25 的公式里，`yolo` 这个"该领域通用词"给每一篇提到它的文档都发差不多大小的分，
   而"顺带提到这件事"的篇章（`zh/README_MaixCAM#h10.2` 这类"运行例程"）数量多、长度也可能更短，
   于是真正系统讲它的 `zh/vision/yolov5` 被压到第 6——**这是 IDF 的定义，不是 bug**。
3. 与文档值的对照：`concepts/03` 和 tutorial 04 引用的近似值是
   `yolo ≈ 4.18（59 篇）`、`检测 ≈ 3.28（144 篇）`、`rtsp ≈ 5.21（21 篇）`、`yolov5 ≈ 5.12（23 篇）`，
   与我上面实测的 4.1754 / 3.2832 / 5.2084 / 5.1175 **一致到小数第二位**（文档写的是约数）。
   若你跑出来不一致，先查三件事：`corpus/processed/chunks.jsonl` 的 chunk 数是不是 3838、
   `indexes/index_meta.json` 的 `corpus_fingerprint` 与 `chunks` 是否与语料对得上、
   你用的配置是不是 `l2_hybrid.yaml`。
4. **[未实测，需你运行确认]**：索引是本地可重建状态（`corpus/`、`indexes/` 在 `.gitignore` 里），
   如果你在本机改过切分策略（`heading` ↔ `fixed`）再重跑，chunk 数与 `df` 都会变——
   tutorial 04 · 3.1 讲过怎么对齐语料与索引。

### H2. 在真实语料上给三个查询做检索器分诊（这一题对应概念文档第 7 节的动手题）

**操作步骤**：

```bash
# 1) 内置三个查询：dense / bm25 / fused 三列
python scripts/demo_retrieval.py

# 2) 只跑 BM25 的干净排名（--query 给了之后，内置查询就不再跑，三条要写全）
python scripts/demo_retrieval.py --config configs/l3_bm25_only.yaml -k 20 --query "maix.camera.Camera 怎么拍一张图" --query "YOLOv5 物体检测" --query "怎么列出 MaixCAM 上可用的摄像头设备？"

# 3) 融合配置下的同一批查询（dense / bm25 / fused 三列都在）
python scripts/demo_retrieval.py --config configs/l2_hybrid.yaml -k 20 --query "maix.camera.Camera 怎么拍一张图" --query "YOLOv5 物体检测" --query "怎么列出 MaixCAM 上可用的摄像头设备？"
```

`demo_retrieval.py` 只从 `indexes/` 载入已有索引（不重建，所以秒级返回），
`--config` 决定载入哪些检索器、`-k` 决定各列取几名。

**我已经在本机验证过的期望结果**（直接对照，不必重跑也能判断你对没对）：

- 查询 `怎么列出 MaixCAM 上可用的摄像头设备？`，BM25 取前 20：
  `api/maix.camera.list_devices` **不在前 20**；前 3 名是
  `zh/README_MaixCAM#h10`、`zh/README_MaixCAM2#h10`、`zh/README_no_screen#h10`（[实测，本机实跑]）。
  把查询换成 `maix.camera.list_devices`，它**排第 1**（第 2、3 名是
  `api/maix.network.wifi.list_devices`、`api/maix.peripheral.uart.list_devices`）。
  —— 这两次实跑合起来就是分诊：**失败不在"检索器没找到"，而在"查询里没有那个字符串"**。
- 查询 `YOLOv5 物体检测`：`zh/vision/yolov5` 在 dense 列排第 5、bm25 列排第 6、
  融合列掉到第 12（[tutorial 04 · 4](../../tutorial/04-检索与消融.md)，本命令同为复现入口）。
  这条是**"两边都不稳、且融合会把它挤出去"**的现场。
- 查询 `maix.camera.Camera 怎么拍一张图`：dense 与 bm25 都会靠字面/语义落在
  `zh/vision/camera` 一带（[`concepts/03`](../concepts/03-检索-稀疏与稠密.md) 第 4 节给了
  `maix.camera.Camera` 这组查询的前 3 名：BM25 是 `vision/camera#code` ×2 + `#prose`）。
  **读第 4 节那两组数字时要带上它自己的警告**：稠密那一侧用的是**假嵌入**（无语义能力的哈希词袋），
  它只能证明"管线通了"，不能代表真实 bge-m3；所以你本机跑 `demo_retrieval.py` 时，
  dense 列的名次与概念文档那份**不应该被拿来互相印证**，除非你确认嵌入是真客户端。
- 对应的 ground truth（`eval/datasets/seed.jsonl`）：
  `maix.camera.Camera 怎么拍一张图` → `q001`，`required_docs = ["zh/vision/camera", "zh/vision/display"]`；
  `YOLOv5 物体检测` → `q005`，`required_docs = ["zh/vision/yolov5"]`；
  `怎么列出可用的摄像头设备` → `q004`，`required_docs = ["api/maix.camera"]`。

**验收怎么自查**：三条查询各写一行结论，格式是
"查询 X 的答案是<doc_id>，在 <检索器> 下排第 N / 不在前 K → 该偏 <稀疏/稠密/都不稳>"。
名次是别人为你的结论背书的唯一凭据，所以**结论里必须带名次**；
另外要能指出至少一条"融合也救不回来"的查询（`q004` 是候选：BM25 前 20 里没有它、
dense 只把它放在第 17，它靠的是两路各自的名次推出来的融合分，两路都不高时融合也抬不动它），
以及至少一条**语料层**的修法
（`api/maix.camera.list_devices` 的说明是英文 `List all supported camera devices.`，
中文提问没有任何词面可打——补一条中文说明比重排更直接）。

**[未实测，需你运行确认]**：上面 `YOLOv5 物体检测` 与 `maix.camera.Camera` 两组名次
引自 tutorial 04 与 concepts/03 的报告快照，我本轮没有重跑 `demo_retrieval.py` 的三列输出；
你自己跑时若 `corpus/` 与 `indexes/` 不是同一份语料，名次会变。
