## 一、概念问答

### Q1. 链与循环的区别只有一个，但它带来四类新问题；为什么这四类问题不能靠"更强的模型"解决？

**答案**：链的每一步决策都是**代码在编写时**定下的——走哪条路、走几步、用什么参数，
编译期就固定了，运行时的输入只影响内容不影响路径。循环把**每一跳的决策**移到了
**运行时、由模型看着观察结果做**：它看到上一步返回什么，才决定再调一次工具还是给最终答案。
这个转移本身不产生"更聪明的链"，它产生四个**链里根本不存在**的位置：
能力要能被换掉（可插拔）、能力要能让模型看见（可描述）、循环要能停（可停止）、
调用要能被拒（可约束）。这四件事全部发生在**模型之外**——注册表、工具契约、预算计数器、
权限判定，没有一件是模型参数变大就会自动长出来的；模型再强，它也不知道一个没被注册成工具
的能力存在，也不会自己给自己设上限。

**如果你答到了**：决策位置的转移（编写时 → 运行时） / 四件事都是系统边界问题而非模型能力问题 /
"没被注册的能力等于不存在" —— 说明你理解了这一层。
**如果你答成**："因为 agent 更复杂，所以要更多机制" —— 那是把现象当原因：复杂不是原因，
**决策权交出去之后责任没有跟着交出去**才是原因，需要回去读 [concepts/06](../concepts/06-Agent与链的区别.md) 第 3.3 节与第 6 节误解三。
如果你答成："换个更强的模型，它自己就会规划" —— 那就漏掉了"规划的前提是它先得知道有什么可规划"，
需要回去读 [tutorial 06 · 3.2](../../tutorial/06-Agent-五块机制.md) 关于"描述即提示词、空描述当场拒绝注册"的那一节。

### Q2. 三条预算线只能留一条，你留哪条？放弃的那两条让你暴露在什么失效下？

**答案**：三条线各防一种失效，而且**失效的可见性不一样**：轮次线防"模型反复横跳、想不清楚"
（保住它，失败还是显式的——"轮次达到上限（N）"），工具调用线防"单轮内疯狂并发调工具"
（只有轮次线时，一轮里可以调一百次工具），token 线防"上下文无限膨胀"
（每轮把全部历史塞回去，成本指数上升）。所以"留哪条"取决于**在你的场景里哪种失效最贵、
以及你还能不能看见它**：如果一次失控的账单比"答不出来"贵得多，就要留那条能挡住成本爆发的线；
如果一次答不出来就能被人发现并重试，那条线的优先级反而低。**只留一条必然漏**——
这是被断言锁住的事实，不是判断：`test_tool_call_budget_limits_calls_within_turns`
就是防止"只用 max_turns 就以为够了"。

**如果你答到了**：三条线各防谁 / 显式失败与无声失败的差别 / "留哪条取决于哪种失效更贵" —— 说明你理解了这一层。
**如果你答成**："当然留轮次，轮次最重要" —— 那是凭直觉排序，没有代价分析：你既没说清
"一轮里调一百次工具"这种失效在你的场景里代价多大，也没说清另外两条放弃之后你还看不看得见。
需要回去读 [concepts/06](../concepts/06-Agent与链的区别.md) 第 6 节误解二，以及
[tutorial 06 · 3.4](../../tutorial/06-Agent-五块机制.md) 那张"三条线各防什么 / 出问题时的样子"的表。
如果你答成："都留着不就行了" —— 那不是回答取舍问题，是把题目绕过去了。

### Q3. 怎么判断一次 agent 失败是"预算不够"还是"方法不行"？给出可操作的判据。

**答案**：判据在**轨迹**里，不在最终指标里。打开 `RunResult` 的事件流，逐个看每一步：
如果每一步都在推进——改写查询、从检索切到确定性工具、再用新学到的类名回去重检索——
最后一步被截断，那结论是"预算不够"；如果轨迹在原地打转（用几乎相同的参数反复调同一个工具，
或连续同类失败的签名不变），那才是"方法不行"。
第二个证据是**资源消耗快照**：`{'turns': 'N/M', 'tool_calls': 'N/M', 'tokens': 'N/M'}`，
哪一条贴着上限就说明是哪条线在起作用——`Budget.exhausted()` 返回的就是具体原因，
因为"因为轮次用完了"和"因为 token 用完了"对应完全不同的调参方向。
第三个证据是**失败形态**：显式的"未能完成回答 + 已完成的部分"说明它知道自己没做完（可诊断）；
而"每次都成功、只是没有进展"是无声失败，那跟预算太小是**相反**的两个坑，
`python scripts/demo_budget.py` 的场景一就是它的现场。
可操作的验证动作是：**只动预算、不动别的**再跑一次同一道题，然后对比答案形态有没有变。

**如果你答到了**：看轨迹里每一步是否合理（而不是看最终指标） / 分清显式失败与无声失败 /
预算消耗与上限的比值 / "只动预算"的对照实验 —— 说明你理解了这一层。
**如果你答成**："多试几次看看" —— 那是没有判据，只是碰运气：随机性混进来越试越说不清。
需要回去读 [事故 06 · 怎么发现的](../../postmortem/06-预算与任务不匹配.md) 和
[tutorial 06 · 6.4](../../tutorial/06-Agent-五块机制.md)。
如果你答成**："指标差就是方法不行"** —— 这一章恰好有一个反例：检索轴的 `Recall@K` 只看第一次
检索的 Top-5，agent 是多次检索、累积证据的，**那把尺子量不了它**，
所以 `0.611 → 0.556` 不能读成"agent 更差"。回去读
[concepts/06 误解四](../concepts/06-Agent与链的区别.md)。

### Q4. 链式成本固定、循环成本不确定，这对评测设计意味着什么？

**答案**：意味着"评测"不再只是"打分"，而是**必须同时产出成本记账**。
不确定的成本无法被假设，只能被度量——链式是固定的 1 次检索 + 1 次生成，
循环是"平均 4.9 次工具调用 + 对应轮次的模型调用"`[本项目实测]`，这个数会随题目变化，
所以报告里必须有工具调用总数、失败数、被拒数、按工具分布、平均每题调用数，
以及 `RunResult` 里的预算快照。第二个后果是**尺子必须匹配被测对象的口径**：
agent 的正确文档可能出现在第 2、3 次检索里，而检索轴的 `Recall@K` 只看第一次检索的前 5 个片段，
所以 agent 的检索轴数字反而更低，却**不代表它更差**——想真正量 agent，
需要"累积证据"口径的检索指标，而这是一个**明确的待办**，不是已解决的问题（本项目还没做）。
第三个后果是**可比性要靠记录配置来保证**：两份报告的数字只有在同一份语料、同一套配置、
同一时刻量出来时才能相减——本项目里链式复跑是 0.694、而文档记录的 agent 是 0.556，
这两个数来自不同时刻，**不能直接相减**。

**如果你答到了**：不确定 ⇒ 必须度量（`RunResult` 带 `events` 与 `budget`） /
尺子要匹配口径、检索轴量不了 agent / 报告必须记录配置与时刻 —— 说明你理解了这一层。
**如果你答成**："要多跑几次取平均" —— 那只碰到了方差问题，没碰到这一章的核心：
**成本本身就是一个必须被报告的结果**，不是可以平均掉的噪声。
回去读 [concepts/06 · 4.4 与误解四](../concepts/06-Agent与链的区别.md)，
以及 [tutorial 00 · 4.3](../../tutorial/00-主线导览.md)。
如果你答成**："agent 的指标差一点，说明还是链式好"** —— 那是拿一把量不了它的尺子去下结论，
回去读 [tutorial 06 · 6.4](../../tutorial/06-Agent-五块机制.md)。

## 二、工程问答

### Q5. 为什么"`maix.camera.Camera.read()` 的参数是什么"这一类问题不该交给 agent？什么条件下这个判断会翻转？

**判断依据**（这几条都要考虑到才算合格）：
1. **任务需要几步**——原子查询（一次查表就能确定命中）不需要"看到结果后改变策略"，
   这类任务用确定性工具一次就到底；
2. **代价的量级**——要把 agent 的调用数和链式/单工具调用的调用数摆在一起比，
   而不是笼统地说"agent 贵"；
3. **翻转条件**——什么情况下同样的查询**值得**花这些调用（需要多跳、需要改写查询、
   需要写代码后自检），这是答案里最容易被漏掉的一半；
4. **定式失效时的后果**（可选加分）——问题不在"贵"，而在这一条查询**一次查表不一定够**：
   `read()` 的形式参数只有两个（`block` / `block_ms`），但用户问的可能是
   "我想非阻塞读一帧该传什么"或"它不阻塞时返回什么"，那就得把签名和用法接起来——
   这时"一趟查表"这条定式自己就不成立了。

**一个示范回答**：
签名类问题不该交给 agent。"`maix.camera.Camera.read()` 的参数是什么"只有一个原子动作——
查符号表，`lookup_api` 一次就是确定性命中（我们语料里的白名单是 1898 个符号 / 4868 条），
命中就是命中，没有需要"看到结果再决定下一步"的空间。而 agent 在 18 题上用了 88 次工具调用、
**平均 4.9 次/题**`[本项目实测]`，其中 `search_docs` 31 次、`lookup_api` 25 次；
在 signature 类问题上这 4.9 次里大部分是在浪费——检索一遍再去查签名，
而查签名一步本来就能给出答案。所以成本对比不是"贵一点"，
而是**4.9 次工具调用 + 对应轮次的模型调用，去换一个 1 次调用就能拿到的确定性结果**。
这个代价必须由"答得更好"来偿还，而在这类题上它换不到更好的答案。
**翻转条件**是我会把它交给 agent 的三种情况：（a）要**多跳**——
先查 `read()` 的签名、再用返回的类型去查另一个 API；（b）第一跳结果不理想需要**改写查询**；
（c）要写一段代码并**自检**——这正是 agent 真实值得的地方：
`check_api_usage` 在 18 题里被主动调用了 21 次，链式基线完全没有这个行为。
另外有一条定式失效的情形值得留意：`read(block=True, block_ms=-1)` 的形式参数是两个，
如果用户问的是"`read()` 有哪些参数、默认值分别是什么"，
一次 `lookup_api` 命中 `def read` 那一条就够；但如果用户问的是"我想非阻塞读一帧该传什么"、
"它不阻塞时返回什么"，那就需要把签名和"怎么用"接起来，才轮到 agent。

**常见的浅答案**（以及为什么浅）：
- "简单问题不该用 agent" —— 没有定义什么叫"简单"，也没给出代价量级；
  合格答案要说清"简单"在这类题上具体指**一次确定性调用就能命中**。
- "agent 太贵了" —— 只说了成本，没说清在什么条件下贵是值得的；
  这一章的立场恰恰是"能力上限更高，但要求预算与任务深度匹配"，
  一句话否掉 agent 就把结论推到了另一个极端。
- "看情况，看用户需求" —— 对，但等于没说；合格的答案要给出判据（步数、可验证性、
  是否需要改写查询），以及"我按哪条判据裁"。
- "agent 更准，多花点钱值得" —— 这条在 signature 类问题上没有依据：
  确定性工具 `lookup_api` 是查表，agent 并不会让查表更准。

### Q6. YOLO 例程失败后，"加预算到 20 轮"和"砍掉 agent"两种声音，你凭什么裁决？

**判断依据**（这几条都要考虑到才算合格）：
1. **看轨迹，不看最终指标**——失败之前每一步是否在推进（改写查询、切确定性工具、
   用新学到的类名重检索），这个观察直接把结论指向"预算不够"或"方法不行"；
2. **区分两类失败**——"我没做完"（显式失败，可诊断，加预算有救）与
   "每次都成功、只是没有进展"（无声失败，加预算**反而有害**，它只是让账单更长）；
3. **预算使用率**——平均消耗与上限的比值：现在平均 4.9 次/题而工具调用上限是 12，
   所以多数题预算充足，而**个别题**可能贴着上限；
4. **裁决的标准是"加预算后有没有换来更好"**——这是一个可执行的对照实验，
   而不是一次投票；加预算不是免费的，它要为答案变好负责。

**一个示范回答**：
我会先要两样东西，再表态：一是那道题的完整轨迹，二是评测报告里的预算消耗记账。
看轨迹的理由是事故 06 给出的判据——4 轮预算下那四步"检索 → 自己改写查询 →
切到确定性工具 → 用第 3 步学到的 `nn.YOLOv5` 回去重检索"**没有一步是浪费的**，
而链式在结构上做不到第 4 步；把预算调到 10 轮后同一道题在第 5、7 轮各做了一次自检、
第 8 轮给 final，答案里的 `cam = camera.Camera(detector.input_width(), detector.input_height(), ...)`
不是文档里逐字抄来的`[本项目实测]`。**同一个问题、同一份语料，只有预算变了**——
这就是"参数不匹配"而不是"方法不行"的证据。但"加预算"这个动作有前提：
加钱必须换来答案变好，所以我会用**加预算前后同一道题的答案形态对比**来裁决，
而不是投票。第二样东西是使用率：现在 18 题平均 4.9 次工具调用/题，
而 `--max-turns 10` 装配出来的工具调用上限是 `max(6, 10+2) = 12`
（`maixrag/cli.py`），也就是平均使用率约 4.9/12 ≈ 41%——**平均还剩一半以上余量**，
说明"全线翻倍到 20 轮"是拿全局成本去补个别题，不划算；该做的是
**按题给预算**（把 signature 类给小预算、多跳类给大预算），而它的前提是系统得先知道 qtype。
至于"砍掉 agent"这一方，我会拿两条反证：预算给够时它做到了链式做不到的事；
以及 18 题里 `check_api_usage` 被主动调用 21 次`[本项目实测]`——链式想要这个能力，
得把它写成一次固定步骤。**"我不知道答案所以拒答"和"我查到一半被掐断"是两件不同的事**，
前者是能力边界的诚实，后者是我的配置错误。

**常见的浅答案**（以及为什么浅）：
- "加预算试试看，不行再说" —— 没有判据也没有停止条件；正确的做法是**只动预算、
  同一道题、预先写下答案形态的预测**，跑一次就能裁决。
- "agent 就是不如链式，砍掉" —— 用一个配置错的方案和基准比较，得到的结论不是
  "这个方案不好"，而是"这个方案在配置错的时候不好"。
- "20 轮比 10 轮更保险，反正有预算上限" —— 方向错了：预算是**任务与成本之间的谈判**，
  不是安全阀；而且预算大得等于没有约束时，失败会从"我没做完"变成无声的空转
  （`python scripts/demo_budget.py` 场景一是 30/30 轮、30 次工具调用全部"成功"却返回
  "找到 0 个片段"）。
- "看哪个方案分高" —— YOLO 这道题在现有报告里没有单独的分数字段，
  而检索轴那把尺子量不了 agent；在这里只有轨迹和答案形态能说话。

### Q7. 用 18 题的结果给"预算给多少才够"写一条判据。

**判断依据**（这几条都要考虑到才算合格）：
1. **分子分母都要说对**——分子是"平均每题工具调用"，分母是**实际生效的上限**；
2. **上限不是 `max_turns`**——`cli.py` 里工具调用上限是 `max(6, max_turns + 2)`，
   所以 `--max-turns 10` 对应的是 12，不是 10；
3. **要给出阈值和它的理由**，并且说清在哪个区间代表"够"、哪个区间代表"该调"；
4. **要说出这条判据的失效条件**（样本量、平均值掩盖长尾、token 线量不到）。

**一个示范回答**：
判据是**预算使用率 = 平均每题工具调用 ÷ 实际工具调用上限**。
分子来自报告里的"平均每题工具调用"（`_avg_tool_calls`，读的是 `app.total_tool_calls`
这个**累计计数**，不是被逐题清空的 `tools.history`——那个口径 bug 出现过两次，
所以口径与来源都写在 docstring 里）；分母来自预算装配：
`max_turns` 命令行优先、其次配置、否则兜底 4，而 `max_tool_calls = max(6, max_turns + 2)`，
所以 `--max-turns 10` 时上限是 **12**。代入实测：18 题 88 次调用 ⇒ 平均 **4.9 次/题**，
使用率 ≈ **4.9 / 12 ≈ 41%**。判据是：**平均值逼近上限（比如 ≥80%）说明预算系统性偏紧，
该调大；平均值在 40% 上下说明对多数题目够，个别贴顶的题要按题处理**。
这个数为什么是 80% 而不是 50%：平均值会被少数难题拉高，留出的余量是给长尾题的，
而"平均已经贴着上限"意味着长尾题必然被大量截断。它还给我一个可观察信号：
`--max-turns 4` 那次之所以是错的配置，正是因为多跳题需要 6–10 轮，
而 4 轮**在平均值之外的那部分题目上**才暴露出来——只看平均分是看不出来的。
失效条件有三条：18 题样本太小，平均值容易被一两道题带偏，所以**要按 qtype 分组看**；
预算是全局的一个数，掩盖了"某些题 2 轮就够、某些题 10 轮才够"；
以及 token 那条线在假模型下**量不到东西**（`--fake-chat` 的假模型不报 token，
快照里是 `0/60000`，只有 `tests/test_agent_loop.py::test_token_budget_is_tracked`
那类确定性断言能验证它），
所以这条判据目前只在轮次和工具调用两条线上成立。

**常见的浅答案**（以及为什么浅）：
- "平均 4.9 次，上限 10 轮，使用率 49%" —— 分母取错了：`--max-turns` 限的是**轮次**，
  而 4.9 是**工具调用**数，两者的上限是两个不同的数（12 而不是 10）；
  口径错位会让判据在真正的瓶颈上失灵。
- "让它跑，报错了再调大" —— 那是事后补救，不是判据；而且预算太小是显式失败
  （"轮次达到上限（4）"），预算缺失才是无声失败，两者的信号完全不同。
- "设大一点总没错" —— 这一章明确否掉了这个方向：等于没设的预算让失败变成无声的空转。
- "看平均分，分低就加预算" —— 分数低可能来自检索、可能来自尺子量不了 agent、
  也可能来自预算；不加区分地加预算只是把成本推高。

## 三、动手题

### H1. 假模型下 `--max-turns 1` 与 `--max-turns 3` 的对比

先说清楚为什么这道题用假模型还能做：`--fake-chat` 的假模型是一个**确定性的坏决策器**，
它只走 `search_docs → final` 一两步，所以输出稳定可复现；而真实模型的多跳恰恰是它复现不出来的。

步骤与预期（下面给出的都是**按 `maixrag/cli.py` 的 `_SimpleFake` 与 `loop.py` 的循环逻辑确定**的，
[tutorial 06 · 4](../../tutorial/06-Agent-五块机制.md) 里那次已记录的运行也印证了第 2 步；
但**我本人没有运行过这两条命令**，所以三条都标为待确认）：

1. `--fake-chat --max-turns 1`：第 1 轮预算检查通过（turns 0 < 1），消耗一轮后模型调
   `search_docs`，工具结果回灌；回到循环顶部时 `exhausted()` 命中"轮次达到上限（1）"，
   走 `_degrade` 分支——`stopped_reason` 是 `budget`，【答案】里是**"未能完成回答"+
   具体的耗尽原因 + "已完成的部分"**，而不是空文本、也不是异常。
   `[未实测，需你运行确认]`
2. `--fake-chat --max-turns 3`：第 2 轮模型给 `final`，循环从 `final` 分支正常退出——
   `stopped_reason` 是 `final`，消耗快照里 turns 是 `2/3`，预算还有余量。
   [tutorial 06 · 4](../../tutorial/06-Agent-五块机制.md) 记录的那次输出是
   `结束原因：final   消耗：{'turns': '2/3', 'tool_calls': '1/6', 'tokens': '0/60000'}`。
   `[未实测，需你运行确认]`
3. **为什么必须换真实模型才能复现"agent 比链式还差"**：假模型第 1 轮就 `search_docs`、
   第 2 轮就 `final`，**2 轮对它够用**——也就是说它根本不会去改写查询、不会切到
   `lookup_api`、不会写完自检。而"预算 4 轮输给链式"那个现场，靠的正是
   真实模型做的四步多跳（第 2 步自己改写查询、第 3 步切确定性工具、
   第 4 步用学到的 `nn.YOLOv5` 回去重检索）。所以用 `--fake-chat` 复现这件事是**结构性做不到**的，
   换真实模型是必需条件，不是偏好。

**验收对照**：两次运行的【执行轨迹】末尾"结束原因 / 消耗"与你事先写的预测一致；
1 轮那次出现"未能完成回答"+ 具体耗尽原因；并且你能指出它走的是 `_degrade`
（`tests/test_agent_loop.py::test_budget_exhaustion_degrades_gracefully` 锁住的正是这条断言）
而不是抛异常。

> 依据：[事故 06](../../postmortem/06-预算与任务不匹配.md) · [tutorial 06 · 6.4](../../tutorial/06-Agent-五块机制.md) ·
> `maixrag/agent/loop.py`（`run` 的预算检查在 `consume_turn` 之前、`_degrade` 在耗尽分支里）

### H2. 给评测报告加"预算使用率"

**步骤**：

1. 读 `maixrag/cli.py` 的 `_build_main_branch_agent`（预算怎么装配）与 `_avg_tool_calls`
   （读数口径），确认上限和分子的来源；
2. 在 `cmd_agent_eval` 的【agent 专属指标】那一段加一行：`预算使用率 = 平均每题工具调用 / max_tool_calls`；
3. 用同一套配置跑一次 `agent-eval --max-turns 10`（**真实模型**，否则第 5 步会看到假象）；
4. 把新指标填进报告；
5. 回答"看一个字段"的问题。

**期望结果（用文档里的真实数字推算，不是我跑出来的）**：
分子 88 次调用 / 18 题 = **4.9 次/题**，分母 `max(6, 10+2)` = **12**，
使用率 ≈ **4.9 / 12 ≈ 41%**。判据可以写成：**平均值逼近上限（≥80%）说明预算系统性偏紧；
40% 上下说明对多数题目够，个别贴顶的题按题处理**。
[未实测，需你运行确认] —— 88 / 4.9 来自 [事故 06 · 修复](../../postmortem/06-预算与任务不匹配.md)
与本项目文档，分母 12 来自 `cli.py` 的装配逻辑。

**一个必须先看的坑**：`eval/results/` 下**没有** `agent_loop.json`——
它曾经存在，但里面是一份 `--fake-chat` 复跑**覆盖**出来的结果
（`tool_calls = 1`、`by_tool = {'search_docs': 1}`），
与同一份 `.md` 报告里的实测数字（`88 次 / 4.9 次每题`）**直接矛盾**。
两份文件说着两个数，而没人知道该信哪个——**那比数字算错更糟**，
因为它把"可验证"变成了"看运气"。

所以那份 `.json` 被**删掉了**，权威记录只保留
[`eval/results/agent_loop.md`](<../../../eval/results/agent_loop.md>)（它里面标着 `[本项目实测]`）。
`agent_loop.json` 会在下一次**用真实模型**跑 `agent-eval` 时重新生成——
那才是属于你的数字。

这件事的教训：**同一份结果只留一个可读入口。**
两个文件、两种格式，就会有两种数字，而它们迟早会不一致
（同类问题见 [事故 04 · 被清空的统计](../../postmortem/04-被清空的统计.md)：
**同一件事只有一个数**）。

所以你要算的那个 4.9 次/题，**当前磁盘上取不到**：88 次调用 / 4.9 次每题的出处是
[事故 06 · 修复](../../postmortem/06-预算与任务不匹配.md)
与 [tutorial 06 · 5 证据表](../../tutorial/06-Agent-五块机制.md)（那里标着 `[本项目实测]`），
想拿到属于你自己的数字必须用**真实模型**重跑一次 `agent-eval --max-turns 10`。

顺带回答"报告里哪一格会假到让你误判"：**假模型下**，`平均每题工具调用` 会小到
1/18 ≈ 0.06 次/题（就是上面那份被删掉的 json 里的 `tool_calls = 1`），
`tokens` 那格是 `0/60000`——**两格都量不到东西**，
把它们读成"预算很省"就是误判。报告里现在的数字之所以还没暴露这一点，
是因为 [事故 05](../../postmortem/05-伪装成好消息的0.md) 说的那件事：
**分母是 0 的指标看起来永远是完美的**。

**验收对照**：你能写出分子、分母和出处命令；给出阈值和理由；
并且能指出在假模型下哪两格数据会假（`平均每题工具调用` 与 `tokens`），
以及为什么"用一个字段判断预算对不对"时我选**预算使用率**而不是最终指标——
它直接回答"限制类参数够不够"，而最终指标答不了这个问题
（[事故 06 · 同类问题清单](../../postmortem/06-预算与任务不匹配.md)：
**只看结果指标、不看资源指标，就无法区分"方法不行"和"参数不对"**）。

> 依据：[事故 06 · 修复](../../postmortem/06-预算与任务不匹配.md) · [tutorial 06 · 6.4](../../tutorial/06-Agent-五块机制.md) ·
> [eval/results/agent_loop.md](<../../../eval/results/agent_loop.md>) · `maixrag/cli.py`

## 还没解决的问题（这一章诚实的边界）

这几条是本项目**明确承认没做**的，答题时不要把它们当成已有能力：

1. **"累积证据"口径的检索指标**——想真正量 agent 需要它，目前只有"第一次检索 Top-5"的口径；
2. **按 qtype 分配预算**——需要先知道 qtype，属于查询路由的应用方向，还没做；
3. **token 预算在假模型下无意义**——`--fake-chat` 的假模型不报 token，
   只有 `tests/test_agent_loop.py` 里的确定性断言能验证这条线。
