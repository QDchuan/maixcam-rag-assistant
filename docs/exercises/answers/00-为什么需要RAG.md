## 一、概念问答

### Q1. 队友说"下个月换一个更强的模型，MaixPy 老编 API 的问题就解决了"——为什么换模型不是解法？

幻觉的根因是**知识缺失**，不是**推理不足**：MaixPy v4 那批正确的写法只存在于官方文档里，
而 MaixCAM 是比较新的硬件，这些文档在预训练语料里几乎是缺席的
（[design 00 §2.1](../../design/00-项目定位与教学大纲.md)）。参数量改变不了
"这批文档在不在预训练语料里"这件事——一个更强的模型面对
"MaixPy v4 的 `Camera.read()` 参数是什么"时，处境和弱模型一样：它也只能续写最像的写法，
于是写出 `read_frame()`、`cv2.VideoCapture`、`PiCamera()` 这些它见过的习惯。
能力提升的是它**用好你给的资料**的水平，不是它**凭空知道资料**的水平。
所以解法是"开口之前把权威文档送到它眼前"（RAG），不是换模型。

本项目的实测现场能说明这一层的边界：L1 链式基线在 YOLO 那道题上明确拒答
（"不能凭 OpenCV、K210 时代 MaixPy v1 的习惯推测 API"），符号级幻觉率 **0.000**——
但这个 0.000 起初是**假的好消息**：它是因为"模型压根没写代码"，符号被检查到的题数是
**0/18**；修好检索后覆盖率变成 18/18，同样的 0.000 才是真的
（[事故 05](../../postmortem/05-伪装成好消息的0.md)）。换模型既改不动"文档没进预训练语料"，
也改不动这个覆盖率。

**如果你答到了**：知识缺失 vs 推理不足 / 换模型改不了预训练语料里没有的东西 /
强模型是"用资料更好"而不是"知道资料" —— 说明你理解了这一层。

**如果你答成**："更大模型见过的代码更多，所以会更准" —— 那是把**参数量**当成**知识来源**，
需要回去读 [concepts/00 §3.2 与 误解一](../concepts/00-为什么需要RAG.md)。

### Q2. 手工流程里哪一步对应检索、哪一步对应生成？揉成一个动作会付什么代价？

"翻 wiki、自己判断该看哪几页"对应**检索**——而且是整条链路里最容易出错的一环；
"把内容复制进对话框 + AI 给建议/写代码"对应**上下文注入与生成**
（[concepts/00 §3.3](../concepts/00-为什么需要RAG.md)，
逐条映射表在 [tutorial 02 §2.1](../../tutorial/02-把手工流程变成系统.md)）。
揉成一个动作的代价是：**两个环节的错在现象上长得一样**——你看到的是"答案里没有可运行代码"，
但分不清是"没找对页"还是"模型没用对你复制过去的资料"。

本项目有这道题的现场。同一个 YOLO 问题，链式基线的**生成轴是优秀的**：
不编造 API、明确拒答；**检索轴是失败的**：真正含例程的 `zh/vision/yolov5` 根本没被召回。
两张轴的分离见 [concepts 01 §4.1](../concepts/01-RAG的完整链路.md)，
所以"只看答案里没有代码就去调提示词、换模型"是**全部调错方向**。
拆开之后每一段各自报数字，这就是 [tutorial 02 §2.1](../../tutorial/02-把手工流程变成系统.md)
那张映射表要换来的东西：**手工版本的不稳定、不可复现、不可测量**，被换成两轴评测
（18 题 / 4 类 qtype）。

**如果你答到了**：翻文档=检索 / 复制+生成=上下文注入与生成 / 两环都可能错而现象相同 /
必须拆开才能定位 —— 说明你理解了这一层。

**如果你答成**："检索就是从文档里找答案，生成就是把答案写出来" —— 那只是把名字复述了一遍，
没有说出**排障后果**（两个环节的失败长得一样）。回去读
[concepts/01 §4.1](../concepts/01-RAG的完整链路.md) 和 [tutorial 02 §2](../../tutorial/02-把手工流程变成系统.md)。

### Q3. "20 万 token 以内可以全塞" → "MaixPy 语料 20–22 万 token，所以必须做 RAG"，这个推理哪一步跳了？

那句话的原文是一个**厂商经验判断**：当知识库小于约 20 万 token 时，可以把整个语料
放进 prompt 并配合 prompt caching，跳过检索（[design 00 §6.1](../../design/00-项目定位与教学大纲.md)）。
跳掉的那一步是：**把"这份语料一共有多少 token"当成了"这一次请求必须装多大的范围"。**
真正决定要不要检索的是**你要覆盖多大范围**，不是语料总共有多少。

实测把这个问题摊成了三档，同一份 MaixPy 语料同时落在线的两侧：
单模块（`peripheral` 10 篇 / 73,768 字节 / 约 **2 万** token）远在阈值内，
**该全塞，且很可能优于检索**；全中文教程（130 篇 / 713,520 字节 / 约 **20–22 万** token）
已越线；中文教程 + API 参考约 **26–33 万**，明显不可行
（[design 00 §5.4](../../design/00-项目定位与教学大纲.md)）。所以答案是**一条曲线**，
不是"该"或"不该"。

本项目把它当假设还有第二个理由：**token 是估算的，而且敏感度很高**。
字节数是实测的，token 只能靠"中文占字节比例"这个假设换算——设计初稿凭直觉估成
**12–13 万**、判定"全文上下文可行"，把算式摊开后真实量级是 **20 万以上**，
结论直接翻转（[tutorial 02 §6.1](../../tutorial/02-把手工流程变成系统.md)）。
所以本项目把 L-1 拆成 `L-1a / L-1b / L-1c` 三档去测，而不是拿一个阈值当结论
（[`configs/l_minus1_full_context.yaml`](../../../configs/l_minus1_full_context.yaml) 的注释里
也写着"这一级的意义是给出零检索损失的上界参照"）。

**如果你答到了**：阈值是厂商经验/假设 / 决定因素是你装多大范围而不是语料总体积 /
单模块与全量分属线的两侧 / token 是估算且假设一变结论就翻转 —— 说明你理解了这一层。

**如果你答成**："20 万 token 太多了，所以要检索" —— 那还是二元思维，
没说出"边界取决于覆盖面"。回去读 [concepts/00 误解三](../concepts/00-为什么需要RAG.md)
和 [design 00 §5.4 / §6.1](../../design/00-项目定位与教学大纲.md)。

### Q4. 把提示词写得更严厉（连续五行"绝对不要编造 API"）为什么也拦不住幻觉？

因为模型**不是查表器，是续写器**：它给的是"在这个上下文里最像的下一个 token"，
不是"我记不记得"。劝它"不确定就停下"要求它先准确知道自己不知道——
而"不知道就一定能停下"不是它的原生能力（[concepts/00 §3.2](../concepts/00-为什么需要RAG.md)）。
本项目有一条可复现的现场：`FakeChat` 是一个**刻意会犯错的**假对话客户端，对它问
"MaixCAM 上怎么把一张图放大两倍"，它给出的是限定名、可执行代码、参数 `scale=2` 俱全的
`img.super_resolve(scale=2)`——通顺、自信、**不存在**；而查白名单
（`corpus/processed/api_roster.txt`，实测 **4868 条**）里 `maix.image.Image.super_resolve`
一行都查不到（[tutorial 01 §4.2](../../tutorial/01-失败是什么样的.md)）。

真正让它停下来的是两样**外部机制**：资料被放到眼前（有上下文时 `FakeChat` 只从资料里
抄一个符号），和一次确定性的查表（1898 个符号 / 4868 条白名单）。
纪律段落本身有价值——它**可测、可换、可追溯**（`maixrag/agent/prompt.py` 第 214 行的
`maixcam_rules()`，注册成段落时叫 `maixcam_rules`），但它只能约束**表达**，不能补上**知识**。

**如果你答到了**：续写 vs 查表 / "知道自己不知道"不是原生能力 /
必须靠外部机制（资料 + 白名单查表）兜住 / 措辞是约束不是知识来源 —— 说明你理解了这一层。

**如果你答成**："因为措辞不够狠，再写严一点就行" —— 那正是被 §3.2 第二条否掉的方案，
是把**没有的能力**当成**可以劝出来的能力**。回去读
[concepts/00 §3.2](../concepts/00-为什么需要RAG.md) 和
[tutorial 01 §4.2 / §6](../../tutorial/01-失败是什么样的.md)。

## 二、工程问答

### Q5. `peripheral` 10 篇（73,768 字节，约 2 万 token）的内部工具：全塞 prompt 还是上 RAG？

判断依据（这几条都要考虑到才算合格）：

1. **覆盖面与阈值的关系。** 73,768 字节约合 2 万 token，远在 20 万以内——
   全塞换来的是**零检索损失**，也就是"没有召回失败"这一类失效模式；而检索有。
2. **每轮成本 × 调用频率。** 全塞的代价是**每次请求都付全量 token**，且不能扩展到更大语料；
   检索的代价是一次性建索引 + 每次 top-k 的一小段。内部工具每天几十次调用，
   两笔账都要算，不能只算其中一笔。
3. **可扩展性与失效条件。** 一旦覆盖范围从单模块扩到全站，全塞**立刻越线**
   （119 篇 / 约 20–22 万 token）；届时方案要重做，而检索方案是同一套代码换语料。
4. **正确性上限由谁决定。** 全塞时答案质量的上界由**生成**决定；上检索就多了一个
   **会坏掉的环节**——本项目的证据是 retrieval 确实会丢片段。
5. **维护成本。** 全塞不需要重建索引，文档改了下次请求就是新的；检索要重建索引
   （本项目为此把语料版本固定到 commit，[design 01 §4.1](../../design/01-系统架构设计.md)）。

**一个示范回答**：

> 我会选**全塞 + prompt caching**，但把它当"这一档覆盖面的最优解"，不是最终架构。
> 理由是 2 万 token 远在 20 万阈值以内，全塞买到的是**零检索损失**——没有"该出现的片段
> 没被召回到"这类失效模式。检索会丢片段这件事本项目有实测：YOLO 那道题
> （q005）在 dense+bm25 融合下召回率仍是 **0.00**，真正含例程的 `zh/vision/yolov5`
> 没进 Top-5；只跑 BM25 时 `signature` 那一行的 Recall@5 是 **0.000**
> （[`eval/results/rag_L1_rag[rrf_bm25].md`](<../../../eval/results/rag_L1_rag[rrf_bm25].md>)）。
> 成本侧，每轮付约 2 万 token，但 `peripheral` 就 10 篇 / 73,768 字节，规模不会再涨，
> 每天几十次调用总成本可忽略。**我的退出条件写在这儿**：① 覆盖面一旦从单模块扩到
> 全站（约 20–22 万 token），全塞越线，方案必须重做；② 调用量涨到每天上万次，
> 每轮 2 万 token 会变成真金白银的账单，那时该上检索 + 缓存；
> ③ 一旦问题开始跨模块（比如 UART + 引脚复用一起问），这 10 篇里根本没有答案——
> 那不是"该不该检索"的问题，是**语料范围选错了**，全塞也救不了。

**常见的浅答案（以及为什么浅）**：

- **"语料小就全塞，语料大就检索"** —— 只给了阈值，没有代价分析；也没说清"小"是相对什么：
  同一个项目里 2 万和 20 万两档同时真实存在。
- **"上 RAG 更专业、更好扩展"** —— 只说了收益，没说这一档的代价：多了一个会坏的环节，
  而且检索本身会丢片段（signature 0.000、q005 召回 0.00）。
- **"全塞更简单，所以选全塞"** —— "简单"不是判据；没有失效条件，
  等覆盖面扩到全站时不会知道方案已经坏了。

### Q6. 给整个 MaixPy 中文 wiki 做助手（119 篇，约 20–22 万 token），"全塞更省事"会在哪一步坏掉？

判断依据（这几条都要考虑到才算合格）：

1. **一次请求的规模。** 中文教程实测 130 篇 / 713,520 字节，估算 **20–22 万** token；
   加 API 参考约 **26–33 万**。这已经不是"塞得进去吗"，而是**每轮都付、且随时可能触发截断**。
2. **越线之后的失败形态。** 截断的坏法很讨厌：模型只是没看到那几页，而"没看到"和
   "文档里没有"在答案里长得一样。本项目吃过同类亏——符号级幻觉率 0.000 其实是
   符号被检查到的题数 **0/18**（[事故 05](../../postmortem/05-伪装成好消息的0.md)）。
3. **边界会往哪边走。** 窗口变大只把边界往外挪一点，而语料、日志、多轮对话的增长更快，
   边界会一直被越过去（[concepts/00 误解三](../concepts/00-为什么需要RAG.md)）。
4. **有没有零检索损失的替代。** prompt caching 降的是**重复前缀的成本**，
   不减小"必须装进上下文"的体积，也不能指出依据。
5. **可测量性。** RAG 的两轴指标能把"检索坏了"和"生成坏了"分开
   （[concepts/01 §4.1](../concepts/01-RAG的完整链路.md)）；全塞把这个区分抹掉了。

**一个示范回答**：

> 全塞在这个场景坏在**体积**这一步，不是坏在效果这一步。中文教程实测 130 篇 /
> 713,520 字节、估算 20–22 万 token，加 API 参考 26–33 万——每轮都付，
> 而且随时可能触发截断。截断之后最难查的是：模型只是没看到那几页，
> 而"没看到"和"文档里没有"在答案里一模一样（本项目同名的事故是
> 符号级幻觉率 0.000 而覆盖率 **0/18**）。
> 我能接受的边界划在这里：**单次请求的上下文预算内能整篇装下的范围，就整篇塞**
> ——比如某个问题只涉及 `peripheral`，10 篇 / 73,768 字节 / 约 2 万 token；
> **一旦要覆盖全站，就走检索，并且报告必须给出两轴与按 qtype 分组**（18 题 / 4 类），
> 否则我无法判断是检索坏了还是生成坏了。另外我不接受"先用全塞顶一下"这种没有退出条件的方案：
> 窗口变大只把边界往外挪一点，语料与对话轮次的增长更快。

**常见的浅答案（以及为什么浅）**：

- **"全塞会被截断，所以不行"** —— 方向对，但没给量级，也没说清截断之后为什么危险
  （它会伪装成"文档里没有"）。
- **"20 万 token 就超了，所以必须 RAG"** —— 把厂商经验的阈值当硬结论，而且是二元判断；
  本项目把 20 万当**假设**，而单模块那一档恰恰**该全塞**。
- **"RAG 一定更好"** —— 同一份语料上检索是有代价的：给语料加 API 层让 `signature`
  **+50 pt**，同时 `concept` **−12.5 pt**（Top-5 名额是零和的，
  [concepts 01 §4.2](../concepts/01-RAG的完整链路.md)）。说"更好"就得给出分组数字。

### Q7. 哪一类幻觉是"把权威文档喂给模型"也救不回来的？

判断依据（这几条都要考虑到才算合格）：

1. **先分清幻觉的两种来源**：知识缺失（文档里有、模型没见过 → 喂资料能救）
   vs 文档本身不含答案 / 文档与设备真实状态不一致（喂资料救不回，甚至会更糟）。
2. **喂资料能救的那一类要能说出形状**：`read(block, block_ms)`、
   `find_blobs(thresholds, ...)`、`gpio.GPIO` + `pinmap.set_pin_function` 这种
   "文档里写得明确、只是模型没见过"的写法。
3. **救不回的那一类，判据必须落到"资料里确实没有"或"资料不足以下结论"。**
4. **还要看到一个反向风险**：资料越全，模型越容易把**资料之外**的内容也说成有依据——
   所以这一类必须靠"资料为空必须拒答"和 `must_not_contain` 断言变成可判定的失败。

**一个示范回答**：

> 至少两类救不回来。**第一类是覆盖面缺口**：问题本身在语料里就没有答案。
> 最典型的是 q011（MaixCAM 2 与 MaixCAM Pro 的差异）和 q012（MaixPy 支持哪些 AI 视觉功能）——
> 这两道题的 `must_not_contain` 是**空的**，因为真正该防的不是"串味"，而是"答不出来却答得像有依据"。
> 在链式的融合报告里，q012 的召回率是 **0.00**，q011 是 **0.50**
> （[`eval/results/rag_L1_rag[rrf_dense+bm25].md`](<../../../eval/results/rag_L1_rag[rrf_dense+bm25].md>)）；
> agent 版里 q011 召回到了 1.00 却仍然**拒答**，q012 则是没召回、也没拒答
> （[`eval/results/agent_loop.md`](../../../eval/results/agent_loop.md)）。
> 两种形态恰好各说明一件事：**召回到了也可能答不出来**（生成侧），
> **没召回就更不可能有答案**（检索侧），而把整份语料塞进去并不能让这两题长出答案——
> 只会更容易被编出一个。
> **第二类是"资料和板子上真实状态不一致"**：语料本身会漂移。
> 本项目勘察时就发现文档站与仓库对不上（站点有 `vision/dual_buff.html` 而仓库没有、
> `customize_model_yolo.md` 与站点的 `custmize_model.html` 拼写不同，
> [design 00 §5.3](../../design/00-项目定位与教学大纲.md)），而 K210 时代的 MaixPy v1 文档
> 在网上流传得比 v4 更久——**喂一份过时的文档比不喂更糟**：模型会照抄已经不适用于
> MaixCam 的写法，而且这次它"有依据"。所以我的判据是：喂资料解决的是"知识在哪儿"，
> 不解决"资料里有没有"和"资料够不够新"；后两者只能靠显式拒答、
> 语料版本固定到 commit、以及 `must_not_contain` 这类断言暴露出来。

**常见的浅答案（以及为什么浅）**：

- **"模型还是会瞎编"** —— 没区分"知识缺失"和"资料本身没有"，把两类问题合成一个，
  排障时会去改错东西（该换语料的时候去调提示词）。
- **"把所有文档都给它就不会错了"** —— 缺答反而更危险：资料越全，模型越容易把资料外的东西
  说得像有依据；q011/q012 的 `must_not_contain` 是空的，正说明这一类不能用"串味"断言抓。
- **"加个更强的校验器就好了"** —— 校验器只能查"符号存不存在"，查不出"资料里没有这个结论"；
  而且它的误报会摧毁信任（[事故 03](../../postmortem/03-校验器把正确代码判成幻觉.md)）。

## 三、动手题答案

### H1. 把 `must_not_contain` 按"串了哪个生态"分类，并找出官方正确写法

**操作步骤**

1. 数一遍非空禁项（PowerShell；`python -c` 或 `jq` 同样可以）：

   ```powershell
   $q = Get-Content eval/datasets/seed.jsonl -Encoding UTF8 |
        Where-Object { $_.Trim() -ne '' } | ForEach-Object { $_ | ConvertFrom-Json }
   "总题数 $($q.Count)；带非空禁项 $(($q | Where-Object { $_.ground_truth.must_not_contain.Count -gt 0 }).Count)"
   ```

   我在本仓库跑出来：**总题数 18；带非空禁项 16**。

2. 把 16 题的禁项逐条读出来（`$q | ForEach-Object { "$($_.qid) $($_.qtype) :: " + ($_.ground_truth.must_not_contain -join ' | ') }`），
   填一张四格的分类表：

   | 生态 | 代表禁项 | 出现在哪些 qid |
   | --- | --- | --- |
   | OpenCV | `cv2.VideoCapture`、`cv2.findContours`、`cv2.cvtColor` | q001 q002 q003 q006 q013 |
   | 树莓派 / 别的嵌入式生态 | `RPi.GPIO`、`wiringpi`、`picamera`、`pyserial` / `serial.Serial`、`pyaudio` | q001 q008 q009 q017 |
   | 别的框架 / 通用工具 | `ultralytics.YOLO(`、`torch.hub.load`、`torchvision.models`、`transformers.AutoModel`、`nmcli`、`ffmpeg -f v4l2`、`gst-launch` | q005 q010 q012 q014 q015 |
   | **K210 时代 MaixPy v1（`sensor.*`）** | —— | **空** |
   | 编造不存在的方法（不是串某个生态） | `camera.open_camera`、`read_frame`、`enumerate_cameras`、`super_resolve` | q002 q003 q004 |
   | 不是 API 串味，而是"把某个办法说成唯一办法" | `gc.collect() 是唯一办法`、`tflite_convert 是唯一方式` | q016 q018 |

3. 验证那一格为什么是空的：

   ```powershell
   Select-String -Path eval/datasets/seed.jsonl -Pattern 'sensor\.' -Encoding UTF8
   ```

   实测输出：**没有匹配（0 行）**。而 `sensor.*` 是被写在
   [`maixrag/agent/prompt.py`](../../../maixrag/agent/prompt.py) 第 **226** 行的
   `maixcam_rules()` 里：

   > 2. **不要根据其他框架的习惯猜 MaixPy 的 API。** 特别注意三个最容易混进来的来源：
   >    OpenCV（`cv2.*`）、树莓派（`picamera`）、K210 时代的 MaixPy v1（`sensor.*`）。

   也就是 [tutorial 01 §5 / §6](../../tutorial/01-失败是什么样的.md) 那句结论：
   **写了纪律 ≠ 测了纪律。** 一个只在提示词里被点名的知识点，
   在评测里等于没有被覆盖。

4. 挑一条禁项去找官方原文。两条可用的现场（都能直接打开文件核对）：

   - q008 禁 `RPi.GPIO` / `wiringpi` → 官方写法在
     [`corpus/raw/repo/peripheral/gpio.md`](../../../corpus/raw/repo/peripheral/gpio.md)
     第 **59–60** 行：

     ```python
     err.check_raise(pinmap.set_pin_function(pin_name, gpio_name), "set pin failed")
     led = gpio.GPIO(gpio_name, gpio.Mode.OUT)
     ```

   - q003 禁 `read_frame` / `cv2.imread` → 官方教程用 `img = cam.read()`
     （[`corpus/raw/repo/vision/camera.md`](../../../corpus/raw/repo/vision/camera.md) 第 **69** 行，
     另见第 191、218 行），而完整签名在 API 参考页
     [`corpus/raw/api/maix/camera.html`](../../../corpus/raw/api/maix/camera.html) 第 **492** 行：

     ```python
     def read(self, block: bool = True, block_ms: int = -1) -> maix.image.Image
     ```

**期望结果**：非空禁项 **16** 题（q001–q006、q008–q010、q012–q018；空的只有 q007 与 q011）。
其中 **13** 题的禁项**全部**是"别的生态的 API"——`cv2.*` / `picamera` / `RPi.GPIO` / 树莓派工具
/ `torch.*` / `transformers.*` / `PIL.*` / `pyserial` / `nmcli` / `ffmpeg` / `gst-launch` 这一类；
另外 **3** 题的禁项不是"串味"而是**编造的方法名**（q003 `read_frame`、q004 `enumerate_cameras` /
`os.listdir("/dev/video")`）或**"把某个办法说成唯一办法"**（q016 `gc.collect() 是唯一办法`、
q018 `tflite_convert 是唯一方式`）——后一类有 4 条断言，落在 q003 / q004 / q016 / q018 上。
两个数字都对，只是口径不同（`concepts/00 §4` 数的是前一类）；K210 那一格为空；
`sensor.` 在评测集里 0 行、在 `prompt.py` 第 226 行。

> 数字口径提醒：`16` 与 `13` 都能在仓库文件里逐条数出来
> （[`seed.jsonl`](../../../eval/datasets/seed.jsonl) 与
> [concepts/00 §4](../concepts/00-为什么需要RAG.md) / [tutorial 01 §5](../../tutorial/01-失败是什么样的.md)），
> 这里说的是这两个数**分别数的是什么**，而不是替它们统一成一个数——
> "同一件事两种口径"本身正是
> [design 07 §5.1](../../design/07-文档体系设计.md) 的数字新鲜度检查该抓的东西。

### H2. 亲手量一遍语料，先写预测再验证

**操作步骤**

1. 量全量快照（命令来自 [tutorial 02 §4.1](../../tutorial/02-把手工流程变成系统.md)）：

   ```powershell
   Get-ChildItem corpus/raw/repo -Recurse -Filter *.md |
     Get-Content -Raw -Encoding UTF8 |
     ForEach-Object { [System.Text.Encoding]::UTF8.GetByteCount($_) } |
     Measure-Object -Sum | Select-Object Count, Sum
   ```

   我在本仓库跑出来：**119 篇 / 688,782 字节**，与 tutorial 02 §4.1 记录的
   `119` / `688782` 一致。

2. 量单模块那一档：

   ```powershell
   Get-ChildItem corpus/raw/repo/peripheral -Recurse -Filter *.md |
     Get-Content -Raw -Encoding UTF8 |
     ForEach-Object { [System.Text.Encoding]::UTF8.GetByteCount($_) } |
     Measure-Object -Sum | Select-Object Count, Sum
   ```

   实测：**10 篇 / 73,768 字节**（≈72.0 KB，与
   [design 00 §5.4](../../design/00-项目定位与教学大纲.md) 的"10 篇、72 KB、约 2 万 token"一致）。

3. 按脚本的算式估算 token。算式在
   [`scripts/measure_corpus.py`](../../../scripts/measure_corpus.py) 第 **64–71** 行，
   唯一的假设参数是 `cjk_share`（中文占字节的比例）：

   ```
   cjk_bytes   = nbytes * cjk_share
   latin_bytes = nbytes - cjk_bytes
   tokens ≈ cjk_bytes / 3.0 + latin_bytes * 0.25
   ```

   把上面两个字节数代进去（以下是我按算式改算的估算，不是脚本输出）：

   | 覆盖面 | 字节数 | `cjk_share` | 估算 token | 与 20 万阈值 |
   | --- | --- | --- | --- | --- |
   | 全量快照 | 688,782 | 0.4 | 约 **19.5 万** | 未越线（贴线） |
   | 全量快照 | 688,782 | 0.5 | 约 **20.1 万** | **刚越线** |
   | 全量快照 | 688,782 | 0.6 | 约 **20.7 万** | **越线** |
   | `peripheral` | 73,768 | 0.4 | 约 **2.1 万** | 远在阈值内 |
   | `peripheral` | 73,768 | 0.6 | 约 **2.2 万** | 远在阈值内 |

   要观察的就是**同一个字节数换个假设就翻到线的另一侧**——这就是 H2 存在的理由：
   边界不是二元，而且"我落在哪一侧"取决于你先把哪个范围装进去。

4. 与设计阶段的口径对齐：`713,520 字节` 是上游 `docs/doc/zh` 的 **130 篇**全量，
   `688,782 字节` 是**当前入库的 119 篇快照**——两者不是同一个口径
   （[design 00 §5.4](../../design/00-项目定位与教学大纲.md) ·
   [tutorial 02 §4.1](../../tutorial/02-把手工流程变成系统.md) 明确写了这一点）。
   按上面的算式，713,520 字节在 `cjk_share` 0.4–0.7 之间估算出
   **约 20.2 万 – 22.0 万**，正好落在 design 00 写的"约 20–22 万"。

> **一处口径不一致，值得你自己验一遍。** 脚本真实输出请自己跑
> `python scripts/measure_corpus.py --cjk-share 0.4`（**需要网络**，它量的是上游仓库）
> —— **[未实测，需你运行确认]**。
> 提示：tutorial 02 §4.2 那张敏感度表标着 `[推测]`，它给出的
> 0.4 → 15.3 万 / 0.5 → 17.9 万 与上面脚本算式的口径对不上
> （按算式，713,520 字节在 0.4 时约 20.2 万，而 design 00 的"20–22 万"与算式一致）。
> 我不替它下结论：**以脚本在你机器上的真实输出为准**，并且注意这类"文档里的数字
> 与它引用的脚本对不上"正是 [design 07 §5.1](../../design/07-文档体系设计.md)
> 数字新鲜度检查要抓的东西——**发现它比记住任何一个数都值钱**。

**期望结果**：119 篇 / 688,782 字节（全量）；10 篇 / 73,768 字节（`peripheral`）；
两档的越线判断分别是"贴线到刚越线"和"远在阈值内"；并能说出
`688,782` 与 `713,520` 差在**快照口径**而不是差在"算错了"。
