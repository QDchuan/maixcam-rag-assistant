## 一、概念问答

### Q1. 权限层有三层边界，每一层各回答什么问题？为什么检查顺序必须是能力 → 范围 → 审批，反过来会付出什么代价？

**三层各答一问**：能力边界回答"能做**哪类**事"（读 / 写 / 执行 / 联网，由工具用 `requires` 声明）；
范围边界回答"能做到**多大**"（可读、可写的根目录，由策略给）；
审批边界回答"**什么必须问人**"（判定不自己决定，把请求交出去）。

**前两层是确定规则，第三层要打扰人** —— 这就是顺序的来由。能力与范围都能只靠策略和参数算出来，不消耗任何人的注意力；
而审批要占用一个人。反过来先问审批，就会出现：一次本来会被能力层直接拒掉的调用，先去弹一次审批窗口，
人点了"拒绝"之后系统才告诉他"其实这层本来就不允许"——**白打扰人一次**，而且当这种窗口变多以后，
人会开始无脑点"通过"，那时审批层就退化成装饰。

**代码现场**：`SandboxPolicy.check()` 依次是能力循环 → `_check_scope()` → exec 白名单审批。
回归测试 `test_capability_is_checked_before_scope` 断言的是**拒绝理由**而不是真假值：
`read_only` 策略下写 `/etc/passwd`，报出来的是"策略不允许能力 fs:write"，而不是"路径越界"——
用一个布尔值测不出顺序，只有理由能测出顺序。

**如果你答到了**：三层各管一件事 / 前两层是确定规则而审批要打断人 / 顺序反了会浪费人的注意力（或让审批退化成装饰） —— 说明你理解了这一层。
**如果你答成**："因为先检查便宜的、后检查贵的" —— 这个直觉方向对，但没有说到要害：这里消耗的不是 CPU，是**人的注意力**，
而注意力被浪费的后果是审批层被绕过或关掉（见 [concepts/08](../concepts/08-权限与沙盒.md) 误解五），需要回去读第 2 节。

### Q2. 在 MaixCAM 助手里，agent 被允许写 `<base>/workspace`。有人提交了一个路径 `<base>/workspace-evil/x.txt`，字符串前缀判断放行了它，`relative_to` 却拦住了。差别落在哪个字符上？为什么这个错特别难被发现？

**差别落在一个 `/` 上。** 字符串前缀比的是"文本开头是否相同"：`/base/workspace-evil/x.txt` 确实以 `/base/workspace` 开头，
所以 `startswith` 认为它在范围内。而越界判断要判的根本不是字符串，是**目录包含关系**：
一个路径要么**就是**那个根，要么以 `根 + 分隔符` 开头。`relative_to` 判的正是这个边界——`workspace-evil` 不以 `workspace/` 开头。

所以"拦住了"和"拦对了"是两回事：前缀判断在这里不是"更宽松一点"，而是**判错了对象**——
它把一个字符串关系当成了目录关系。而 `resolve()` 是这条链上不可省的前半步：
`workspace/../secret.txt` 和 `workspace/link -> <base>` 这两种绕过，字符串比较连"看起来不对"都做不到，
必须先规范化并解析符号链接，`relative_to` 才有东西可比。

**为什么特别难被发现**（这才是这道题的重点）：
1. **代码读起来完全合理** —— `str(path).startswith(str(root))` 是很多人下意识会写的那一行；
2. **测试如果只测"工作区内的正常路径"，它会一路通过** —— 你测的是"该放的放行了"，而这个 bug 只在"该拦的"那一侧暴露；
3. **失败是安静的** —— 越界写入成功返回，没有异常、没有日志（本项目工具层默认"放行一切"，
   所以"忘了配权限"不会让程序崩，只会让它安静地什么都能做，见 [concepts/08](../concepts/08-权限与沙盒.md) 第 3 节）。

本项目为此专门写了一组测试，把三种绕过方式各测一遍：
`test_sibling_prefix_is_not_inside` 里最狠的一句是那个**对照断言**——
它先断言 `path_within` 拦住了，再断言这个路径**确实**以 `workspace` 开头，
于是这个 bug 的成因被固化成了一条断言，而不是一句注释。

**如果你答到了**：字符串关系 vs 目录包含关系 / 差在分隔符边界 / 必须先 `resolve()` 再判包含 / 测试只测了"该放的"这一侧 —— 说明你理解了这一层。
**如果你答成**："因为 `startswith` 不够严格，应该用正则" —— 换成正则只是把同一个错误写得更复杂：
只要比较对象还是字符串，`workspace-evil` 就永远是个坑。需要回去读 [concepts/08](../concepts/08-权限与沙盒.md) 误解三与 [`sandbox.py`](../../../maixrag/agent/sandbox.py) 的 `path_within()`。

### Q3. 什么叫"失败关闭"？在本项目的权限层里，它至少落在哪三个具体位置上？

**失败关闭（fail closed）= 拿不准的时候一律拒绝，而不是放行。**
它对抗的不是某一种攻击，而是**某一种默认实现**：一个"找不到策略就用默认值 / 没人可问就先放行"的实现，
会把"忘了配"变成一个静默的安全漏洞。所以这条原则的判据是：**当判断所需的信息缺失时，默认值必须是"否"。**

本项目的三个落点：

1. **没有可用的审批人时，需要审批的能力判为拒绝并标记"需审批"** —— `DenyApprovalUnavailable.request()` 直接 `return False`。
   反过来的默认会让所有审批在无人值守时静默通过，"甚至不出现在日志里"，那正好把这一层作废。
2. **路径解析失败时拒绝** —— `path_within()` 捕获 `OSError / RuntimeError / ValueError` 后返回 `(False, ...)`。
   这一条尤其要紧：如果解析失败时"跳过检查继续走"，就等于留了一个**"构造畸形路径即可绕过"的后门**，
   攻击面从"猜路径"变成"构造让 `resolve()` 抛异常的输入"。
3. **路径参数不是字符串时拒绝** —— `_check_scope()` 里 `isinstance(raw, str)` 不成立就返回问题说明，而不是 `continue`。
   因为一个非字符串路径参数**根本无法被检查**，"没法检查"与"检查通过"必须区分开。

还有一处同源的设计：`SandboxPolicy` 的默认值是**最保守的那一档**（`allowed` 为空集，什么都不能做），
理由与预算默认值同源——**默认值就是大多数人会用的值**。

**如果你答到了**：拿不准就拒绝 / "信息缺失时默认必须是否" / 能举出"没人可问 / 解析失败 / 类型不对"中的至少两个落点 —— 说明你理解了这一层。
**如果你答成**："就是出错的时候不要崩" —— 那是异常处理，不是失败关闭。失败关闭说的不是"程序别崩"，
而是"**判定结果为不确定时，结论取拒绝**"；崩溃和放行都是失败，但放行是那个安静的、更危险的失败。
需要回去读 [concepts/08](../concepts/08-权限与沙盒.md) 第 5 节术语表与误解四。

### Q4（补充概念题）. 权限层为什么会成为 agent 里"最容易被略过"的一层？在同一个工具执行管线里，漏配权限与漏配参数校验，失败形态有什么不同？

**因为它"不配也能跑通"。** 参数校验漏了，模型传错参数的当场就会被抓到（工具报 `invalid_args`，
模型看得见、会自己改）；而权限漏配的后果是**默认那一档替你做完了决定**：
`ToolRegistry.permission` 不传时是 `AllowAll()`，装配时没给策略用的也是完全不限制的那一档。
于是"忘了配权限"不会让程序崩，只会让它**安静地什么都能做**——这与
[事故 01 静默的空结果](../../postmortem/01-静默的空结果.md) 是同一个形状：**没有报错，只是结果不对**。

**两种失败形态的差别**：

| | 漏配参数校验 | 漏配权限 |
| --- | --- | --- |
| 谁先发现 | 调用的当下（工具自己报错） | 事后（人看到文件被改了） |
| 表现 | 一次可观察的失败，模型能补救 | 越界调用"成功"返回，一切正常 |
| 可回滚 | 改参数重试 | 删掉、覆盖的可能回不来 |

顺带说明为什么本项目把权限声明放在**工具**上（`requires`）：不是因为那样更优雅，
而是因为检查需要有一个**明确的检查点**。权限系统不认识 `write_file`，它只认识 `fs:write`；
这个映射关系只有工具自己知道，所以由工具声明、由策略裁定——这就是
[`tools.py`](../../../maixrag/agent/tools.py) 里 `Capability` 那五个字符串的作用。

**如果你答到了**：默认档是"放行一切" / 失败是安静的（无报错） / 与事故 01 同形 / 权限与参数校验的失败可观察性不同 —— 说明你理解了这一层。
**如果你答成**："因为权限比较复杂，写起来麻烦" —— 这是把工程难度当原因。真正的原因不是难，
而是**它的默认值站在错误的一侧**：一个宽松的默认等于把"不安全"设成默认行为。
需要回去读 [concepts/08](../concepts/08-权限与沙盒.md) 第 3 节与 [`sandbox.py`](../../../maixrag/agent/sandbox.py) 的 `SandboxPolicy` 文档字符串。

## 二、工程问答

### Q5. 导出工具声明了 `requires={fs:write}` 却没声明 `path_params`：能力层放行、范围层完全不检查。你会选"约定 + 审查"，还是干脆不提供"以路径为参数"的工具形态？

**判断依据**（这几条都要考虑到才算合格）：
1. **缺口是谁造成的** —— 缺的不是检查逻辑，是**声明**。检查器只能检查它被告知的参数；
   靠猜参数名（`path`? `target`? `file`?）是漏洞的常见来源。
2. **哪一侧的失败更贵** —— 漏声明一次，代价是"越界写入真的发生"（不可回滚）；
   而"约定 + 审查"的代价是持续的人力投入，且**在人员流动或赶工期时最先被放弃**。
3. **约定能被什么强制执行** —— 没有机制兜住的纪律不会被执行。
   能不能把它变成一条测试或一条注册期断言，决定了它是不是真的成立。
4. **工具形态能不能改** —— 如果工具根本不接受"任意路径"，这个缺口在源头上就不存在（只管相对标识符、
   或者由系统注入根目录），而不声明 `path_params` 就退化成无害的。

**一个示范回答**：
两边都不是免费的，所以我要看**这个工具到底需要多大的灵活性**。
MaixCAM 助手的导出场景实际上只需要一个出口——把结果写到工作区下的约定目录；
那我会选"不提供以绝对路径为参数的形态"：工具的入参改成**文件名**，
根目录由系统拼进去，于是范围检查从"每个工具都要记得声明"变成"结构上不可能越界"。
这比约定便宜，因为约定要在每次新增写工具时重新执行一次，而这个设计只需要正确一次。
如果业务上确实必须接受任意路径，那就退一步：约定（每个写工具的 `path_params` 必填）
+ **一条注册期断言**，让"声明了 `fs:write` 却 `path_params` 为空"在注册时直接失败——
把纪律变成机制，而不是靠审查者的记性。代价是有些合法用例（写入的路径来自运行时计算）
要显式写 `path_params` 才能通过，多一行代码。

**常见的浅答案**（以及为什么浅）：
- **"用约定 + 审查就够了，说明文档写清楚"** —— 没有代价分析。它没说这条约定在什么条件下会失效
  （新人不知道、赶工期跳过、工具从第三方插件注册进来时谁审？），也没说审查的成本落在谁身上。
- **"干脆禁止所有带路径参数的工具"** —— 把一个 5 个工具的问题用一刀切解决，
  代价是 agent 连"把结果写到用户指定位置"这种正常需求都做不到。**拦过头同样是坏设计**
  （[concepts/08](../concepts/08-权限与沙盒.md) 误解五：假阳性比漏报更危险，一个动不动就拒绝的权限层会被绕过或关掉）。
- **"这是 bug，应该在 `_check_scope` 里修"** —— 修不了。范围检查没有任何依据可查：
  工具没告诉它哪个参数是路径。把这条写成测试（`test_scope_check_only_applies_to_declared_path_params`）
  的意义正是让这个缺口**可见**，而不是假装它不存在。

### Q6. 本项目的命令白名单用字符串前缀匹配（`cmd.startswith(a)`）。给出一条能绕过它的命令形态，并说明你会把修复放在哪一层、为什么。

**判断依据**（这几条都要考虑到才算合格）：
1. **白名单匹配的是"命令文本的开头"，不是"要执行的那条命令"** ——
   所有把合法前缀放在前面、把别的动作接在后面的写法都能过。
2. **绕过之后的后果落在哪一层** —— 它绕的是**范围/能力**的判定，不是审批的判定，
   所以"加一条更长的白名单"治不了本（白名单本质上是在枚举字符串，而字符串空间是构造出来的）。
3. **修在哪一层取决于"能不能真的解析出要执行的东西"** —— 解析不出来就不能放行，
   这是失败关闭在命令场景的直接应用。
4. **别把问题推给审批层** —— 审批层是"最后一道闸"，它的存在不是为了让前两层可以不做判断。

**一个示范回答**：
最直接的一条是把别的动作接在合法前缀后面：白名单里有 `ls`，那么 `"ls; rm -rf /"` 与 `"ls && curl http://…"`
都以 `ls` 开头，`startswith` 全部放行（本项目实测：两者判定都是 `allowed=True, needs_approval=False`，
而 `"cat /etc/passwd"` 因为不以 `ls` 开头，反而是 `allowed=False, needs_approval=True`——
**最终通过的和最终拦住的，与危险性无关，只与首字母有关**）。
更隐蔽的一条是**同前缀的不同程序**：`"lsof -i"` 同样以 `ls` 开头——这里连"注入了元字符"都不需要，
纯粹是前缀把两个不同的程序混成了一个。
修复我会放在**能力层**：这个策略要么不开放 `exec`（多数任务不需要它——本项目默认档
`workspace_only` 就是不给 `exec`），要么在放行前**真的解析命令**，拿不到可信的 argv 就拒绝。
理由是：范围层管的是"能对多大范围做事"，而这里的问题根本不是范围，是"**要执行的到底是什么**"；
审批层更不该接这个锅——把一条本来就被能力边界拒掉的调用推给人去点，等于用人的注意力给一个假检查兜底
（这也正是 `check()` 把审批放在最后的原因）。
如果暂时做不到解析，那就退一步承认它的性质：**命令白名单是"降低误触"而不是"安全边界"**，
并且在文档与 `describe_policy()` 的输出里写明这一点——**"有白名单"和"白名单拦得住"不是同一句话**。

**常见的浅答案**（以及为什么浅）：
- **"把白名单写成 `["ls -la", "ls -l"]` 这种完整命令就好了"** —— 没有代价分析，也没有失效条件：
  枚举的是字符串，用户换个参数（`ls -la /etc`）就又不匹配，于是白名单会在"太松"和"太紧到不可用"之间来回抖。
- **"用正则 `^ls(\s|$)` 就修好了"** —— 这条正则**拦不住** `"ls; rm -rf /"`（`;` 既不是空白也不是结尾，不匹配），
  却拦住了 `"lsof -i"`。它把"枚举字符串"换成了"枚举模式"，同一个错误换了个写法；
  它唯一确定买到的是**看起来更严谨**。
- **"加一层审批就行了"** —— 审批层是最后一道闸，不是第一道。而且本项目里 `AllowAll` / `AlwaysApprove`
  这两种"演示与测试用"的实现一旦被当成默认，审批就变成静默通过——那正好把这一层作废
  （[concepts/08](../concepts/08-权限与沙盒.md) 误解四）。

### Q7. 无人值守的批处理里跑 agent，有人提议把 `DenyApprovalUnavailable` 改成"没人可问就放行，等有人的时候再问"。这个改动会让哪些收益消失、又会露出哪些新风险？

**判断依据**（这几条都要考虑到才算合格）：
1. **审批层的价值来自"它可能在无人值守时也没有被作废"** —— 一个"没人问就放行"的默认，
   会让所有需要审批的操作在夜间静默通过，而且**甚至不出现在日志里**。
2. **"等有人的时候再问"在批处理里做不到** —— 夜间任务不会停在半路等你早上点一下；
   要么当时放行，要么当时拒绝，没有第三种可能。
3. **同一条命令权限不同结果不同是实测过的** —— 本项目就撞见过：受限环境里因拿不到 TLS 凭证失败
   （`SEC_E_NO_CREDENTIALS`），放开权限后成功返回 200（见 [design 06 · 2.3.1](../../design/06-项目结构与两条分支.md)）。
   "为了让夜间任务跑完"确实是个真实诉求——这正是这个提议有吸引力的原因。
4. **既然诉求真实，方案就得同时满足它** —— 只否定提议是不够的，要给出一条既能跑、又不把审批层作废的路。

**一个示范回答**：
这个改动的收益消失得很干净：审批层原本保证"**需要人点头的事，在没有人的时候不会被做掉**"；
改成放行之后，夜间任务的每一次审批都静默通过，"需审批"这个标记还在，但已经没人会看到它了。
风险不在"多做了几件事"，而在**你不知道它做了哪几件**——本项目连审计这一层都没做
（[tutorial 00 · §6](../../tutorial/00-主线导览.md)：真实系统必须有，出事后要能回答"谁在什么时候做了什么"），
所以夜间放行的操作连事后追溯都没有。
但我不认为应该简单地否决：无人值守是真实需求。我的方案是**失败关闭 + 预授权**：
夜间任务使用的策略显式列出它需要的能力（例如只给 `fs:read` + 工作区写，
把 `net` 留在 `needs_approval` 里），也就是**把"人点头"提前到策略配置的时刻**——
配置策略本身就是那次审批，只不过它由人在白天完成、可以被评审和被版本控制。
代价是任务形态要提前确定：临时冒出来的能力需求在夜间只能失败（此时拒绝并显式标记"需审批"，
让早上的第一件事是看这份拒绝清单），而不能顺手放行。

**常见的浅答案**（以及为什么浅）：
- **"不行，安全第一"** —— 没有代价分析，也没有给出替代方案。它没说"夜间任务跑不完"这个真实成本由谁承担，
  而实际后果往往是有人去把整个沙盒关掉（`SandboxPolicy.unrestricted()` 这个方法的存在本身就是教学材料）。
- **"加个配置开关，让用户自己决定"** —— 这是把一个安全性判断外包给了最没有信息的人；
  而且开关的**默认值**就是大多数人会用的值，于是问题原样保留，只是多了一个没人动的配置项。
- **"加审计日志就够了"** —— 审计解决的是"事后能知道"，不解决"当时该不该做"。
  对一个已经把工作区外文件覆盖掉的任务来说，日志只能告诉你损失有多大
  （与"检查必须在执行之前"是同一条道理）。

### H1. 跑 `scripts/demo_sandbox.py`，逐行判定三种绕过方式的两列结论

场景二：换成 `SandboxPolicy.workspace_only(workspace)`，同一个调用 → **被拒**，

### H2. 给沙盒加一条"写操作需要审批"的策略，让越界写入变成"等待审批"

**参考做法**（一条能跑的对照实验，不是唯一写法）：

造一个声明了 `path_params=["path"]` 的 `write_file` 工具，然后比较三份策略对**同一个越界路径**的判定：

```python
from pathlib import Path
from maixrag.agent.sandbox import SandboxPolicy, AlwaysApprove
from maixrag.agent.tools import Capability

# A：写操作进 needs_approval，且审批人永远批准
SandboxPolicy(allowed={Capability.PURE, Capability.FS_READ},
              needs_approval={Capability.FS_WRITE},
              readable_roots=[ws], writable_roots=[ws],
              approver=AlwaysApprove())

# B：同上，但用默认审批通道（没人可问）
SandboxPolicy(allowed={Capability.PURE, Capability.FS_READ},
              needs_approval={Capability.FS_WRITE},
              readable_roots=[ws], writable_roots=[ws])

# C：能力层放行 fs:write，靠范围层拦
SandboxPolicy.workspace_only(ws, approver=AlwaysApprove())
```

**期望结果** [已实测，本仓库根目录，三份策略 + 越界路径 + 界内路径各跑一次]：

| 策略 | 路径 | `allowed` | `needs_approval` | 理由 |
| --- | --- | --- | --- | --- |
| A | 越界 | `False` | `True` | 能力 fs:write 需要人工审批 |
| B | 越界 | `False` | `True` | 能力 fs:write 需要人工审批 |
| C | 越界 | `False` | `False` | 路径 … 不在可写范围内 |
| C | 界内 | `True` | `False` | — |

**这里有个必须讲清楚的机制，否则这道题会被做错**：
`needs_approval` 只在**能力层**被判到，而能力层里这段代码的写法是
`if cap in self.needs_approval: return PermissionDecision(allowed=False, needs_approval=True, …)`
—— 它**直接返回，从不调用 `approver`**。
所以 A 和 B 的结果**完全一样**，"永远批准"的审批人在这里一次都没被问过。

也就是说：把写操作放进 `needs_approval` 得到的语义是
**"拒绝，并标记为可申请审批"**，而不是"批准"。这是一条**挂起点**，不是一条**授权**：
判定自己不做决定（`needs_approval=True` 把"该问人"这件事显式写在结果里），
放不放行由**读取这个字段的调用方**（循环 / UI）决定。代码里真正会调用 `approver.request()` 的
只有第 3 层那条 exec 白名单分支——那边的语义确实是"批准了就放行"
（`test_exec_allowlist_gates_commands`：`"rm -rf /"` 在 `AlwaysApprove` 下 `allowed=True`，理由"已获人工批准"）。

**结论**：你要的"越界写入变成**等待审批**"能拿到，
但如果你期望的是"越界写入被**批准**"，那 A 也做不到，因为审批判定写在范围检查**之后**，
而这次调用在第 1 层就返回了。**这不是 bug，是顺序的意图**：需要审批的**能力**在能做事之前就该停下来问人，
不该先去看路径——顺序一旦反过来，"能写哪儿"这种确定规则就要等人点头才能算出来。

**验收**：两次对照的 `allowed` / `needs_approval` 组合与你写下的预测一致；
若你预测"A 会放行、B 会拒绝"（这是最容易犯的错），能说出是**能力层的第一个 `return`**
把审批人跳过去了，以及为什么这个顺序是有意的。
