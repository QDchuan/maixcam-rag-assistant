## 一、概念问答

### Q1. 上下文块为什么必须带编号，而不是把片段直接拼成一段文本？

**推理链**：编号不是排版习惯，它是把"引用"从**自然语言里的字符串**变成**结构化字段**的唯一办法。
`build_context_block` 给每个片段一个 `[1][2][3]`，模型被要求用它标注依据，
解析出来的 `citations` 是一串整数下标——这时"引用精确率"就能用集合运算算出来：
`cited = {c.index for c in ans.citations}`，合法引用是 `1 <= i <= n_ctx`，精度 = 合法数 / 引用数；
引用召回率则比"正文里出现的每个 `[n]`"与"结构化 `citations` 里的 `[n]`"是否一致
（`maixrag/evaluation/harness.py` 的 `evaluate_generation`，见第 419–431 行）。
如果没有编号，这两件事都只能退化成**字符串匹配**：你不知道某个片段是不是被引了、
也无法判断"每个论断是否都被某个来源支撑"。
更隐蔽的一层是：编号把"模型说不知道"也变成了一个可检查的出口——
它要么给 `[n]`，要么把这段放进 `unsupported`，而不是写成一句无法验证的"可能吧"。
拼成一段纯文本后，`unsupported` 这个正式出口也跟着失效（误解一讲的就是这件事）。

**如果你答到了**：结构化引用需要 `[n]` 做下标 / 精度与召回率各需要什么输入 / 引用可程序校验而不需语义理解 —— 说明你理解了这一层。
**如果你答成**："带编号更清晰，模型更容易对应" —— 那是把可读性当机制，没有说出"哪一件事因此变得可程序判定"，需要回去读 [`concepts/05`](../concepts/05-生成与忠实性.md) 误解三和 4.4 第 1 条。

### Q2. 幻觉率 0.000 在什么条件下是"真的很好"，在什么条件下是"几乎没测到东西"？

**推理链**：`GenerationMetrics.hallucination_rate` 的实现在 `symbol_checked == 0` 时**直接返回 0.0**
（`maixrag/evaluation/harness.py` 第 219–221 行），也就是说"一个符号都没检查"与"检查了都没问题"
编码成了同一个数字。区分它们的唯一信息是**分母**——"符号被检查到的题数"。
项目里这两种情况都真实出现过：**同一份报告里**，链式的 0.000 底下覆盖率是 **0/18**——
模型按纪律没写代码，于是没有符号可查，这个 0 是"没测到"；
而修掉检索问题（事故 02）之后覆盖率到 **18/18**，幻觉率仍是 0.000，这一次它是真的
（[postmortem 05 · 修复](../../postmortem/05-伪装成好消息的0.md)、[tutorial 07](../../tutorial/07-端到端.md) 第 5 节）。
如果覆盖率是 0，下一步不该去调生成侧：**0/18 是检索失败的"下游症状"**——
模型拒答是因为没召回含例程的文档，所以先查检索轴（`inspect_eval.py` 打出的"有召回片段的题数"）。

**如果你答到了**：分母（覆盖面）才是判据 / 两种 0 的真实来源（没写代码 vs 真没编） / 覆盖率异常时先修上游检索 —— 说明你理解了这一层。
**如果你答成**："0.000 说明提示词写得好" —— 你在用一个可能没有分母的数字下结论，回去读事故 05 的"根因"第二节。

### Q3. 只报"幻觉率 0.000"和同时报"拒答率 0.444"，会让技术决策差在哪一步？

**推理链**：两个数字在同一个旋钮上（误解二），而且拒答本身是**一等输出**——
它有字段（`Answer.refused`）、有理由（`refusal_reason`）、有指标（`refusal_rate` 与 `refusal_correct`）。
agent 那一栏的 `拒答率 0.444` 混着两种完全不同的东西：
真实的"资料不足"，和循环以 `budget` / `stuck` / `error` 结束时被 `_looks_like_refusal`
（`maixrag/agent/app.py`）记为的降级——tutorial 07 顺手核过：18 题里 **8 题**被判定为拒答/降级。
所以"幻觉率 0.000"单独看会让你形成"两条路线忠实性等价"的印象，
而拒答率一旦摆出来，问题就变成另一句话：**这 8 题里有多少题本来有答案？**
如果多数是"有资料但没答完"，该修的是预算与检索；如果多数真是"语料里没有"，那拒答就是正确行为。
**只看幻觉率的代价，是把"没答"当成"答对了"。**

**如果你答到了**：拒答率是配对指标 / 0.444 里混着资料不足与预算降级 / 修的方向由这个拆分决定 —— 说明你理解了这一层。
**如果你答成**："拒答率 0.444 说明 agent 更诚实，宁可拒答也不编" —— 你用一句好话盖住了一个未拆分的复合指标，而且这个结论与"预算用完也记作拒答"直接冲突。回去读 [`concepts/05`](../concepts/05-生成与忠实性.md) 4.1 和 [tutorial 07](../../tutorial/07-端到端.md) 第 6 节"失败三"。

### Q4. 三级校验阶梯为什么从"最便宜最确定的一级"开始，而不是从"最有说服力的一级"开始？

**推理链**：三级阶梯的排序依据是**投入产出比**（[design 01 · 4.5.3](../../design/01-系统架构设计.md)）：
第一级是 AST 解析 + 符号存在性对照 API roster——零成本、纯本地、完全确定，
而它覆盖的正是本项目背景故事里的主要痛点（"写不出能用的代码"主要就是 API 编造）；
第二级签名/参数校验同样零成本、纯本地，但抓的是"函数存在、用法错"；
第三级真实执行最有说服力，却需要真机或精心构造的 `maix` shim——
MaixPy 跑不到笔记本上，所以它是**可选的最后防线，不是默认手段**。
失败处理也随确定性放宽：第一级阻断，第二级警告并标注，第三级只记录。
如果只有一台真机、没有 shim，合理的安排是：**先做满一、二级**（零成本、覆盖主要幻觉），
第三级降级为"抽样跑 + 只在关键代码上跑"——因为真机是稀缺资源，
把它用在"每一段代码都执行一遍"上是投入产出比最差的用法。
代价说清楚：这样安排会漏掉**逻辑错误与运行时才暴露的问题**，这类错误只能靠人工审核或让用户回报。

**如果你答到了**：排的是确定性/成本而不是说服力 / 第三级不可批量（无 shim 就得真机） / 抽样是把第三级落到可行区间的办法 —— 说明你理解了这一层。
**如果你答成**："从最有说服力的开始最保险" —— 你把"单次最有说服力"当成了"整体最优"，需要回去读 design 01 4.5.3 那张成本表的最后一行。

## 二、工程问答

### Q5. 幻觉率与拒答率在同一个旋钮上——什么时候你宁可让它拒答，什么时候宁可让它硬答？

**判断依据**（这几条都要考虑到才算合格）：
1. **按 qtype 分类**：错答的代价在 `signature` / `example` 上最高——那些题要的是可直接粘进 MaixVision 的代码，
   一个不存在的 API 会让用户的板子直接报错，而且肉眼看不出来；
2. **拒答的代价要分题算**：`concept` / `troubleshoot` 题上一句"资料未覆盖"仍然有用（用户知道文档里没有），
   而在 `example` 题上拒答等于零产出——用户的问题没被解决；
3. **上游可修性**：拒答由"检索没召回"引起时，它是**可修的症状**；由"语料里真没有"引起时，它是终局。
   两种情况的处置完全相反，所以决策前必须先看检索轴；
4. **覆盖面**：任何"幻觉率很低"的结论都必须带分母，否则这个旋钮根本不该被拧。

**一个示范回答**：
我会先按 qtype 拆开看。`signature` 和 `example` 合计占评测集的一半（8 / 4 / 4 / 2 共 18 题：
concept 8 / signature 4 / example 4 / troubleshoot 2），这两类是幻觉重灾区，
所以在这两类上我宁可拒答：编造的 `camera.super_zoom()` 会一路骗到 MaixVision 里才报错，
而拒答至少是诚实的。但在 `concept` 题上我会让它硬答并要求引用——
因为"资料里没有直接答案"本身就是一个可用的回答，用户能据此去翻文档。
代价也要说明白：往保守调会推高拒答率，而 agent 那条路已经实测到 **拒答率 0.444**
（`eval/results/agent_loop.md`），其中一部分只是循环以 `budget` / `stuck` 结束被记成拒答
（`_looks_like_refusal`），并不是"资料不足"。所以这个取舍会**在我的评测口径不够细的时候失效**：
如果 `refusal_rate` 不拆成"资料不足"与"预算降级"，我会把预算问题误当成忠实性问题，
于是去调提示词——方向整个错掉。**这个取舍的失效条件就是：拒答率没有按原因拆分。**

**常见的浅答案**（以及为什么浅）：
- "保守一点总没错" —— 没有定义"保守"付出的代价，而这里的代价有具体数字（拒答率 0.444，即 18 题里 8 题没有正面回答）；
- "看用户能不能接受" —— 把工程判断推给了没有数据的直觉；合格的答案要给出判据（qtype、上游可修性、覆盖面）；
- "幻觉危害大，所以一律拒答" —— 极端保守会让每一道题都变成"资料未覆盖"，系统等于没有产出；
  而且它同样造得出一个漂亮的 0.000，这正是误解二描述的陷阱。

### Q6. 什么时候必须上第一级校验（硬阻断），什么时候只该警告或记录？

**判断依据**（这几条都要考虑到才算合格）：
1. **信号确定性**：第一级是 AST + 符号精确查表，结论是"这个名字在 4868 条 roster 里不存在"——
   二值、可复现、无歧义；参数顺序错误没有这种确定性（要先正确抽取签名，再比参数）；
2. **误报率**：能硬阻断的前提是误报率低到用户不会开始忽略警告。一旦误报，第一级会从"帮忙"变成"帮倒忙"；
3. **可操作性**：第一级拦下来之后必须给出一条能走通的路（`lookup_api` 查真实 API），
   否则用户只会把校验关掉；
4. **代价**：硬阻断的代价是这次回答作废（甚至降级为拒答），所以只在"错误一定会造成用户损失"时用。

**一个示范回答**：
`camera.Camera()` 参数顺序写错，符号全部存在，所以它在第一级**必然查不出来**——
第一级只回答"这个名字存不存在"，不回答"这个调用对不对"。它应该落在**第二级**：
对照抽取出的签名比参数名、个数、顺序，然后**警告并在答案里标注**，不阻断。
理由是 design 01 4.5.3 已经写明的：签名抽取本身可能有解析误差，不宜硬阻断。
我允许第一级真的拦下答案并拒答的条件有三个，缺一不可：
① 报出来的符号确实不在 roster 里（不是"疑似"）；
② roster 的误报率被量过，并且有回归用例锁住已知误报
（`scripts/regress_symbol_false_positive.py` 同时锁住"该放行的"和"该抓到的"两个方向）；
③ 系统给了一次自修机会，重试后仍存在才降级为拒答（design 01 的拒答触发条件第三条）。
代价说明：这三条把第一级的"能拦"变成"敢拦"，但它的保护范围只覆盖**命名与映射类**幻觉；
资源类与逻辑类问题（参数、顺序、运行时行为）它一律看不见——那要靠第二、三级，而第三级在无 shim 时只能抽样。

**常见的浅答案**（以及为什么浅）：
- "错误严重就该硬阻断" —— 判据放错位置：能硬阻断靠的是**信号确定性**，不是错误的严重程度；
- "全部改成警告，别拦用户" —— 等于放弃第一级唯一的优势（它是确定性的），也解释了为什么本项目把第一级定为阻断、二三级放宽；
- "让模型自己再检查一遍" —— 把确定性检查交给了概率系统，正是"能程序判的绝不交给模型"要避免的那一步。

### Q7. 第一级校验误报了，你必须先看哪里？（无唯一答案）

**判断依据**（这几条都要考虑到才算合格）：
1. **先怀疑校验器，不先怀疑模型**：报出来的名字太规整（`GPIO`、`Mode.IN`、`Mode.OUT`、`set_pin_function`），
   而编造的 API 通常似是而非（`super_zoom`、`cv2_imread`）——形态本身就是一个线索；
2. **去查语料的原文**：`corpus/raw/repo/peripheral/gpio.md` 里官方教程写的就是 `from maix import gpio`，
   所以 `maix.gpio.GPIO` 是正确写法；
3. **根因在生成侧而不是判定侧**：白名单是从 API 文档页 URL 推模块名的
   （`maix/peripheral/gpio.html` → `maix.peripheral.gpio`），而用户实际 import 的是扁平形式
   → 正确代码被**系统性**误报；而且只影响带子包的模块（`maix.camera.Camera` 两种形式一致，所以看不出问题）；
4. **只修白名单不够**：还要让"漏了什么"变得可见——`check_roster_covers_corpus` 在每次 `corpus build`
   输出 `corpus/reports/roster_gaps.md`，并从教程原文里扫 `from maix import X` 补上未文档化的模块
   （`sdv1_5`、`sensevoice` 这类）。

**一个示范回答**：
我会先跑 `python scripts/regress_symbol_false_positive.py` 看这两条用例：`gpio 扁平导入（曾经被误报）`
与 `照搬树莓派 camera.PiCamera()`——**两个方向必须同时通过**，因为修假阳性最容易的错法是把校验放宽到抓不住真幻觉。
然后按白名单的三次变化定位：2996 → **4833**（生成扁平别名 `maix.peripheral.gpio.GPIO` → `maix.gpio.GPIO`）
→ **4868**（从教程原文补未文档化模块）。
但只改白名单是治标，我会同时改三件事：① 把扁平别名规则写进生成流程，规则来源是语料自身证据而不是猜；
② 每次 `corpus build` 产出 `roster_gaps.md`，把"漏了什么"变成可见输出；
③ 量校验器的误报率。第 ③ 条是硬要求：**一个工具的误报率决定它会不会被使用，而没被使用的工具等于不存在**——
误报会训练使用者忽略警告，于是真幻觉也一起被忽略。
代价要说明：roster 变宽会同时放松"前缀命中 + 常量后缀"那条放行规则，
所以修完必须重跑 MUST_FAIL 那三条（OpenCV / 树莓派 / 编造方法），确认检出没有退化。

**常见的浅答案**（以及为什么浅）：
- "把 `maix.gpio.GPIO` 加进白名单就好了" —— 只治了这一个符号，下个子包模块（`maix.peripheral.pinmap` 之类）会以同样形式再来一次；没有建立发现这类漏项的机制；
- "模型又编 API 了，加强提示词" —— 归因错了对象，会去调一个本来正确的提示词，而真正的 bug 留在白名单生成里；
- "关掉符号校验" —— 把唯一的确定性防线拆了，等于接受"模型编的 API 会一路到用户板上"。

2. `python scripts/inspect_eval.py "eval/results/agent_loop.json"`（我只读，没有覆盖任何报告）：

   以及 `拒答题数 8/18`。

**回答**：**不能直接读成"agent 不编 API"，但它的分母是满的。** 这份报告里的
`符号级幻觉率 0.000` 建立在 **16/18** 的覆盖面上（101 个符号被查过、0 个不在白名单里），
而链式那份 L1 报告的覆盖面是 **0/18**——同一个 0.000，一份有分母、一份没有。
结论：读任何一个比率型指标之前，先读它的分母。

**[未实测，需你运行确认]** 这里有一处必须如实标出的**文档内部不一致**：
仓库里 `eval/results/agent_loop.json` 现读出来的覆盖率是 `16/18`（逐题 `symbol_checked`
之和为 101），而 [tutorial 07](../../tutorial/07-端到端.md) 第 4、5 节记录的 agent 覆盖率是
`11/18`；`refusal_rate` 两边倒是一致的（磁盘上 8 题为 `是`，即 **0.444**）。
也就是说"这份 JSON 是哪一次运行"没人能确认——**它是本地可重建产物**。
所以：**不要把我上面那一步读到的 16/18 当成 agent 的固定水平**，
要下结论，请按 [tutorial 07 · 7 自检](../../tutorial/07-端到端.md) 的命令自己重跑一次 `agent-eval`，
用那一次的报告来读分母。

### H2. 把"会犯错的假模型"关掉，看第一级校验会失去什么。

**操作步骤**：

```powershell
$env:CHAT_MODEL = "fake"
python -m maixrag --config configs/l0_no_rag.yaml ask "MaixCAM 上怎么把一张图放大两倍？" --level no_rag
```

我在本机跑过，输出（实测原文）：

```
{"answer": "可以使用 `maix.image.Image.super_resolve()` 来提升分辨率。\n\n```python\nimg = image.Image()\nimg = img.super_resolve(scale=2)\n```", "citations": [], "unsupported": []}
```

这里有一个**真实存在的坑，值得单独记住**：用 `--fake` 得到的是**空答案**。
我在本机实测 `ask ... --level no_rag --fake` 输出为空——
因为那个开关换的是 `NoopChat`（`maixrag/builders.py`），它什么都不答；
要看到幻觉必须用 `CHAT_MODEL=fake` 拿到 `FakeChat`（[tutorial 01 · 3 动作三](../../tutorial/01-失败是什么样的.md) 已经写过这一点）。

**预测与实测**：把 `hallucinate_on_miss` 关掉（`FakeChat(hallucinate_on_miss=False)`）后，
没有上下文时它输出 `"资料中没有相关信息。"`——**代码块消失**。
于是第一级校验在这两次运行里检查的符号数是：**开 = 2 个**（`maix.image.Image`、`super_resolve`，其中后者被抓），
**关 = 0 个**。也就是说关掉靶子之后，校验器那一次**没有任何东西可测**
（与 `check_symbols_demo.py` 第 7 条"检查 0 个符号"是同一个现象）。
**这个假模型在教学项目里不是偷懒的替代品**：它是给第一级校验准备的可复现靶子——
没有它，读者第一次跑就要卡在 API Key 上，而"能看到幻觉"正是这一章要建立的第一眼。
**[未实测，需你运行确认]** 具体那两行输出的措辞与计数，请按 [tutorial 01 · C1](../../tutorial/01-失败是什么样的.md) 的命令自己跑一遍核对。

**验收自检**：如果你预测"关掉之后答案会变成拒答、所以幻觉率更低"——方向对了一半：
幻觉率确实不受影响，但它不是因为"变好了"，而是因为**分母变成 0**。
这正是 Q2 那道题要你学会的那个区分。

### H3. 给"覆盖面"造一次现场：让同一个 0.000 的两种含义同时出现。

**操作步骤**：

```powershell
python -m maixrag --config configs/l2_hybrid.yaml eval --level rag --fake-chat
python scripts/inspect_eval.py "eval/results/rag_L1_rag[rrf_dense+bm25].json"
```

> ⚠️ 先备份 `eval/results/`：`eval` 会按 `{level}_{profile}.md/json` **覆盖同名文件**
> （[tutorial 05 · 6 ①](../../tutorial/05-评测.md)）。想避开这个坑，就只跑 `inspect_eval.py` 读已有 JSON。
> 另外注意：**融合那一份报告在仓库里只留了 `.md`、没有 `.json`**，
> 所以上面第二条命令要能跑，得先执行第一条把 `.json` 生成出来。
> 想不跑评测就看"有分母 vs 没分母"的对照，用仓库里现成的 `eval/results/agent_loop.json`
> （现读 `16/18`，有分母）对比那份 `.md`（18 题 `幻觉符号` 全是 `-`，没分母）。

**期望结果**：
- 这次跑会在报告里打出一条 ⚠️ 警告：**"生成用的是空客户端：生成轴未被真实测量"**
  （`cmd_eval` 在 `--fake-chat` 时把这条 note 写进报告，见 `maixrag/cli.py`）；
- `inspect_eval.py` 打出 **`符号被检查到的题数 0/18 (0%)`** 以及
  "没有任何题目被检查到符号——幻觉率 0.000 不具参考意义"。
  （`--fake-chat` 换的是 `NoopChat`，它返回空答案，所以没有代码就没有符号可查——
  这正是本题要造的现场。真实对话模型跑到的那份 `agent_loop.json` 是 `16/18`，两者对照着看。）

**[未实测，需你运行确认]** 分组表那四行（`concept` / `example` / `signature` / `troubleshoot` 的 Recall@K）
我没有在这次配置下重跑，所以不写具体数字。仓库里已记录的分组（[tutorial 05 · 第 4 节](../../tutorial/05-评测.md)）是
`concept 8 / 0.500`、`example 4 / 0.750`、`signature 4 / 0.500`、`troubleshoot 2 / 1.000`——
你自己的数字会随语料与检索配置移动，对不上时先分清是语料变了、检索配置变了，还是你跑的是另一个 `--fake*` 开关。

**回答**：**不是同一件事。** 这一次的 0.000 是"没测到"：
`NoopChat`（`maixrag/builders.py`）返回 `{"answer": "", "citations": [], "unsupported": []}`，
答案里没有代码，所以没有任何 `maix.*` 符号可查——0.000 的分母是 0。
而"模型真的一个 API 都没编"要求分母是满的（例如 18/18）。

**为什么检索轴仍然可以看**：`--fake-chat` 只换生成侧；
嵌入与检索器不受影响（`cmd_eval` 里 `fake_chat` 与 `fake_embed` 是两个独立开关，
`--fake-chat` 的 note 自己也写着"检索轴不受影响"）。
所以要判断"该召回的有没有召回"，这一次的报告照样能用；要判断"模型忠不忠实"，这一次的报告一个字都不能用。
**一句话记住这条边界：换掉的是哪一侧，就只有另一侧的数字还能读。**
