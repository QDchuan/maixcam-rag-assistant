## 一、概念问答

### Q1. `chunking.max_tokens` 默认 500 而中位数只有 45，能不能把它调到 45 来"对齐粒度"？

**推理链**：`max_tokens` 是**上限**，不是目标值，也不是"每个 chunk 会被切成多大"的旋钮。
这套切分器是两级的：第一级按标题结构切，一个标题段就是一个候选 chunk；第二级**只在某个标题段自身超过预算时**才触发，按段落装箱并保留重叠。
而 MaixPy 的文档是作者手写标题的技术文档，绝大多数小节本来就远小于 500 token——[本轮实测] 3838 个 chunk 的中位数是 45、p25 是 27、均值 78.8，越过 500 的只有 **17 个**（最大的是 `zh/projects/README#h5.1` 这张 1223 token 的表）。
所以把 `max_tokens` 调小，受影响的是这十几块以及被 `min_tokens`（默认 80）控制的碎片合并，**整体分布几乎不动**。
真正决定粒度的是文档的标题结构。想要"每个 chunk 都差不多大"，需要的不是调参，而是**放弃按结构切**——而那正是本项目明确不选的路。

**如果你答到了**：上限 ≠ 实际分布 / 二级切分只在超预算时触发 / 粒度由标题结构（加上 `min_tokens` 合并）决定 —— 说明你理解了这一层。
**如果你答成**："调小 `max_tokens` 就能切得更细、更精确" —— 那是把上限当旋钮，也是把"小块 = 更精确"这条纯散文语料的经验套到有代码和表格的语料上；回去读 [concepts/02 · 4.3 与 6.1 误解五](../concepts/02-语料与切分.md)，再看 `maixrag/corpus/chunker.py` 的 `_node_segments`。

### Q2. 代码块与表格"绝不二次切开"，这条约束在下游保护了什么？强行让表格服从 `max_tokens` 会坏在哪一步？

**推理链**：它保护的不是检索那一步，而是**"检索回来之后这东西还能不能用"**。
一张参数表被从中间截断，后半截**连列名都没有**，模型读到的是一堆无主的单元格——它会把某一列的取值误当成参数名；代码块被切散，召回的是函数的下半截，粘进 MaixVision 直接跑不起来。
所以这条纪律把"可用性"从生成阶段前移成了切分阶段的责任：chunk 是模型的输入单位，输入单位本身不完整，后面没有任何环节能补回来。
它**不是靠策略实现的**，而是靠两个偶然性质：`_para_split` 只按**空行**切段，而 Markdown 表格行之间是换行不是空行，于是整张表是一个不可分割的段落；`_pack` 又只在"当前块非空且加不下"时断开，所以超长的单个段落不会被切开。
代价的现场是 [本轮实测] 的 `scripts/demo_corpus_cut.py`：同一篇 `projects/README.md`，`heading` 切出 15 块（1 个 table），`fixed` 切出 9 块（0 个 table），而两行的 `'|'` 总数都是 **240**——表格文字一个字没丢，但 `kind` 全变成 `prose`，下游按 `kind` 做结构感知检索时再也认不出这是一张表。

**如果你答到了**：原子块 / 截断后失去列名或可执行性 / 坏在"进上下文之后的可用性"与"结构标签丢失"这两处 —— 过。
**如果你答成**："因为表格很重要，不能破坏它的完整性" —— 那是结论不是原因；合格答案要能指到**哪一步坏掉、坏成什么样**。回去读 [concepts/02 · 4.3、6.1 误解一](../concepts/02-语料与切分.md) 与 [tutorial 03 · 6](../../tutorial/03-语料工程.md)。

### Q3. 语义切分在什么语料上合理？它和标题感知切分依赖的信号本质差别在哪？

**推理链**：语义切分真正不可替代的场景是**没有结构的长文本**——会议记录、访谈稿、口述稿。那里没有作者标出的边界，"嵌入相似度骤降"是唯一能拿到的近似边界信号。
本质差别在**信号的来源与性质**：标题感知切分用的是文档自身的结构，是作者给的、确定的、免费的，边界就是标题，读者能逐条核对；语义切分用的是 embedding 相似度的相对变化，要花一遍嵌入计算，带噪声，边界是阈值产物，难解释。
MaixPy 的文档恰恰是前者：作者已经用标题把语义边界标出来了。放着免费且确定的信号不用，去花算力猜一个增益还不稳定的边界（公开研究对它的增益评价不一致，见 [design 05 · 1.5](../../design/05-调研与借鉴.md)），不划算。
本项目把语义切分保留为**配置里的对照项**，而不是实现它——让读者自己跑出"多花的钱没换来增益"这个结论，比直接告诉他们更有说服力。

**如果你答到了**：无结构长文本 / 信号是"作者给的"对"模型算出来的" / 成本与可解释性的差别 —— 过。
**如果你答成**："语义切分更先进，只是更贵，等以后有预算再上" —— 那是把"先进"当判据；判据是"你的语料里有没有一个免费且确定的边界信号"。回去读 [concepts/02 · 4.4 与 6.1 误解四](../concepts/02-语料与切分.md)。

## 二、工程问答

### Q4. 加 API 层 chunk 后 concept 掉 12.5 pt，而"检索算法没变"，这两件事为什么能同时成立？

**判断依据**（这三条都要考虑到才算合格）：

1. **Top-K 名额是零和的**——新 chunk 进来，就一定有旧 chunk 被挤出去，"多召回一点总没坏处"不成立；
2. **必须按 qtype 分组看**——总分 +5.5 pt 是两股相反力量抵消后的净值，它对这个结构性变化**没有信息量**；
3. **要区分"变的是什么"**——算法没动，变的是**候选集合本身**；而召回率度量的正是"该找到的东西有没有进 Top-K"，所以候选池换了，分数当然会动。

**一个示范回答**：
新增的 1898 个 API chunk 把语料从 1940 推到 3838 个 chunk（[本项目实测]，见 [事故 02](../../postmortem/02-有文档却召不回.md)），而 Top-5 永远只有 5 个名额。概念类问题的答案在教程散文里（本项目 prose chunk 1268 个），而 API chunk 的文本里塞满了限定名、签名和参数名，与查询词面高度重合，于是它们成批挤进 Top-5，把概念类需要的教程散文挤了出去——concept 从 0.625 掉到 0.500。同一时间 signature 从 0.000 涨到 0.500，是因为这一类问题**原来在语料里根本没有可召回的 chunk**。两件事完全相容：检索算法一行没改，改的是"池子里有什么"，而"池子里有什么"恰恰是召回率的上限。总分 +5.5 pt 把 +50 pt 和 −12.5 pt 平均掉了，所以只看总分的人会得出"小幅提升、可以上线"的结论——这正是必须按 qtype 分组的原因。

**常见的浅答案**（以及为什么浅）：

- "因为 API chunk 太多，噪声大" —— 没说清**席位机制**，也解释不了为什么受害的是 concept 而不是别的类；"噪声"是个形容词，不是机制。
- "语料变多了，检索自然变差" —— 语料变多本身不必然是坏事；"越多越好"只在**新增内容确实有答案、且不挤掉别的答案**时成立，合格的答案要说出后半句。
- "总分还是涨的，可以接受" —— 只看总分正是这个消融要反对的做法；它等于承认自己没看分组表。
- "因为 embedding 对概念类不敏感" —— 这批数字是在同一嵌入模型下测的，把差异归给模型等于放弃了唯一变量（语料）的归因。

### Q5.（无唯一答案）60% API + 40% 教程、80% 概念类提问，怎么组织索引与 Top-5 名额？

**判断依据**（这几条都要考虑到才算合格）：

1. **名额是否零和**——只要两类 chunk 共用一个 Top-K，它们就会互相挤；
2. **问题分布与语料分布不对称**——这里用户 80% 问概念，而语料 60% 是 API；应当按**问题分布**分配名额，而不是按语料分布；
3. **分层之后跨层问题由谁兜**——"`find_blobs` 的参数有哪些、怎么用"这种半签名半概念的问法，硬路由一定会误伤；
4. **代价与失效条件**——路由本身要有分类器，分类器会错；没有标注就没有基线；长尾混类问题是它天然的失效区。

**一个示范回答**：
我会先做**物理分层**：教程层与 API 层各自建索引（chunk 上已经带了 `kind` / `module` / `heading_path` 这些元数据，见 [design 01 · 3.2](../../design/01-系统架构设计.md)），再按问题类型分配名额——概念类走教程层 Top-5，签名类走 API 层 Top-3～5，混类问法两层各取几个再融合。
理由是：本项目当前的语料是 signature 1898 个（约占一半）对教程 chunk 1940 个（1268 prose + 605 code + 67 table），而 concept 类问题只需要教程散文。把 5 个名额交给同一个池子，等于替用户默认了"API 优先"，concept −12.5 pt 就是这件事的账单。按用户的 80% 而不是语料的 60% 分配，才是在优化真实分布。
代价要一起说：这需要一个查询分类器（本项目对应 L4 查询路由，目前是**待做项**，动机已经由这个消融给定），它在混类问法上会误判；误判的直接后果是概念问题被送进 API 层、召回为 0——比"挤掉几名"更糟。
所以我不会一上来就硬过滤，过渡做法是**保留统一池做兜底**，路由只用来调名额配额与加权，并且在报告里按 qtype 分组对比路由前后的数字。
**失效条件**：如果"概念类"里有相当比例其实是"某个函数怎么用"，硬路由会持续误伤；如果两层内容高度重复（API 页的说明文字本来就是教程的摘录），分层收益会接近 0。

**常见的浅答案**（以及为什么浅）：

- "把 `top_k` 调大就行" —— 加大 top_k 只是把更多不该进的片段带进上下文，并没有解决"两类内容互相挤"这个结构问题（[concepts/03 · 误解三](../concepts/03-检索-稀疏与稠密.md)）。
- "按语料比例分配，60/40" —— 用户提问分布和语料分布不是一回事；按语料分等于让占多数的语料支配结果。
- "加 rerank 就好了" —— 题设排除了它，而且 rerank 改的是排序精度，不改候选池里两类内容混在一起这件事。
- "看情况，先做实验" —— 方向对，但等于没说；合格的答案要给出**判据**、一个可执行的配额方案，以及它在什么条件下失效。

### Q6. 为一份新的 MaixPy 类语料定切分粒度，你的决定流程是什么？

**判断依据**（这几条都要考虑到才算合格）：

1. **粒度由评测决定，不能凭感觉**——切分器把 `strategy` 暴露出来，就是为了做对照实验，而不是给人调参用；
2. **必须有对照基线**——"标题感知更好"这句话在没有定长对照时只是一句没有数字的主张；
3. **要同时看质量与结构代价**——定长切分下 code / table chunk 会双双归零，而分数未必下降，甚至可能上升；
4. **要按 qtype 分组看，不能只看总分。**

**一个示范回答**：
我会把 `chunking.strategy` 当实验变量，而不是旋钮。先跑 `heading`（当前默认，[本轮实测] 3838 chunk：signature 1898 / prose 1268 / code 605 / table 67），再跑 `fixed`（`fixed_size_tokens: 256`），同一评测集、同一嵌入模型、同一 `top_k`，一次只改这一项。
仓库文档记录的结果是：fixed 下 chunk 3838 → 2812、code 605 → **0**、table 67 → **0**，而总体 Recall@5 反而从 0.611 **升到** 0.694、concept 从 0.500 升到 0.688（[本项目实测]，见 [tutorial 03 · 5](../../tutorial/03-语料工程.md)；**[未实测，需你运行确认]**，我这一轮没有重跑整库）。
这时候不能直接选 fixed，因为分数看不出两件事：① `kind` 标签没了，**结构感知检索的物理基础**就没了（L4 要靠 `kind` 分层）；② code / table 两类 chunk 归零，意味着"给我一段能跑的例程""某函数参数表"这两类需求在语料层失去了答案——那是 [事故 02](../../postmortem/02-有文档却召不回.md) 的形态。
所以我的决定流程是：**先定架构问题（要不要结构感知检索），再在该约束下选粒度**；如果确实不需要结构标签，也必须把 18 题里 signature 那 4 题单独看一遍，确认它们没有因为 code / table chunk 消失而退化。
**失效条件**：评测集只有 18 题、每类 2–8 题，分组数字的置信区间很宽；而且粒度收益高度依赖文档形态——[本轮实测] 换一篇 `vision/find_blobs.md`，`heading` 是 26 chunk（6 code / 1 table），`fixed` 是 14 chunk（0 code / 0 table），结构损失比 `projects/README.md` 严重得多。

**常见的浅答案**（以及为什么浅）：

- "先调几个 `max_tokens` 值试试" —— 它只在某一节超预算时生效；3838 个 chunk 里只有 17 个越线，调它对分布几乎无影响。
- "看总分，哪个高用哪个" —— 总分正是这个消融里信息量最低的一列。
- "直接上语义切分试试" —— 没有先问"我的语料有没有免费且确定的边界信号"，属于把技术当默认选项。
- "保持现状，标题切分是标准做法" —— 用"标准做法"代替判据；合格答案要说出对照基线是什么、什么结果会让你改变选择。

### H1. 把 `strategy` 从 `heading` 改成 `fixed`，先写预测再验证

```powershell
Copy-Item indexes indexes_backup -Recurse -Force

# ② 复制 configs/l2_hybrid.yaml -> configs/_tmp_fixed.yaml，只改：
#    chunking.strategy: fixed        （fixed_size_tokens 保持 256）

# ③ 重切 + 建索引 + 测检索轴
python -m maixrag --config configs/_tmp_fixed.yaml corpus build
python -m maixrag --config configs/_tmp_fixed.yaml index build --rebuild
python -m maixrag --config configs/_tmp_fixed.yaml eval --level rag --fake-chat

# ④ 收工还原
python -m maixrag --config configs/l2_hybrid.yaml corpus build
python -m maixrag --config configs/l2_hybrid.yaml index build --rebuild
#    或直接用 indexes_backup 覆盖回 indexes/
```

`code` 与 `table` 归零这件事，我用**单篇文档**在同一天实测过，机制上是确定的 [本轮实测]：

```
projects/README.md     策略      chunk  代码  表格  散文  '|'总数  最大token
                       heading     15    0     1    14     240       1223
```

**注意**：如果你用 `--fake`（假嵌入）跑评测，绝对数字会和上表不同（假嵌入无语义能力，只证明管线通了，见 [concepts/03 · 4](../concepts/03-检索-稀疏与稠密.md)）；这时只比对**方向**。

**验收标准**：
1. 预测写在动手之前，且写明了 code / table 两类 chunk 会怎么变；
2. 能指出实际变化，并解释"分数可能反而升高"——`kind` 不参与打分，但 code chunk 消失会改变 BM25 的文档长度归一化与 token 池；
3. 能说出这次实验为什么**不能**直接得出"fixed 更好"（结构标签是结构感知检索的物理基础，而分数看不出标签没了）。

### H2. 找出最大的 table chunk，确认它有没有被切开

**操作步骤**：用题目文件里那段脚本打印 chunk 总数、table 数与前 3 大的 table chunk；再打开
[`corpus/reports/stats.md`](../../../corpus/reports/stats.md) 核对"chunk 按类型"四行。

**期望结果** [本轮实测]：

```
chunk 3838 table 67
zh/projects/README#h5.1            table 1223
zh/ai_model_converter/maixcam2#h45.3 table  459
zh/peripheral/uart#h70             table  413
```

- 最大的 table chunk 是 `zh/projects/README#h5.1`，**1223 token，没有被切开**；
- 全库越过 `max_tokens=500` 的 chunk 只有 **17 个**，它是其中最大的一个；
- `stats.md` 的"chunk 按类型"四行齐全：signature 1898 / prose 1268 / code 605 / table 67；
- 另外两个可对的口径 [本轮实测]：token 中位数 45、p25 27、均值 78.8、最大 1223。

**它为什么没被切开**（机制，不是"因为它重要"）：表格是原子块，不参与二次切分；而 `_para_split` 只按**空行**切段，Markdown 表格行之间是换行不是空行，所以整张表在切分器眼里是**一个不可分割的段落**，`_pack` 遇到"当前块为空 + 单段超限"时会照收不误。
顺带一个必须知道的边界：这个保证是**靠"表格内部没有空行"这个偶然性质实现的，不是靠策略实现的**——一旦上游表格里出现空行，这个保证就没了（[tutorial 03 · 6](../../tutorial/03-语料工程.md) 把它明确写成"已知的边界，不是已解决的问题"）。
