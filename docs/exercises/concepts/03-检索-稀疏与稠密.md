## 一、概念问答（考框架 / 流程 / 算法 / 术语）

**Q1. 在 MaixPy 助手里问「怎么列出 MaixCAM 上可用的摄像头设备？」，稠密检索很容易翻车；而问「maix.camera.list_devices」几乎必中。从「文本被压成向量之后发生了什么」这个角度，说清前一问为什么常常输给 BM25。**

- 提示：想两件事——这个查询里最像"答案"的词在训练语料里出现过几次；以及 BM25 打分时到底看不看语义

> 参考答案：[answers/03-检索-稀疏与稠密.md](../answers/03-检索-稀疏与稠密.md) 第 Q1 题

**Q2. BM25 的 IDF 在什么情况下会变成负数？为什么那是个问题？本项目的实现是怎么绕开它的——而绕开之后，还有哪一类查询它治不好？**

- 提示：从 `df` 与 `N` 的相对大小出发；注意"不为负"和"有区分力"是两件事

> 参考答案：[answers/03-检索-稀疏与稠密.md](../answers/03-检索-稀疏与稠密.md) 第 Q2 题

**Q3. 你接手了一个 MaixPy 问答机器人。还没跑任何实验，先给你五条真实查询：`maix.camera.Camera 的构造函数有哪些参数？` / `拍一张图存起来` / `YOLOv5 物体检测` / `MaixCAM 2 和 MaixCAM Pro 有什么区别？` / `报错找不到摄像头怎么办`。逐条判断该偏稀疏还是偏稠密，并说清你的判据；其中至少有一条要说明"两边都不稳、得靠别的环节"。**

- 提示：概念文档 3.3 那张表是按"查询里有没有罕见字符串"排的，不是按"问题长短"排的

> 参考答案：[answers/03-检索-稀疏与稠密.md](../answers/03-检索-稀疏与稠密.md) 第 Q3 题

**Q4. 你要给一个自己的语料做检索选型：约 3000 个 chunk，几乎全是中文散文和教程，几乎没有 API 标识符，查询也都是"怎么做 X"。只上稠密检索可以吗？如果你的语料其实是 MaixPy 文档（119 篇教程 + 56 页 API，共 3838 chunk），答案会不会变？给出判据，而不是结论。**

- 提示：先想清"稀疏检索相对稠密，多买到的是什么"——是语义，还是**确定性**；再想你的查询里有多少条需要那个确定性

> 参考答案：[answers/03-检索-稀疏与稠密.md](../answers/03-检索-稀疏与稠密.md) 第 Q4 题

## 二、工程问答（考局限性 / 选型 / 取舍 / 边界）

**Q5. 场景：你的 MaixPy 助手被反馈「问怎么列出摄像头设备，答得含糊」。你一查评测明细，这题在只 dense、只 bm25、以及两者融合三份报告里全部未命中（对应评测集 q004，答案是 `api/maix.camera.list_devices`）。列出你的排查步骤：先查什么、怎么排除、最后大概率落在哪一层。**

- 提示：本项目的通用排查路径是"先在索引里找这个 doc_id、再看它排第几、最后才怀疑检索算法"；注意"检索器没召回"和"语料里根本没有"在日志里长得一样

> 参考答案：[answers/03-检索-稀疏与稠密.md](../answers/03-检索-稀疏与稠密.md) 第 Q5 题

**Q6. 场景：你换了语料、重建了索引，18 题的总分没怎么动，但用户说「签名类问题最近老是答不对」。你的评测报告只有一个总分。你要加什么切法、什么字段，才能在下一次改动时立刻发现「某一类查询一直在召回失败」？说清你的分组依据是怎么来的，以及为什么单看总分永远发现不了。**

- 提示：分组要能从数据里冒出来，而不是你凭直觉挑的；另外"覆盖率"是这条链路里唯一能区分"真的没问题"和"根本没测到"的字段

> 参考答案：[answers/03-检索-稀疏与稠密.md](../answers/03-检索-稀疏与稠密.md) 第 Q6 题

**Q7.（无唯一正确答案的取舍题）场景：老板说「下个迭代只有约两周的检索可投入工时」。你先跑了一轮消融，手上是这样两组事实：把 `retrieval.retrievers` 从 `[dense, bm25]` 的融合改成只跑 `[dense]`，总体 Recall@5 是 0.611，和融合打平；`[bm25]` 只有 0.444。而按 qtype 分组看：`example` 只 dense 是 1.000，融合是 0.750；`signature` 只 bm25 是 0.000、只 dense 是 0.500；`troubleshoot` 只 bm25 是 0.500、融合是 1.000（18 题 / `top_k=5`，数字见 `eval/results/`）。你打算把这两周投在哪：继续做稀疏侧（字段化 BM25、标题 / `heading_path` 加权、分词与词典打磨），还是换成更强的 embedding？**

- 提示：先算清楚"你想改善的那类查询，现在丢在哪一环"，再看哪一路的钱花在那一环上；别忘了本项目引用两份报告时有个前提——**只跑 BM25 那份的评测里，检索器只有 BM25，稠密那一路的数字在另一份报告里**

> 参考答案：[answers/03-检索-稀疏与稠密.md](../answers/03-检索-稀疏与稠密.md) 第 Q7 题

## 三、动手题

**H1. 用 IDF 表与分词结果，亲手验证"BM25 对高频领域词失灵"，并解释数字从哪来。**

- 步骤：
  1. 先跑一遍真实分词——把查询 `YOLOv5 物体检测` 交给
     `from maixrag.corpus.tokenize import tokenize_query`，打印返回的 tuple；
  2. 再用 `maixrag.indexing.bm25` 的 `debug_idf_table`（它接收 `BM25Index` 与一组词，
     返回 `(词, df, idf)`）打出这几个词的 `df` 与 `idf`：`yolo`、`检测`、`物体检测`、
     `rtsp`、`yolov5`、`camera`、`list_devices`、`find_blobs`；
  3. 对照 [tutorial 04 第 6 节 ③](../../tutorial/04-检索与消融.md) 给出的那组 `df` / `idf`，
     指出**你实测到的值与文档里写的是否一致**，不一致就说出是哪一步不同（语料变了？分词变了？跑的是另一份索引？）；
  4. 最后回答：为什么查询词 `YOLOv5 物体检测` 里，真正系统讲 YOLO 的那一篇
     （`zh/vision/yolov5`）会排在"运行例程"这类顺带提一句的篇章后面。
- 提示：第 1 步和第 2 步要分开做——**"这个词没被检索到"与"这个词被检索到了但排不上来"是两种失效**；
  另外注意索引里一共有多少个 chunk（`BM25Index.size`），IDF 依赖它
- **验收标准**：
  1. 你能打印出 `物体检测` 作为一个整体 token 时的 `df = 0`，并说清"为什么会是 0"；
  2. 你能说出至少一对"高频词 vs 稀有词"的 `idf` 大小关系，并说明**为什么这个方向不是 bug**；
  3. 文档值与你的实测值如果不一致，你能给出至少一个可检验的原因（语料 / 分词 / 索引版本）。
- 依据：[`concepts/03`](../concepts/03-检索-稀疏与稠密.md) 第 3.1 与 3.3 节 ·
  [`tutorial/04`](../../tutorial/04-检索与消融.md) 第 4、6 节 ·
  [`maixrag/indexing/bm25.py`](../../../maixrag/indexing/bm25.py) ·
  [`maixrag/corpus/tokenize.py`](../../../maixrag/corpus/tokenize.py)

**H2. 在真实语料上给三个查询做检索器分诊（这一题对应概念文档第 7 节的动手题）。**

- 步骤：
  1. 跑 `python scripts/demo_retrieval.py`（内置三个查询，配置默认 `configs/l2_hybrid.yaml`），
     记下每个查询在 `dense` / `bm25` / `fused` 三列下的前 3 个 `chunk_id` 与名次；
  2. 再用 `--query` 显式指定你关心的查询，并分别用 `--config configs/l2_hybrid.yaml`
     与 `--config configs/l3_bm25_only.yaml` 各跑一次（`--query` 一旦给了，内置查询就不再跑，
     所以要三条都写全）；**每次都要先在纸上写下"我预测哪个检索器更强"**；
  3. 回到 `eval/datasets/seed.jsonl`，找到与你三条查询对应的那个 `qid`，把它的
     `ground_truth.required_docs` 抄出来——那是"该被召回的东西"的定义；
  4. 用一个脚本或一段代码，对每个查询、每个检索器记录**目标 doc_id 是否进入 Top-K、排第几**，
     三个查询各产出一行"分诊结论"。
- 提示：判断"该偏稀疏还是偏稠密"的依据不是分数，而是**这个查询里有没有罕见字符串、
  以及答案所在的文档里有没有出现它**；另外 `demo_retrieval.py` 只载入已有索引，不会重建，
  所以它秒级返回——但前提是你本地的 `indexes/` 与 `corpus/processed/chunks.jsonl` 是同一份语料
- **验收标准**（三条都要能答）：
  1. 三个查询各自给出"偏稀疏 / 偏稠密 / 两边都不稳"的结论，并且每条结论都能指出
     **目标 doc_id 在对应检索器下的名次**（不是"感觉"）；
  2. 至少指认一条**融合也救不回来**的查询，并用两路的名次说明"为什么救不回来"
     （提示：`configs/l3_bm25_only.yaml` 那份配置打出来的 `[bm25]` 列才是"只跑 BM25"的干净排名）；
  3. 对至少一条未命中的查询，给出一个**语料层**的修法（改 chunk 内容或边界），
     而不是"加大 `top_k`"。
- 依据：[`concepts/03`](../concepts/03-检索-稀疏与稠密.md) 第 3.3 与第 7 节 ·
  [`tutorial/04`](../../tutorial/04-检索与消融.md) 第 4、6 节 ·
