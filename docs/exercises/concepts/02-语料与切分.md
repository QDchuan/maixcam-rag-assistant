## 一、概念问答（考框架 / 流程 / 算法 / 术语）

**Q1. 切分器里 `chunking.max_tokens` 默认 500，而这套语料切出来的 3838 个 chunk，token 中位数只有 45。有同事据此说"这个粒度参数没调好，把 `max_tokens` 调到 45 就能对齐"。这个说法错在哪？在这套 MaixPy 语料上，chunk 的实际大小到底由什么决定？**

- 提示：先分清"上限"和"实际切出来的大小"这两件事；再看两级切分里，第二级在什么条件下才会被触发。

> 参考答案：[answers/02-语料与切分.md](../answers/02-语料与切分.md) 第 Q1 题

**Q2. 默认切分器规定代码块与表格"各自独立成段，且绝不参与二次切分"。这条约束在下游保护了什么？如果为了服从 `max_tokens` 强行把一张参数表切开，会坏在哪一步？**

- 提示：想清楚一张参数表被从中间截断之后，后半截还剩哪些信息；再想它进了模型上下文之后会被拿去干什么。

> 参考答案：[answers/02-语料与切分.md](../answers/02-语料与切分.md) 第 Q2 题

**Q3. 语义切分（用 embedding 相似度找边界，在相似度骤降处切开）在什么样的语料上是合理选择？它和标题感知切分依赖的信号，本质差别在哪？**

- 提示：问题不是"哪种更先进"，而是先回答"这两种切法各自把什么当作边界依据、这个依据是谁提供的"。

> 参考答案：[answers/02-语料与切分.md](../answers/02-语料与切分.md) 第 Q3 题

## 二、工程问答（考局限性 / 选型 / 取舍 / 边界）

**Q4. 给语料加上 API 层的 1898 个 signature chunk 之后（同一评测集、同一配置，**检索算法一行没改**）：signature +50 pt、example +50 pt、troubleshoot +100 pt，而 concept **−12.5 pt**，总分只有 +5.5 pt。concept 为什么会掉？"检索算法没变"和"某一类问题的分数变了"为什么能同时成立？**

- 提示：想清楚 Top-5 那 5 个名额是怎么发出去的，以及新增的 chunk 和原来已在榜上的 chunk 之间是什么关系。

> 参考答案：[answers/02-语料与切分.md](../answers/02-语料与切分.md) 第 Q4 题

**Q5.（无唯一正确答案）假设你接手一份语料：60% 是 API 参考页、40% 是教程，而线上 80% 的提问是概念类（"某个功能怎么实现"）。在不换 embedding 模型、不加 rerank 的前提下，你会怎么组织索引与 Top-5 名额？请给出方案、代价，以及它在什么条件下会失效。**

- 提示：注意问的是"用户里 80%"，不是"语料里 60%"；再想分层之后，跨层的问法由谁兜底。

> 参考答案：[answers/02-语料与切分.md](../answers/02-语料与切分.md) 第 Q5 题

**Q6. 你要为一份新的 MaixPy 类语料定切分粒度：继续按标题切，还是改成定长切分？说出你的决定流程——看哪个指标、拿什么当对照、什么情况下会推翻当前选择。**

- 提示：粒度在本项目里是**被评测的对象**，不是配置里的一个旋钮；先把"哪种切法会让哪一类 chunk 消失"答出来。

> 参考答案：[answers/02-语料与切分.md](../answers/02-语料与切分.md) 第 Q6 题

## 三、动手题

**H1. 把 `chunking.strategy` 从 `heading` 改成 `fixed`，先写下两条轴的预测，再跑评测验证。**

做法（**用临时配置，别动正式索引**）：

```powershell
# ① 先备份索引。tutorial 02 §6.2 记过一次真实事故：
#    一次 `index build --fake --rebuild` 把 1024 维真实向量索引覆盖成了 256 维假索引。
Copy-Item indexes indexes_backup -Recurse -Force

# ② 复制 configs/l2_hybrid.yaml 为 configs/_tmp_fixed.yaml，
#    只把 chunking.strategy 改成 fixed（fixed_size_tokens 保持 256，与 configs/l1_baseline.yaml 对齐）

# ③ 重切语料 -> 看 reports/stats.md
python -m maixrag --config configs/_tmp_fixed.yaml corpus build

# ④ 重建索引 -> 跑检索轴评测
python -m maixrag --config configs/_tmp_fixed.yaml index build --rebuild
python -m maixrag --config configs/_tmp_fixed.yaml eval --level rag --fake-chat

# ⑤ 收工：用 configs/l2_hybrid.yaml 重跑 corpus build + index build --rebuild，
#    或用 indexes_backup 把 indexes/ 还原
```

- 提示：跑之前先在纸上写两个预测——"哪些 chunk 会消失"，以及"总体 Recall@5 会升还是降"。
- **验收标准**（三条都要满足）：① 预测写在动手之前，且写明了 code 与 table 两类 chunk 会怎么变；
  ② 跑完能在 `stats.md` 与评测报告里指出这两类 chunk 的**实际**变化，并与预测逐条比对；
  ③ 如果分数方向与直觉相反，能指出是哪一步想错了，并说清背后的机制（不接受"没想到"这种回答）。
- 依据：[tutorial 03 · C1](../../tutorial/03-语料工程.md) ·
  [concepts/02 · 4.3 / 6.1](../concepts/02-语料与切分.md) ·
  [`scripts/demo_corpus_cut.py`](../../../scripts/demo_corpus_cut.py)

**H2. 从 `corpus/processed/chunks.jsonl` 里挑出最大的那个 `kind="table"` chunk，确认它有没有被切开；再核对 `corpus/reports/stats.md` 里"chunk 按类型"的四行是否齐全。**

做法：

```powershell
.venv/Scripts/python.exe -c @"
import json
from pathlib import Path
L=[json.loads(l) for l in Path('corpus/processed/chunks.jsonl').read_text(encoding='utf-8').splitlines() if l.strip()]
T=[c for c in L if c['kind']=='table']
print('chunk', len(L), 'table', len(T))
for c in sorted(T, key=lambda c: -c['meta']['tokens'])[:3]:
    print(c['chunk_id'], c['kind'], c['meta']['tokens'])
"@
```

- 提示：注意看最大那个 chunk 的 `chunk_id` 后缀——`#h5.1` 这种形状和 `#fixed3` 这种形状，
  分别说明它是被哪种策略切出来的；再回到 `maixrag/corpus/chunker.py` 的 `_para_split` 和 `_pack`，
  看"超过上限的单个段落"会被怎么处理。
- **验收标准**：① 报出最大 table chunk 的 `chunk_id` 与 token 数；② 明确回答它有没有被切开，并给出机制层面的理由（不是"因为它很重要"）；
  ③ `stats.md` 的四行数量与 `chunks.jsonl` 里的实际计数对得上，且你能说出四行里哪一行归零对应哪一篇事故。
- 依据：[tutorial 03 · 4.1 / 7](../../tutorial/03-语料工程.md) ·
  [concepts/02 · 4.3](../concepts/02-语料与切分.md) ·
