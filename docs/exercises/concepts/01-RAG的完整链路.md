# 习题 · 01 RAG 的完整链路

> 对应概念文档：[concepts/01-RAG的完整链路.md](../concepts/01-RAG的完整链路.md)
> 参考答案：[answers/01-RAG的完整链路.md](../answers/01-RAG的完整链路.md)　← **先自己想，再看答案**

这一章的题全部长在同一个判断上：**答得不好时，先分清是哪半段坏了。**
前半段（语料 → 索引 → 检索 → 融合）决定模型能看到什么，后半段（生成 → 校验）决定模型怎么用看到的东西。

---

## 一、概念问答（考框架 / 流程 / 算法 / 术语）

**Q1. 链路的七个环节里，哪些属于检索轴、哪些属于生成轴？为什么这两类失败的修法几乎不交集？**

- 提示：先用一句话说清"上游交付给下游的是什么"，再看每环输入输出表的最后一列
> 参考答案：[answers/01-RAG的完整链路.md](../answers/01-RAG的完整链路.md) 第 Q1 题

**Q2. 为什么本项目的主指标是召回率，而不是精确率或延迟？请用"上限"这个词解释。**

- 提示：想清楚"哪个指标一变差，后面所有环节就再努力也没用"
> 参考答案：[answers/01-RAG的完整链路.md](../answers/01-RAG的完整链路.md) 第 Q2 题

**Q3. 加 API 语料层换来 `signature` +50 pt、同时付出 `concept` −12.5 pt。这个代价的机制是什么？**

- 提示：Top-K 名额是零和的——先问"多了 1898 个 chunk 之后，谁的位置被占了"
> 参考答案：[answers/01-RAG的完整链路.md](../answers/01-RAG的完整链路.md) 第 Q3 题

**Q4. 一份评测报告写着"符号级幻觉率 0.000"。列出至少两种它其实什么都没测到的情况，并说明你会额外要哪个数字。**

- 提示：0.000 有两种含义——真的很好，或几乎没测到东西；区别不在数字，在覆盖面
> 参考答案：[answers/01-RAG的完整链路.md](../answers/01-RAG的完整链路.md) 第 Q4 题

## 二、工程问答（考局限性 / 选型 / 取舍 / 边界）

**E1. 你接手了这个项目。手上两份评测报告：一份只跑 dense，一份 dense+bm25 走 RRF 融合，两份的总分都是 Recall@5 = 0.611，但 MRR 一个是 0.557、一个是 0.453。你会从哪一环开始查、先改什么？**

- 提示：总分相同不等于两条链路等价；先对齐口径，再按 `qtype` 分组，最后才决定改哪一环
> 参考答案：[answers/01-RAG的完整链路.md](../answers/01-RAG的完整链路.md) 第 E1 题

**E2. 团队里有人报告"召回率低"，第一反应是把 `retrieval.top_k` 从 5 调到 50。这个动作在什么条件下有用，在什么条件下纯粹是浪费——你怎么判断？**

- 提示：分母里有没有东西可召回，是两件完全不同的事；参考 `signature` 类从 0.000 到 0.500 的那次改动
> 参考答案：[answers/01-RAG的完整链路.md](../answers/01-RAG的完整链路.md) 第 E2 题

**E3. 如果只能给评测报告加一个字段，来防止"0.000 伪装成好消息"，你加什么？为什么它够用？**

- 提示：这个字段要能一眼看出"分母覆盖了哪些题"，而不是再加一个比率
> 参考答案：[answers/01-RAG的完整链路.md](../answers/01-RAG的完整链路.md) 第 E3 题

## 三、动手题

**H1. 验证"这篇文档确实在语料里"，再用两份配置跑同一道题，看它的名次为什么消失。**

先确认 `zh/vision/yolov5` 真的产出了可检索 chunk，然后分别用
[`configs/l3_dense_only.yaml`](../../configs/l3_dense_only.yaml) 与
[`configs/l2_hybrid.yaml`](../../configs/l2_hybrid.yaml) 重跑评测，
把 `q005`（"MaixPy 里怎么做 YOLO 物体检测？给出一个完整例程"）在两份报告里的
**召回率与首位命中**抄下来对照。

- 提示：两份报告都在 [`eval/results/`](../../eval/results/) 里；
  想看**三路各自的名次**（而不是只看进没进 Top-5），用
  `python scripts/demo_retrieval.py --query "MaixPy 里怎么做 YOLO 物体检测？给出一个完整例程。" -k 20`。
  **只跑 `eval` 与这个脚本，不要跑 `index build --rebuild`**
  （一次 `--fake --rebuild` 会把 1024 维真实向量索引覆盖成 256 维假索引）
- 验收标准（三条全中才算过）：
  1. 能报出 `corpus/processed/chunks.jsonl` 里 `doc_id` 为 `zh/vision/yolov5` 的 chunk 条数，并说出它是**大于 0** 的；
  2. 能报出 `q005` 在 dense 报告与融合报告里的 `召回率` 和 `首位命中` 两列，并指出**哪一份丢了它**；
  3. 能说出这个现象是"语料缺失"还是"名额竞争"造成的——用检索时先各取多少个候选、最后取前几个来解释，
     并说清"没进 Top-5"与"根本没被召回"的区别（提示：三者里有一路它只是排在第 6）。
- 依据：[concepts/01 · 2 / 4.1](../concepts/01-RAG的完整链路.md) ·
  [tutorial 04 · 4.2 / R2](../../tutorial/04-检索与消融.md) ·
  [事故 02 · 同类问题清单](../../postmortem/02-有文档却召不回.md) ·
  [`scripts/inspect_eval.py`](../../scripts/inspect_eval.py)

**H2. 把评测的 K 从 5 改成 50，先写下预测再跑。**

先预测三件事：`Recall@K` 会怎么动、`Context Precision` 会怎么动、每个问题多塞进上下文的片段对生成成本意味着什么；
然后用 `--top-k 50` 再跑一次，与自己写下的预测比对。

- 提示：报告题目头里写着 `Top-K：5`，而检索指标本身就是按那个 K 算的——先想清楚"这个数字变了，
  是我的检索变好了，还是尺子变长了"
- 验收标准：
  1. 预测与实测**方向**一致；不一致时能说出是哪一步想错了；
  2. 能回答一个问题：**拿这次 k=50 的 `Recall@K` 去和之前 k=5 的基线比，这个对比成立吗？为什么？**
  3. 能指出本次评测里哪个指标受 K 影响最直接、哪个几乎不动。
- 依据：[design 03 · 4.1 / 4.3](../../design/03-评测与质量提升路线.md) ·
  [`corpus/reports/stats.md`](../../../corpus/reports/stats.md) ·
  [事故 02 · 同类问题清单](../../postmortem/02-有文档却召不回.md)
