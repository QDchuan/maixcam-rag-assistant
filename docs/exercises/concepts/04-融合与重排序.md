## 一、概念问答（考框架 / 流程 / 算法 / 术语）

**Q1. RRF 只读名次、完全不读原始分数。这个做法在什么前提下才成立？**
（换成 MaixCAM 的场景：如果哪天你把 BM25 换成一个"分数本身就带强度含义"的打分器，
或者两路检索器返回的候选数差了一个量级，RRF 还站得住吗？）

- 提示：RRF 丢掉的是"强度"，换来的是"不用对齐坐标系"——想想你把哪个信息扔了，
  以及什么时候扔了它就会出事
> 参考答案：[answers/04-融合与重排序.md](../answers/04-融合与重排序.md) 第 Q1 题

**Q2. `rrf_k`（默认 60）起什么作用？把它调到很小或很大，融合出的那份榜单分别会变成什么样？**
（用本项目能看到的例子说：查询 `YOLOv5 物体检测` 时 `zh/vision/yolov5` 在 dense 排第 5、
在 bm25 排第 6，融合后排第 12——分别把 `rrf_k` 调向两端，它的名次会往哪边走？）

- 提示：写一遍 `1/(k+rank)`，代 `k=1` 和 `k=1000` 各算两个名次的分，看差距被压缩成什么样
> 参考答案：[answers/04-融合与重排序.md](../answers/04-融合与重排序.md) 第 Q2 题

**Q3. 召回阶段与精排阶段各自要什么？为什么它们对"查询和文档要不要一起进模型"的要求正好相反？**
（把这件事落到 MaixCAM 的具体困难上：`maix.camera.Camera 的构造函数有哪些参数` 这类问题，
召回阶段漏掉它和精排阶段排错它，是两种性质完全不同的失败。）

- 提示：一个阶段怕漏，一个阶段怕错位；再想"cross-encoder 为什么慢"
> 参考答案：[answers/04-融合与重排序.md](../answers/04-融合与重排序.md) 第 Q3 题

**Q4. 概念文档说融合的产出"应当被当作候选，而不是判决"。Rerank 消费的是融合的哪一份产出？**
（如果融合那一层给出的候选池本身就编进了错误，rerank 有没有机会纠正？）

- 提示：先看清 `HybridRetriever.retrieve` 的输入输出分别是什么形状，再回答"rerank 的上游是谁"
> 参考答案：[answers/04-融合与重排序.md](../answers/04-融合与重排序.md) 第 Q4 题

## 二、工程问答（考局限性 / 选型 / 取舍 / 边界）

**Q5. 本项目的三方实测摆在这里：只 dense 的 Recall@5 = 0.611、MRR = 0.557；
只 bm25 的 Recall@5 = 0.444、MRR = 0.335；RRF（dense+bm25）的 Recall@5 = 0.611、MRR = 0.453。
也就是说融合在召回上"一分没赚"，在 MRR 上还退了 0.104。那你还要不要融合？给出判断依据与代价分析。**

- 提示：先别回答"要"或"不要"。先问一句：0.611 打平，**内容是同一批吗**？
  再问：MRR 退的这 0.104，是均匀地退，还是集中在某一类 `qtype` 上？
> 参考答案：[answers/04-融合与重排序.md](../answers/04-融合与重排序.md) 第 Q5 题

**Q6. 什么情况下不该开 rerank？给判据，并说明每条判据对应的是哪一种失败。**
（不许答"看情况"。判据要能让你在评审会上当场拍板：开，或者不开。）

- 提示：概念文档第 6 节给了三个前提，但你要把它们变成三条**能查的**判据——
  也就是"我怎么知道这条不满足"，而不是"这条应该满足"
> 参考答案：[answers/04-融合与重排序.md](../answers/04-融合与重排序.md) 第 Q6 题

**Q7. 现在给你一个决策：把 rerank 在 `configs/l2_hybrid.yaml` 里打开、接上 cross-encoder，
下一次评测就带它上线。你接还是不接？如果接，你先要拿到什么数字才肯接？**

- 提示：先看 rerank 只能在什么范围内工作（`HybridRetriever.retrieve` 里那个 `pool`），
  再去 `docs/concepts/04` 第 4 节"还没测到的部分"看本项目缺的是哪个数字
> 参考答案：[answers/04-融合与重排序.md](../answers/04-融合与重排序.md) 第 Q7 题

## 三、动手题

**H1. 把 `configs/l2_hybrid.yaml` 的 `fusion` 从 `rrf` 改成 `weighted`，跑一次对照 —— 但动手之前先写下预测：`weighted` 那一份的 MRR 会高于、低于还是等于 `rrf` 的 0.453？为什么？**

- 操作：改 `fusion: weighted` → `python -m maixrag --config configs/l2_hybrid.yaml eval --level rag --fake-chat --top-k 5`
  → 在 `eval/results/` 里找到新报告，对比两份报告的 MRR 与「按问题类型分组」那张四行表
- 提示：读懂 `maixrag/retrieval.py` 里 `weighted_score_fusion` 与 `reciprocal_rank_fusion`
  在实现上的**唯一区别**，以及 `weighted_score_fusion` 里那句 `top = max(h.score for h in hits)`
  会让哪一个检索器主导排序
- **验收标准**：① 写出两份报告的 MRR 与四条 `qtype` 行，逐行对比；
  ② 至少有一行的差异方向是你事先预测对的；③ 若某行预测错了，能说出是哪一步想错了
  （预告：BM25 的分数是无界的，稠密分数在 0–1，想一想归一化之后谁还在影响排序）
- 依据：[`concepts/04`](../concepts/04-融合与重排序.md) 第 3.3 节 ·
  [`tutorial/04`](../../tutorial/04-检索与消融.md) 第 7 节 ·
  [`maixrag/retrieval.py`](../../../maixrag/retrieval.py)

**H2. 把 MRR 那 0.104 的下降拆到题目上：在 `eval/results/rag_L1_rag[rrf_dense].md` 与
`rag_L1_rag[rrf_dense+bm25].md` 两份报告的「逐题明细」里，按 `首位命中` 这一列逐题对齐，
找出名次变化最大的三道题，并说清 MRR 的下降是被什么吃掉的。**

- 操作：把两份报告的逐题明细抄进一张表（列：`qid` / `qtype` / 只 dense 的首位命中 /
  融合的首位命中 / 只 dense 的召回率 / 融合的召回率），然后按题算 `1/rank` 的差
- 提示：本项目的 MRR 定义是 `sum(reciprocal_rank) / n`（**n = 全部 18 题**，
  没命中的题记 0，见 `maixrag/evaluation/harness.py` 的 `_agg`）——
  所以"首位命中从第 1 掉到第 5"和"某一题从没命中变成第 2"都会被算进去，两者方向相反
- **验收标准**：能指出 MRR 的净变化由哪几题贡献，并且用一句话解释
  "为什么 Recall@5 打平、MRR 却会下降"（这正是本题要逼你看清的东西）
- 依据：[`eval/results/rag_L1_rag[rrf_dense].md`](<../../../eval/results/rag_L1_rag[rrf_dense].md>) ·
  [`eval/results/rag_L1_rag[rrf_dense+bm25].md`](<../../../eval/results/rag_L1_rag[rrf_dense+bm25].md>) ·
  [`tutorial/04`](../../tutorial/04-检索与消融.md) 第 5 节
