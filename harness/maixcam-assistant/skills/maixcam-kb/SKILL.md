# 用知识库回答 MaixCAM 问题

这套纪律要治的是一个具体的病：**检索一次，拿到最像整题的那一页，就当成答案了。**
那一页通常是某个示例项目，它看起来像完整方案，实际上只覆盖了这个系统的一个部件。

## 核心：这是个**循环**，不是一次调用

```
读问题
  → 决定要不要查知识库（关于 MaixCAM/MaixPy 就要查；纯闲聊/纯通用编程不用）
  → search_docs 查一批文章
  → 读这些文章
  → 文章里出现了你不确定用法的函数 / 类 / 参数
        → lookup_api 确认它的**精确签名**
        → 不确定的地方再 search_docs 换词查
  → 还有哪些子系统没有证据？回到上面继续
  → 全部清楚了，才写答案；仍然没有证据的，明说「本地知识库没有这部分」
```

**什么时候算够**：你写出来的每一个 API 名字，你都能说出它的签名从哪来；
这个系统要用到的每个部件，你要么有本地证据，要么明确说了没有。

## 具体做法

### 1. 先判断要不要查
问的是 MaixCAM / MaixPy 的事 → **必须查**，不许凭记忆答。
你的训练数据里几乎没有这个平台，凭记忆写出「看起来合理」的 API 是这个项目要治的病。

### 2. 第一查之后，**不要停**
拿到结果先问自己：**这个系统还要用到什么？**

例如「设计一个人脸跟随系统」，至少要分别查证：

| 部件 | 查什么 |
| --- | --- |
| 人脸检测 | 用哪个模型类、输入尺寸、输出怎么读 |
| 云台/舵机 | PWM 怎么输出、占空比怎么算、频率多少 |
| 通信 | 串口怎么配、协议怎么定 |
| 引脚 | 哪些脚能干这些事、有没有冲突 |
| 供电 | 舵机电流从哪来 |

对每个部件单独 `search_docs`。**一次查询只覆盖一个面向** —— 这是检索的本性，不是工具的缺陷。

### 3. 遇到不认识的符号，**逐个核对**
文章里出现 `nn.YOLOv8`、`image.Image.draw_rect`、`pwm.PWM.duty` 这类名字时：

- 先用 `lookup_api` 拿到**精确签名**，再写进代码；
- 查不到 → **这个名字不存在**，别换个更像的猜，回去 `search_docs` 找真的；
- 不确定就说不确定。

### 4. 交付代码前，过一遍自检
把要给出的**整段代码**传给 `check_api_usage`。它报「发现 N 个不存在」时，
用 `lookup_api` 查到真名再改，**不要改一个更像的名字就交**。这一关是机器判的。

### 5. 边界必须写出来
- 本地知识库没覆盖的部分 → 直说「本地知识库里没有这部分」，并说明还需要什么；
- 你自己的推断 → 标明是推断；
- 涉及硬件行为（引脚、电平、外设型号）而语料没覆盖 → 说明这是需要实测的。

**不要用看起来合理的代码把空白填上。** 那是这个助手存在的理由。

## 反过来也要知道

- **不要**为了「查得更全」把整份语料读进来。用 `search_docs` 换查询词，不要用 shell 去翻
  `chunks.jsonl` —— 那会绕过出处标注，而且一次能烧掉几十万 token。
- **不要**在没有本地证据时用「一般来说可以……」把子系统糊过去。
- **不要**指望一次检索给你一个完整方案。它不是那么设计的；循环才是。
